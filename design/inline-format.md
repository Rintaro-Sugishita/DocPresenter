# 文字書式の設計案 — 太字・斜体・文字色

作成: 2026-09-24 / 対象: 本文中の文字書式を切り替える UI
関連: [表モデル §5.1](table-model.md)（意味トークン） / [シートモデル](sheet-model.md) / [編集 UI](editor-model.md)

## 0. 決定事項（ロック済み）

- **太字・斜体・コードは Markdown の記法そのまま**（`**` / `*` / `` ` ``）。発明しない（§1）。
- **文字色は用意しない。代わりに意味トークンを置く**（§2）。
- **トークンの語彙は表の塗りつぶしと同一**（`changed` / `pending` / `disabled` / `removed`）。増やさない（§2）。
- **記法は Pandoc の bracketed span `[文字列]{.token}`**（§3）。
- **語彙に無いクラスは span にしない。** 素のテキストとして残す（§3）。
- **UI にカラーピッカーは置かない。** ボタンは 4 つの意味である（§4）。

## 1. 太字・斜体・コード

`**太字**` / `*斜体*` / `` `コード` ``。Markdown のままである。ボタンは記号を打つ手間を省くだけで、新しい意味は持たない。

トグルとして働く。すでに掛かっているものをもう一度押すと外れる。

一点だけ実装上の注意がある。**`**` の内側の `*` を「斜体の印」と誤認してはいけない。** 太字に斜体を重ねるつもりで記号を 1 個食うと、記法が壊れて以降の本文すべてが傾く。

## 2. なぜ「文字色」を置かないか

設計書で文字に色を付けるとき、人が伝えたいのは色ではない。

| 書いた人の意図 | 選ばれがちな色 |
|---|---|
| ここは変更した | 赤・オレンジ |
| ここは未確定・要確認 | 青 |
| ここは対象外 | 灰 |
| ここは削除予定 | 赤＋取り消し線 |

**色は意図の符丁であって、意図そのものではない。** 符丁のほうを保存すると、次の全部が同時に手に入る。

1. **凡例を自動生成できる。** `#c00` からは何も分からないが、`removed` なら集計して凡例を出せる
2. **白黒印刷で潰れない。** 濃度の調整をテーマ側で一箇所に効かせられる（設計書は印刷・納品される）
3. **色覚に配慮できる。** 取り消し線・下線・網掛けをテーマが併用できる。直値を許さないからこそ一箇所で効く
4. **AI が読める。** 「赤い文字」は推測を要するが、`removed` は読める（[軸 B](requirements.md)）
5. **PPTX / PDF へ写せる。** 出力先ごとに何色にするかをテーマが決められる

これは[表の塗りつぶしでまったく同じ判断をしている](table-model.md)。**同じ問題に違う答えを出す理由が無い**ので、語彙も 4 種のまま共有する。文字と背景で語彙が違えば、凡例が二重になり、書く人も覚え直すことになる。

> 4 種で表せないことは、色ではなく**言葉で書く**べきである。

### 区分トークン（`tint-*`）は文字には無い

表の `tint-1`〜`tint-4` は「意味を持たない色分け」で、行や列の塊を視覚的に分けるためのものである。本文の文字にこれは要らない。文字を意味なく色分けしたくなったら、それは節を分けるべき場面である。

## 3. 記法 — `[文字列]{.token}`

```markdown
ここは[要確認]{.pending}である。
[**強い**変更]{.changed}のように中身の markdown も効く。
```

Pandoc の bracketed span をそのまま借りた。これで借用は四度目になる。

| 借用元 | 記法 | 用途 |
|---|---|---|
| Markdown Preview Enhanced | `@import "path" {attr}` | 外部要素の参照 |
| Mermaid | `A[ラベル] --> B{判定}` | グラフ型の作図 |
| Marp | `---` | ページ・スライド・シートの区切り |
| **Pandoc** | **`[文字列]{.token}`** | **意味トークン** |

利点は、**本製品の外でも意味が通る**ことである。Pandoc に通せば span になり、素の Markdown ビューアで見ても文字は読める。

### 語彙に無いクラスは受け付けない

`[赤]{.red}` や `[青]{color:#00f}` は **span にしない。** 素のテキストとしてそのまま残す。

ここで緩めると、テーマの知らないクラスや直値の色が文書に入り込み、§2 の利点がすべて崩れる。「読めないものは黙って解釈しない」は [P6](decisions.md) の裏返しである。

## 4. UI

編集中のブロックの上に出る小さなバー。

```
┌──────────────────────────────────────────────┐
│ B │ I │ </> ││ ■変更 │ ■要確認 │ ■対象外 │ ■削除予定 │
└──────────────────────────────────────────────┘
```

- **ボタンは 4 つの「意味」であって、色見本ではない。** ただし各ボタンにテーマの色を小さく添える。語彙を名前だけで覚えさせない
- **いま掛かっている書式はボタンが点灯する**（選択範囲を見て判定する）
- **同じトークンをもう一度押すと外れる。別のトークンを押すと置き換わる。** 二重には付かない — 一続きの文字列が同時に二つの意味を持つことはない
- `Ctrl+B` / `Ctrl+I` も効く
- **バーは選択範囲ではなくブロックに固定する。** テキストボックスは選択範囲の矩形を返さないため、位置を追うには隠し要素で描画を再現する仕掛けが要る。動かないバーのほうが押しやすくもある

### 編集の単位

本文をクリックすると、**その段落を生んだ markdown がそのまま開く**。閉じると、開いた範囲がそのまま 1 回のバイト範囲書き換えとして書き戻る。

開いた範囲と書き戻す範囲が同一であることが要点である。レンダリング結果から元の記法を逆算する必要が無く、[バイト範囲だけを書き換える](editor-model.md)という原則がそのまま守られる。

### 新しいブロックを書き始める場所

クリックできるのは既にあるブロックだけなので、**何も無いところから書き始める手段が要る。**

- **シートの末尾に、書き始めるための領域を置く。** 内容のあるシートでは、ポインタを乗せたときだけ「ここに本文を書く」と出る。空のシートでは最初から出す
- 書き込むのは**長さ 0 の範囲への挿入**である。直前のブロックとの間に空行を 1 つ入れる
- **何も書かずに閉じたら、何も書かない。** 既存ブロックを空にする操作（削除）と、新しいブロックを書かずにやめる操作は別物である

段落を増やすだけなら、**開いている入力欄の中で空行を 1 つ入れれば足りる**。確定した時点で 2 つの段落として解釈される。上の領域が要るのは、**クリックできる要素がそもそも無い場合**（空のシート、最後のブロックより下）だけである。
