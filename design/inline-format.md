# 文字書式の設計案 — 太字・斜体・文字色

作成: 2026-09-24 / 対象: 本文中の文字書式を切り替える UI
関連: [表モデル §5.1](table-model.md)（意味トークン） / [シートモデル](sheet-model.md) / [編集 UI](editor-model.md)

## 0. 決定事項（ロック済み）

- **太字・斜体・コードは Markdown の記法そのまま**（`**` / `*` / `` ` ``）。発明しない（§1）。
- **文字色は自由に選べる**（§2）。**意味トークンの語彙は撤回した**（§2.1）。
- **記法は Pandoc の bracketed span `[文字列]{color=#c62828}`**（§3）。
- **色として読めない値は span にしない。** 素のテキストとして残す（§3）。
- **UI は色見本 ＋ カラーピッカー**（§4）。
- **変更箇所は手で塗らない。**[Git の差分から自動で付ける](diff-marking.md)（§2.1）。

## 1. 太字・斜体・コード

`**太字**` / `*斜体*` / `` `コード` ``。Markdown のままである。ボタンは記号を打つ手間を省くだけで、新しい意味は持たない。

トグルとして働く。すでに掛かっているものをもう一度押すと外れる。

一点だけ実装上の注意がある。**`**` の内側の `*` を「斜体の印」と誤認してはいけない。** 太字に斜体を重ねるつもりで記号を 1 個食うと、記法が壊れて以降の本文すべてが傾く。

## 2. 文字色は自由に選ぶ

色見本から選ぶか、ピッカーで決める。表の塗りつぶし・文字色も同じである。

### 2.1 意味トークンをやめた経緯

当初は色を `changed` / `pending` / `disabled` / `removed` の 4 つの意味に固定していた。
根拠は「色は意図の符丁であって意図そのものではない。符丁のほうを保存すれば、凡例を自動生成でき、
白黒印刷に配慮でき、AI が読める」というものだった。**この根拠が崩れた。**

崩したのは **`changed` である。**

> Git で差分が取れるのに、変更箇所を手で塗る運用は続かない。

塗る作業が要り、剥がし忘れ、塗り忘れれば差分と食い違う。食い違った色は誰も読まなくなる。
つまり `changed` は**そもそも人が書くべき情報ではなかった**。[P1](decisions.md)（計算で出せるものは
ファイルに書かない）を、自分たちの決定に当てていなかった。変更箇所は[差分から自動で付ける](diff-marking.md)（R13）。

残る 3 つも同じ疑いにかかる。`pending` は本文に「要確認」と書けばよく、`disabled` と `removed` は
表の「状態」列が担うべきものである。**語彙として固定するほどの必要が無い。**

そして、語彙を外して残るものが本当の用途である。

> **人が色を使うのは「目立たせたい」ときである。** 目立たせたいことに、保存すべき意味は無い。

#### 失ったものと、その埋め合わせ

| 失ったもの | どう埋めるか |
|---|---|
| 凡例の自動生成 | 変更・削除の凡例は[差分表示](diff-marking.md)が出す。任意の色に凡例は要らない |
| AI が色の意味を読めない | 変更箇所は差分として渡せる。**色ではなく差分そのもの**を AI に渡す |
| 白黒印刷での識別 | 差分表示は色に加えて記号と網掛けを併用する |

**差分に移したことで、いずれも強くなっている。** 手で塗った `changed` は間違いうるが、差分は間違えない。

#### 古い記法は読み続ける

`[文字列]{.changed}` のように書かれた既存のファイルは、そのまま描画する（[P6](decisions.md)）。
新しく書く手段としては提供しない。

## 3. 記法 — `[文字列]{color=#c62828}`

```markdown
ここは[目立たせたい]{color=#c62828}。
[**強い**文字](color も重ねられる){color=#1f5fa8} のように中身の markdown も効く。
```

Pandoc の bracketed span をそのまま借りた。これで借用は四度目になる。

| 借用元 | 記法 | 用途 |
|---|---|---|
| Markdown Preview Enhanced | `@import "path" {attr}` | 外部要素の参照 |
| Mermaid | `A[ラベル] --> B{判定}` | グラフ型の作図 |
| Marp | `---` | ページ・スライド・シートの区切り |
| **Pandoc** | **`[文字列]{color=…}`** | **文字色** |

利点は、**本製品の外でも意味が通る**ことである。Pandoc に通せば span になり、素の Markdown ビューアで見ても文字は読める。

### 色として読めない値は受け付けない

`{color=red}` や `{color=expression(1)}` は **span にしない。** 素のテキストとしてそのまま残す。

受け付けるのは `#abc` と `#aabbcc` だけである。ここを緩めると**任意の CSS が style 属性に入り込む**。
色を自由にしたことと、何でも通すことは別である。

## 4. UI

編集中のブロックの上に出る小さなバー。

```
┌────────────────────────────────────┐
│ B │ I │ </> ││ ■ ■ ■ ■ ■ ■ │ 🎨 │
└────────────────────────────────────┘
```

- **色見本 4 色（赤・青・緑・紫）＋ カラーピッカー ＋ 解除。** 見本は**はっきりした色**にする。文書の色は目立たせるためにあるので、控えめな配色を並べるとその目的を潰す。それ以外の色はピッカーから
- **この行は 1 つの部品**で、本文の書式バー・セルの書式バー・表の塗り／文字色が共有する。同じ仕事をする控えが 3 つあれば、[インラインの解釈が 2 つに分かれたとき](table-model.md)と同じことが起きる
- **いま掛かっている書式はボタンが点灯する**（選択範囲を見て判定する）
- **同じ色をもう一度押すと外れる。別の色を押すと置き換わる。** 二重には付かない — 一続きの文字列の色は一つ
- `Ctrl+B` / `Ctrl+I` も効く（固定。[設定にはしない](settings-model.md)）
- **バーは選択範囲ではなくブロックに固定する。** テキストボックスは選択範囲の矩形を返さないため、位置を追うには隠し要素で描画を再現する仕掛けが要る。動かないバーのほうが押しやすくもある

### 編集の単位

本文をクリックすると、**その段落を生んだ markdown がそのまま開く**。閉じると、開いた範囲がそのまま 1 回のバイト範囲書き換えとして書き戻る。

開いた範囲と書き戻す範囲が同一であることが要点である。レンダリング結果から元の記法を逆算する必要が無く、[バイト範囲だけを書き換える](editor-model.md)という原則がそのまま守られる。

### 図と表は、それが住んでいるファイルを開く

本文と同じ考え方を[外部ファイル](editor-model.md)にも当てる。

| クリックした場所 | 開くもの | 書き戻す先 |
|---|---|---|
| 本文の段落・見出し | その範囲の markdown | **本文**のバイト範囲 |
| **図・表そのもの** | **`.dgm` / `.table` の全体** | **そのファイル** |
| **図表のキャプション** | **`@import` 行** | **本文**のバイト範囲 |

図と表は[それぞれ独立したファイル](editor-model.md)なので、開く範囲は**そのファイルの端から端まで**になる。
一方、その図をどこに置きどう採番するかを決めているのは `@import` 行であり、これは本文に属する。
**キャプションは `@import` 行の見え方**なので、キャプションをクリックすると `@import` 行が開く。
キャプションを持たない図表には、編集画面だけに `@import` 行そのものを表示する。

> **押したものが編集される。** 図を押せば図のファイル、説明文を押せば説明文を書いている行。

#### 参照ファイルには書式バーを出さない

書式バーが書くのは markdown である。表のセルは inline markdown を認めるが、
**表の意味トークンは `fill:` であってこの記法ではない**し、図のラベルはそもそも markdown ではない。
語彙の違うところに同じバーを出すと、間違った記法を書く。
表のセル書式は、[グリッド編集](table-model.md)を作るときに表の語彙で用意する。

#### 壊れたファイルはその場に出す

編集できるということは、**半端な状態のファイルが存在しうる**ということである。
`.dgm` の記法が壊れていたらパーサは落ちるが、**落ちるのはその図だけ**にする。
図の場所に理由とソースを出し、ページの残りはそのまま描く（[P6](decisions.md) — 黙って捨てない）。

本文側も同じで、**文書のパーサが受け付けない編集は書き戻さずに差し戻す**。
編集画面が壊れるくらいなら、キーストロークを断るほうがよい。

### 新しいブロックを書き始める場所

クリックできるのは既にあるブロックだけなので、**何も無いところから書き始める手段が要る。**

- **シートの末尾に、書き始めるための領域を置く。** 内容のあるシートでは、ポインタを乗せたときだけ「ここに本文を書く」と出る。空のシートでは最初から出す
- 書き込むのは**長さ 0 の範囲への挿入**である。直前のブロックとの間に空行を 1 つ入れる
- **何も書かずに閉じたら、何も書かない。** 既存ブロックを空にする操作（削除）と、新しいブロックを書かずにやめる操作は別物である

段落を増やすだけなら、**開いている入力欄の中で空行を 1 つ入れれば足りる**。確定した時点で 2 つの段落として解釈される。上の領域が要るのは、**クリックできる要素がそもそも無い場合**（空のシート、最後のブロックより下）だけである。
