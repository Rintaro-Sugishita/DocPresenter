# 作図モデル設計案 — PPTX / draw.io / Mermaid の「いいとこ取り」

作成: 2026-09-20 / 対象: DocPresenter の要件 R2「簡便さと複雑さを兼ね備えた作図」
前提調査: [既存サービス調査](../docs/research/existing-solutions.md)

---

## 0. 決定事項（ロック済み）

- **正本は 1 ファイル・セクション分割**。`foo.dgm` の中に意味 / レイアウト / スタイルをセクションとして並べる。差分の分離は「セクション境界」と「id 昇順の安定出力」で担保し、ファイル分割には頼らない。
- **図形語彙は DrawingML がネイティブに表現できる範囲に制限する**。超える表現はラスタ画像へのフォールバックとし、「この図は pptx で編集できない」と明示的に警告する。
- **自動レイアウトは TALA を第一候補とする**（2026-09 に MPL-2.0 で OSS 化）。§8 参照。
- **自由配置型を基盤とし、グラフ型はその上の特殊化として載せる**（§9.1）。両者は別機能ではなく、L2 レイアウト層をどれだけ埋めるかの違いでしかない。
- **ER 図は ErCreator（`.ermlx`）に、シーケンス図は Mermaid に、恒久的に委譲する**（§9.3）。
- **グラフ型の編集はキーボードだけで完結させる。** マウスは自動レイアウトの例外を直すためにある（§9.4）。L1 の記法は Mermaid の flowchart に寄せる。
- **スタイルトークンは表と共通**にし、凡例を文書単位で一つにまとめる。§10.4 参照。
- **図形（語彙）と部品（絵）を分ける**（§10.2）。語彙は十数個で固定し、ネットワークやクラウドのアイコンのような数の多い絵は `icon:` で名前かパスを指す。ベンダのアイコンセットは同梱しない。
- **ドラッグは L2 に 1 行書く操作である**（§12）。移動・リサイズ・ピン解除がその全部で、意味層は一切触らない。吸着は他の図形の辺・中心に対して行い、グリッドは持たない。

## 1. 三者から何を取り、何を捨てるか

| | 取りたいもの | 捨てるもの（＝その道具の敗因） |
|---|---|---|
| **PPTX** | 直接操作で誰でも描ける / 自由配置とピクセル制御 / 整列ガイド・スナップ / **図形に吸着するコネクタ** / 成果物がそのまま相手の編集可能な納品物 | 意味を持たない / 差分が取れない / コピペ増殖で原本が分からなくなる |
| **draw.io** | ブラウザで動く / 豊富な図形ライブラリ / コンテナ・スイムレーン・レイヤ / 配線の自動ルーティング / 任意コマンドとしての自動整列 | 保存形式が機械生成 XML で、**Git に置けても差分が人間に読めない** |
| **Mermaid** | テキストが 1 次ソース / **差分がレビュー可能** / AI がそのまま書ける / レイアウトを書かなくていい手軽さ | 10〜12 ノードを超えるとレイアウトが崩れる / **崩れても手で直せない**（逃げ道が無い） |

## 2. 核心にある対立と、その解き方

三者の違いは突き詰めると 1 点、**自動レイアウト vs 手動配置**に還元される。

- Mermaid = 座標は 100% 導出。手で触る余地が無い。
- PPTX / draw.io = 座標は 100% 手動。意味が残らない。

両立不能に見えるが、次の一手で解ける。

> **既定は自動レイアウト。人間が動かした要素だけを「ピン留め」として疎に記録する。**

30 ノードの図でも、実際に人が位置にこだわるのは 3〜5 個。その 3〜5 個だけを座標として持ち、残りは毎回レイアウトエンジンに解かせる。
これにより「Mermaid の手軽さ」と「PPTX の最終調整」が同じファイルの中で共存し、しかも差分は 3〜5 行に収まる。

## 3. 3 層モデル（本設計の要）

保存形式を**意味 / レイアウト / スタイル**の 3 層に分離する。

### L1 意味層（必須・人間が手で書く層）

ノード・エッジ・グループとラベルだけ。Mermaid と同等の簡潔さを目標にする。

```
flow システム構成 {
  web    "Web フロント"   : ui
  api    "API サーバ"     : service
  db     "PostgreSQL"     : store

  group 社内ネットワーク { api; db }

  web -> api  "HTTPS"
  api -> db   "接続プール"
}
```

### L2 レイアウト層（任意・GUI が書く。ただし人間可読）

**人が動かした要素だけ**を記録する。触っていない要素は一切現れない。

```
layout {
  api  @ (320, 160)
  db   @ (320, 320)
  web -> api : waypoints [(200,160)]
}
```

#### L2 は「ピン」だけではない — 入れ物（2026-10-03）

ピンしか持たない L2 には、**同じ事実が座標の数だけ複製される**という弱点があった。

```
layout {
  idLabel  @ ( 70,  96) 320x18
  idBox    @ ( 70, 116) 320x34
  pwLabel  @ ( 70, 162) 320x18     # ← 116 + 34 + 12
  pwBox    @ ( 70, 182) 320x34
}
```

ここに書いてある事実は「縦に積む・間隔 12・幅は枠いっぱい」の 3 つだけで、
残りは足し算の結果である。項目を 1 つ挿入すると下の全部が書き換わり、**1 行足した
だけの変更が 6 行の差分になる**。[P1「計算で出せるものはファイルに書かない」](decisions.md)に
反しているのは、ピンしか語彙が無かったからである。

**入れ物**は、その 3 つを言う。

```
layout {
  frame @ ( 40,  20) 380x392          # 座標を持つのは枠だけ

  stack frame (down; gap: 22; pad: 30) {
    title
    idField
    pwField
    submit
  }

  stack idField (down; gap: 2; pad: 0) { idLabel ; idBox ; idHint }
}
```

| 決めたこと | |
|---|---|
| **区切りは `;`** | グループの membership と同じ記号。行が 1 行 ＝ 1 行である |
| **空のセルは `.`** | 新しい記号はこの 1 つだけ |
| **またぐときは同じ名前を並べる** | `title ; title`。CSS の `grid-template-areas` から借りた——**書いた形がそのまま画面の形**になる記法として設計されたものである |
| **入れ子は名前で繋ぐ** | 入れ物の中に入れ物を書かない。別のブロックとして横に並べる。**どんな画面でもブロックの深さは 1**で、XAML のように深くならない |
| **1 つのバイト範囲** | 入れ物は宣言から閉じ括弧までで 1 つの範囲。セルの入れ替えはその範囲の書き換えになる |
| **ピンが勝つ** | 入れ物の中の図形にピンを書けば、そこに描かれて入れ物から外れる。[既存の規則](#122-ピンは外せなければならないただし戻す先がある図に限る)のまま |

伸び方は、**主軸は部品のまま・交差軸は伸ばす**。縦に積めば幅が揃い、横に並べれば
高さが揃う（WPF の `Stretch`、CSS の flex と同じ）。横に並べたものが入りきらない
ときは、`auto` の列が**割合で譲る**——これも flex と同じ。

| 入れ物 | 幅 | 高さ |
|---|---|---|
| `stack` 縦 | セルいっぱい | 部品のまま |
| `stack` 横 | 部品のまま | 部品のまま（上下中央） |
| `grid` | セルいっぱい | 部品のまま（上下中央） |

列の幅は `cols: 120, 1fr` のように書く。省けば**均等割り**で、数値を 1 つも書かずに
2 列のフォームが組める。入れ物に使えるのは**中身を持てる図形なら何でも**：枠を
見せたいなら `frame`、見出し付きなら `group`、何も見せたくないなら `""`（枠線の
無い文字は何も描かない）。

**入りきらない中身は、描いたうえで注記する。** 隠せば間違いも隠れる。

これで足りないものは[画面設計 §3.7](screen-design.md)にある（`scroll` `tabs` と、
中身を文字で持つ `tree` `list` `menu`）。

### L3 スタイル層（任意）

テーマとクラス定義。色やフォントを直接ノードに書かず、クラス経由にする。

```
style {
  ui      { fill: accent;  shape: round-rect }
  service { fill: primary }
  store   { shape: cylinder }
}
```

### なぜ層を分けるのか

**差分を分離するため**。draw.io が Git で使い物にならないのは、この 3 つが 1 つの XML に混ざっているからに尽きる。

- 意味を変えたら → L1 だけが動く。レビュアはここだけ読めばよい。
- 位置を微調整したら → L2 だけが動く。レビュー時に読み飛ばせる。
- 配色を変えたら → L3 だけが動く。

「レビュー可能」とは「差分が小さい」ことではなく、**「差分のどこを読むべきか自明である」**こと。層の分離はそのための手段。

## 4. 差分を汚さないための規律

layer 分離だけでは足りない。GUI で描いた結果がテキストに落ちる以上、以下を仕様として強制する。

1. **グリッド量子化** — 座標は 8px 等のグリッドに丸めて保存する。マウスの微小なブレでは差分がまったく出ない。
2. **id をキーにした安定出力** — L2 は配列でなく id キーのマップ。常に id 昇順で直列化し、要素の追加が他要素の行を動かさない。
3. **自動レイアウト結果は保存しない** — 計算で出せるものはファイルに書かない。書いた瞬間に「ノードを 1 個足したら全ノードの座標が動く」差分地獄が始まる。
4. **コネクタは座標でなくポート参照で持つ** — `web.right -> api.left`。PPTX のコネクタ・グルーと同じ考え方で、図形を動かしても配線の記述は変わらない。
5. **id は人間が読める安定 id** — `db-primary` のような命名。GUID は禁止。差分に GUID が並んだ時点でレビュー不能になる。

## 5. PPTX 出力を「後付け」にしない

調査の結論どおり、**編集可能な PPTX 出力は既存エコシステムの明確な空白地帯**（Marp の `--pptx-editable` は実験的、Slidev は画像化寄り）。ここを取りにいくなら、後から変換器を足すのでは間に合わない。

そこで **L1 / L3 の表現語彙を、DrawingML がネイティブに表現できる範囲に意図的に制限する**。

- 図形 → preset geometry（角丸四角・円柱・ひし形…）
- 配線 → connector shape（直線・カギ線・曲線）
- ラベル → text body
- グループ → group shape

この制約を最初に飲むことで、PPTX は画像貼り付けではなく**受け取った側が PowerPoint で直せるネイティブ図形**として出力できる。
制約を超える表現が必要な図（凝ったインフォグラフィック等）は、ラスタ画像へのフォールバックを明示的な逃げ道として用意し、「この図は pptx で編集できない」ことを警告する。

## 6. 入出力 — ErCreator 譲りの多形式

ErCreator の強みは「多くの形式を話せること」だった。作図でも同じ構えを取る。

| 方向 | 形式 | 意図 |
|---|---|---|
| import | **Mermaid** | AI が書いた図・既存 README 資産をそのまま受ける |
| import | **.drawio** | 既存の作図資産の移行パス |
| import | **.pptx の図形** | 「Excel/PowerPoint 設計書からの脱却」需要に直接応える |
| export | **SVG / PNG** | HTML・PDF 出力への埋め込み |
| export | **PPTX 図形** | §5 のとおり編集可能なネイティブ図形 |
| export | **Mermaid** | GitHub 上でそのまま描画させる用 |

ErCreator の [`mermaid-ermlx-spec.md`](../../ErCreator/design/mermaid-ermlx-spec.md) が確立した作法をそのまま踏襲する。すなわち **ラウンドトリップの基準記法を 1 つ決め、変換で失われる情報（ロス）を仕様書に明記する**。Mermaid にポート概念もピン留めも無い以上、Mermaid export は必ずロスを伴う。それを隠さず書く。

## 7. ErCreator.Canvas は移植元として参照する

当初は `ErCreator.Canvas`（Blazor の共有キャンバス）を**そのまま再利用する**前提で書いていたが、[実装スタックを TypeScript 単一言語に決めた](stack.md)ことにより、これは成立しない。

ただし価値が消えたわけではない。`Canvas.Geometry` / `Grid` / `Pointer` / `Selection` / `History`（undo/redo） / `Shapes` / `Rendering` / `Clipboard` には、**実際に動いている対話ロジック**がある。当たり判定・グリッド吸着・範囲選択・undo スタックといったアルゴリズムは言語に依存しないため、**参照実装として移植する**。

白紙から設計するのとは負荷が違う。「何を作るか」が既に確定している状態から始められる。

## 8. 自動レイアウトエンジン

**TALA を第一候補とする。**

TALA は D2 のレイアウトエンジンで、長らく D2 の収益源だったクローズドソース資産だったが、**2026-09 に MPL-2.0 で OSS 化された**。D2 が「ノード 10〜12 を超えても崩れない」評価を得ている理由がまさにこのエンジンであり、本設計が最も必要とするもの（有向グラフ・UML クラス図・シーケンス図の自動整列）にそのまま合致する。D2 本体（言語・CLI・dagre/ELK の 2 エンジン・テーマ・VS Code 拡張）も MPL-2.0。

| 候補 | 品質 | 備考 |
|---|---|---|
| **TALA** | 最良 | Go 実装。MPL-2.0。2026-09 に OSS 化されたばかりで、長期の保守体制は要観察 |
| ELK (elkjs) | 良 | 実績十分。JS 依存が入る |
| dagre | 可 | Mermaid が採用。本設計が超えたい水準そのもの |

### 判断が必要な点

1. **ライセンス** — MPL-2.0 はファイル単位のコピーレフト。ErCreator と同じく「無償・商用可だがソース非公開」の形態を取る場合、MPL ファイル**そのものを改変したときだけ**その改変の公開義務が生じる。改変せずリンク／プロセス分離で使う限り、自社コードの非公開は維持できる。**改変しない運用を前提に設計する**のが安全。
2. **実行形態** — TALA は Go 実装のため、(a) Go→WASM にコンパイルしてブラウザから呼ぶ（D2 Playground が同方式でブラウザ実行している実績あり）、(b) デスクトップ / CLI ではネイティブバイナリを同梱、の 2 系統になる見込み。Web とデスクトップでレイアウト結果が一致することが**必須要件**（結果が違うとピン留めの意味が崩れる）なので、同一エンジン・同一バージョンを両面で使う。
3. **フォールバック** — TALA の保守が滞った場合に備え、レイアウトエンジンは差し替え可能なインタフェースの背後に置く。§3 の設計上、レイアウト結果はファイルに保存しない以上、エンジン差し替えは図の再計算だけで済む。

## 9. 図の種類とスコープ

§3 の例は `flow`（フロー図）だが、設計書で要る図はそれだけではない。**レイアウトをどう決めるか**で三つに分かれる。

| 区分 | レイアウトの決まり方 | 図の例 | 扱い |
|---|---|---|---|
| **自由配置型** | **人が置く** | 概念図・構成イメージ・ポンチ絵・注釈図 | **自前（基盤）** |
| **グラフ型** | **計算で導出＋部分的にピン留め** | フロー図・画面遷移図・状態遷移図・システム構成図 | **自前（基盤の上に載せる）** |
| **委譲型** | 専用ツールが持つ | ER 図・シーケンス図 | **持たない**（§9.3） |

### 9.1 自由配置型が基盤である

当初のモデルは「自動レイアウト＋疎なピン留め」を前提にしていたが、**設計書には自動レイアウトの効かない図が大量にある**。任意の図形を任意の位置に置き、矢印や囲みを添えて説明する図がそれで、グラフ構造を持たない。

重要なのは、これが**別機能ではない**ということである。

> **自由配置型 ＝ L2 レイアウト層が全要素について埋まっている状態。**
> **グラフ型 ＝ L2 がほぼ空で、座標を計算で埋める状態。**

[§3 の 3 層モデル](#3-3-層モデル本設計の要)はそのまま使える。違いは **L2 をどれだけ埋めるか**だけであり、両者は連続している。自動レイアウトで描き始めて全部ピン留めすれば自由配置図になるし、その逆もできる。

したがって順序は明確になる。**自由配置型が一般形で、グラフ型はその上に自動レイアウトを載せた特殊化である。** 基盤を先に作る（§11）。

### 9.2 自由配置型に必要な追加要素

グラフ型だけを想定していたモデルに、以下が要る。

| 要素 | 内容 |
|---|---|
| **単独図形** | どのエッジにも繋がらない図形。四角・吹き出し・囲み枠 |
| **自由端点の線** | 図形間ではなく、任意の座標から座標へ引く矢印・線 |
| **z 順** | 図形が重なるため、前後関係が要る。グラフ型では不要だった |
| **整列・スナップ** | PowerPoint 相当の操作性。グリッド吸着、左揃え・等間隔配置 |

整列・スナップは `ErCreator.Canvas` の `Canvas.Grid` / `Canvas.Geometry` が既に持っている（§7）。

z 順は L1（意味層）ではなく **L2（レイアウト層）に置く**。「どちらが手前か」は見た目の話であり、座標と同じ性質のため。

### 9.3 委譲する二つ

#### ER 図 → ErCreator（`.ermlx`）

`.ermlx` は既に完成した形式であり、専用エディタも DDL 生成も差分機能も揃っている。**同じものを作り直す理由が無い。**

```markdown
@import "shared/customer-domain.ermlx"
```

#### シーケンス図 → Mermaid（恒久的に委譲する）

当初は「段階 3 に後回し」としたが、**恒久的に持たない**方針に改める。理由は明確である。

> **シーケンス図はレイアウトが順序から完全に導出される。**

`A->>B: 認証要求` と書けば、位置は決まる。ライフラインの間隔も、矢印の縦位置も、すべて記述順が決める。**人が位置を決める余地が無い。**

このことから二つの帰結が出る。

1. **本モデルの価値がまったく効かない。** 3 層モデルの核心は「自動レイアウトを人が部分的に上書きできること」だが、シーケンス図には上書きすべき位置が存在しない。ピン留めする対象が無い
2. **位置を扱う GUI はむしろ不利。** draw.io がシーケンス図で使いにくいのは、ライフラインを手で引き、矢印を手で揃えるという、本来不要な作業を強いるからである。Mermaid が書きやすいのは、順序だけ書けば済む構造に素直に合っているため

自前で作っても Mermaid を超えられず、モデルの強みも活きない。**素直に委譲する。**

```markdown
@import "auth-design/login-sequence.mmd"
```

この判断は、ER 図を ErCreator に委ねるのと同じ規律である。**専用ツールが明確に優れている領域には手を出さない。**

### 9.4 入力方法は図の種類で決まる

フローチャートを例に、既存ツールの長短を整理する。

| | draw.io | Mermaid |
|---|---|---|
| 書きやすさ | **誰でも書ける** | 記法の学習が要る |
| **速度** | **遅い** — マウスとキーボードを往復する | **速い** — キーボードから手を離さない |
| **レンダリング品質** | 良い | **悪い** — レイアウトも見た目も |

draw.io が遅いのは操作が下手だからではなく、**モード切替が構造的に入る**ためである。図形ツールを選ぶ → ドラッグ → ダブルクリックして文字を打つ → Esc → 線ツールを選ぶ → ドラッグ → またダブルクリック。この往復が本質的に遅い。

Mermaid が速いのは、**位置を書かないから**である。構造だけ打てば済むので、手がキーボードから離れない。

#### 本モデルでは、この対立が自動的に解ける

[§3 の 3 層モデル](#3-3-層モデル本設計の要)は、既にこの答えを内蔵している。

| 層 | 入力手段 | 作業量の比率 |
|---|---|---|
| **L1 意味層** | **キーボード**（テキストを打つ） | **ほぼ全部** |
| L2 レイアウト層 | マウス（ピン留めしたい数個だけ） | わずか |
| L3 スタイル層 | ほぼ触らない（テーマが決める） | ほぼゼロ |

グラフ型の図では **L1 を打つことが作図そのもの**であり、これは Mermaid を書く体験と等価である。マウスは「自動レイアウトの結果が気に入らない数個を動かす」ときにだけ使う。

したがって設計上の要請はこうなる。

> **グラフ型の編集 UI は、キーボードだけで図を書き切れなければならない。**
> **マウスは例外処理のためにある。**

これは通常のキャンバス設計の逆である。普通は「マウスで描き、テキストは書き出し結果」だが、本モデルでは **テキストが正であり、マウスは微調整**。draw.io 型のキャンバスを作ってしまうと、モデルの利点を自ら捨てることになる。

#### 入力手段は L2 の埋まり具合に一致する

§9.1 で「自由配置型とグラフ型は L2 をどれだけ埋めるかの違い」と整理した。入力手段はこれに正確に対応する。

| | L2 | 位置の決まり方 | 主な入力 |
|---|---|---|---|
| グラフ型 | 空 | 計算 | **キーボード** |
| 自由配置型 | 満 | 人 | **マウス** |

**入力手段は UI の好みではなく、モデルから導かれる。** 位置を決めない図にマウスは要らず、位置が本質の図にキーボードは向かない。

#### 具体的な UI

テキストペインとキャンバスの並置とする。

- テキストを打つ → キャンバスが即座に更新される
- キャンバス上でドラッグ → **L2 だけが書き変わり、テキスト（L1）は 1 バイトも変わらない**

後者が[差分衛生の規律](#4-差分を汚さないための規律)をそのまま UI に表したものになる。

#### レンダリング品質は既に手当てされている

Mermaid の「レンダリングが良くない」は二つに分解できる。どちらも既に決定済みの手段が当たる。

| 内訳 | 手当て |
|---|---|
| レイアウト品質（配置・配線） | **TALA**（§8）。Mermaid が採用する dagre を明確に上回る |
| 見た目（字組み・図形・余白） | 自前レンダラ ＋ テーマ（§10）。DrawingML プリセットに限定した図形語彙 |

#### L1 の記法は Mermaid に寄せる

学習コストをほぼゼロにするため、**グラフ型の L1 記法は Mermaid の flowchart 記法に近づける**。ポート参照・グループ・ID といった本モデル固有の概念があるため完全一致はしないが、Mermaid を書ける人がそのまま書ける水準を目標とする。

これにより「Mermaid の書き味 × TALA のレンダリング」が成立する。Mermaid からの取り込み（§6）も、ほぼ恒等変換に近くなる。


## 10. 図形とスタイルの語彙 — 表と共通にする

### 10.1 図形は DrawingML のプリセットに限る

§5 の制約を具体化する。**記法は Mermaid の括弧をそのまま借り**、それぞれに DrawingML のプリセットが 1 つ対応する。

| 記法 | 図形 | DrawingML |
|---|---|---|
| `[ ]` | rect | `rect` |
| `( )` | round-rect | `roundRect` |
| `([ ])` | stadium（開始・終了） | `flowChartTerminator` |
| `{ }` | diamond（判断） | `flowChartDecision` |
| `[( )]` | cylinder（データストア） | `flowChartMagneticDisk` |
| `(( ))` | ellipse | `ellipse` |
| `> ]` | note（吹き出し・注記） | `foldedCorner` |
| `" "` | text（枠の無い文字） | テキストボックス |
| `[/ /]` | parallelogram（入出力） | `flowChartInputOutput` |
| `{{ }}` | hexagon（準備） | `flowChartPreparation` |
| `[/ \]` | loop-start（ループ開始） | `trapezoid` |
| `[\ /]` | loop-end（ループ終了） | `flowChartManualOperation` |
| `group … { }` | group（囲い） | グループ |
| `--` | line（単独の線） | `straightConnector1` |

**ループの開始と終了は対で読む記号**なので、互いの鏡像にした（上が狭い / 下が狭い）。
どちらも Mermaid が台形として持っている記法であり、発明していない。

#### 単独の線は、接続ではない（2026-10-02 追記）

`rule1 --` と書くと、**どこにも繋がっていない 1 本の線**が置ける。

最初は接続（`a --> b`）だけで足りると考えていた。足りなかったのは画面を描き
始めてからで、**画面を仕切る罫線**と**何かを指す矢印**はどちらも「2 つの図形が
関係している」ことを言っていない。接続で書けば、繋ぐためだけの図形を 2 つ
置くことになる——図に無いものをファイルに書くことになる。

| 決めたこと | |
|---|---|
| **記法は接続から借りる** | `--`。線の書き方を 2 つ覚えさせない。ハイフン 3 つ以上でも同じ |
| **文字は持たない** | 入れる括弧が無い。部品経由で文字を書いた場合は[黙って捨てず](decisions.md)に注記を出す |
| **接続より先に読む** | id は `-` で終われるので `rule1 ---` は「`-` への接続」とも読める。そんな図形が無い以上、読みは 1 つに決まる |
| **幾何は箱の対角線** | 置き方・動かし方・揃え方・大きさの変え方が、ほかの図形とすべて同じになる。高さ 0 なら水平線、幅 0 なら垂直線 |
| **PPTX ではコネクタ** | 受け取った人が端を掴める。図形（プリセット）として出すとただの細い箱になる |

見た目は[スタイル層](#104-スタイルトークンは表と揃える)で言う。

| 宣言 | 値 | |
|---|---|---|
| `line` | 色 / `dashed` | ほかの図形と同じ鍵。色と破線が同時に書けないのは既存の制約である |
| `weight` | 正の数 | 線の太さ。**線に限らずどの図形の輪郭にも効く**。値なので class ではなく変数（`--dp-weight`）で渡す |
| `arrow` | `none` / `start` / `end` / `both` | 矢じりを付ける端。`icon` や `align` と同じく、レンダラが自分で読む宣言である |
| `slope` | `down` / `up` | 箱の対角線は 2 本ある。どちらを引くかは「どこに置いたか」では決まらない |

**矢印を意味層（`-->`）ではなくスタイル層に置いた**のは、部品が持てるようにする
ためである。「この製品で何かを指す矢印」は `pointer` という名前で 1 回決めれば
よく、使うたびに `-->` と書き分けるものではない。接続の矢印が意味層にあるのは、
そちらは**向きが関係そのもの**だからで、矛盾しない。

この範囲を超える表現が要る図は、ラスタ画像へのフォールバックとし「pptx で編集できない」と警告する（§5）。

**ここに際限なく足さない。** 語彙は「どの設計書にも出てくる図形」に限る。
ネットワーク図のルータや AWS のアイコンのような**数の多い絵**は、この語彙ではなく[部品ライブラリ](#102-数の多い絵は語彙ではなく部品ライブラリに置く)に置く。

### 10.2 数の多い絵は、語彙ではなく部品ライブラリに置く

> **2026-10-02 追記。** この分け方は画面部品でそのまま効いた。ラジオボタン・
> スライダー・スクロールバー・数値入力は、どれも「丸の中に点」「線の上につまみ」で
> あって、括弧 1 組を与えるほどの語彙ではない。`ui/*` として同梱の絵に加えた
> （[画面設計 §3.5](screen-design.md)）。

ネットワーク図のルータ・スイッチ・ファイアウォール、AWS / Azure / GCP のアイコン。
これらは**図形ではなく絵**であり、しかも**数が多い**。§10.1 の語彙に足していくと、

- 「四角」を選ぶ一覧に「EC2」が並ぶ。**使用頻度が 100 倍違うものが同格に並ぶ。**
- 語彙が出力先（DrawingML のプリセット）と対応しなくなる。
- ベンダのアイコンには**ライセンス**があり、同梱できるとは限らない。

だから分ける。

> **図形は語彙（十数個・恒久・記法を持つ）。部品は絵（多数・分野ごと・名前で指す）。**

#### 書き方 — 絵は見た目なのでスタイル層に入る

```
free {
  rtr [社内ルータ]
}

style {
  rtr { icon: net/router }        # 同梱の部品
  ec2 { icon: ./icons/ec2.svg }   # 手元のファイル
}
```

意味層は「これは社内ルータという要素だ」としか言わない。**どんな絵で描くかは L3** である。
`icon:` が付いた図形は、**絵とその下に名前**という形で描かれる（ネットワーク図の描き方）。枠は引かない。

#### 同梱するのは「どの会社の図にも出てくる絵」だけ

クラウド / インターネット / VPN / ルータ / スイッチ / ファイアウォール / サーバ / ストレージ /
利用者 / 携帯端末。**自分で描いた 10 個**なので、ライセンスが付いてこない。

**ベンダのアイコンセットは同梱しない。** AWS も Azure も GCP も Cisco も、公式が配布しており、
利用条件はその配布元が決める。**利用者が落としてきたファイルを `icon: ./icons/….svg` で指す**のが正しい形で、
これなら数が何百あっても本体は太らず、条件も混ざらない。

#### UI でも同格にしない

「＋ 図形」と「＋ 部品」は別のボタン・別の一覧である。部品の一覧は分野ごとに増えていくが、
図形の一覧は十数個のまま変わらない。

### 10.3 図形の中の文字は、本文と同じ記法で書く

ラベルは**箱に入った文章**である。だから本文と同じ記法が効く。

```
free {
  a [**必須** の項目]
  b [`user_id` を送る]
  c [[要確認]{color=#c62828} の分岐]
}
```

太字 `**…**` / 斜体 `*…*` / コード `` `…` `` / 色 `[…]{color=#rrggbb}`。
[本文](inline-format.md)でも[表のセル](table-model.md)でも同じ 4 つで、**覚え直しが要らない**。

三点だけ決めた。

1. **閉じていない印はただの文字。** `2 * 3 = 6` は掛け算であって斜体ではない。
   `_` は斜体に使わない（`user_id_1` は識別子であって強調ではない）。`\*` で逃げられる。
2. **折り返しは見える文字で決まる。** `**` は数えない。印を足しただけで箱が大きくなるのは嘘である。
3. **描き方は SVG の `tspan`。** HTML の span と同じ構造なので、同じモデルから HTML にも PPTX にも出せる。

書くときは、**表のセルと同じ書式バー**が図形の上に浮く。B / I / `</>` と色見本で、
記法を覚えていなくても書ける。[同じ部品を 3 か所で共有している](decisions.md)ので、
本文・セル・ラベルで操作が食い違うことがない。`Ctrl+B` / `Ctrl+I` も同じ。

### 10.4 スタイルトークンは表と揃える

[表モデル設計案 §5.1](table-model.md) で定めた語彙を、**そのまま図でも使う**。

```
# 意味トークン（4 種で確定）
fill: changed / pending / disabled / removed

# 区分トークン
fill: tint-1 / tint-2 / tint-3 / tint-4
```

揃える利益は大きい。

1. **凡例が文書単位で一つにまとまる。** 表で `changed` を使い、図でも `changed` を使えば、文書末の凡例（[表モデル設計案 §5.1](table-model.md)）は両方を合算した 1 つで済む。表と図で別々の凡例が出るのは読み手にとって無意味な分断である
2. **表と図で見た目が一致する。** 同じ「変更あり」が別の色で出ることが無くなる
3. **軸 B** — AI が表と図を同じ語彙で読める

直値（`#3A7BD5` 等）を書かせない理由も表と同じ。出力先での再現性、文書間の一貫性、差分の可読性。

### 10.5 SVG のソースマップを出す

[レビューモデル設計案 §3.4](review-model.md) が全出力形式に要求するものの、図における実装。

> **SVG の各ノード → `.dgm` 上のバイト範囲**

これにより、顧客が HTML 上で図のノードをクリックしてコメントしたとき、アンカーが `.dgm` のバイト範囲として確定する。図へのコメントが表や本文と同じ仕組みに乗る。

## 11. 段階的に作る

| 段階 | 範囲 |
|---|---|
| **1** | **自由配置型**（図形・自由端点の線・テキスト・z 順・スナップ・整列）、3 層ファイル形式、既定テーマ、SVG ＋ PPTX 図形出力、ソースマップ |
| **2** | **グラフ型**（node / edge / group、TALA による自動レイアウト、疎なピン留め）、Mermaid 入出力 |
| **3** | スタイル層（意味・区分トークン）、画像オーバーレイ、`.drawio` / `.pptx` インポート |

### 段階 1 に自由配置型を置く理由

自動レイアウトのほうが差別化要因として目を引くが、**先に作るべきは基盤のほうである**。

1. **一般形だから。** §9.1 のとおり、グラフ型は自由配置型に自動レイアウトを載せた特殊化にすぎない。一般形を先に作れば、段階 2 は「L2 を計算で埋める」だけで済む
2. **外部依存が無い。** TALA の Go→WASM 統合、レイアウトの決定性検証といった重い検証を待たずに進められる
3. **出力経路を先に検証できる。** ファイル形式・エディタ・SVG / PPTX 出力・ソースマップという縦の一本が、レイアウトエンジン抜きで通る。ここが通れば残りは載せるだけになる

段階 2 まで到達した時点で「テキストで書けて、崩れない自動レイアウトで、編集可能な PPTX 図形として出る」が成立する。[既存サービス調査](../docs/research/existing-solutions.md)のとおり、ここに到達しているものは無い。

## 12. 直接操作 — ドラッグは 1 行を書く操作である

図形を引きずるのは、絵を描き替えることではない。**[L2 レイアウト層](#l2-レイアウト層任意gui-が書くただし人間可読)に 1 行書く**ことである。
この 1 行が、この機能の設計のほぼ全部を決めている。

```
layout {
  home   @ (320, 640)
  locked @ (540, 640)   ← これを 1 行書き換えるのがドラッグ
}
```

### 12.1 1 回のドラッグ ＝ 1 つのバイト範囲

意味層（`flow { … }`）は**移動では一切触らない**。ピンが既にあればその行を書き換え、無ければ
`layout` ブロックの末尾に 1 行足す。ブロックが無ければブロックごと作る。したがって

- 図形を 1 つ動かした差分は、**座標 1 行の差分**である。
- 図形を増やしても、動かしていない図形の行は 1 行も増えない（[§4 の規律](#4-差分を汚さないための規律)）。
- 動かしただけで図の**意味**が変わることは、構造上あり得ない。

**手で揃えた桁は保つ。** 書き換える行の空白の形を読み取り、名前の幅と各数値の桁をそのまま使う。
`frame @ ( 40,  20) 380x330` を動かしても `frame @ ( 44,  24) 380x330` になる。
桁が崩れるだけの差分は、レビューする人にとって嘘の変更でしかない。
**大きさと奥行き（`z:`）は移動では失われない。** 動かすことは動かすことであって、書き直すことではない。

### 12.2 ピンは外せなければならない。ただし戻す先がある図に限る

`layout` が増える一方のファイルは、**自動レイアウトを捨てたファイル**である。それは draw.io に戻ることを意味する。
だから「自動配置に戻す」を移動と同じ重さの操作として置く。行を消せば、その図形はまたエンジンが決める。

**ただし自由配置（`free`）の図では外せない。** 自由配置にはレイアウトエンジンが動く余地が無く、ピンだけが
「その図形がどこにあるか」を言っている。外せば置き場所そのものが消える。だからボタンは押す前から押せない状態にする
（押してから「消えました」では遅い）。グループだけはどの図でも外せる。グループの枠は中身から計算されるからである。

なお、**置き場所の無い図形は黙って消さず、図の下に並べる**。手で書いたファイルにピンの書き漏れがあっても、
掴める場所にあれば直せる。消してしまうと、ファイルには在るのに画面に無い図形ができる（[P6](decisions.md)）。

| 操作 | ファイルへの結果 |
|---|---|
| ドラッグ / 矢印キー | その図形の 1 行を書く（無ければ足す） |
| 右下の取っ手を引く | 同じ行に `WxH` を書く |
| 自動配置に戻す | その 1 行を消す |

### 12.3 吸着は他の図形に対して行う。グリッドは持たない

辺が他の図形の辺に、中心が中心に 5 以内で近づいたとき、そこへ吸わせ、吸った線を表示する。
**辺と中心は混ぜない。** 左端がチェックボックスの中心に吸い付くのは、誰も引いていない線である。
**グリッド（何 px 刻み）は持たない。** 設計書の画面図で揃えたいのは「他の部品の左端」であって、
方眼の交点ではない。方眼に吸わせると、既に揃っている座標がかえってずれる。

矢印キーは 4、Shift 付きは 1 動かす。最後の 1 px は目で決める作業なので、キーボードに残す。

### 12.4 画面には図そのものを出す

編集中に見えているのは**レンダラが出した SVG そのもの**である。編集用の別の描画は持たない。
上に載せるのは選択枠・取っ手・吸着ガイドだけで、これらはファイルにも出力にも現れない。

ドラッグ中、動かしている図形は指に追従するが、**線は薄くなるだけで伸び縮みしない**。
線の経路は[レイアウト時に決まる](#4-差分を汚さないための規律)ので、置いた瞬間に引き直される。
中途半端に伸びる線を見せるより、「置いたら引き直される」と分かるほうが正直である。

### 12.5 グループは中身の結果である

グループの枠は、含む図形から計算される。**計算結果をドラッグさせてはいけない**ので、
ピン留めされていないグループは動かせない（そう言って断る）。既に人が留めたグループは、その人のものなので動かせる。

### 12.6 注釈（overlay）も同じ作法で動かす

画面キャプチャへの注釈は、丸（marker）と、それが指す先の 2 点を持つ。**丸をドラッグすれば位置、
先端の点をドラッグすれば指す先**が動き、書かれるのはやはり 1 行である。文言には触らない。

```
overlay "../assets/login-screen.png" {
  ② @ (168, 186) -> (188, 192)  "パスワード"   ← 前の 2 数字が丸、後ろの 2 数字が指す先
}
```

ここだけは**レンダラが出した HTML をその場で乗っ取る**。図と違って overlay の描画には画像のパス解決が要り、
[どのファイルがどこにあるかは器の責務](platforms.md)だからである。エディタが画像を引きに行った時点で、
エディタは場所の方針を持ってしまう。

### 12.7 図形の追加・削除は意味層の編集である

移動と違い、追加・削除・改名・線引きは**意味層**（`free { … }` / `flow { … }`）を書く。
人が手で書く層なので、書かれる行は**その人が書いたであろう行**でなければならない。

| 操作 | ファイルへの結果 |
|---|---|
| 図形を足す | 意味層に 1 行。自由配置ならレイアウト層にもピンを 1 行（[置き場所を決める層が他に無い](#122-ピンは外せなければならないただし戻す先がある図に限る)） |
| 文字を変える | 同じ行の括弧の中だけ |
| 種類を変える | 同じ行の括弧だけ。`:::スタイル` は残る |
| 線を引く | 意味層に 1 行 |
| 図形を消す | その行と、**それを指していたもの全部** |

#### 複数行の変更も 1 回の書き換えにする

削除は最大で 4 種類の行に触る（図形の行・線の行・ピンの行・グループの所属）。
これを別々の編集にすると、途中で失敗したファイルが残りうる。**触った行だけを含む 1 つのバイト範囲**として書き戻し、
間に挟まる行はそのまま写す。差分に出るのは消えた行だけで、書き戻しは 1 回のままである。

#### 消えたものを指したままにしない

線の片端が消えていれば、その図は警告付きで描画される。**それは「削除」ではない。**
だから削除は、その図形を指していた線・ピン・グループの所属を一緒に消す。

取り消しが無いので、**消える線の本数はメニューのラベルに書く**（「削除（線 2 本も消える）」）。
[結合で消える文字を先に知らせる](table-model.md)のと同じ判断である。

#### 名前は `box1` / `oval2`

id は差分に出るので、**人間が読める安定した名前**でなければならない（[GUID は禁止](requirements.md)）。
種類ごとの短い語に連番を付け、使われていないものを選ぶ。気に入らなければソースで直せる。

#### 置き場所はコンテキストメニュー

追加・種類変更・線引き・削除は**右クリック**に置いた。ときどき使うものをツールバーに並べると、
常に使うもの（移動・大きさ・自動配置に戻す）が押しのけられる。[表の行・列操作と同じ判断](table-model.md)である。
文字の書き換えは**ダブルクリック**と `F2`、削除は `Delete` でも届く。

文字を書き換えるときは、**図形の上にテキストボックスを重ねる**。
[セル編集と同じ理由](table-model.md)で、IME には最初の 1 打から変換対象が要る。

### 12.8 線は選べて、付け替えられて、折れる

線も図形と同じく**選んで操作する対象**である。ただし線は自分の位置を持たないので、操作は 3 つになる。

| 操作 | ファイルへの結果 |
|---|---|
| 消す | 意味層のその 1 行が消える |
| 端をドラッグして別の図形へ | 意味層の同じ行を書き換える（線種・ラベル・桁はそのまま） |
| 線をドラッグ | **レイアウト層**に折れ点の行が 1 行 |

**線は「近さ」で拾う。** 当たり判定のための透明な太い線を上に重ねると、それが図形へのクリックまで奪う。
描かれた線からの距離で拾えば、図形が手前にあるときは図形が勝つ。

#### 折れ線 — 1 つの操作で、直角に

折れ点は座標なので[レイアウト層](#l2-レイアウト層任意gui-が書くただし人間可読)に入る。意味層は「何と何が繋がるか」しか言わない。

```
layout {
  browser -> web @ (110, 210); (110, 260)
}
```

操作は**線をドラッグするだけ**である。モードも、ポートも、線種の選択も無い。

- **1 回目のクリックで線を選び、2 回目のドラッグで折る。** 選ぶだけのつもりで触った線が折れてしまわないため。
- 折れ点は**隣の点と直角に吸着する**。系統図は直角で描かれるもので、2 px だけ直角を外した線は折れていないより悪い。
- 線を消したりつなぎ替えたりすれば、**折れ点の行も一緒に動く**。指す先の無い折れ点をファイルに残さない。
- **折れ点は消せる。** □をダブルクリックでその 1 つ、右クリックの「まっすぐに戻す」で全部。線の上に戻しても消える。
  **消し方が要る**のは、[取り込みで大量に湧いた折れ点](#)を人が片付ける場面が必ずあるからで、
  そこで 1 つずつしか消せない道具は使われない。

draw.io の操作感（ツールを選んでから描く、端点をポートに吸わせる）にも、Mermaid の曲線にもしない。
**線は直線の連なりであり、角は人が置いた点である。**

### 12.9 まだやらないこと

- グループの**作り直し**（どの図形を含むかの GUI）。
- 線の**ラベル**の GUI 編集（今はソースで書く）。
- **元に戻す（undo）**。今はどの操作も取り返しがつかないので、失うものは操作の前に言う。

## 13. 残る未決定事項

- レイアウト結果の**決定性**の検証 — 同一入力から常に同一座標が出ることを CI で担保する必要がある（ピン留めの前提）。
- Mermaid export 時のロス仕様の確定（ポート参照・ピン留め・グループの扱い）。
- `.drawio` / `.pptx` インポート時の図形マッピング表（DrawingML プリセットへの寄せ方）。
- **オーバーレイの座標**（§9.3）— 画像のピクセル座標で持つと、画像を差し替えた瞬間に全部ずれる。相対座標にするか、画像のバージョンを併記するか。
- **自由配置型での L2 分離の是非**（§9.1）— 全要素がピン留めされた図では、図形とその座標が別セクションに分かれる。形式の一貫性は保てるが、その図に限れば座標を図形の隣に置くほうが読みやすい可能性がある。
- **自由端点の線の座標**（§9.2）— 図形に繋がらない線の端点は絶対座標になる。周囲の図形を動かしても追随しないため、扱いを決める必要がある。
