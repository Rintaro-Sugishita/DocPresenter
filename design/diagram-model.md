# 作図モデル設計案 — PPTX / draw.io / Mermaid の「いいとこ取り」

作成: 2026-09-20 / 対象: DocPresenter の要件 R2「簡便さと複雑さを兼ね備えた作図」
前提調査: [既存サービス調査](../docs/research/existing-solutions.md)

## 1. 三者から何を取り、何を捨てるか

| | 取りたいもの | 捨てるもの（＝その道具の敗因） |
|---|---|---|
| **PPTX** | 直接操作で誰でも描ける / 自由配置とピクセル制御 / 整列ガイド・スナップ / **図形に吸着するコネクタ** / 成果物がそのまま相手の編集可能な納品物 | 意味を持たない / 差分が取れない / コピペ増殖で原本が分からなくなる |
| **draw.io** | ブラウザで動く / 豊富な図形ライブラリ / コンテナ・スイムレーン・レイヤ / 配線の自動ルーティング / 任意コマンドとしての自動整列 | 保存形式が機械生成 XML で、**Git に置けても差分が人間に読めない** |
| **Mermaid** | テキストが 1 次ソース / **差分がレビュー可能** / AI がそのまま書ける / レイアウトを書かなくていい手軽さ | 10〜12 ノードを超えるとレイアウトが崩れる / **崩れても手で直せない**（逃げ道が無い） |

## 2. 核心にある対立と、その解き方

三者の違いは突き詰めると 1 点、**自動レイアウト vs 手動配置**に還元される。

- Mermaid = 座標は 100% 導出。手で触る余地が無い。
- PPTX / draw.io = 座標は 100% 手動。意味が残らない。

両立不能に見えるが、次の一手で解ける。

> **既定は自動レイアウト。人間が動かした要素だけを「ピン留め」として疎に記録する。**

30 ノードの図でも、実際に人が位置にこだわるのは 3〜5 個。その 3〜5 個だけを座標として持ち、残りは毎回レイアウトエンジンに解かせる。
これにより「Mermaid の手軽さ」と「PPTX の最終調整」が同じファイルの中で共存し、しかも差分は 3〜5 行に収まる。

## 3. 3 層モデル（本設計の要）

保存形式を**意味 / レイアウト / スタイル**の 3 層に分離する。

### L1 意味層（必須・人間が手で書く層）

ノード・エッジ・グループとラベルだけ。Mermaid と同等の簡潔さを目標にする。

```
flow システム構成 {
  web    "Web フロント"   : ui
  api    "API サーバ"     : service
  db     "PostgreSQL"     : store

  group 社内ネットワーク { api; db }

  web -> api  "HTTPS"
  api -> db   "接続プール"
}
```

### L2 レイアウト層（任意・GUI が書く。ただし人間可読）

**人が動かした要素だけ**を記録する。触っていない要素は一切現れない。

```
layout {
  api  @ (320, 160)
  db   @ (320, 320)
  web -> api : waypoints [(200,160)]
}
```

### L3 スタイル層（任意）

テーマとクラス定義。色やフォントを直接ノードに書かず、クラス経由にする。

```
style {
  ui      { fill: accent;  shape: round-rect }
  service { fill: primary }
  store   { shape: cylinder }
}
```

### なぜ層を分けるのか

**差分を分離するため**。draw.io が Git で使い物にならないのは、この 3 つが 1 つの XML に混ざっているからに尽きる。

- 意味を変えたら → L1 だけが動く。レビュアはここだけ読めばよい。
- 位置を微調整したら → L2 だけが動く。レビュー時に読み飛ばせる。
- 配色を変えたら → L3 だけが動く。

「レビュー可能」とは「差分が小さい」ことではなく、**「差分のどこを読むべきか自明である」**こと。層の分離はそのための手段。

## 4. 差分を汚さないための規律

layer 分離だけでは足りない。GUI で描いた結果がテキストに落ちる以上、以下を仕様として強制する。

1. **グリッド量子化** — 座標は 8px 等のグリッドに丸めて保存する。マウスの微小なブレでは差分がまったく出ない。
2. **id をキーにした安定出力** — L2 は配列でなく id キーのマップ。常に id 昇順で直列化し、要素の追加が他要素の行を動かさない。
3. **自動レイアウト結果は保存しない** — 計算で出せるものはファイルに書かない。書いた瞬間に「ノードを 1 個足したら全ノードの座標が動く」差分地獄が始まる。
4. **コネクタは座標でなくポート参照で持つ** — `web.right -> api.left`。PPTX のコネクタ・グルーと同じ考え方で、図形を動かしても配線の記述は変わらない。
5. **id は人間が読める安定 id** — `db-primary` のような命名。GUID は禁止。差分に GUID が並んだ時点でレビュー不能になる。

## 5. PPTX 出力を「後付け」にしない

調査の結論どおり、**編集可能な PPTX 出力は既存エコシステムの明確な空白地帯**（Marp の `--pptx-editable` は実験的、Slidev は画像化寄り）。ここを取りにいくなら、後から変換器を足すのでは間に合わない。

そこで **L1 / L3 の表現語彙を、DrawingML がネイティブに表現できる範囲に意図的に制限する**。

- 図形 → preset geometry（角丸四角・円柱・ひし形…）
- 配線 → connector shape（直線・カギ線・曲線）
- ラベル → text body
- グループ → group shape

この制約を最初に飲むことで、PPTX は画像貼り付けではなく**受け取った側が PowerPoint で直せるネイティブ図形**として出力できる。
制約を超える表現が必要な図（凝ったインフォグラフィック等）は、ラスタ画像へのフォールバックを明示的な逃げ道として用意し、「この図は pptx で編集できない」ことを警告する。

## 6. 入出力 — ErCreator 譲りの多形式

ErCreator の強みは「多くの形式を話せること」だった。作図でも同じ構えを取る。

| 方向 | 形式 | 意図 |
|---|---|---|
| import | **Mermaid** | AI が書いた図・既存 README 資産をそのまま受ける |
| import | **.drawio** | 既存の作図資産の移行パス |
| import | **.pptx の図形** | 「Excel/PowerPoint 設計書からの脱却」需要に直接応える |
| export | **SVG / PNG** | HTML・PDF 出力への埋め込み |
| export | **PPTX 図形** | §5 のとおり編集可能なネイティブ図形 |
| export | **Mermaid** | GitHub 上でそのまま描画させる用 |

ErCreator の [`mermaid-ermlx-spec.md`](../../ErCreator/design/mermaid-ermlx-spec.md) が確立した作法をそのまま踏襲する。すなわち **ラウンドトリップの基準記法を 1 つ決め、変換で失われる情報（ロス）を仕様書に明記する**。Mermaid にポート概念もピン留めも無い以上、Mermaid export は必ずロスを伴う。それを隠さず書く。

## 7. ErCreator からの再利用

`ErCreator.Canvas` は Razor クラスライブラリで、**Web(Blazor WASM) と デスクトップ(WPF / BlazorWebView) の双方から参照される単一ソース**として作られている。しかも既に以下が揃っている。

`Canvas.Geometry` / `Canvas.Grid` / `Canvas.Pointer` / `Canvas.Selection` / `Canvas.History`（undo/redo） / `Canvas.Shapes` / `Canvas.Rendering` / `Canvas.Clipboard` / `Canvas.AutoSave`

要件 R8（Web と VS Code の両方で編集）は、この構造をそのまま引き継げば解ける。**VS Code 拡張は WebView に同じ Blazor キャンバスを載せる**ことで、Web・デスクトップ・VS Code の三面が単一実装で賄える。ErCreator と同じ `Model.Abstractions / Engine / Canvas / Web / Cli` のレイヤリングを踏襲する。

## 8. 未決定事項（要判断）

1. **正本ファイルの持ち方** — L1〜L3 を 1 ファイルのセクションに収めるか、サイドカー（`foo.dgm` ＋ `foo.dgm.layout`）に分けるか。
   サイドカー案は「意味の差分だけをレビュー対象にする」のを徹底できる一方、ファイルが増え取り回しが悪くなる。
2. **PowerPoint 語彙への制約を飲むか** — §5 の制約は表現力とのトレードオフ。
3. **自動レイアウトエンジン** — ELK(elkjs) / dagre / 自前実装。Blazor WASM から JS interop で呼ぶか、C# で実装するか。品質は ELK が最良だが JS 依存が入る。
4. **D2 の現行ライセンス** — 記法・レイアウトを参考／組み込みできるか要確認。
