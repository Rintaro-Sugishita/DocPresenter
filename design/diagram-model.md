# 作図モデル設計案 — PPTX / draw.io / Mermaid の「いいとこ取り」

作成: 2026-09-20 / 対象: DocPresenter の要件 R2「簡便さと複雑さを兼ね備えた作図」
前提調査: [既存サービス調査](../docs/research/existing-solutions.md)

---

## 0. 決定事項（ロック済み）

- **正本は 1 ファイル・セクション分割**。`foo.dgm` の中に意味 / レイアウト / スタイルをセクションとして並べる。差分の分離は「セクション境界」と「id 昇順の安定出力」で担保し、ファイル分割には頼らない。
- **図形語彙は DrawingML がネイティブに表現できる範囲に制限する**。超える表現はラスタ画像へのフォールバックとし、「この図は pptx で編集できない」と明示的に警告する。
- **自動レイアウトは TALA を第一候補とする**（2026-09 に MPL-2.0 で OSS 化）。§8 参照。
- **自前で持つのは node / edge / group の図だけ**とする。ER 図は ErCreator（`.ermlx`）に委譲し、シーケンス図は後回しにする。§9 参照。
- **スタイルトークンは表と共通**にし、凡例を文書単位で一つにまとめる。§10.2 参照。

---

## 1. 三者から何を取り、何を捨てるか

| | 取りたいもの | 捨てるもの（＝その道具の敗因） |
|---|---|---|
| **PPTX** | 直接操作で誰でも描ける / 自由配置とピクセル制御 / 整列ガイド・スナップ / **図形に吸着するコネクタ** / 成果物がそのまま相手の編集可能な納品物 | 意味を持たない / 差分が取れない / コピペ増殖で原本が分からなくなる |
| **draw.io** | ブラウザで動く / 豊富な図形ライブラリ / コンテナ・スイムレーン・レイヤ / 配線の自動ルーティング / 任意コマンドとしての自動整列 | 保存形式が機械生成 XML で、**Git に置けても差分が人間に読めない** |
| **Mermaid** | テキストが 1 次ソース / **差分がレビュー可能** / AI がそのまま書ける / レイアウトを書かなくていい手軽さ | 10〜12 ノードを超えるとレイアウトが崩れる / **崩れても手で直せない**（逃げ道が無い） |

## 2. 核心にある対立と、その解き方

三者の違いは突き詰めると 1 点、**自動レイアウト vs 手動配置**に還元される。

- Mermaid = 座標は 100% 導出。手で触る余地が無い。
- PPTX / draw.io = 座標は 100% 手動。意味が残らない。

両立不能に見えるが、次の一手で解ける。

> **既定は自動レイアウト。人間が動かした要素だけを「ピン留め」として疎に記録する。**

30 ノードの図でも、実際に人が位置にこだわるのは 3〜5 個。その 3〜5 個だけを座標として持ち、残りは毎回レイアウトエンジンに解かせる。
これにより「Mermaid の手軽さ」と「PPTX の最終調整」が同じファイルの中で共存し、しかも差分は 3〜5 行に収まる。

## 3. 3 層モデル（本設計の要）

保存形式を**意味 / レイアウト / スタイル**の 3 層に分離する。

### L1 意味層（必須・人間が手で書く層）

ノード・エッジ・グループとラベルだけ。Mermaid と同等の簡潔さを目標にする。

```
flow システム構成 {
  web    "Web フロント"   : ui
  api    "API サーバ"     : service
  db     "PostgreSQL"     : store

  group 社内ネットワーク { api; db }

  web -> api  "HTTPS"
  api -> db   "接続プール"
}
```

### L2 レイアウト層（任意・GUI が書く。ただし人間可読）

**人が動かした要素だけ**を記録する。触っていない要素は一切現れない。

```
layout {
  api  @ (320, 160)
  db   @ (320, 320)
  web -> api : waypoints [(200,160)]
}
```

### L3 スタイル層（任意）

テーマとクラス定義。色やフォントを直接ノードに書かず、クラス経由にする。

```
style {
  ui      { fill: accent;  shape: round-rect }
  service { fill: primary }
  store   { shape: cylinder }
}
```

### なぜ層を分けるのか

**差分を分離するため**。draw.io が Git で使い物にならないのは、この 3 つが 1 つの XML に混ざっているからに尽きる。

- 意味を変えたら → L1 だけが動く。レビュアはここだけ読めばよい。
- 位置を微調整したら → L2 だけが動く。レビュー時に読み飛ばせる。
- 配色を変えたら → L3 だけが動く。

「レビュー可能」とは「差分が小さい」ことではなく、**「差分のどこを読むべきか自明である」**こと。層の分離はそのための手段。

## 4. 差分を汚さないための規律

layer 分離だけでは足りない。GUI で描いた結果がテキストに落ちる以上、以下を仕様として強制する。

1. **グリッド量子化** — 座標は 8px 等のグリッドに丸めて保存する。マウスの微小なブレでは差分がまったく出ない。
2. **id をキーにした安定出力** — L2 は配列でなく id キーのマップ。常に id 昇順で直列化し、要素の追加が他要素の行を動かさない。
3. **自動レイアウト結果は保存しない** — 計算で出せるものはファイルに書かない。書いた瞬間に「ノードを 1 個足したら全ノードの座標が動く」差分地獄が始まる。
4. **コネクタは座標でなくポート参照で持つ** — `web.right -> api.left`。PPTX のコネクタ・グルーと同じ考え方で、図形を動かしても配線の記述は変わらない。
5. **id は人間が読める安定 id** — `db-primary` のような命名。GUID は禁止。差分に GUID が並んだ時点でレビュー不能になる。

## 5. PPTX 出力を「後付け」にしない

調査の結論どおり、**編集可能な PPTX 出力は既存エコシステムの明確な空白地帯**（Marp の `--pptx-editable` は実験的、Slidev は画像化寄り）。ここを取りにいくなら、後から変換器を足すのでは間に合わない。

そこで **L1 / L3 の表現語彙を、DrawingML がネイティブに表現できる範囲に意図的に制限する**。

- 図形 → preset geometry（角丸四角・円柱・ひし形…）
- 配線 → connector shape（直線・カギ線・曲線）
- ラベル → text body
- グループ → group shape

この制約を最初に飲むことで、PPTX は画像貼り付けではなく**受け取った側が PowerPoint で直せるネイティブ図形**として出力できる。
制約を超える表現が必要な図（凝ったインフォグラフィック等）は、ラスタ画像へのフォールバックを明示的な逃げ道として用意し、「この図は pptx で編集できない」ことを警告する。

## 6. 入出力 — ErCreator 譲りの多形式

ErCreator の強みは「多くの形式を話せること」だった。作図でも同じ構えを取る。

| 方向 | 形式 | 意図 |
|---|---|---|
| import | **Mermaid** | AI が書いた図・既存 README 資産をそのまま受ける |
| import | **.drawio** | 既存の作図資産の移行パス |
| import | **.pptx の図形** | 「Excel/PowerPoint 設計書からの脱却」需要に直接応える |
| export | **SVG / PNG** | HTML・PDF 出力への埋め込み |
| export | **PPTX 図形** | §5 のとおり編集可能なネイティブ図形 |
| export | **Mermaid** | GitHub 上でそのまま描画させる用 |

ErCreator の [`mermaid-ermlx-spec.md`](../../ErCreator/design/mermaid-ermlx-spec.md) が確立した作法をそのまま踏襲する。すなわち **ラウンドトリップの基準記法を 1 つ決め、変換で失われる情報（ロス）を仕様書に明記する**。Mermaid にポート概念もピン留めも無い以上、Mermaid export は必ずロスを伴う。それを隠さず書く。

## 7. ErCreator からの再利用

`ErCreator.Canvas` は Razor クラスライブラリで、**Web(Blazor WASM) と デスクトップ(WPF / BlazorWebView) の双方から参照される単一ソース**として作られている。しかも既に以下が揃っている。

`Canvas.Geometry` / `Canvas.Grid` / `Canvas.Pointer` / `Canvas.Selection` / `Canvas.History`（undo/redo） / `Canvas.Shapes` / `Canvas.Rendering` / `Canvas.Clipboard` / `Canvas.AutoSave`

要件 R8（Web と VS Code の両方で編集）は、この構造をそのまま引き継げば解ける。**VS Code 拡張は WebView に同じ Blazor キャンバスを載せる**ことで、Web・デスクトップ・VS Code の三面が単一実装で賄える。ErCreator と同じ `Model.Abstractions / Engine / Canvas / Web / Cli` のレイヤリングを踏襲する。

## 8. 自動レイアウトエンジン

**TALA を第一候補とする。**

TALA は D2 のレイアウトエンジンで、長らく D2 の収益源だったクローズドソース資産だったが、**2026-09 に MPL-2.0 で OSS 化された**。D2 が「ノード 10〜12 を超えても崩れない」評価を得ている理由がまさにこのエンジンであり、本設計が最も必要とするもの（有向グラフ・UML クラス図・シーケンス図の自動整列）にそのまま合致する。D2 本体（言語・CLI・dagre/ELK の 2 エンジン・テーマ・VS Code 拡張）も MPL-2.0。

| 候補 | 品質 | 備考 |
|---|---|---|
| **TALA** | 最良 | Go 実装。MPL-2.0。2026-09 に OSS 化されたばかりで、長期の保守体制は要観察 |
| ELK (elkjs) | 良 | 実績十分。JS 依存が入る |
| dagre | 可 | Mermaid が採用。本設計が超えたい水準そのもの |

### 判断が必要な点

1. **ライセンス** — MPL-2.0 はファイル単位のコピーレフト。ErCreator と同じく「無償・商用可だがソース非公開」の形態を取る場合、MPL ファイル**そのものを改変したときだけ**その改変の公開義務が生じる。改変せずリンク／プロセス分離で使う限り、自社コードの非公開は維持できる。**改変しない運用を前提に設計する**のが安全。
2. **実行形態** — TALA は Go 実装のため、(a) Go→WASM にコンパイルして Blazor WASM から呼ぶ（D2 Playground が同方式でブラウザ実行している実績あり）、(b) デスクトップ / CLI ではネイティブバイナリを同梱、の 2 系統になる見込み。Web とデスクトップでレイアウト結果が一致することが**必須要件**（結果が違うとピン留めの意味が崩れる）なので、同一エンジン・同一バージョンを両面で使う。
3. **フォールバック** — TALA の保守が滞った場合に備え、レイアウトエンジンは差し替え可能なインタフェースの背後に置く。§3 の設計上、レイアウト結果はファイルに保存しない以上、エンジン差し替えは図の再計算だけで済む。

## 9. 図の種類とスコープ

§3 の例は `flow`（フロー図）だが、設計書で要る図はそれだけではない。何を自前で持ち、何を持たないかを決める。

| 図種 | 構造 | 扱い |
|---|---|---|
| システム構成図 | node / edge / group | **自前（段階 1）** |
| フロー図 | node / edge | **自前（段階 1）** |
| 画面遷移図 | node / edge | **自前（段階 1）** |
| 状態遷移図 | node / edge | **自前（段階 1）** |
| **ER 図** | 実体・属性・関連 | **ErCreator に委譲**（§9.1） |
| **シーケンス図** | ライフライン ＋ 時系列メッセージ | **段階 3 に後回し**（§9.2） |

### 9.1 ER 図は ErCreator に委ねる

`.ermlx` は既に完成した形式であり、専用のエディタも DDL 生成も差分機能も揃っている。**同じものを `.dgm` で作り直す理由が無い。**

[参照記法](reference-syntax.md)が `@import` で拡張子ごとにレンダラを決める方式なので、そのまま書ける。

```markdown
@import "shared/customer-domain.ermlx"
```

**専用ツールがある領域には手を出さない**という線引きは、DocPresenter 全体のスコープ規律（[表モデル設計案 §1](table-model.md)）と一致している。副次的に ErCreator との連携価値も生まれる。

### 9.2 シーケンス図を後回しにする理由

シーケンス図は **node / edge のグラフではない**。ライフラインという縦軸と、時系列に並ぶメッセージという構造を持ち、自動レイアウトの考え方も違う。

汎用モデルに無理に押し込めると、どちらつかずの表現になる。**構造が違うものを一つのモデルで扱わない。** 段階 1 では対象外とし、必要なら `@import` で Mermaid の `sequenceDiagram` を使える逃げ道を残す。

### 9.3 画像の上に重ねる

[編集 UI 設計案 §9](editor-model.md) で画面設計書への応用として挙げた、**画像に注釈を重ねる**用途を `.dgm` が担う。

```
overlay "assets/login-screen.png" {
  ① @ (120, 88)   "ログイン ID"
  ② @ (120, 140)  "パスワード"
}
```

画像はバイナリのままだが、**重ねた注釈はテキストなので差分が読める**。番号の振り直しや説明文の変更が Git で追える。

## 10. 図形とスタイルの語彙 — 表と共通にする

### 10.1 図形は DrawingML のプリセットに限る

§5 の制約を具体化する。

```
shape : rect / round-rect / diamond / cylinder / ellipse /
        parallelogram / hexagon / document / note
line  : solid / dashed / dotted
arrow : none / open / filled
```

この範囲を超える表現が要る図は、ラスタ画像へのフォールバックとし「pptx で編集できない」と警告する（§5）。

### 10.2 スタイルトークンは表と揃える

[表モデル設計案 §5.1](table-model.md) で定めた語彙を、**そのまま図でも使う**。

```
# 意味トークン（4 種で確定）
fill: changed / pending / disabled / removed

# 区分トークン
fill: tint-1 / tint-2 / tint-3 / tint-4
```

揃える利益は大きい。

1. **凡例が文書単位で一つにまとまる。** 表で `changed` を使い、図でも `changed` を使えば、文書末の凡例（[表モデル設計案 §5.1](table-model.md)）は両方を合算した 1 つで済む。表と図で別々の凡例が出るのは読み手にとって無意味な分断である
2. **表と図で見た目が一致する。** 同じ「変更あり」が別の色で出ることが無くなる
3. **軸 B** — AI が表と図を同じ語彙で読める

直値（`#3A7BD5` 等）を書かせない理由も表と同じ。出力先での再現性、文書間の一貫性、差分の可読性。

### 10.3 SVG のソースマップを出す

[レビューモデル設計案 §3.4](review-model.md) が全出力形式に要求するものの、図における実装。

> **SVG の各ノード → `.dgm` 上のバイト範囲**

これにより、顧客が HTML 上で図のノードをクリックしてコメントしたとき、アンカーが `.dgm` のバイト範囲として確定する。図へのコメントが表や本文と同じ仕組みに乗る。

## 11. 段階的に作る

| 段階 | 範囲 |
|---|---|
| **1** | node / edge / group、自動レイアウト（TALA）、疎なピン留め、既定テーマ、SVG ＋ PPTX 図形出力、ソースマップ |
| **2** | スタイル層（意味・区分トークン）、画像オーバーレイ、Mermaid 入出力 |
| **3** | シーケンス図、`.drawio` / `.pptx` インポート |

段階 1 の時点で「テキストで書けて、崩れない自動レイアウトで、編集可能な PPTX 図形として出る」が成立する。[既存サービス調査](../docs/research/existing-solutions.md)のとおり、ここに到達しているものは無い。

## 12. 残る未決定事項

- レイアウト結果の**決定性**の検証 — 同一入力から常に同一座標が出ることを CI で担保する必要がある（ピン留めの前提）。
- Mermaid export 時のロス仕様の確定（ポート参照・ピン留め・グループの扱い）。
- `.drawio` / `.pptx` インポート時の図形マッピング表（DrawingML プリセットへの寄せ方）。
- **オーバーレイの座標**（§9.3）— 画像のピクセル座標で持つと、画像を差し替えた瞬間に全部ずれる。相対座標にするか、画像のバージョンを併記するか。
- **シーケンス図を最終的に自前で持つか**（§9.2）— Mermaid への委譲で足りるなら、持たない判断もありうる。
