# サーバの位置づけ — 同時編集とコメント収集をどう扱うか

作成: 2026-09-20 / 対象: [レビューモデル設計案](review-model.md) §10 の未確定事項「HTML ビューアのホスティング形態」「同時編集・会話性」
関連: [要件定義](requirements.md)

## 1. 二つを分けて考える必要がある

「直接同時編集」と「コメント記入」は、一緒に語られがちだが**性質がまったく違う**。

| | 本文の同時編集 | コメントの同時記入 |
|---|---|---|
| 操作 | 既存の内容を**書き換える** | **追記するだけ** |
| 衝突 | 起きる。解決が必要 | 起きない（追記のみ） |
| 正本への影響 | 正本そのものが変わる | 正本は変わらない（サイドカー） |
| Git モデルとの関係 | **衝突する**（§2） | 衝突しない |
| 実装コスト | 非常に高い（CRDT） | 低い |

結論を先に言うと、**前者は避けるべきで、後者はサーバがあると明確に良い**。

## 2. 本文の同時編集は、この製品の思想と衝突する

### 2.1 Git モデルとリアルタイムモデルは、協働の思想が逆

| | Git モデル | リアルタイムモデル |
|---|---|---|
| 作業単位 | ブランチを切って**一人で書く** | 全員が**同じ生の状態**を触る |
| 品質ゲート | PR レビューを通ってからマージ | ゲートが無い |
| 「承認済みの版」 | 明確に存在する | **存在しない** |
| 変更の意図 | コミットメッセージに残る | 残らない |

本文に同時編集を入れると、**PR というレビューゲートが消える**。これは R10（顧客レビュー）と軸 A（差分がレビュー単位として成立する）が乗っている土台そのものである。

「会話しながら同時編集できる」は Wiki の利点として実際に挙げられているが、それを丸ごと取りにいくことは **Wiki になること**を意味する。そして Wiki になった時点で、本製品が Quarto や Wiki に対して持っていた差別化（Git 差分・多形式出力・編集可能な PPTX）の土台が崩れる。

### 2.2 実装コストがモデル設計全体に波及する

同時編集を本気でやるなら、中間モデルを **CRDT ネイティブで設計する**必要がある。これは後から足せない。さらに GUI キャンバスの操作・undo/redo の意味論・ピン留めの扱いがすべて CRDT の上で再定義される。

**差別化要因は R6（編集可能な PPTX）・R7（複雑テーブル）・R2（作図）にある。**そこに使うべき予算を CRDT に溶かすのは配分として誤っている。

### 2.3 「顧客と画面を見ながら詰めたい」への代替案

同時編集が欲しくなる実際の場面は、**顧客との打ち合わせでその場で設計を詰めたい**というものだろう。これは同時編集でなくても解ける。

> 顧客がコメントを入れる → エンジニアが即座に直す → 再描画されて顧客に見える

**速いコメント→修正ループ**があれば、体験上はほぼ同じことができる。しかも「誰が何を指摘し、誰がどう直したか」が §5 のとおり Git に残る。同時編集ではこれが残らない。

### 2.4 推奨

> **本文の同時編集はやらない。「後で考える」ではなく、今決めておく。**

未決のまま置くと、モデル設計を CRDT 対応の可能性に備えて防御的に作ることになり、そのコストを永続的に払い続けることになる。

## 3. コメント収集は、サーバがあると明確に良い

こちらは追記のみで衝突しないため、思想と競合しない。段階を整理する。

| | 形態 | 顧客の操作 | サーバ | 弱点 |
|---|---|---|:--:|---|
| **Level 0** | PDF 往復 | 普段どおり PDF に注釈して返送 | 不要 | 往復が遅い。複数人の指摘が統合されない |
| **Level 1** | 静的 HTML ＋ ファイル書き出し | HTML 上でコメントし、`*.review.yml` をダウンロードして返送 | 不要（静的配信のみ） | 「ダウンロードして送る」操作が要る。同時に見ている複数人の指摘が統合されない |
| **Level 2** | コメント収集サーバ | HTML 上でコメントするだけ。そのまま届く | **必要** | 運用が要る |

Level 2 だけが、顧客側の操作を**ゼロ**にできる。[レビューモデル設計案 §1](review-model.md) で「導入コストゼロ」を PDF の最大の強みとして挙げた以上、そこに並ぶには Level 2 が要る。

## 4. 「サーバ前提」と「データが外に出ない」は両立する

ここが誤解されやすい点。ErCreator の訴求は正確には

> **「開発元のサーバにアップロードされない」**

であって、「サーバを一切使わない」ではない。したがって、**顧客側または開発ベンダ側の環境に立てる self-host サーバ**であれば、この訴求と矛盾しない。単一バイナリで配布し、社内ネットワークに置ければ、設計書が外部に出ることはない。

矛盾するのは「開発元が運営する SaaS に設計書を預ける」形態のみ。業務システムの設計書を扱う以上、**SaaS 単独提供は避け、self-host を必ず選べるようにする**のが妥当。

## 5. 決定的な原則 — サーバは真実の源ではない

サーバを入れる場合、次を絶対の原則として置く。

> **正本は常に Git。サーバはコメントを受け取って Git に書き戻すだけの薄い層である。**

この原則から自動的に次が導かれる。

- **サーバが落ちてもデータは失われない。** Git に入った時点で確定している
- **サーバを使わない運用が常に成立する。** Level 0 / Level 1 に落とせる。サーバは機能を増やすが、前提にはならない
- **サーバの実装が薄くなる。** 認証と受け口と Git 書き戻しだけ。ドキュメントの状態管理を持たない
- **ロックインが生じない。** 顧客のデータは常に顧客のリポジトリにある

逆に、サーバがドキュメントの状態を持ち始めた瞬間に、Notion / Confluence と同じ土俵に降りることになる。**そこは我々が勝てる土俵ではない。**

## 6. 事業面への影響

| | サーバ必須 | サーバ任意（推奨） |
|---|---|---|
| アカウント | 必要 | コア機能には不要 |
| 課金・テナント管理 | 必要 | self-host なら不要 |
| 顧客のセキュリティ審査 | 通す必要がある | 回避できる（ローカル完結で試せる） |
| 「まず触ってみる」導線 | 登録が要る | **ブラウザで即** |
| ErCreator と揃うポジション | 崩れる | 保てる |

ErCreator が取っている「アカウント不要・インストール不要・データが外に出ない」というポジションは、**業務システムを扱う開発者に対して非常に強い**。サーバ必須にするとこれを手放すことになる。

## 7. 推奨アーキテクチャ

```
[ コア ] サーバ無しで全機能が動く
  - Web (Blazor WASM) / VS Code 拡張 / デスクトップ / CLI
  - 正本は Git 上のファイル
  - 出力: HTML / PDF / PPTX / 構造化コンテキスト
  - レビュー: Level 0（PDF 往復）・Level 1（HTML ＋ 書き出し）

        ＋（任意で追加）

[ レビュー収集サーバ ] self-host 可能な単一バイナリ
  - 役割は「コメントを受け取り、Git に書き戻す」だけ
  - 本文の状態は持たない
  - 落ちてもデータは失われない
```

**サーバはオプショナルな層であり、前提ではない。**

## 8. 未確定事項

- レビュー収集サーバを**いつ作るか**（初版に含めるか、コア確立後か）
- self-host サーバの認証方式（顧客にアカウントを作らせない前提で、招待リンク等で足りるか）
- 同時に閲覧している参加者の**プレゼンス表示**（誰が見ているか）まで持つか。同時編集とは別物で、コストは低い
