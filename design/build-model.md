# ビルド単位設計案 — 何を出力対象とし、何を集めるか

作成: 2026-09-21 / 対象: [未決事項 A-6](open-issues.md)（ビルドの単位と CLI）
関連: [参照記法](reference-syntax.md) / [横断一覧](index-model.md) / [編集 UI](editor-model.md) / [テーマ](theme.md)

## 0. 決定事項（ロック済み）

- **frontmatter に `output:` を持つ文書だけが「ビルドルート」**（＝成果物になる）（§1）。
- **ビルド対象は、ルートから `@import` を推移的に辿った閉包**（§2）。
- **ルートであることと部品であることは排他ではない**（§3）。
- **ルート探索はリポジトリ全体、収集は参照閉包**。この二つを区別する（§4）。
- **テーマも frontmatter で指定する**（§1.2）。

## 1. ビルドルートは frontmatter が決める

Markdown Preview Enhanced は、frontmatter に出力器の設定（`puppeteer:` 等）を書いた文書を出力対象として扱う。
**「出力設定を持つ文書が成果物になる」**という考え方を借りる（[P4](decisions.md)）。

```yaml
---
document: SD-AUTH-001
title: 認証機能 設計書
version: 1.2
theme: corporate-a4
output: [pdf, html]
---
```

`output:` を持たない文書・要素ファイルは、**単体ではビルドされない**。

### 1.1 部品と成果物が自然に分かれる

`shared/glossary.table` や `auth-design/login-flow.dgm` を単体で PDF にしても意味がない。
**出力設定の有無が、そのまま「成果物か、部品か」の宣言になる。**

ディレクトリ規約やグロブでビルド対象を決める方式と違い、**どれが成果物になるかが文書自身に書いてある**。

### 1.2 出力形式ごとに別の文書を立てられる

[PPTX は概要設計図の器](pptx-model.md)と決めた運用が、この仕組みにそのまま乗る。

```yaml
# docs/auth-design.md      詳細な設計書
output: [pdf, html]
```
```yaml
# docs/auth-overview.md    概要図を並べた短い文書
output: [pptx]
```

同じ `.dgm` を両方から `@import` すれば、**図は 1 つ、成果物は 2 つ**になる。

### 1.3 テーマの指定も frontmatter で行う

[テーマの配布単位と指定方法](theme.md)が未確定だったが、ここで決まる。**`theme:` を frontmatter に書く。**
出力設定と同じ場所にあるのが自然で、文書ごとにテーマを変えられる。

## 2. 収集は参照の推移閉包

ルートから **`@import` を辿って集める。遷移的な参照も許す。**

```
docs/auth-overview.md          ← ルート（output: [pptx]）
  └ @import docs/auth-design.md
      ├ @import auth-design/login-flow.dgm
      ├ @import auth-design/screen-items.table
      └ @import ../shared/glossary.table
```

`auth-overview.md` のビルドには、**2 段目以降も含めて全部**が含まれる。
設計書の分冊や共通部の切り出しで、この連鎖は自然に起きる。

**新しい走査規則は要らない。** [R12 のインデックス](index-model.md)が持つ参照グラフを辿るだけである。

## 3. ルートと部品は排他ではない

上の例で `auth-design.md` は、

- **自身がルート**（`output: [pdf, html]` を持つ）として PDF になり、
- 同時に `auth-overview.md` の**部品**としても展開される。

**両方成立してよい。**

このとき採番はどうなるか。[採番は文書単位](reference-syntax.md)と決めてあるため、
**`auth-design.md` 単体の PDF での「図 2」と、`auth-overview.md` に展開されたときの「図 2」は別番号になりうる**。

これは[共有要素は置かれた文書で番号を得る](reference-syntax.md)という既定の挙動と一致しており、矛盾しない。

## 4. ルート探索と収集は別のもの

| | 範囲 | 目的 |
|---|---|---|
| **ルート探索** | **リポジトリ全体**（設定で限定可） | frontmatter を読んで `output:` を持つ文書を見つける |
| **収集** | **ルートからの参照閉包** | その成果物に何が含まれるかを決める |
| **インデックス**（[R12](index-model.md)） | **全ルートの和集合** | 横断一覧・トレーサビリティ・診断 |

三つ目が重要である。**トレーサビリティは文書をまたぐ。**
要件が文書 A に、設計が文書 B にあるとき、ビルド単位で閉じてしまうと繋がらない。

> **個々のビルドはルート単位。インデックスはリポジトリ全体。**

これが[横断一覧の走査範囲](index-model.md)への回答になる。

## 5. 診断

参照グラフが手に入るため、次を検出できる（[P6](decisions.md)）。

| 診断 | 扱い |
|---|---|
| **循環参照**（A → B → A） | **ビルド失敗** |
| 参照先が存在しない | **ビルド失敗**（[決定済み](editor-model.md)） |
| **孤児ファイル** — `output:` を持たず、どこからも参照されていない | **警告**「このファイルはどの成果物にも含まれません」 |
| ルートが 1 つも見つからない | 警告 |

孤児ファイルの検出は地味だが効く。**書いたのに誰も見ていない設計書**は実務で普通に発生する。

## 6. CLI

**`export`・`check`・`format`・`import`・`init`・`new` は実装済み**（2026-10-22。`packages/dgm`・`packages/cli`、
`npm run build:cli` で `media/` に束ねる）。開発用の `tools/*.mjs` は検査スクリプトが
使っているので残してあり、置き換えは後で行う。
コマンドは **文書側の `docpresenter` と作図側の `dgm` の 2 つ**で、どちらもサブコマンドで分ける（パッケージは下の「パッケージ」）。
当初案の `build` は **`export`** に改めた（形式を引数で選ぶのだから「書き出す」が正しく、VS Code のコマンド名とも揃う）。
以下の例は `docpresenter` で書くが、`.dgm` だけを扱う使い方は `dgm` でも同じ引数で書ける。

### 6.1 共通の決まり

- **作業場のルート**は、指定したパスから上へ辿って `.docpresenter/` のある所、無ければ `.git` のある所。
  `--root <dir>` で上書きする（今の `--in` に当たる）。ファイルを 1 つだけ指しても、`{{root}}`・文書番号の重複・
  テーマ・`reviews/` はルートで解く。
- **対象**はファイルとフォルダを混ぜて**いくつでも**指定できる。フォルダは中を再帰的に辿る。省略するとルート全体。
- **フォルダから拾う `.md` はルート（`output:` を持つ文書）だけ**。改訂履歴のような部品を成果物にしないため。
  ファイルを直に指したときは `output:` が無くても扱う。
- **ファイルを書き換えるコマンド（`format`・`import`）は、`--write` が無ければ変わる中身を見せるだけ**。
  `export` は新しいファイルを作るだけなので `--write` は要らない。
- `--lang ja|en`（無ければ `LANG` など）・`--quiet`・`--json`（機械向けの出力）。
- **終了コード**：0 成功、1 内容の問題（エラー・未整形・`--strict` での警告）、2 使い方の誤り。
- 位置は `path:line:column` で出す（VS Code の端末でリンクになる）。

### 6.2 `export` — 書き出す

```bash
docpresenter export <ファイル|フォルダ>... [--to <形式>[,<形式>...]] [--out <dir>] [--flat]
```

| 入力 | 書ける形式 | `--to` が無いとき |
|---|---|---|
| `.md` | `html` `pdf` `pptx` | frontmatter の `output:` のとおり |
| `.dgm` | `svg` `png` | `svg` |

- `--to`（`-t`）はカンマ区切りでも、繰り返しても書ける。フォルダに `--to pdf,svg` なら `.md` は PDF、`.dgm` は SVG。
  合わない組み合わせはフォルダからなら黙って飛ばし、**直に指したファイルなら誤り**（`a.dgm --to pdf`）。
- **`docpresenter` がフォルダから拾う図は、`--to` に svg か png があるときだけ単独で書き出す**（実装して決めた）。
  図はすでに文書の中に入っているので、`docpresenter export` だけで図の SVG が並ぶと煩い。直に指した図は常に書く。
  `dgm export` は図しか扱わないので、フォルダの図を常に書く。
- **画面キャプチャへの注釈（overlay）は PNG だけ**。絵が画素なので SVG にはならず、そう言って飛ばす。
  PNG は注釈の一覧も含めて描く。部品の定義（`parts`）は絵を持たないので飛ばす。
- **出力先の既定はルートの `out/build/`**（VS Code 拡張の `docpresenter.outDir` の既定と同じ）。元ファイルの隣には
  書かない（`docs/` に成果物が混ざり、差分が汚れるため）。`--out`（`-o`）で変える。
- **フォルダ構造は保つのが既定**で、ルートからの相対パスをそのまま出力先の下に再現する
  （`docs/order/design.md` → `out/build/docs/order/design.pdf`）。`docs/` も省かない。VS Code 拡張と Web の閲覧ページも
  同じ規則で書く（`outputStem`、2026-10-22 に揃えた）。`--flat` で出力先の直下に並べる。
- `--flat` で名前がぶつかったら**何も書かずに誤り**とする。片方が黙って消えるのを防ぐ。
- **PDF と PNG はこの機械の Chromium 系ブラウザで描く**（[PDF エンジン](pdf-engine.md)と同じ。PNG のために
  変換ライブラリは足さない）。`--chromium <path>`・`--font <path>`、PNG には `--scale <n>`・`--background <色|transparent>`。
- 今の `tools/build.mjs` から引き継ぐもの：`--diff-from <rev|dir>`・`--show-removed`・`--no-review-notes`。

### 6.3 `check` — 書き出さずに確かめる

```bash
docpresenter check [<ファイル|フォルダ>...] [--strict] [--json]
```

対象の決め方は `export` と同じ。参照切れ・循環・孤児（§5）、図と表の構文の誤りを出す。

### 6.4 そのほかのコマンド

| コマンド | 中身 | 今の置き場所 |
|---|---|---|
| `format <…> [--write] [--check]` | `.dgm` を決まった形に整える（[spec/dgm.md §6.3](../spec/dgm.md)）。`--check` は CI 向け | `tools/format-dgm.mjs` |
| `import <file.pptx\|file.pdf>... [--write] [--into <x.review.yml>]` | `export` の逆。拡張子で決まる：PPTX は図への読み戻し、PDF は注釈を指摘として取り込む | `tools/pptx-back.mjs` / `tools/pdf-review.mjs` |
| `init --title <題名> [--name <名前>] [--number <番号> | --series <接頭辞>]` | 作業場を用意する（VS Code の「作業場を初期化する」と同じ中身。`planScaffold`）。既にあるファイルは上書きせず「そのまま」と言う。**文書がもうある作業場では、`--name` を指定したときだけ最初の文書を作る**（もう一度走らせて guide や spec を戻すとき、`docs/design.md` を勝手に増やさない） | `packages/build/src/scaffold.ts`（VS Code と共有） |
| `new doc <file> --title <題名> [--number | --series]` | 文書と改訂履歴をテンプレートから作る。番号は指定どおり（使われていれば断る）、`--series` ならその系列の次、どちらも無ければ一番多い系列の次 | 同上 |
| `new diagram <file> [--kind flow|free]`（`dgm new` も同じ） | 雛形の図を作る（`starterDiagram`、作図のパッケージ） | `packages/diagram/src/starter.ts` |

`init` と `new` は質問をしない。足りない引数は使い方の誤り（終了コード 2）、既にあるファイル・使われている番号は内容の誤り（1）。
`index`（横断一覧）は本体が未実装なので見送る。`export --watch` も後回し。

### パッケージ（2026-10-22 決定）

作図は**単独で入れられなければならない**（[パッケージ分割](packaging.md)）。そこで**コマンド名を分ける**。

| | 作図側 | 文書側 |
|---|---|---|
| コマンド（`bin`） | **`dgm`** | **`docpresenter`** |
| npm のパッケージ | **`@docpresenter/dgm`** | **`docpresenter`** |
| 中身 | base ＋ diagram だけ | markdown・build・pdf・pptx。作図側に依存する |
| できること | `.dgm` の `export`（svg / png）・`check`・`format` | 全部。`.dgm` は作図側に任せる |

- **`dgm` は拡張子と同じ名前**にした（`dgm export login.dgm --to png`）。直感で分かり、作図ツールの公開名（[未決](packaging.md)）にも左右されない。
- **2 つの `bin` は名前が違うので、両方をグローバルに入れても衝突しない。** npm がグローバルに繋ぐのは直に入れたパッケージの
  `bin` だけなので、文書側だけを入れた人は `dgm` を持たないが、`docpresenter export a.dgm` で同じことができる。
- **名前の空き**（npm、2026-10-22 時点）：`docpresenter`・`@docpresenter` スコープは空き。`dgm` という**パッケージ名**は
  DrupalGap の小さな道具が使っており、同じ `dgm` コマンドを持つ。そのためパッケージはスコープ付きにする。
  両方を同じ機械に入れたときだけコマンドがぶつかるが、許容する。
- 公開前に npm の Organization `docpresenter` を取ってスコープを押さえる。
- **`npx dgm` と書いてはいけない。** npm は `dgm` という名前のパッケージ（上の DrupalGap の道具）を取ってきて動かす。
  案内は `npx @docpresenter/dgm` か、入れてから `dgm`。リポジトリの中で試すときも `npx --no-install dgm`。
- リポジトリの中では、VS Code 拡張が `docpresenter` という名前を使っている（拡張の ID になる）ので、文書側の
  パッケージは `@docpresenter/cli` という名前で置き、公開するときに `docpresenter` として出す。どちらも、
  私用の `@docpresenter/*` は束の中に入れ、依存として残るのは `playwright-core` だけにする（`tools/build-cli.mjs`）。
  公開用の `package.json`（依存を `playwright-core` だけにしたもの）を作る手順は公開のときに決める。

## 6.5 実装したもの（2026-09-29）

`packages/build` にパイプラインを置いた。**このパッケージはファイルシステムを触らない。**

| 段 | 中身 | 置き場所 |
|---|---|---|
| **器の口** | `list()` / `read()` / `dataUrl()` の 3 つ | `workspace.ts`（実装は器の側。Node 版は `tools/build.mjs`） |
| **ルート探索** | 全 `.md` の frontmatter を読み、`output:` を持つものを集める | `graph.ts` |
| **収集** | `@import` の推移閉包。循環・不在・孤児の診断（§5） | 同上 |
| **組み立て** | 取り込んだ文書を 1 つに畳み、採番し、診断を集める | `build.ts` |
| **HTML** | 単一ファイル。テーマを埋め込み、画像は data URL | `html.ts` |

決めたことが 3 つある。

1. **作業域（ワークスペース）は引数で渡す。** ルート探索は「リポジトリ全体」だが、その「全体」がどこかは
   器が決める（`node tools/build.mjs --in sample`）。**製品のリポジトリ自身を走査して警告を出すのは無意味**で、
   実装して最初に分かったのがこれだった。
2. **取り込んだ文書は 1 つの文書に畳む**（`expandDocument`）。採番も `---` も参照も、
   畳んだあとで一度に効く。[§3 のとおり](#3-ルートと部品は排他ではない)、同じ節が
   `auth-design.md` では 6、`auth-overview.md` では 3 になる——**畳んでから数えるからそうなる**。
3. **畳んだブロックは出自のファイルを持つ**（HTML では `data-doc`）。
   バイト範囲は**どのファイルの範囲か**が決まって初めて意味を持つ。
   レビューのコメントも[差分マーキング](diff-marking.md)も、ここが無いと文書をまたいだ瞬間に壊れる。

**HTML は 1 枚で完結させる。** テーマの CSS を埋め込み、画像を data URL にする。
設計書は人に送るものであり、**スタイルシートを隣に置かないと崩れるページは、崩れて届く**。
検証（`tools/check-build.mjs`）は実際に開いて、**外に 1 本も取りに行かないこと**まで見る。

## 7. web 上の画像は、ビルドが取り込む（2026-10-01）

文書は `http(s)` の住所で画像を指せる。そのとき守るべきことが 2 つあり、両立する。

1. **作業フォルダには落とさない。** 文書は住所を言っているのであって、その絵を
   自分のものだと言っているのではない。落とせば複製が増え、元が差し替わっても
   気づけなくなる
2. **配った成果物は外に取りに行かない。** 読み手がネットワークに繋がっていなくても
   開けることは、[単一ファイルで配る](output-model.md)という決定の中身そのものである

**ビルドの最中に一度だけ取りに行き、出力の中に入れる。** これが両方を満たす唯一の
場所である。文書は住所のまま、成果物は自己完結する。

| | 取り込み |
|---|---|
| CLI | `fetch` する。何を取り込んだかはビルドの出力に出る |
| ブラウザ（編集画面の書き出し） | `fetch` する。**相手のサーバ（CORS）が許す範囲**でしか取れない |
| 取り込む手段が無い器 | 取り込まない。図が「取り込めなかった画像がある」と言い、診断にも出る |

**取れなかったときに住所のまま `<img>` を出すことはしない。** それは「配ったファイルが
外に取りに行く」ことそのもので、黙って約束を破るより、図が空いているほうがよい（P6）。

同じ住所は**文書ごとに一度**しか取りに行かない。形式が 3 つあっても、1 枚の絵は 1 回である。
