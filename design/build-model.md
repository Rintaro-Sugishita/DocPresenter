# ビルド単位設計案 — 何を出力対象とし、何を集めるか

作成: 2026-09-21 / 対象: [未決事項 A-6](open-issues.md)（ビルドの単位と CLI）
関連: [参照記法](reference-syntax.md) / [横断一覧](index-model.md) / [編集 UI](editor-model.md) / [テーマ](theme.md)

## 0. 決定事項（ロック済み）

- **frontmatter に `output:` を持つ文書だけが「ビルドルート」**（＝成果物になる）（§1）。
- **ビルド対象は、ルートから `@import` を推移的に辿った閉包**（§2）。
- **ルートであることと部品であることは排他ではない**（§3）。
- **ルート探索はリポジトリ全体、収集は参照閉包**。この二つを区別する（§4）。
- **テーマも frontmatter で指定する**（§1.2）。

## 1. ビルドルートは frontmatter が決める

Markdown Preview Enhanced は、frontmatter に出力器の設定（`puppeteer:` 等）を書いた文書を出力対象として扱う。
**「出力設定を持つ文書が成果物になる」**という考え方を借りる（[P4](decisions.md)）。

```yaml
---
document: SD-AUTH-001
title: 認証機能 設計書
version: 1.2
theme: corporate-a4
output: [pdf, html]
---
```

`output:` を持たない文書・要素ファイルは、**単体ではビルドされない**。

### 1.1 部品と成果物が自然に分かれる

`shared/glossary.table` や `auth-design/login-flow.dgm` を単体で PDF にしても意味がない。
**出力設定の有無が、そのまま「成果物か、部品か」の宣言になる。**

ディレクトリ規約やグロブでビルド対象を決める方式と違い、**どれが成果物になるかが文書自身に書いてある**。

### 1.2 出力形式ごとに別の文書を立てられる

[PPTX は概要設計図の器](pptx-model.md)と決めた運用が、この仕組みにそのまま乗る。

```yaml
# docs/auth-design.md      詳細な設計書
output: [pdf, html]
```
```yaml
# docs/auth-overview.md    概要図を並べた短い文書
output: [pptx]
```

同じ `.dgm` を両方から `@import` すれば、**図は 1 つ、成果物は 2 つ**になる。

### 1.3 テーマの指定も frontmatter で行う

[テーマの配布単位と指定方法](theme.md)が未確定だったが、ここで決まる。**`theme:` を frontmatter に書く。**
出力設定と同じ場所にあるのが自然で、文書ごとにテーマを変えられる。

## 2. 収集は参照の推移閉包

ルートから **`@import` を辿って集める。遷移的な参照も許す。**

```
docs/auth-overview.md          ← ルート（output: [pptx]）
  └ @import docs/auth-design.md
      ├ @import auth-design/login-flow.dgm
      ├ @import auth-design/screen-items.table
      └ @import ../shared/glossary.table
```

`auth-overview.md` のビルドには、**2 段目以降も含めて全部**が含まれる。
設計書の分冊や共通部の切り出しで、この連鎖は自然に起きる。

**新しい走査規則は要らない。** [R12 のインデックス](index-model.md)が持つ参照グラフを辿るだけである。

## 3. ルートと部品は排他ではない

上の例で `auth-design.md` は、

- **自身がルート**（`output: [pdf, html]` を持つ）として PDF になり、
- 同時に `auth-overview.md` の**部品**としても展開される。

**両方成立してよい。**

このとき採番はどうなるか。[採番は文書単位](reference-syntax.md)と決めてあるため、
**`auth-design.md` 単体の PDF での「図 2」と、`auth-overview.md` に展開されたときの「図 2」は別番号になりうる**。

これは[共有要素は置かれた文書で番号を得る](reference-syntax.md)という既定の挙動と一致しており、矛盾しない。

## 4. ルート探索と収集は別のもの

| | 範囲 | 目的 |
|---|---|---|
| **ルート探索** | **リポジトリ全体**（設定で限定可） | frontmatter を読んで `output:` を持つ文書を見つける |
| **収集** | **ルートからの参照閉包** | その成果物に何が含まれるかを決める |
| **インデックス**（[R12](index-model.md)） | **全ルートの和集合** | 横断一覧・トレーサビリティ・診断 |

三つ目が重要である。**トレーサビリティは文書をまたぐ。**
要件が文書 A に、設計が文書 B にあるとき、ビルド単位で閉じてしまうと繋がらない。

> **個々のビルドはルート単位。インデックスはリポジトリ全体。**

これが[横断一覧の走査範囲](index-model.md)への回答になる。

## 5. 診断

参照グラフが手に入るため、次を検出できる（[P6](decisions.md)）。

| 診断 | 扱い |
|---|---|
| **循環参照**（A → B → A） | **ビルド失敗** |
| 参照先が存在しない | **ビルド失敗**（[決定済み](editor-model.md)） |
| **孤児ファイル** — `output:` を持たず、どこからも参照されていない | **警告**「このファイルはどの成果物にも含まれません」 |
| ルートが 1 つも見つからない | 警告 |

孤児ファイルの検出は地味だが効く。**書いたのに誰も見ていない設計書**は実務で普通に発生する。

## 6. CLI

```bash
docpresenter build                     # 全ルートをビルド
docpresenter build docs/auth-design.md # 指定ルートのみ
docpresenter index                     # インデックスと横断一覧
docpresenter check                     # 診断のみ（CI 用）
```

出力先は規約とする（`dist/<文書名>.<拡張子>`）。設定で変更可。

## 6.5 実装したもの（2026-09-29）

`packages/build` にパイプラインを置いた。**このパッケージはファイルシステムを触らない。**

| 段 | 中身 | 置き場所 |
|---|---|---|
| **器の口** | `list()` / `read()` / `dataUrl()` の 3 つ | `workspace.ts`（実装は器の側。Node 版は `tools/build.mjs`） |
| **ルート探索** | 全 `.md` の frontmatter を読み、`output:` を持つものを集める | `graph.ts` |
| **収集** | `@import` の推移閉包。循環・不在・孤児の診断（§5） | 同上 |
| **組み立て** | 取り込んだ文書を 1 つに畳み、採番し、診断を集める | `build.ts` |
| **HTML** | 単一ファイル。テーマを埋め込み、画像は data URL | `html.ts` |

決めたことが 3 つある。

1. **作業域（ワークスペース）は引数で渡す。** ルート探索は「リポジトリ全体」だが、その「全体」がどこかは
   器が決める（`node tools/build.mjs --in sample`）。**製品のリポジトリ自身を走査して警告を出すのは無意味**で、
   実装して最初に分かったのがこれだった。
2. **取り込んだ文書は 1 つの文書に畳む**（`expandDocument`）。採番も `---` も参照も、
   畳んだあとで一度に効く。[§3 のとおり](#3-ルートと部品は排他ではない)、同じ節が
   `auth-design.md` では 6、`auth-overview.md` では 3 になる——**畳んでから数えるからそうなる**。
3. **畳んだブロックは出自のファイルを持つ**（HTML では `data-doc`）。
   バイト範囲は**どのファイルの範囲か**が決まって初めて意味を持つ。
   レビューのコメントも[差分マーキング](diff-marking.md)も、ここが無いと文書をまたいだ瞬間に壊れる。

**HTML は 1 枚で完結させる。** テーマの CSS を埋め込み、画像を data URL にする。
設計書は人に送るものであり、**スタイルシートを隣に置かないと崩れるページは、崩れて届く**。
検証（`tools/check-build.mjs`）は実際に開いて、**外に 1 本も取りに行かないこと**まで見る。

## 7. 未確定事項

- **`output:` の書式** — `[pdf, html]` のような配列で足りるか。形式ごとに設定を持たせたくなった場合（PDF は A4、PPTX は 16:9 など）の書き方
- **ルート探索の除外** — `node_modules` 相当のものをどう除くか。`.docpresenterignore` を置くか
- **出力先の規約** — 文書の階層構造を `dist/` に反映するか、平らに置くか
- **部分ビルド** — 変更されたルートだけを再ビルドする仕組み。参照グラフがあるので「この要素を変えたらどのルートが影響を受けるか」は導ける
