# 設定の設計案 — 画面を作らない

作成: 2026-09-25 / 対象: キー割り当てなどの利用者設定
関連: [提供形態](platforms.md) / [実装スタック](stack.md) / [文字書式](inline-format.md)

## 0. 決定事項（ロック済み）

- **エディタは設定画面を持たない。設定は「値」として受け取るだけ**（§1）。
- **設定画面は器（VS Code / Web シェル）が持つ**（§2）。VS Code では `contributes.configuration` に宣言し、専用画面を作らない。
- **設定にするのは、意見が割れる項目だけ**（§3）。Escape で取り消し・フォーカスを外して確定は固定する。
- **最初の設定項目は「編集を確定するキー」**（§4）。既定は `Ctrl+Enter` で確定、`Enter` で改行。

## 1. 設定画面を作らない

VS Code 拡張が[デスクトップを担う](platforms.md)と決めた以上、**VS Code には設定システムが既にある**。
`package.json` の `contributes.configuration` に項目を宣言すれば、

- 設定 UI（検索・説明・既定値・ワークスペース別の上書き）が**そのまま手に入る**
- `settings.json` で書ける。**設定をリポジトリにコミットしてチームで揃えられる**
- 同期・プロファイル・拡張機能の設定一覧に**自動的に載る**

ここに自前の設定画面を足すと、**同じ設定が二箇所に出る**。どちらが勝つのか、片方を変えたらもう片方はどうなるのかを、利用者にも実装にも背負わせることになる。

> これは[テーマの二重化を認めない](decisions.md)のとまったく同じ判断である。**同じ事実を二箇所に置かない。**

## 2. では誰が持つのか

```
core / render / editor        ← 設定を「値」として受け取る。UI を持たない
        ↑                        EditorSettings { commitKey: … }
   ┌────┴────┐
app-vscode   app-web
  ↑            ↑
settings.json  Web シェルの設定パネル（localStorage）
（VS Code の設定 UI がタダで付く）
```

`editor` パッケージが公開するのは次のものだけである。

| 公開するもの | 何のため |
|---|---|
| `EditorSettings` 型 | 器が何を渡せばよいか |
| `DEFAULT_SETTINGS` | 器が何も持っていないとき |
| `COMMIT_KEYS` / `COMMIT_KEY_LABEL` | 器が選択肢を組み立てるため（画面は器が作る） |
| `view.configure(settings)` | 設定変更を編集中の状態を壊さずに反映する |

**ラベルは持つが画面は持たない。** 選択肢の文言まで器ごとに書くと、VS Code と Web で説明が食い違う。

Web 版は VS Code のような設定基盤を持たないので、**Web シェルだけが小さな設定パネルを実装する**。
保存先は `localStorage` で足りる（[この用途は端末ごとの好みであり、Git に置く情報ではない](platforms.md)）。

## 3. 何を設定にするか

**設定項目は「増やせる」ものではなく「厳選する」もの**である。[P8](decisions.md)（設定にせず固定する）は生きている。

| 項目 | 判断 |
|---|---|
| **編集を確定するキー** | **設定にする。** アプリごとに流儀が割れており、手が覚えているものが人によって違う |
| Escape で取り消し | **固定。** これに異論は無い |
| フォーカスを外したら確定 | **固定。** 同上 |
| `Ctrl+B` / `Ctrl+I` | **固定。** ほぼ全てのエディタで共通 |
| 意味トークンの語彙・色 | **固定**（[文字書式](inline-format.md)）。テーマが決める |
| 図表の採番方式 | **固定**（[参照記法](reference-syntax.md)） |

判断の基準は「**流儀が実在して割れているか**」である。割れていないものを設定にすると、選択肢が増えるだけで誰も得をしない。

## 4. 編集を確定するキー

本文を開いた状態で、`Enter` は「改行」か「確定」か。実在するアプリで割れている。

| 割り当て | 例 |
|---|---|
| `Ctrl+Enter` で確定 / `Enter` で改行 | GitHub のコメント欄、多くのエディタ |
| `Enter` で確定 / `Shift+Enter` で改行 | Slack の既定、チャット系 |
| `Shift+Enter` で確定 / `Enter` で改行 | 一部の業務アプリ |
| `Alt+Enter` で確定 / `Enter` で改行 | Excel のセル編集（逆向きだが Alt+Enter を使う） |

**既定は `Ctrl+Enter` で確定**とする。設計書の本文では `Enter` が改行である場面のほうが圧倒的に多く、
**既定を「Enter で確定」にすると、そう思っていなかった人の書きかけが閉じる**。取り返しのつかない側に倒さない。

規則は二つだけである。

1. **割り当てた組み合わせだけが確定になる**
2. **それ以外の `Enter` は、修飾キーが付いていても必ず改行を入れる**

2 が要る。テキストボックスは `Ctrl+Enter` や `Alt+Enter` を素通ししてしまい、何も起きないことがある。
**押したのに何も起きない**のは、間違った動作より質が悪い。

`Cmd+Enter` は `Ctrl+Enter` と同じものとして扱う。名前が違うだけで同じ身振りである。
