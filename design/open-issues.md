## A. 着手前に決めるべきこと

構造に関わり、後から変えると手戻りが大きいもの。**うち 1〜6 はまだどの設計ドキュメントにも挙がっていない。**

### A-1. D12 横断一覧・トレーサビリティを要件化するか — 決定

**R12 として要件化した**（[横断一覧設計案](index-model.md)）。実体は「ビルド時のインデックス」と「そこからの一覧生成」。トレーサビリティは R11 のラベルと参照グラフにそのまま乗るため、新しい関係記法は作らない。

以下が依存していた。

- 凡例の文書単位集計（[表モデル §5.1](table-model.md)）
- 共有要素の被参照逆引き（[編集 UI §5](editor-model.md)）
- 図表一覧の自動生成（[参照記法 §7.2](reference-syntax.md)）
- 相互参照の逆引き（[参照記法 §7.8](reference-syntax.md)）

加えて、**[P6「黙って捨てない」](decisions.md)で約束した診断（壊れた参照・欠字・orphaned コメント）の実装基盤**でもあった。

### A-2. PDF のページ設計 — 決定（[テーマ設計案 §6](theme.md)）

用紙・余白・向き、前付け（表紙・改訂履歴・目次・図表一覧）、ヘッダ／フッタ、ページ番号の体系、改ページ制御まで設計した。テーマは **CSS ＋ フォント ＋ 前付けテンプレート**の三点で構成する。

用紙の向きを表ごとに変えられることは[検証済み](../prototype/paged-landscape/FINDINGS.md)。ただし Paged.js は文書全体で 1 つのページサイズしか持てないため、**向きごとに別パスで組版して PDF を自前で綴じる**実装になる。

~~残る最大の課題は §6.7~~ → **解決。**セル結合を持つ表のページ分割とヘッダ行の繰り返しを自前実装で[検証済み](../prototype/table-paging/FINDINGS.md)。結合セルを境界で切って次ページに継続する処理まで動作を確認した。

残るのは細部 — 1 行がページ高を超える場合の行分割、結合を含む複数行ヘッダ、収束の打ち切り。

### A-3. PPTX のスライド分割規則 — 決定（[PPTX 出力設計案](pptx-model.md)）

分割規則（`---` ＋ 見出し単位、既定 `h2`）、収まらない内容の扱い（継続スライド。表は PDF の分割アルゴリズムを流用、図のみ縮小可）、プレースホルダへの流し込み、スライドマスタと CSS の分担まで設計した。

**要点**: 期待される用途は**「1 スライド 1 つの、PowerPoint で自由に編集できる概要設計図」**であり、長い設計書の全文変換は機能として備えるが運用しない。**R6 の核心は「編集可能な PPTX」ではなく「編集可能な図」**だった。

**出力した図形にノード ID を埋めることで、PowerPoint で動かした位置・直した文字を `.dgm` に戻せる見込み**（§8）。ID の埋め込み先が PowerPoint の保存で保持されるかは実測が必要。

スライドレイアウトは CSS からは導けないため、**CSS からはトークンだけを引き、配置はスライドレイアウトが持つ**。既定マスタはトークンから生成し、`.potx` の持ち込みも許す。

### A-4. テーマの定義形式 — 一部決定

**テーマは CSS で書く**ことが確定した（[PDF をブラウザで組版する](pdf-engine.md)決定の帰結）。
フォントについては[テーマ設計案](theme.md)で決定済み — スタイルは自由、**フォントファミリはテーマが同梱するものに限る**（OS のシステムフォントは画面と PDF が一致しないため指定できない）。

残りは未設計。ページ設計（表紙・目次・ヘッダ／フッタ・余白）、PPTX のスライドマスタ、[表](table-model.md)と[作図](diagram-model.md)のトークンを CSS でどう表現するか、テーマの配布単位。

### A-5. PDF 生成エンジンと日本語組版 — 決定（[PDF 生成エンジンの比較検討](pdf-engine.md)）

**案 A（HTML ＋ CSS 組版）に確定。** テーマの二重化を認めないため Typst は不採用。

ただしブラウザの印刷パイプラインは使わず、**ブラウザをレイアウトエンジンとして使い、PDF は自前で書く**（Paged.js でページ分割 → pdf-lib で書き出し）。これにより Web 版でも PDF バイト列が得られ、三面が単一実装になる。ソースマップは副産物として手に入る。

**最優先の実測「日本語のテキストが選択・検索できる PDF を出せるか」は検証済み・問題なし**（[検証結果](../prototype/pdf-text/FINDINGS.md)）。Chrome・Firefox 両エンジンで抽出と検索が成功し、方式の最大リスクは解消した。

残る実測は、ブラウザのレイアウト結果の組版品質と、その読み取り方。

### A-6. ビルドの単位と CLI — 決定（[ビルド単位設計案](build-model.md)）

**frontmatter に `output:` を持つ文書だけがビルドルート**となり、そこから `@import` を推移的に辿った閉包がビルド対象になる（Markdown Preview Enhanced の発想を借りた）。

**ルート探索はリポジトリ全体、収集は参照閉包、インデックスは全ルートの和集合**という三層に分かれる。これが R12 の走査範囲への回答にもなる。あわせて**テーマの指定方法**（`theme:` を frontmatter に書く）も決まった。

### A-7. 用語の整理 — 済

企画初期の `.docmlx`（独自ファイル形式としての中間モデル）は、「地は Markdown、特殊要素は外部ファイル」の決定により**消滅している**。設計ドキュメント側は修正済み。`docs/research/` に残るものは企画初期の記録として扱う。

## 所見

**A-2 / A-3 / A-4 が同じ場所を向いている。** PDF のページ設計も、PPTX のスライド分割も、結局テーマが持つ情報である。
個別に決めるより、**出力側の設計として一度にまとめる**ほうが整合が取れる。

実際、区切り記法 `---` の決定は A-2 と A-3 の両方を同時に進めた（[出力モデル §2](output-model.md)）。
残りも同じ構造で、**テーマが規則を持ち、`---` と属性が例外を担う**という分担に収束していく見込み。

企画としては、ここまでで**入力側（記法・編集・レビュー）はほぼ固まり、出力側がまるごと残っている**状態にある。
