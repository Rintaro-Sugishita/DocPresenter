# パッケージ分割 — 単独で出せるものを、単独で出せる形に保つ

作成: 2026-09-28 / 対象: 作図と Markdown レンダリングの単独公開
関連: [作図モデル](diagram-model.md) / [出力モデル](output-model.md) / [提供形態](platforms.md) / [ライセンス方針](licensing.md)

## 0. 決定事項（ロック済み）

- **公開単位は 3 つに分ける。**「作図（エンジン ＋ GUI）」「Markdown レンダリングエンジン（GUI なし）」「設計書製品」。
- **依存は一方向。** `base ← diagram ← { markdown, pdf, pptx } ← build`、`markdown ← editor`。逆流も循環も作らない。
- **設計書製品は二重実装しない。** `.dgm` の描画も編集も、作図パッケージのものをそのまま使う。
- **共有の土台（base）は最小に保つ。** バイト範囲・編集・inline 記法・共通 UI 部品まで。「共有できるから」で太らせない。
- **CSS もパッケージごとに持つ。** 器が連結して 1 つ入れる。
- **パーサとレンダラは npm のライブラリとして配る。GUI は製品として配る**（§6）。
- **初公開と同時にリポジトリを public にする。再配布は許し、改変は許さない**（[ライセンス方針 §6](licensing.md)）。リポジトリは 2026-11 に public にした。条文は確定前で、それまでは全権利留保（[同 §7.5](licensing.md)）。

## 1. なぜ分けるか

### 1.1 作図は単体で価値がある

記法が簡単で、差分が読め、GUI で直接操作できる作図ツールは、それだけで需要がある。
設計書という文脈が無くても成立する。**設計書の一機能として埋めておく理由が無い。**

### 1.2 Markdown エンジンは GUI 無しで価値がある

CI で HTML や PDF を吐く、他の製品に組み込む、AI に読ませる形へ投影する。
**画面を持たない使い方のほうが多い**かもしれない。

### 1.3 分ければ二重実装が構造的に起きない

設計書製品が作図の「使う側」になれば、`.dgm` の描画が 2 つ存在しようがない。
[片方だけ直して食い違う](decisions.md)という、最も起きやすい壊れ方が消える。

## 2. 境界線

| パッケージ | 中身 | 依存 | 単独公開 |
|---|---|---|:--:|
| **base** | バイト範囲（`ByteSpan` / `sliceBytes`）、編集（`Edit` / `applyEdit`）、inline 記法の付け外し、共通 UI 部品（メニュー・書式バー・色見本）とその CSS | — | しない（土台） |
| **diagram** | 作図の意味 / レイアウト / スタイル、SVG 描画、部品ライブラリ、編集操作、キャンバス GUI | base | **する** |
| **markdown** | 文書モデル、シート、採番と相互参照、表（`.table`）、HTML 描画 | base, diagram | **する**（GUI なし） |
| **pdf** | PDF（ページ計画・組版済み DOM の読み取り・改ページ・書き出し） | base, diagram | 設計書製品の一部 |
| **pptx** | PPTX（デッキ・DrawingML・書庫） | base, diagram | 設計書製品の一部 |
| **build** | ビルド（ルート探索・参照閉包・診断・成果物の書き出し） | base, markdown, diagram, pdf, pptx | 設計書製品の一部 |
| **editor** | 設計書の GUI（シートタブ・本文ブロック・表のグリッド） | base, markdown, diagram | 設計書製品の一部 |
| **app-vscode-diagram** | VS Code 拡張「DocPresenter Diagram」：`.dgm` の言語・整形・キャンバス・SVG 書き出し | base, diagram | **する**（VS Code 拡張として） |
| **app-vscode** | VS Code 拡張「DocPresenter」：設計書の編集画面・書き出し・レビュー。作図の拡張を拡張パックで連れてくる | base, build, diagram, editor, markdown, pdf | 設計書製品 |

**build と editor は互いを知らない。** ビルドは画面を持たず、エディタは成果物を作らない。
両方が markdown と diagram を使う、というだけの関係である。

**markdown が diagram に依存するのは正しい。** `@import "foo.dgm"` を描けなければ設計書のレンダラではない。
逆に diagram が markdown を知る理由は無い（図は文書を知らない）。

## 3. 何を base に置き、何を置かないか

置く。**どちらの製品でも、同じものが同じ意味で要る**ものだけ。

- **バイト範囲**と**編集**。[編集は必ず 1 つのバイト範囲の置換](decisions.md)という規律は両方に効く。
- **inline 記法の付け外し**（`**` / `*` / `` ` `` / `[…]{color=…}`）。
  [本文・セル・図形ラベルで同じ記法](diagram-model.md)と決めた以上、実装も 1 つでなければ意味がない。
- **共通 UI 部品** — コンテキストメニュー、書式バー、色見本。3 か所で同じ操作にするための部品。

置かない。

- **文書モデル・表・採番・テーマ** — 作図には要らない。
- **レンダラの共通化** — HTML と SVG は出力先が違う。`escapeHtml` のような数行のために依存を作らない。

## 4. CSS もパッケージごとに持つ

エディタの見た目は 1 つの文字列だったが、分けると所属が変わる。

| CSS | 置き場所 |
|---|---|
| メニュー・書式バー・色見本 | base |
| キャンバス（選択枠・取っ手・吸着ガイド・部品の絵） | diagram |
| シートタブ・本文ブロック・表のグリッド | editor |

器が連結して `<style>` に入れる。**作図を単独で動かすときは base ＋ diagram だけで足りる**、という形を保つ。

## 5. 分けたあとも壊れないことの担保

パッケージごとに単体テストを持つ。**境界を越えた import は型検査が止める**
（`tsc --build` のプロジェクト参照）ので、markdown が editor を呼ぶような逆流はコンパイルが通らない。

そのうえで、**作図だけのページを 1 枚ビルドして検証に含める**。

- `tools/build-canvas-demo.mjs` — base ＋ diagram だけを束ねた単独ページ。
- `tools/check-canvas-app.mjs` — そのページを実際に操作して、描画・ドラッグ・図形追加・部品追加・書式バーが動くことを見る。

このページが**文書エンジンを 1 バイトも含まない**ことが、分離が言葉だけでない証拠になる。
実際、作図だけなら 128 KB、設計書の編集画面は 676 KB である。
作図側がうっかり文書側へ依存した瞬間、このページはビルドできなくなる。

## 6. 何を配り、何を製品として持つか

| 出すもの | 形 | ライセンス |
|---|---|---|
| `base` / `diagram` / `markdown` のうち**パーサとレンダラ** | npm のライブラリ | [再配布可・改変不可](licensing.md)（source-available） |
| キャンバス GUI と設計書の編集 UI | 製品（Web / VS Code） | 同上。無償・商用可 |
| リポジトリ全体（`design/` を含む） | public | 同上 |

**ライブラリとして出すのは「読み書きできること」であって、「道具」ではない。**
`.dgm` を読んで SVG にする、Markdown を読んで HTML にする——ここが外から使えると、
CI で出力したい人、別のエディタに組み込みたい人、AI に読ませたい人が自分で繋げる。
道具（GUI）はそのうえに載る製品であり、[分割で既に別パッケージになっている](#2-境界線)。

### 6.1 パッケージの粒度をもう一段割るか

`diagram` は今、**記法・レイアウト・描画**（＝ライブラリとして配りたい部分）と
**キャンバス GUI**（＝製品）を 1 つのパッケージに持っている。依存は
`view/` → その他の一方向なので、**割る必要が出たら割れる**。
[作図だけのページ](#5-分けたあとも壊れないことの担保)が既にその境界を通っている。

割るのは「GUI を配らない」と決めたときでよい。今は同じライセンスで両方出すので、急がない。
