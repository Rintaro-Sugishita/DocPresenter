## 0. 決定事項（ロック済み）

- **案 A（HTML ＋ CSS 組版）に確定。Typst は採らない。**
  理由は単純で、**テーマの二重化を認めないから**。HTML 出力（R4）が必須である以上、Typst を採ればテーマを二系統持つことになり、[直値を禁止しトークンに限定した設計](table-model.md)の根拠そのものが崩れる。
- **ただしブラウザの「印刷パイプライン」は使わない。** ブラウザは**レイアウトエンジン**として使い、**PDF は自前で書く**（§6）。
- これにより Web / デスクトップ / CLI の三面すべてで PDF バイト列が得られ、C1〜C5 を同時に満たす。

## 1. 我々固有の制約

一般論としての「HTML→PDF と Typst の比較」ではなく、**本製品の既決事項から来る制約**で判断する。

| # | 制約 | 出典 |
|---|---|---|
| C1 | **コアはサーバ無しで全機能が動く** | [サーバの位置づけ](server-architecture.md) |
| C2 | **Web(WASM) / デスクトップ / VS Code の三面が単一実装** | [編集 UI](editor-model.md) |
| C3 | **HTML 出力は必須**（R4） | [要件定義](requirements.md) |
| C4 | **ソースマップ（バイト範囲 ↔ ページ座標）が必須** | [レビューモデル §3.4](review-model.md) |
| C5 | **PDF に生成元コミットを埋める** | [レビューモデル §3.3](review-model.md) |
| C6 | 日本語組版（禁則・和欧文間） | — |
| C7 | 納品物としての再現性（版が変わっても同じ見た目） | — |

### ErCreator の PDF 出力は転用できない

`canvas-interop.js` を確認した。**キャンバスを PNG 化して jsPDF の `addImage` で包んでいる**。画像 PDF であって組版ではないため、本件の参考にならない。

## 2. 案 A — ブラウザ（HTML ＋ CSS 組版）

HTML を印刷用 CSS で組版し、ブラウザエンジンに PDF を吐かせる。

### 状況が変わっている

歴史的に、この方式の最大の欠点は**「ヘッダ・フッタが CSS で書けない」**ことだった。Chromium が `@page` のマージンボックスに未対応で、`@top-center` 等が使えなかった。

**Chrome 131（2024-11）でマージンボックスに対応した。** これにより文書番号・版数・ページ番号を CSS で組めるようになり、従来の最大の障害が消えている。

なお WebView2 の `CoreWebView2PrintSettings` が持つヘッダ・フッタ設定は `HeaderTitle` と `FooterUri` のみで実用にならないが、**CSS 側で組むなら関係ない**（組み込みのヘッダ・フッタは無効化して使う）。

### 三面での実現性

| 面 | 手段 | PDF のバイト列を得られるか |
|---|---|---|
| デスクトップ（WebView2） | `PrintToPdfStreamAsync` | **○** |
| CLI / CI | headless Chrome | **○** |
| **Web（ブラウザ）** | `window.print()` のみ | **✗ 印刷ダイアログ経由のみ** |

最後の行が案 A の急所である。**Web 版だけ、プログラムから PDF を生成できない。**

- PDF メタデータに生成元コミットを埋め込めない（C5 違反）
- ソースマップを PDF と一緒に出力できない（C4 違反）
- → **Web 版では [PDF レビュー経路](review-model.md)が成立しない**

### 日本語組版

ブラウザの禁則処理は実用水準にあり、`text-spacing-trim` 等も実装が進んでいる。さらに **Vivliostyle**（日本発の CSS 組版実装、CLI あり）を使えば書籍品質まで上げられる。**現時点では案 B より明確に良い。**

## 3. 案 B — Typst

中間モデルから Typst マークアップを生成し、Typst に PDF を組ませる。

### 三面での実現性

**WASM にコンパイルして三面すべてで同一のものを使える。** ブラウザ上で完結して PDF バイト列を直接得る実装は既に複数存在する（typst.ts、Typst WASM Compiler 拡張など）。

| 面 | 手段 | PDF のバイト列を得られるか |
|---|---|---|
| デスクトップ | ネイティブ or WASM | **○** |
| CLI / CI | ネイティブ | **○** |
| **Web** | **WASM** | **○** |

**C1・C2 に対して完全に整合する。** これが案 B の最大の長所。

### 日本語組版

改善途上である。0.14 で**文字レベルの空き調整**が入り、日本語の均等割りや禁則に効くようになった。ただし歴史的に CJK は弱く、実用には有志のテンプレートに頼る面がある。**現時点では案 A に劣る。**

### HTML をどうするか

**ここが案 B の急所。** C3（HTML 必須）がある以上、Typst で PDF を組むなら **HTML は別経路で作ることになり、テーマを二重に持つ**。

Typst 自身の HTML 出力は 0.14 時点でも experimental であり、当てにできない。

テーマの二重化は、単なる実装量の問題ではない。**[直値を禁止しトークンに限定した設計](table-model.md)は「出力先で同じ見た目が保証できる」ことを根拠にしていた。** レンダラとテーマ定義が二系統に分かれると、この根拠が弱くなる。

## 5. 言語を変えても `window.print()` は解決しない

「C# WASM に限定しない」ことで Web 版の PDF 生成が解けるか、を先に整理しておく。

**解けない。** `window.print()` しか使えないのは**ブラウザの API 制限**であって、C# の制限ではない。JS でも Rust でも、ページ内のコードからブラウザの印刷エンジンを呼んで PDF バイト列を受け取ることはできない。実装言語を変えても、この壁は 1 ミリも動かない。

動くのは別の場所である。

> **ブラウザの印刷パイプラインを使うのをやめればよい。**

## 6. 採用方式 — ブラウザでレイアウトし、PDF は自前で書く

### 6.1 パイプライン

```
中間モデル
   ↓ HTML ＋ CSS（テーマ）           ← HTML 出力と完全に同一のものを使う
 DOM
   ↓ Paged.js                        ← CSS Paged Media をポリフィルし、DOM 上でページに分割
 ページ分割済み DOM
   ↓ 位置を読む                       ← 各要素がどのページのどの座標にあるかが分かる
   ↓ pdf-lib（CJK サブセット埋め込み）
 PDF バイト列
```

**Paged.js** は CSS Paged Media / Generated Content をポリフィルし、**ブラウザの印刷機能を使わずに DOM 上でページ分割を行う**ライブラリである。分割結果はページボックスとして DOM に存在するため、そこから位置を読める。

**pdf-lib** は JS の PDF 書き出しライブラリで、fontkit によるフォントのサブセット埋め込みに対応する。日本語フォントは全体で 15〜20 MB あるが、**実際に使われた字だけを埋め込めば数百 KB に収まる**。

### 6.2 なぜこれが効くのか

| 制約 | 満たせる理由 |
|---|---|
| **C1・C2 三面で同一** | 必要なのは「ブラウザがあること」だけ。Web は利用者のブラウザ、デスクトップは WebView2、CLI は headless Chrome。**同じ JS パイプラインがそのまま動く** |
| **C3 HTML とテーマ共用** | PDF の元が HTML 出力そのもの。CSS は 1 つ |
| **C4 ソースマップ** | **自分で配置するので、どの要素がどのページのどの座標に来たかを完全に把握している。副産物として手に入る** |
| **C5 コミット埋め込み** | 自分で PDF を書くので、メタデータは自由に入れられる |
| **C6 日本語組版** | **行分割・禁則・字詰めはブラウザがやる。** ブラウザの組版品質をそのまま受け取れる |
| **C7 再現性** | ページ分割は Paged.js が行うため、ブラウザの印刷実装の差に左右されにくくなる |

**C4 が副産物として手に入る点が決定的である。** 前節までは「ソースマップが取れるか」が最大の不安だったが、PDF を自分で書くならこれは疑問ですらなくなる。

印刷パイプラインを使う案では、ブラウザが不透明に PDF を吐くため、DOM 上の位置と PDF のページ座標を突き合わせる必要があった。自前で書けばその突き合わせ自体が存在しない。

### 6.3 図は SVG を経由しない

作図は既に **SVG（HTML 用）と DrawingML（PPTX 用）の 2 系統のレンダラ**を持つ（[作図モデル](diagram-model.md)）。PDF についても、SVG を PDF に変換するのではなく、**作図モデルから直接 PDF の描画命令を出す 3 番目のターゲット**とするほうが素直である。

図形語彙を DrawingML のプリセットに限定してあるため、対象は小さい。

### 6.4 リスクと、正直な見積もり

| リスク | 内容 |
|---|---|
| **ToUnicode CMap の正しさ** | **最も重要。** PDF 内のテキストが選択・検索・コピーできるかは ToUnicode の正しさで決まる。**顧客は PDF 上でテキストを選択してハイライト注釈を付ける**（[レビューモデル §6](review-model.md)）。ここが壊れると PDF レビューがフリーハンド注釈に劣化し、アンカーの精度が落ちる |
| ~~日本語サブセットの不具合~~ | **確認済み。pdf-lib の `subset: true` は CFF フォントのグリフを一切描かなくする。**自前サブセット（harfbuzzjs）で回避する（[検証結果](../prototype/pdf-text/FINDINGS.md)） |
| フォントライセンス | 埋め込み可能なフォントを選ぶ必要がある |
| **実装量** | これはライブラリ呼び出しではなく、**本製品の中核コンポーネントになる**。テキスト配置・フォント埋め込み・罫線・塗り・画像・図形描画を自前で持つ |

実装量は小さくない。ただし**これは PPTX 出力（OOXML 直生成）で既に引き受けている性質の仕事と同種**であり、本製品が差別化のために元々払うと決めていたコストの延長線上にある。

### 6.5 採らなかった代替案

| 案 | 内容 | 不採用の理由 |
|---|---|---|
| A-2 | 同じ CSS を別の組版エンジン（WeasyPrint 等）で処理し、WASM 化する | テーマは単一のままだが、**画面の HTML とレンダラが違うため見た目がずれる**。C7 を損なう |
| A-3 | Web 版では PDF を出さず、デスクトップ / CLI に寄せる | C1・C2 に反する。§6 が成立するなら妥協する理由が無い |
| A-4 | ローカルの補助プロセスを立てる | Web 版の「インストール不要」を壊す |

| # | 測ること | 決まること |
|---|---|---|
| ~~1~~ | ~~pdf-lib で日本語を埋め込み、PDF 上でテキストの選択・検索・コピーが正しく効くか~~ | **✅ 検証済み・問題なし**（[検証結果](../prototype/pdf-text/FINDINGS.md)）。Chrome と Firefox の両エンジンで抽出・検索とも成功。サブセットは 4.2 MB → 29.3 KB。副産物として、文字単位の矩形が取得でき注釈アンカーの往復が成立する見込みも立った |
| 2 | Paged.js による日本語の組版品質（禁則・字詰め・表の分割） | 素の Paged.js で足りるか、Vivliostyle 等を併用するか |
| 3 | ページ分割済み DOM から「バイト範囲 → ページ座標」を取れるか | C4 の実装方式 |
| 4 | 同じ HTML / CSS が ブラウザ・WebView2・headless Chrome で同じページ分割になるか | C7 の実害 |
| 5 | `@page` マージンボックスとの併用可否（Paged.js のポリフィルとネイティブ実装の衝突） | ヘッダ・フッタの実装方式 |

**1 は検証済みで、通った。** 方式の最大リスクは解消している。

ただし検証で新たな要件が 1 つ出た。**フォントが持たない字は「描画は豆腐、抽出は消滅」という非対称な壊れ方をする。** 設計書で人名が静かに欠けることになるため、**書き出し前の欠字検出を必須とする**（`fontkit` の `hasGlyphForCodePoint()` で可能なことを確認済み）。

残る最優先は **2・3**、すなわちブラウザのレイアウト結果の品質と読み取りである。

## 7.5 実装したもの（2026-09-29）— と、設計から外した 3 点

`packages/pdf` に入れた。**ブラウザが組版し、PDF はこちらが書く**という §6 の骨格はそのままである。

| 段 | 中身 | 置き場所 |
|---|---|---|
| 計画 | ページに何がどこにあるか。HTML も PDF も知らない素のデータ | `plan.ts` |
| 読み取り | 組版済みの DOM から印を読む。色・太さ・罫線は `getComputedStyle` から | `collect.ts` |
| 改ページ | 断片（行・表の行・図）に切り、ページに詰める。表は見出し行を繰り返す | `measure.ts` |
| 書き出し | pdf-lib で PDF にする。フォント埋め込みと欠字検出を含む | `write.ts` / `fonts.ts` |
| 器 | ブラウザを開き、計測を注入し、フォントを渡す | `tools/pdf-writer.mjs` |

**計画（`plan.ts`）を挟んだのが要点である。** 片側はブラウザが要るが、
もう片側は**紙の上の座標だけ**で完結する。書き出しはブラウザ無しで試験でき、
読み取りは PDF を読まずに確かめられる。[C4 のソースマップ](#62-なぜこれが効くのか)も
この計画に乗る——各印が `span` と出自のファイルを持って運ばれる。

### 設計から外した 3 点（理由つき）

1. **Paged.js を使っていない。** §6.1 は組版済み DOM を Paged.js に作らせる前提だったが、
   **ページ箱そのものが要らない**ことが実装して分かった。必要なのは「どの印がどのページか」であり、
   PDF を自分で書く以上、DOM 上にページ箱を作る意味が無い。加えて、
   [表の見出し行の繰り返しは結局こちらで分割する](theme.md)と決めてあり、
   Paged.js に任せる部分が残っていなかった。[§7 の懸念 5](#7-プロトタイプで確かめること)
   （`@page` マージンボックスとポリフィルの衝突）も消える。
   **ブラウザは組版に使い続ける**——行分割・禁則・和欧文間はブラウザの結果をそのまま読む。
2. **図は SVG を経由する。** §6.3 は「作図モデルから直接 PDF の描画命令を出す」としていたが、
   **図の色はテーマが CSS で決めている**（`.dp-class-pending`、`--dp-fill`、群の破線）。
   モデルから描くと、その解決を PDF 側でもう一度実装することになり、
   [テーマの二重化を認めない](#0-決定事項ロック済み)という本方式の前提そのものと衝突する。
   組版済みの SVG を読めばテーマは 1 つで済む。
   なお**幾何は `packages/diagram/src/draw/geometry.ts` に切り出した**——
   PPTX（DrawingML）はモデルから描くしかないので、そこで要る。
3. **埋め込むフォントは当面 TrueType。** Noto Sans CJK JP は CFF で、
   [pdf-lib のサブセッタが壊す](../prototype/pdf-text/FINDINGS.md)。
   harfbuzzjs による自前サブセットはまだ繋いでいない。
   代わりに**書き出しが CFF を拒否する**（`fonts.ts`）。
   拒否しなければ「文字は取り出せるが 1 字も描かれない PDF」が出来上がり、
   **テキスト検証は通ってしまう**。フォントは器から渡す形にしてあるので、
   サブセッタが入れば渡すものが変わるだけである。

### 実測で見つかった壊れ方

**円弧のフラグを座標と同じに扱ってはいけない。** `A rx ry rot large sweep x y` の 7 つのうち
座標は末尾 2 つだけである。全部に倍率を掛けると sweep が `0.75` になり、
**以降の直線が消える**（円柱と群の枠が角だけになった）。単体試験に固定した。

### 検証

`tools/check-pdf.mjs` が **pdf.js（Firefox の PDF エンジン）で読み返して 16 項目**を見る。
日本語が取り出せること、参照が番号に解決されていること、柱が全ページにあること、
図が**線と塗りの描画命令**として出ていること（貼った絵ではないこと）、
埋め込みフォントで描かれていること。
