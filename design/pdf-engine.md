# PDF 生成エンジンの比較検討

関連: [要件定義](requirements.md) / [出力モデル](output-model.md) / [レビューモデル](review-model.md) / [サーバの位置づけ](server-architecture.md)

## 1. 我々固有の制約

一般論としての「HTML→PDF と Typst の比較」ではなく、**本製品の既決事項から来る制約**で判断する。

| # | 制約 | 出典 |
|---|---|---|
| C1 | **コアはサーバ無しで全機能が動く** | [サーバの位置づけ](server-architecture.md) |
| C2 | **Web(WASM) / デスクトップ / VS Code の三面が単一実装** | [編集 UI](editor-model.md) |
| C3 | **HTML 出力は必須**（R4） | [要件定義](requirements.md) |
| C4 | **ソースマップ（バイト範囲 ↔ ページ座標）が必須** | [レビューモデル §3.4](review-model.md) |
| C5 | **PDF に生成元コミットを埋める** | [レビューモデル §3.3](review-model.md) |
| C6 | 日本語組版（禁則・和欧文間） | — |
| C7 | 納品物としての再現性（版が変わっても同じ見た目） | — |

### ErCreator の PDF 出力は転用できない

`canvas-interop.js` を確認した。**キャンバスを PNG 化して jsPDF の `addImage` で包んでいる**。画像 PDF であって組版ではないため、本件の参考にならない。

## 2. 案 A — ブラウザ（HTML ＋ CSS 組版）

HTML を印刷用 CSS で組版し、ブラウザエンジンに PDF を吐かせる。

### 状況が変わっている

歴史的に、この方式の最大の欠点は**「ヘッダ・フッタが CSS で書けない」**ことだった。Chromium が `@page` のマージンボックスに未対応で、`@top-center` 等が使えなかった。

**Chrome 131（2024-11）でマージンボックスに対応した。** これにより文書番号・版数・ページ番号を CSS で組めるようになり、従来の最大の障害が消えている。

なお WebView2 の `CoreWebView2PrintSettings` が持つヘッダ・フッタ設定は `HeaderTitle` と `FooterUri` のみで実用にならないが、**CSS 側で組むなら関係ない**（組み込みのヘッダ・フッタは無効化して使う）。

### 三面での実現性

| 面 | 手段 | PDF のバイト列を得られるか |
|---|---|---|
| デスクトップ（WPF ＋ WebView2） | `PrintToPdfStreamAsync` | **○** |
| CLI / CI | headless Chrome | **○** |
| **Web（ブラウザ上の Blazor WASM）** | `window.print()` のみ | **✗ 印刷ダイアログ経由のみ** |

最後の行が案 A の急所である。**Web 版だけ、プログラムから PDF を生成できない。**

- PDF メタデータに生成元コミットを埋め込めない（C5 違反）
- ソースマップを PDF と一緒に出力できない（C4 違反）
- → **Web 版では [PDF レビュー経路](review-model.md)が成立しない**

### 日本語組版

ブラウザの禁則処理は実用水準にあり、`text-spacing-trim` 等も実装が進んでいる。さらに **Vivliostyle**（日本発の CSS 組版実装、CLI あり）を使えば書籍品質まで上げられる。**現時点では案 B より明確に良い。**

## 3. 案 B — Typst

中間モデルから Typst マークアップを生成し、Typst に PDF を組ませる。

### 三面での実現性

**WASM にコンパイルして三面すべてで同一のものを使える。** ブラウザ上で完結して PDF バイト列を直接得る実装は既に複数存在する（typst.ts、Typst WASM Compiler 拡張など）。

| 面 | 手段 | PDF のバイト列を得られるか |
|---|---|---|
| デスクトップ | ネイティブ or WASM | **○** |
| CLI / CI | ネイティブ | **○** |
| **Web** | **WASM** | **○** |

**C1・C2 に対して完全に整合する。** これが案 B の最大の長所。

### 日本語組版

改善途上である。0.14 で**文字レベルの空き調整**が入り、日本語の均等割りや禁則に効くようになった。ただし歴史的に CJK は弱く、実用には有志のテンプレートに頼る面がある。**現時点では案 A に劣る。**

### HTML をどうするか

**ここが案 B の急所。** C3（HTML 必須）がある以上、Typst で PDF を組むなら **HTML は別経路で作ることになり、テーマを二重に持つ**。

Typst 自身の HTML 出力は 0.14 時点でも experimental であり、当てにできない。

テーマの二重化は、単なる実装量の問題ではない。**[直値を禁止しトークンに限定した設計](table-model.md)は「出力先で同じ見た目が保証できる」ことを根拠にしていた。** レンダラとテーマ定義が二系統に分かれると、この根拠が弱くなる。

## 4. 比較

| | 案 A ブラウザ | 案 B Typst |
|---|---|---|
| **HTML とテーマを共用できる（C3）** | **◎ 同一レンダラ・同一 CSS** | **✗ 二重に持つ** |
| **Web 版で PDF を生成できる（C1・C2）** | **✗ 印刷ダイアログのみ** | **◎ WASM で同一** |
| ソースマップ（C4） | ○ DOM から取りやすい | △ span 情報はあるが要検証 |
| コミット埋め込み（C5） | デスクトップ・CLI のみ ○ | ◎ 全面 |
| 日本語組版（C6） | **◎（Vivliostyle 併用で更に上）** | △ 改善途上 |
| 再現性（C7） | △ ブラウザ版差で揺れる | **◎ 決定性が高い** |
| 配布サイズ | ◎ WebView2 は OS 側にある | ◎ 小さい |
| テーマ記述 | **◎ CSS。書ける人が多い** | △ Typst 言語 |
| 組版のプログラマビリティ | △ CSS の範囲 | ◎ 高い |

## 5. 判断が難しい理由

**上位 2 行が正面衝突している。**

- 案 A を採ると、**Web 版で PDF レビュー経路が使えない**
- 案 B を採ると、**HTML と PDF でテーマが二重になり、見た目の一致を保証しにくい**

どちらも既決事項に直接ぶつかる。片方を選べば、もう一方の約束を一部諦めることになる。

「Web 版だけ Typst を併用する」は解にならない。**PDF の見た目が面によって変わる**ためで、C7 をより深く損なう。

## 6. 現時点の推奨 — 案 A を本命とし、実測して確定する

理由は非対称性にある。

- **テーマの二重化（案 B の代償）は恒久的な構造コスト**であり、製品が続く限り払い続ける。しかも「出力先で見た目が揃う」という設計全体の前提を弱める
- **Web 版の PDF 制約（案 A の代償）は運用で緩和できる。** [レビューモデル](review-model.md)では HTML ビューアが主経路で PDF は普遍経路だった。Web 版は「まず触ってみる」導線であり、レビュー用 PDF の生成はデスクトップ / CLI に寄せる運用で成立しうる

加えて **C6（日本語組版）でも現時点では案 A が優る**。設計書は印刷・納品されるため、ここは軽くない。

ただし**確信には至っていない**。次の実測で確定する。

### 実測項目

| # | 測ること | 決まること |
|---|---|---|
| 1 | Chrome の `@page` マージンボックスで、文書番号・版数・ページ番号・機密区分のヘッダ／フッタが組めるか | 案 A の前提が成立するか |
| 2 | 素の Chromium と Vivliostyle で、日本語の禁則・和欧文間の品質差 | 追加依存を負う価値があるか |
| 3 | `PrintToPdfStreamAsync` でバイト列取得 ＋ メタデータ埋め込みができるか | C5 がデスクトップで満たせるか |
| 4 | DOM から「バイト範囲 → ページ座標」のソースマップを取れるか | **C4 が成立するか（最重要）** |
| 5 | ブラウザのバージョン差でどれだけ出力が揺れるか | C7 の実害 |
| 6 | 同じ文書を Typst でも組み、日本語品質とテーマ記述の工数を比較 | 案 B を捨ててよいか |
| 7 | Web 版で PDF が作れないことが、実運用でどれだけ痛いか | 案 A の代償の大きさ |

**4 が最重要。** ソースマップが取れなければ、顧客レビューの PDF 経路（R10）が丸ごと成立しない。案 A・案 B のどちらでも、ここが通らなければ設計を見直す必要がある。

## 7. 未確定事項

- Vivliostyle を採るか、素の Chromium で足りるか（実測 2 次第）
- CLI / CI でブラウザをどう用意するか（headless Chrome の同梱か、環境依存か）
- `--print-to-pdf` と印刷ダイアログの挙動差という既知の罠への対処
- 案 A の場合、PPTX 出力は結局別経路（OOXML 直生成）のままである。**レンダラが 2 系統になる点は案 A でも変わらない**ため、案 B の「二重化」がどれだけ余計な負担かは相対的に評価する必要がある
