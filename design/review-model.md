# レビューモデル設計案 — Git を使わない参加者のレビュー

作成: 2026-09-20 / 対象: 要求 D8（レビューのコメント・会話）への回答
関連: [要件定義](requirements.md) / [Excel 脱却要求の整理](../docs/research/excel-migration-japan.md) / [作図モデル設計案](diagram-model.md)

## 0. 決定事項（ロック済み）

- **レビュアは二種類いる**という前提を置く。
  - **エンジニア** → **Git の Pull Request でレビューする**。製品として独自のレビュー機能は持たない。
  - **顧客・業務部門** → **成果物に直接コメントを書く**。PDF に注釈を残すのと同じ体験。
- これを **R10「Git を使わない参加者がレビューできること」** として要件に加える。
- **注釈のアンカーは「コミットハッシュ ＋ ファイル ＋ バイト範囲 ＋ 引用テキスト」とする**（§3）。モデル要素 ID 方式は採らない。
- **注釈レコードは append-only。** 現在の版での位置は保存せず、読むたびに Git 差分から導出する。
- **全出力形式がソースマップを出す**（§3.4）。図・表を含め、アンカーの型は一つに統一する。

## 1. なぜ PDF コメントが正解に見えるのか

顧客レビューにおける PDF 注釈は、次の点で完成している。

- **学習コストがゼロ。** 誰でもやり方を知っている。
- **導入コストがゼロ。** アカウント作成もツール導入も要らない。顧客の情シスの協力が要らないことは、実務上きわめて大きい。
- **本文を壊さない。** 注釈は content の外側に付く。顧客が原本を書き換えてしまう事故が起きない。
- **位置が明示される。** 「3 章のあの表の話」ではなく、その場所に紐づく。

Markdown + Git が顧客レビューで負けるのは、この 4 つをどれも満たせないからである。Wiki 設計書に流れる事例があるのも同じ理由（「第三者が内容にコメントを残せる」ことが Wiki の利点として明確に挙げられている）。

## 2. しかし PDF 注釈には致命的な欠陥がある

**注釈がページ座標に固定されている。**

その結果、次の周知の苦痛が起きる。

1. `v1.pdf` に顧客が 40 件コメントする
2. 指摘を反映して `v2.pdf` を再生成する
3. ページ割りが変わり、**40 件のコメントはどこにも紐づかなくなる**
4. 人力で突き合わせ直す。あるいは Excel の指摘管理表に手で転記する

**レンダリング結果に注釈を固定していることが原因**であり、PDF という形式の本質的な限界である。

## 3. 解 — 注釈は「コミットハッシュ＋ファイル＋バイト範囲」に固定する

注釈が持つのは次の四つだけでよい。

```yaml
- id: 12
  anchor:
    commit: a3f9c21                       # 指摘時点のコミットハッシュ
    file:   docs/auth-design.docmlx
    start:  4821                          # バイトオフセット（開始）
    end:    4907                          # バイトオフセット（終了）
    quote:  "管理者は全ロールを編集できる"   # その範囲に実際にあったテキスト
  body: "管理者でも監査ロールは編集不可の想定です"
  status: open
```

### なぜこれで十分か

**コミットハッシュが付いている時点で、その範囲は永久に正しい。** `a3f9c21` の `docs/auth-design.docmlx` の 4821〜4907 バイト目が何であったかは、Git がある限り未来永劫確定している。**アンカーは「ずれる」のではなく、その版に対しては常に正しいまま凍結される。**

したがって注釈レコードは **append-only で、一度書いたら二度と書き換わらない**。これは [作図モデル設計案](diagram-model.md) で定めた「計算で出せるものはファイルに書かない」規律とも一致する。現在の版のどこに当たるかは**読むたびに導出する**（§3.2）のであって、保存はしない。

### 3.1 モデル要素 ID 方式を採らない理由

当初は「モデル上の要素 ID に固定する」案を検討したが、**バイト範囲方式のほうが優れている**と判断する。

| | 要素 ID 方式 | **コミット＋バイト範囲** |
|---|---|---|
| ID 安定性の担保 | **必須。しかも未解決の難問** | **不要。問題自体が消える** |
| 対象ファイル | モデルを持つファイルのみ | **任意のテキストファイル**（`.docmlx` / `.dgm` / 参照先のソースコードまで） |
| 指摘時点の内容の再現 | **保証されない**（ID が同じでも中身が変わりうる） | **完全に再現できる** |
| 陳腐化の検出 | できない | `quote` の不一致で**検出できる** |
| 実装コスト | 高い | 低い |
| 前例 | 無い | **GitHub の PR レビューコメントが同じ方式**（commit_sha ＋ path ＋ 位置） |

特に三行目が重要である。要素 ID 方式は「ID が同じなら同じ場所」としか言えず、**その要素の中身が書き換わっていても気付けない**。顧客が読んだ文章と、エンジニアが見ている文章が別物になっていても、システムは平然と「解決済み」と扱ってしまう。バイト範囲＋`quote` 方式は、この食い違いを構造的に検出できる。

**この判断により、「本文編集時に ID をどう維持するか」という最優先課題は消滅する。** 作図のピン留め（`.dgm` の L2 層）は引き続き ID を使うが、それは**同一ファイル内で著者が自分で付ける ID** であり、はるかに易しい問題に縮小する。

### 3.2 現在の版への移送（forward mapping）

指摘時点と現在で版が違う場合、表示のために現在位置へ移送する。**保存はせず、読むたびに導出する。**

1. `anchor.commit` から現在の HEAD までの差分を Git で辿る
2. 当該バイト範囲が**その差分で触られていなければ**、オフセットを機械的にずらして移送完了
3. 触られていれば、`quote` を現在の本文に対して曖昧一致させ、見つかればそこへ移送する（`stale` として印を付ける）
4. それも失敗すれば `orphaned`（§7）

これは Myers 差分の上に乗る**解決済みの問題**であり、Git 自身が `git blame` や `git log -L` で日常的にやっていることと同じである。「安定 ID を発明する」という未解決問題を、「差分を辿る」という既知の問題に置き換えたことが、この設計の要点。

### 3.3 成果物に生成元コミットを刻む

PDF / PPTX / HTML を生成するとき、**どのコミットから生成されたかを成果物自身に埋め込む**。

- 顧客が注釈した PDF を受け取ったとき、それが**どの版に対する指摘か**が自動的に確定する
- 納品物としても「この設計書はどの版か」が特定できる。実務上もそのほうが望ましい

PDF はメタデータに加え、フッタにも短縮ハッシュを印字する運用を想定する。

### 3.4 ソースマップは、すべての出力形式で必要になる

顧客はバイトオフセットを見てコメントするわけではない。HTML の文字列を選択し、PDF の一節をハイライトする。したがって**各レンダラは「出力上の位置 → ソースのバイト範囲」の対応表（ソースマップ）を出す**必要がある。

当初は PDF 取り込みのための個別の工夫として考えていたが、バイト範囲方式に統一したことで、**全出力形式に共通の一つの仕組み**になった。

| 出力 | ソースマップの役割 |
|---|---|
| HTML | DOM 要素 → バイト範囲。選択範囲からそのままアンカーが作れる |
| PDF | ページ座標 → バイト範囲 |
| PPTX | 図形 → バイト範囲 |
| 図（SVG） | SVG のノード → `.dgm` 上のバイト範囲 |

最後の行が効いている。**図のノードへのコメントも、表のセルへのコメントも、特別扱いが要らない。**どちらも「ソースファイルのこのバイト範囲」に帰着し、エンジニアが実際に編集する箇所を直接指す。要素種別ごとにアンカーの型を分ける必要が無くなった。

## 4. コメントはどこに置くか — サイドカーファイル

本文ファイルには**書かない**。レビューラウンド単位のサイドカーに置く。

```
docs/
  auth-design.docmlx
reviews/
  2026-10-01-customer.review.yml
```

理由は [作図モデル設計案](diagram-model.md) の 3 層分離とまったく同じ原則である。**生成物・注釈が本文を侵食してはならない**。

サイドカーにすることで副次的に次が得られる。

- コメントが **Git 管理下のテキスト**になる。差分が読める
- エンジニアは **PR の中で顧客の指摘を見られる**。別システムを開かなくてよい
- **レビューラウンドがファイルという単位を持つ**。開始・指摘・回答・完了というライフサイクルが自然に表現される

## 5. これは「指摘管理表」そのものである

日本の設計レビュー実務には**指摘管理表**という定着した様式がある。指摘 No / 指摘内容 / 対象箇所 / 回答 / 対応状況 / 完了日 を並べた Excel が典型。

`*.review.yml` は、**この指摘管理表を自動アンカー付き・Git 管理下にしたもの**に他ならない。従来の指摘管理表が抱えていた問題がそのまま解ける。

- 「対象箇所」を人が手で書く → **アンカーが自動で持つ**
- 表とドキュメントが別管理で、版が合わなくなる → **同じリポジトリ・同じコミットに載る**
- 指摘とその修正コミットが結び付かない → **PR で結び付く**

そして指摘一覧・未対応一覧は、モデルから**生成**できる（未確定要求 D12「横断一覧」と同じ仕組みに乗る）。

## 6. 顧客はどうやって書き込むのか — 三つの経路

顧客に「Git を使え」とも「新しいツールを入れろ」とも言わないことが要件なので、**成果物そのものを書き込み経路にする**。

| 経路 | 体験 | 位置づけ |
|---|---|---|
| **HTML ビューア** | 公開された HTML 上で選択してコメント。その場で反映される | Web にアクセスできる顧客向けの主経路。往復が要らない |
| **PDF 注釈の取り込み** | 顧客は普段どおり PDF に注釈を書いて返送。それを取り込む | **導入コストゼロの普遍経路。ここが肝** |
| **PPTX コメントの取り込み** | PowerPoint のコメント機能で書いて返送 | 報告会の場で出た指摘を拾う |

### PDF 経路が成立する理由

PDF 注釈はページ座標に紐づくため、本来はソースに戻せない。しかし **PDF を生成しているのは我々自身**である。したがって出力時に §3.4 のソースマップ（ページ座標 → バイト範囲）を一緒に吐けばよい。取り込み時にこれを引けば、注釈の座標から元のバイト範囲が特定できる。どの版に対する指摘かは §3.3 のとおり PDF 自身が持っている。

つまり顧客の体験は「PDF にコメントを残す」のまま一切変わらず、受け取る側では構造が復元されている。

**精度についての正直な但し書き**: テキスト選択を伴う注釈（ハイライト、下線、テキストへの注記）は高精度に解決できる。一方、フリーハンドの囲みやスタンプはページ領域にしか紐づかないため、「この要素のあたり」という粒度に落ちる。これは仕様として明記し、解決できなかったものは §7 の扱いにする。

## 7. アンカーを見失ったコメントを、絶対に落とさない

§3.2 の移送に失敗する場合がある。そのとき求められる挙動は明確である。

| 状態 | 意味 | 扱い |
|---|---|---|
| `resolved` | 差分で触られておらず、機械的に移送できた | そのまま表示 |
| `stale` | 範囲が編集された。`quote` の曖昧一致で移送した | **印を付けて表示。**「指摘後に本文が変わっている」と分かる |
| `orphaned` | 移送先が特定できない | **一覧に残し、ビルド時に警告する** |

**黙って捨ててはならない。** 顧客の指摘を静かに失うことは、このシステムで起こしてよい最悪の事故である。

`stale` を区別できることは、要素 ID 方式に対する明確な優位点である。**顧客が読んだ文章と、いまエンジニアが見ている文章が別物になっている**という、レビューで最も危険な状態を検出できる。

## 8. 解決フロー

```
顧客が指摘を書く
      ↓
*.review.yml に open として入る
      ↓
エンジニアが本文を直し、同じ PR で該当コメントに status と回答を書く
      ↓
PR がマージされる ＝ 指摘と修正が同じ履歴に載る
      ↓
顧客は次の成果物で「自分の指摘がどうなったか」を見られる
```

`status` は `open` / `resolved` / `wontfix` / `question` 程度を想定。エンジニアの回答も同じファイルに入るので、**指摘と回答が一対になって Git に残る**。

## 9. 出力の対称性が完成する

[要件定義 §4](requirements.md) で「AI は第四の読者」と整理した。R10 を入れると、**各読者に投影を出し、各読者から指摘を受け取る**という対称形になる。

| 読者 | 投影（出力） | 指摘の経路（入力） |
|---|---|---|
| 画面で読む人 | HTML | Web ビューアのコメント |
| 印刷・納品する人 | PDF | PDF 注釈の取り込み |
| 報告を受ける人 | PPTX | PowerPoint コメントの取り込み |
| AI | 構造化コンテキスト | （将来: AI レビュー結果の取り込み） |
| エンジニア | リポジトリそのもの | Pull Request |

出力だけの一方通行だったものが、**双方向**になる。
