# レビューモデル設計案 — Git を使わない参加者のレビュー

作成: 2026-09-20 / 対象: 要求 D8（レビューのコメント・会話）への回答
関連: [要件定義](requirements.md) / [Excel 脱却要求の整理](../docs/research/excel-migration-japan.md) / [作図モデル設計案](diagram-model.md)

## 0. 決定事項（ロック済み）

- **レビュアは二種類いる**という前提を置く。
  - **エンジニア** → **Git の Pull Request でレビューする**。製品として独自のレビュー機能は持たない。
  - **顧客・業務部門** → **成果物に直接コメントを書く**。PDF に注釈を残すのと同じ体験。
- これを **R10「Git を使わない参加者がレビューできること」** として要件に加える。

## 1. なぜ PDF コメントが正解に見えるのか

顧客レビューにおける PDF 注釈は、次の点で完成している。

- **学習コストがゼロ。** 誰でもやり方を知っている。
- **導入コストがゼロ。** アカウント作成もツール導入も要らない。顧客の情シスの協力が要らないことは、実務上きわめて大きい。
- **本文を壊さない。** 注釈は content の外側に付く。顧客が原本を書き換えてしまう事故が起きない。
- **位置が明示される。** 「3 章のあの表の話」ではなく、その場所に紐づく。

Markdown + Git が顧客レビューで負けるのは、この 4 つをどれも満たせないからである。Wiki 設計書に流れる事例があるのも同じ理由（「第三者が内容にコメントを残せる」ことが Wiki の利点として明確に挙げられている）。

## 2. しかし PDF 注釈には致命的な欠陥がある

**注釈がページ座標に固定されている。**

その結果、次の周知の苦痛が起きる。

1. `v1.pdf` に顧客が 40 件コメントする
2. 指摘を反映して `v2.pdf` を再生成する
3. ページ割りが変わり、**40 件のコメントはどこにも紐づかなくなる**
4. 人力で突き合わせ直す。あるいは Excel の指摘管理表に手で転記する

**レンダリング結果に注釈を固定していることが原因**であり、PDF という形式の本質的な限界である。

## 3. 解 — 注釈はレンダリングではなく「モデル」に固定する

DocPresenter は中間モデル `.docmlx` を持ち、その要素は**安定した人間可読 ID** を持つ（[要件定義 §2-2](requirements.md)）。したがって注釈を**ページ座標ではなくモデル上のアンカー**に付けられる。

```yaml
anchor:
  node: sec-auth/tbl-role-matrix   # モデル上の要素 ID
  cell: [3, 2]                     # 表なら、さらにセル単位
  quote: "管理者は全ロールを編集できる"   # アンカー喪失時の手掛かり（§6）
```

これが成立すると、次がすべて手に入る。

| | PDF 注釈 | モデルアンカー |
|---|---|---|
| 再生成してもコメントが残る | ✗ | **○** |
| ページ割り変更に耐える | ✗ | **○** |
| 同じコメントを HTML でも PDF でも PPTX でも表示できる | ✗ | **○** |
| 表のセル単位・図のノード単位で指せる | ✗ | **○** |
| 指摘と、それを解決したコミットが同じ履歴に載る | ✗ | **○** |

**これは中間モデルを持つ設計だからこそ出てくる帰結**であり、Markdown を直接各形式に変換する先行事例には実装する場所が無い。

## 4. コメントはどこに置くか — サイドカーファイル

本文ファイルには**書かない**。レビューラウンド単位のサイドカーに置く。

```
docs/
  auth-design.docmlx
reviews/
  2026-10-01-customer.review.yml
```

理由は [作図モデル設計案](diagram-model.md) の 3 層分離とまったく同じ原則である。**生成物・注釈が本文を侵食してはならない**。

サイドカーにすることで副次的に次が得られる。

- コメントが **Git 管理下のテキスト**になる。差分が読める
- エンジニアは **PR の中で顧客の指摘を見られる**。別システムを開かなくてよい
- **レビューラウンドがファイルという単位を持つ**。開始・指摘・回答・完了というライフサイクルが自然に表現される

## 5. これは「指摘管理表」そのものである

日本の設計レビュー実務には**指摘管理表**という定着した様式がある。指摘 No / 指摘内容 / 対象箇所 / 回答 / 対応状況 / 完了日 を並べた Excel が典型。

`*.review.yml` は、**この指摘管理表を自動アンカー付き・Git 管理下にしたもの**に他ならない。従来の指摘管理表が抱えていた問題がそのまま解ける。

- 「対象箇所」を人が手で書く → **アンカーが自動で持つ**
- 表とドキュメントが別管理で、版が合わなくなる → **同じリポジトリ・同じコミットに載る**
- 指摘とその修正コミットが結び付かない → **PR で結び付く**

そして指摘一覧・未対応一覧は、モデルから**生成**できる（未確定要求 D12「横断一覧」と同じ仕組みに乗る）。

## 6. 顧客はどうやって書き込むのか — 三つの経路

顧客に「Git を使え」とも「新しいツールを入れろ」とも言わないことが要件なので、**成果物そのものを書き込み経路にする**。

| 経路 | 体験 | 位置づけ |
|---|---|---|
| **HTML ビューア** | 公開された HTML 上で選択してコメント。その場で反映される | Web にアクセスできる顧客向けの主経路。往復が要らない |
| **PDF 注釈の取り込み** | 顧客は普段どおり PDF に注釈を書いて返送。それを取り込む | **導入コストゼロの普遍経路。ここが肝** |
| **PPTX コメントの取り込み** | PowerPoint のコメント機能で書いて返送 | 報告会の場で出た指摘を拾う |

### PDF 経路が成立する理由

PDF 注釈はページ座標に紐づくため、本来はモデルに戻せない。しかし **PDF を生成しているのは我々自身**である。したがって出力時に**座標 → モデルアンカーの対応表（PDF 用ソースマップ）を一緒に吐けばよい**。取り込み時にこれを引けば、注釈の座標から元の要素が特定できる。

つまり顧客の体験は「PDF にコメントを残す」のまま一切変わらず、受け取る側では構造が復元されている。

**精度についての正直な但し書き**: テキスト選択を伴う注釈（ハイライト、下線、テキストへの注記）は高精度に解決できる。一方、フリーハンドの囲みやスタンプはページ領域にしか紐づかないため、「この要素のあたり」という粒度に落ちる。これは仕様として明記し、解決できなかったものは §7 の扱いにする。

## 7. アンカーを見失ったコメントを、絶対に落とさない

本文が編集され、アンカー先の要素が消えることは必ず起きる。このとき求められる挙動は明確である。

1. **ID が生きていれば** それで解決する
2. **ID が消えていれば**、`quote` に保存した引用で近傍を曖昧一致させる（GitHub が outdated なレビューコメントを扱うのと同じ考え方）
3. **それも失敗したら**、コメントを **`orphaned`（宙に浮いた指摘）として明示的に surface する**

**黙って捨ててはならない。** 顧客の指摘を静かに失うことは、このシステムで起こしてよい最悪の事故である。未解決アンカーはビルド時に警告として出し、一覧に残す。

## 8. 解決フロー

```
顧客が指摘を書く
      ↓
*.review.yml に open として入る
      ↓
エンジニアが本文を直し、同じ PR で該当コメントに status と回答を書く
      ↓
PR がマージされる ＝ 指摘と修正が同じ履歴に載る
      ↓
顧客は次の成果物で「自分の指摘がどうなったか」を見られる
```

`status` は `open` / `resolved` / `wontfix` / `question` 程度を想定。エンジニアの回答も同じファイルに入るので、**指摘と回答が一対になって Git に残る**。

## 9. 出力の対称性が完成する

[要件定義 §4](requirements.md) で「AI は第四の読者」と整理した。R10 を入れると、**各読者に投影を出し、各読者から指摘を受け取る**という対称形になる。

| 読者 | 投影（出力） | 指摘の経路（入力） |
|---|---|---|
| 画面で読む人 | HTML | Web ビューアのコメント |
| 印刷・納品する人 | PDF | PDF 注釈の取り込み |
| 報告を受ける人 | PPTX | PowerPoint コメントの取り込み |
| AI | 構造化コンテキスト | （将来: AI レビュー結果の取り込み） |
| エンジニア | リポジトリそのもの | Pull Request |

出力だけの一方通行だったものが、**双方向**になる。

## 10. 未確定事項

- **HTML ビューアのホスティング形態** — 静的ファイルで完結させるか、コメント収集のためにサーバを持つか。ErCreator の「データを外に出さない」訴求との整合をどう取るか
- **同時編集・会話性** — Wiki の利点として挙がっていたもう一つ（複数人が会話しながら同時編集）までを狙うか、コメントの往復に留めるか
- **承認（承認印に相当するもの）** — レビューラウンドに承認ステータスを持たせるか
- **ID 安定性の担保** — アンカーが依存する以上、本文編集時に ID をどう維持するかはモデル設計側の必須課題
