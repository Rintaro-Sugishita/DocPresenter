# レビューモデル設計案 — Git を使わない参加者のレビュー

作成: 2026-09-20 / 対象: 要求 D8（レビューのコメント・会話）への回答
関連: [要件定義](requirements.md) / [Excel 脱却要求の整理](../docs/research/excel-migration-japan.md) / [作図モデル設計案](diagram-model.md)

## 0. 決定事項（ロック済み）

- **レビュアは二種類いる**という前提を置く。
  - **エンジニア** → **Git の Pull Request でレビューする**。製品として独自のレビュー機能は持たない。
  - **顧客・業務部門** → **成果物に直接コメントを書く**。PDF に注釈を残すのと同じ体験。
- これを **R10「Git を使わない参加者がレビューできること」** として要件に加える。
- **注釈のアンカーは「コミットハッシュ ＋ ファイル ＋ バイト範囲 ＋ 引用テキスト」とする**（§3）。モデル要素 ID 方式は採らない。
- **注釈レコードは append-only。** 現在の版での位置は保存せず、読むたびに Git 差分から導出する。
- **全出力形式がソースマップを出す**（§3.4）。図・表を含め、アンカーの型は一つに統一する。
- **コメントは「指摘元の文書」に閉じる**（§3.5）。共有要素へのコメントが、それを参照する他の文書に現れることはない。

## 1. なぜ PDF コメントが正解に見えるのか

顧客レビューにおける PDF 注釈は、次の点で完成している。

- **学習コストがゼロ。** 誰でもやり方を知っている。
- **導入コストがゼロ。** アカウント作成もツール導入も要らない。顧客の情シスの協力が要らないことは、実務上きわめて大きい。
- **本文を壊さない。** 注釈は content の外側に付く。顧客が原本を書き換えてしまう事故が起きない。
- **位置が明示される。** 「3 章のあの表の話」ではなく、その場所に紐づく。

Markdown + Git が顧客レビューで負けるのは、この 4 つをどれも満たせないからである。Wiki 設計書に流れる事例があるのも同じ理由（「第三者が内容にコメントを残せる」ことが Wiki の利点として明確に挙げられている）。

## 2. しかし PDF 注釈には致命的な欠陥がある

**注釈がページ座標に固定されている。**

その結果、次の周知の苦痛が起きる。

1. `v1.pdf` に顧客が 40 件コメントする
2. 指摘を反映して `v2.pdf` を再生成する
3. ページ割りが変わり、**40 件のコメントはどこにも紐づかなくなる**
4. 人力で突き合わせ直す。あるいは Excel の指摘管理表に手で転記する

**レンダリング結果に注釈を固定していることが原因**であり、PDF という形式の本質的な限界である。

## 3. 解 — 注釈は「コミットハッシュ＋ファイル＋バイト範囲」に固定する

注釈が持つのは次の四つだけでよい。

```yaml
- id: 12
  anchor:
    commit: a3f9c21                       # 指摘時点のコミットハッシュ
    file:   shared/system-architecture.dgm  # 指摘対象のファイル（外部要素のこともある）
    start:  1204                          # バイトオフセット（開始）
    end:    1260                          # バイトオフセット（終了）
    quote:  "auth-api"                    # その範囲に実際にあったテキスト
  context:
    document: docs/auth-design.md         # 指摘者が見ていた文書（§3.5）
  body: "認証 API は別チームの管理なので、ここは点線で示してほしい"
  status: open
```

### なぜこれで十分か

**コミットハッシュが付いている時点で、その範囲は永久に正しい。** `a3f9c21` の `docs/auth-design.md` の 4821〜4907 バイト目が何であったかは、Git がある限り未来永劫確定している。**アンカーは「ずれる」のではなく、その版に対しては常に正しいまま凍結される。**

ただし「その版のバイト」は、**改行を LF として読んだ本文**のバイトとする。同じコミットでも、Linux では LF、Windows（`core.autocrlf`）では CRLF で取り出されるので、作業ツリーのバイトで測ると同じ指摘が機械ごとに別の場所を指してしまう。LF で測れば、どの機械で付けた指摘も同じ範囲になり、`eol=lf` で保存されたリポジトリの中身とも一致する。製品の中では、ファイルを読んだところで LF にそろえ（ビルドの `asLf`、VS Code の WebView）、出力のソースマップ・差分の印・編集の範囲はすべてこの上で測る。CRLF のファイルに書き戻すときにだけ、範囲と挿入する文字を実際のファイルに合わせて置き直す（`spanInFile`）。

したがって注釈レコードは **append-only で、一度書いたら二度と書き換わらない**。これは [作図モデル設計案](diagram-model.md) で定めた「計算で出せるものはファイルに書かない」規律とも一致する。現在の版のどこに当たるかは**読むたびに導出する**（§3.2）のであって、保存はしない。

### 3.1 モデル要素 ID 方式を採らない理由

当初は「モデル上の要素 ID に固定する」案を検討したが、**バイト範囲方式のほうが優れている**と判断する。

| | 要素 ID 方式 | **コミット＋バイト範囲** |
|---|---|---|
| ID 安定性の担保 | **必須。しかも未解決の難問** | **不要。問題自体が消える** |
| 対象ファイル | モデルを持つファイルのみ | **任意のテキストファイル**（`.md` / `.dgm` / `.table` / 参照先のソースコードまで） |
| 指摘時点の内容の再現 | **保証されない**（ID が同じでも中身が変わりうる） | **完全に再現できる** |
| 陳腐化の検出 | できない | `quote` の不一致で**検出できる** |
| 実装コスト | 高い | 低い |
| 前例 | 無い | **GitHub の PR レビューコメントが同じ方式**（commit_sha ＋ path ＋ 位置） |

特に三行目が重要である。要素 ID 方式は「ID が同じなら同じ場所」としか言えず、**その要素の中身が書き換わっていても気付けない**。顧客が読んだ文章と、エンジニアが見ている文章が別物になっていても、システムは平然と「解決済み」と扱ってしまう。バイト範囲＋`quote` 方式は、この食い違いを構造的に検出できる。

**この判断により、「本文編集時に ID をどう維持するか」という最優先課題は消滅する。** 作図のピン留め（`.dgm` の L2 層）は引き続き ID を使うが、それは**同一ファイル内で著者が自分で付ける ID** であり、はるかに易しい問題に縮小する。

### 3.5 コメントは指摘元の文書に閉じる

[編集 UI 設計案](editor-model.md)のとおり、図や表は外部ファイルであり、複数の文書から参照されうる。このときアンカーは参照先ファイル（例: `shared/system-architecture.dgm`）のバイト範囲になるため、**放置すると共有要素へのコメントが、それを参照するすべての文書に現れてしまう**。

これは望ましくない。ある案件のレビューで出た指摘が、無関係な別案件の設計書に表示されることになる。

> **コメントは `context.document`（指摘者が見ていた文書）に閉じる。** 表示・集計はこの文書で絞り込む。

#### ただし「影響」は閉じない

コメントの表示は閉じるが、**指摘に応じて共有要素を直せば、参照している他の文書もすべて変わる**。これは避けられない。

したがって[編集 UI 設計案 §5](editor-model.md) の**被参照の逆引き**が、ここでより重要になる。共有要素に付いた指摘に対応するときは、エディタが影響範囲を提示しなければならない。

> この図は 3 つの文書から参照されています。修正は全てに反映されます。

**コメントは閉じる。影響は閉じない。** この非対称を UI で明示することが、共有要素を安全に扱うための条件になる。

### 3.2 現在の版への移送（forward mapping）

指摘時点と現在で版が違う場合、表示のために現在位置へ移送する。**保存はせず、読むたびに導出する。**

1. `anchor.commit` から現在の HEAD までの差分を Git で辿る
2. 当該バイト範囲が**その差分で触られていなければ**、オフセットを機械的にずらして移送完了
3. 触られていれば、`quote` を現在の本文に対して曖昧一致させ、見つかればそこへ移送する（`stale` として印を付ける）
4. それも失敗すれば `orphaned`（§7）

これは Myers 差分の上に乗る**解決済みの問題**であり、Git 自身が `git blame` や `git log -L` で日常的にやっていることと同じである。「安定 ID を発明する」という未解決問題を、「差分を辿る」という既知の問題に置き換えたことが、この設計の要点。

### 3.3 成果物に生成元コミットを刻む

PDF / PPTX / HTML を生成するとき、**どのコミットから生成されたかを成果物自身に埋め込む**。

- 顧客が注釈した PDF を受け取ったとき、それが**どの版に対する指摘か**が自動的に確定する
- 納品物としても「この設計書はどの版か」が特定できる。実務上もそのほうが望ましい

PDF はメタデータに加え、フッタにも短縮ハッシュを印字する運用を想定する。

### 3.4 ソースマップは、すべての出力形式で必要になる

顧客はバイトオフセットを見てコメントするわけではない。HTML の文字列を選択し、PDF の一節をハイライトする。したがって**各レンダラは「出力上の位置 → ソースのバイト範囲」の対応表（ソースマップ）を出す**必要がある。

当初は PDF 取り込みのための個別の工夫として考えていたが、バイト範囲方式に統一したことで、**全出力形式に共通の一つの仕組み**になった。

| 出力 | ソースマップの役割 |
|---|---|
| HTML | DOM 要素 → バイト範囲。選択範囲からそのままアンカーが作れる |
| PDF | ページ座標 → バイト範囲 |
| PPTX | 図形 → バイト範囲 |
| 図（SVG） | SVG のノード → `.dgm` 上のバイト範囲 |

最後の行が効いている。**図のノードへのコメントも、表のセルへのコメントも、特別扱いが要らない。**どちらも「ソースファイルのこのバイト範囲」に帰着し、エンジニアが実際に編集する箇所を直接指す。要素種別ごとにアンカーの型を分ける必要が無くなった。

## 4. コメントはどこに置くか — サイドカーファイル

本文ファイルには**書かない**。レビューラウンド単位のサイドカーに置く。

```
docs/
  auth-design.md
reviews/
  2026-10-01-customer.review.yml
```

理由は [作図モデル設計案](diagram-model.md) の 3 層分離とまったく同じ原則である。**生成物・注釈が本文を侵食してはならない**。

サイドカーにすることで副次的に次が得られる。

- コメントが **Git 管理下のテキスト**になる。差分が読める
- エンジニアは **PR の中で顧客の指摘を見られる**。別システムを開かなくてよい
- **レビューラウンドがファイルという単位を持つ**。開始・指摘・回答・完了というライフサイクルが自然に表現される

## 5. これは「指摘管理表」そのものである

日本の設計レビュー実務には**指摘管理表**という定着した様式がある。指摘 No / 指摘内容 / 対象箇所 / 回答 / 対応状況 / 完了日 を並べた Excel が典型。

`*.review.yml` は、**この指摘管理表を自動アンカー付き・Git 管理下にしたもの**に他ならない。従来の指摘管理表が抱えていた問題がそのまま解ける。

- 「対象箇所」を人が手で書く → **アンカーが自動で持つ**
- 表とドキュメントが別管理で、版が合わなくなる → **同じリポジトリ・同じコミットに載る**
- 指摘とその修正コミットが結び付かない → **PR で結び付く**

そして指摘一覧・未対応一覧は、モデルから**生成**できる（未確定要求 D12「横断一覧」と同じ仕組みに乗る）。

## 6. 顧客はどうやって書き込むのか — 三つの経路

顧客に「Git を使え」とも「新しいツールを入れろ」とも言わないことが要件なので、**成果物そのものを書き込み経路にする**。

| 経路 | 体験 | 位置づけ |
|---|---|---|
| **HTML ビューア** | 公開された HTML 上で選択してコメント。その場で反映される | Web にアクセスできる顧客向けの主経路。往復が要らない |
| **PDF 注釈の取り込み** | 顧客は普段どおり PDF に注釈を書いて返送。それを取り込む | **導入コストゼロの普遍経路。ここが肝** |
| **PPTX コメントの取り込み** | PowerPoint のコメント機能で書いて返送 | 報告会の場で出た指摘を拾う |

### PDF 経路が成立する理由

PDF 注釈はページ座標に紐づくため、本来はソースに戻せない。しかし **PDF を生成しているのは我々自身**である。したがって出力時に §3.4 のソースマップ（ページ座標 → バイト範囲）を一緒に吐けばよい。取り込み時にこれを引けば、注釈の座標から元のバイト範囲が特定できる。どの版に対する指摘かは §3.3 のとおり PDF 自身が持っている。

つまり顧客の体験は「PDF にコメントを残す」のまま一切変わらず、受け取る側では構造が復元されている。

**精度についての正直な但し書き**: テキスト選択を伴う注釈（ハイライト、下線、テキストへの注記）は高精度に解決できる。一方、フリーハンドの囲みやスタンプはページ領域にしか紐づかないため、「この要素のあたり」という粒度に落ちる。これは仕様として明記し、解決できなかったものは §7 の扱いにする。

## 7. アンカーを見失ったコメントを、絶対に落とさない

§3.2 の移送に失敗する場合がある。そのとき求められる挙動は明確である。

| 状態 | 意味 | 扱い |
|---|---|---|
| `resolved` | 差分で触られておらず、機械的に移送できた | そのまま表示 |
| `stale` | 範囲が編集された。`quote` の曖昧一致で移送した | **印を付けて表示。**「指摘後に本文が変わっている」と分かる |
| `orphaned` | 移送先が特定できない | **一覧に残し、ビルド時に警告する** |

**黙って捨ててはならない。** 顧客の指摘を静かに失うことは、このシステムで起こしてよい最悪の事故である。

`stale` を区別できることは、要素 ID 方式に対する明確な優位点である。**顧客が読んだ文章と、いまエンジニアが見ている文章が別物になっている**という、レビューで最も危険な状態を検出できる。

## 8. 解決フロー

```
顧客が指摘を書く
      ↓
*.review.yml に open として入る
      ↓
エンジニアが本文を直し、同じ PR で該当コメントに status と回答を書く
      ↓
PR がマージされる ＝ 指摘と修正が同じ履歴に載る
      ↓
顧客は次の成果物で「自分の指摘がどうなったか」を見られる
```

`status` は `open` / `resolved` / `wontfix` / `question` 程度を想定。エンジニアの回答も同じファイルに入るので、**指摘と回答が一対になって Git に残る**。

## 9. 出力の対称性が完成する

[要件定義 §4](requirements.md) で「AI は第四の読者」と整理した。R10 を入れると、**各読者に投影を出し、各読者から指摘を受け取る**という対称形になる。

| 読者 | 投影（出力） | 指摘の経路（入力） |
|---|---|---|
| 画面で読む人 | HTML | Web ビューアのコメント |
| 印刷・納品する人 | PDF | PDF 注釈の取り込み |
| 報告を受ける人 | PPTX | PowerPoint コメントの取り込み |
| AI | 構造化コンテキスト | （将来: AI レビュー結果の取り込み） |
| エンジニア | リポジトリそのもの | Pull Request |

出力だけの一方通行だったものが、**双方向**になる。

## 9.5 実装したもの — PDF 注釈の取り込み（2026-10-08）

§6 の「PDF 注釈の取り込み」経路を実装した。HTML ビューアと PPTX コメントはまだ。

**PDF は自分の出どころを添付ファイルとして持つ。** 書き出すとき、`docpresenter-review.json` を
PDF の添付ファイル（EmbeddedFiles）として入れる（`packages/pdf/src/review.ts`）。中身は次の 3 つ。

| 入れるもの | 何のため |
|---|---|
| 印字した各行の位置と、その行が来た**ファイルとバイト範囲** | 注釈の座標から元の場所を引く（§3.4 のソースマップ） |
| 文書が使った**全ファイルの本文**（LF で読んだもの） | 取り込むときに Git を引かずに、注釈の語をソースの中で探せる |
| 文書のパス・コミット・作業ツリーがそのコミットと同じだったか | §3.3。未コミットの変更を含む版から作ったなら、アンカーに `uncommitted: true` と書く |

ページの座標にではなく添付ファイルにしたのは、**閲覧ソフトが注釈を付けて保存し直しても残る、
PDF の標準の入れ物**だからである。コミットは従来どおりキーワード（`commit:…`）にも入る。

**注釈は、できるだけ細かく戻す。** 精度は 3 段階で、レビューファイルの `source.precision` に書く。

| 注釈 | 戻り先 | 精度 |
|---|---|---|
| ハイライト・下線など、語に付けたもの | その**語のバイト範囲**。図や表の中の語なら、取り込んだ `.dgm` / `.table` の中の範囲 | `text` |
| 付箋・囲み・フリーハンドなど、場所に付けたもの | 下（付箋なら隣）の**段落や図表の全体** | `block` |
| 何も印字していない場所のもの | 場所なし。`status: orphaned` として**必ず残す**（§7） | `none` |

語を探すときは、ページに出ない文字（空白・改行・`**` などの書式記号）を飛ばして一致させる。
同じ段落に同じ語が 2 回あるときは、どちらか決められないので段落全体に留める。

**レビューファイルには後ろに足すだけ。** `reviews/<日付>-<PDF 名>.review.yml` を作るか、
既にあるものを選んで追記する（`packages/pdf/src/review-file.ts`）。前の行は 1 バイトも変えない。
同じ PDF の同じ注釈は二度入らない。返信（PDF の `IRT`）は元の指摘の `replies:` に入る。

入口は VS Code のコマンド「PDF の注釈を指摘として取り込む…」（`.pdf` の右クリックにも）と、
`node tools/pdf-review.mjs <pdf> [--into <file>] [--write]`。検証は `tools/check-pdf-review.mjs`
（サンプルの実際の PDF に、pdf.js が語を見つけた位置へ注釈を置いて取り込む）。

**まだ確かめていないこと:** 実際の閲覧ソフト（Edge / Acrobat）で注釈を付けて保存し直した PDF が、
添付ファイルを残すか。残さない閲覧ソフトでは、注釈は読めるが場所が無くなる（`orphaned` として入る）。

## 9.6 実装したもの — 編集と閲覧（レビュー）のモード（2026-10-09）

VS Code の DocPresenter の画面に、**編集**と**閲覧（レビュー）**の 2 つのモードを置いた。上の帯で切り替え、
エディタごとに覚える。

| | 編集 | 閲覧（レビュー） |
|---|---|---|
| 本文を押す | そのブロックが開いて書ける | 文字を選べる（何も開かない） |
| 指摘の印 | 「指摘の印」で出す／消す（既定は出す） | いつも出す |
| 印にマウスを合わせる | 指摘・回答・状態が出る | 同じ |
| 指摘の一覧 | 出さない | 横に出す。押すとその箇所へ |
| 指摘を付ける | — | 本文を選ぶ →「指摘を追加」 |
| 挿入・改名・タブの追加など | できる | 出さない |

**今の位置（§3.2）。** 指摘のアンカーを今のファイルの中で探す（`packages/base/src/anchor.ts` の `locateAnchor`）。

1. 指摘したコミットのファイルが手に入るなら（`git show <commit>:<file>`）、その版と今の版の行の差分をたどる。
   範囲の行が書き換えられていなければ、それが答え（同じ語が何か所あっても取り違えない）。
2. そうでなければ `quote` を探す。見つかれば `moved`。空白や `**` の違いは同じ語として扱う。
3. 語そのものが書き換えられていれば、`quote` の残っている部分に付け、**「指摘のあとで本文が変わっています」**
   と出す（`changed`、§7 の `stale`）。
4. 何も残っていなければ `lost`（§7 の `orphaned`）。一覧には「場所が見つからない」として残す。

印は語そのものに付ける。図や表のファイルへの指摘は、その図表の中の語（表のセル、図形の文字）に付け、
見つからなければ図表を枠で囲む。取り込んだ別の `.md`（改訂履歴など）の中への指摘は、取り込みの枠に付ける。

**画面で付けた指摘。** 選んだ語に、PDF の注釈と同じ規則でアンカーを付ける（`narrowAnchor`。図の中の語なら
`.dgm` / `.table` の中）。最初の 1 件で書き込むレビューファイルを選ばせ、以後そのエディタではそこへ足す。
コミット・作者（`git config user.name`）・日時を付け、ファイルがそのコミットと違えば `uncommitted: true` を付ける。
書くのはファイルの後ろだけ（`source.via: editor`）。

**状態と回答も画面から（2026-10-12）。** 閲覧モードの一覧の各指摘に、状態（未対応 / 対応済み / 対応しない / 質問）の
選択と「回答を書く」がある。書き換えるのは、レビューファイルのその指摘の `status:` と `reply:` の行だけ
（`updateReviewEntry`）。複数行の回答（`reply: |`）はまるごと置き換え、空にすると回答の行を消す。
書いた回答は、次に書き出す PDF に返信として載る（§9.7）。

## 9.7 実装したもの — PDF での往復（2026-10-09）

顧客は Git も VS Code も使わないので、**回答は PDF で届け、返信も PDF で受け取る**（サーバを立てる案 B は後回し）。

**書き出す PDF に、ここまでのレビューを載せる。** その文書への指摘（`context.document`）を、今の位置（§3.2）に
PDF の注釈として入れる（`packages/pdf/src/review-notes.ts`）。

- 語が分かる指摘は、その語の**ハイライト**（行をまたいでもよい）。分からなければ、その段落の横の**付箋**。
- 状態・回答（`reply:`）・前に受け取った返信（`replies:`）は、**その注釈自身の文**に「【状態】」「【回答】」
  「【返信（名前）】」の見出しを付けて書く。2026-10-12 までは返信の注釈（`IRT`）として並べていたが、
  **Edge は返信のスレッドを表示しない**ため、回答が見えなかった。注釈自身の文ならどの閲覧ソフトでも読める。
- 注釈の題（`Subj`）に状態（未対応・対応済み など）を書く。
- 載せた注釈には `dp-review:<レビューファイル>#<番号>` という名前（`NM`）を付ける。
- 場所が見つからない指摘は載せない（レビューファイルには残っている）。
- 納品用には外せる（VS Code の設定 `docpresenter.pdfReviewNotes`、CLI の `--no-review-notes`）。

**取り込むときは 3 つに分ける**（`planImport`）。

| 注釈 | 扱い |
|---|---|
| 名前が `dp-review:` で始まる | こちらが載せたもの。取り込まない |
| `dp-review:` の注釈への返信（Acrobat などのスレッド） | その指摘の**レビューファイルの、その番号の下**の `replies:` に入れる（`appendReplies`）。行を足すだけで、前の行は変えない。同じ返信は二度入らない |
| `dp-review:` の注釈の文への書き足し（Edge での返し方） | 対応表に「その注釈に書いた文」を残してあるので、それより後ろに足された文を返信として、同じく指摘の下に入れる |
| それ以外 | 新しい指摘。これまでどおり、選んだレビューファイルの後ろに足す |

これで「顧客が指摘する → エンジニアが回答を書く → 次の PDF で顧客が回答を読み、返信する → 返信が指摘の下に入る」が
PDF だけで回る。検証は `tools/check-pdf-review.mjs`（サンプルの実際の PDF に載った 4 件の注釈と、それへの返信の取り込み）。

**Edge で確かめた（2026-10-12）。** Edge で注釈を付けて保存した PDF を取り込み、位置（表のセルの語まで）も
本文も正しく入った。Edge は対応表（添付ファイル）を保存し直しても残す。

**複数の PDF をまとめて取り込める。** PDF は自分がどの文書か（パスと文書番号）を持っているので、ラウンドの
PDF を全部選んで一度に取り込めばよい。新しい指摘を入れるレビューファイルを 1 回選ぶだけで、各指摘はそれぞれの
文書に付く。返信はそれぞれの元の指摘の下へ入る。

**指摘は文書番号にも結び付く。** PDF の対応表とレビューファイル（`context.number`）に文書番号を入れ、画面と
PDF は「パスが同じ、または文書番号が同じ」指摘をその文書のものとして出す。文書を動かしたり改名したりしても
指摘は離れない（文書自身の本文へのアンカーは、今の場所の文書で探す）。このため文書番号は必須にした。

- 「新しい文書を作る」コマンドは、テンプレートの frontmatter と改訂履歴を作り、文書番号を**採番**する。
  リポジトリで使われている系列（`SD-AUTH-` など、最後の数字の前まで）ごとに次の空き番号を出し、新しい系列
  （`001` から）や自分で入力した番号も選べる。使われている番号は受け付けない。「作業場を初期化する」も同じ。
- ビルドは、同じ文書番号の文書があれば両方に、書き出す文書に番号が無ければその文書に警告を出す。
