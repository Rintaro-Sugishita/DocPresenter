# 編集 UI 設計案 — Markdown に浮く埋め込みオブジェクト

作成: 2026-09-20 / 対象: 要件 R8（Web / VS Code 双方での編集）の操作モデル
関連: [要件定義](requirements.md) / [作図モデル設計案](diagram-model.md) / [レビューモデル設計案](review-model.md)

## 0. 決定事項（ロック済み）

- **編集 UI はノートブック型**とする。1 ページに文章・図・表・画像を**混在**させ、上から下に並べる（Polyglot Notebooks / Jupyter と同じ操作感）。
- **ただし「すべてがセル」ではない。** 地は Markdown のテキストであり、**特殊形式の要素がその中に埋め込みオブジェクトとして浮く**（§3）。
- **UI はノートブック、ファイルは Markdown。** `.ipynb` のような JSON は**採らない**（§2）。
- **特殊形式の要素は Markdown に直書きせず、外部ファイルに分ける**（§4）。再利用性と専用エディタの素直さのため。
- **セルの種類ごとに最適なエディタを当てる。** 表は Excel と同じグリッド操作（§6）。

## 1. 「Excel の操作性」の正体

[Excel 脱却要求の整理 §1](../docs/research/excel-migration-japan.md) で、方眼紙の価値は「自由レイアウト」「一覧性」だと整理した。だが**操作**の観点で見ると、設計者が実際にやっていることはもっと単純である。

> **シートの上に、文章・表・図・画像を、好きな順に置いていく。**

セルという単位はレイアウトの手段であって目的ではない。「方眼紙にする」のは、異種の要素を混在させたいからであって、表計算がしたいからではない。

**上から下に並ぶ、種類の違うブロック**は、この操作感の正統な継承である。自由配置という一点だけを捨て、それ以外はそのまま残る。

## 2. 決定的な分岐 — ファイル形式に JSON を採らない

ここを間違えると、これまでの設計が全部崩れる。

**Jupyter の `.ipynb` は JSON であり、人間が読めない。** セル配列・出力・メタデータが 1 つの JSON に詰まっているため、1 文字直しただけで巨大な差分が出る。`nbdime` や `jupytext` といった道具が存在すること自体が、この形式が Git と相性最悪であることの証明である。

これは[要件定義](requirements.md)の**軸 A（ソースファイルそのものが人間に読める）と真正面から衝突する**。

> **ノートブック型の UI を採ることと、ノートブック型のファイル形式を採ることは、完全に切り離す。**

`jupytext` は `.ipynb` ⇔ `.md` の相互変換でこの問題に後から対処している。我々は**最初から Markdown を正本にする**ので、変換層すら要らない。

## 3. 地は Markdown、特殊要素は「浮く」

モデルは「全部がセル」ではない。

```
┌─────────────────────────────┐
│ 地の文（Markdown）            │  ← 普通に書く。セルという意識は無い
│                             │
│  ┏━━━━━━━━━━━━━━━━━━━━━┓    │
│  ┃ 図（埋め込みオブジェクト）┃    │  ← 浮いている。専用エディタが立つ
│  ┗━━━━━━━━━━━━━━━━━━━━━┛    │
│                             │
│ 地の文（Markdown）            │
│                             │
│  ┏━━━━━━━━━━━━━━━━━━━━━┓    │
│  ┃ 表（埋め込みオブジェクト）┃    │
│  ┗━━━━━━━━━━━━━━━━━━━━━┛    │
└─────────────────────────────┘
```

文章を書いているときはただの Markdown エディタであり、**特殊要素の位置に来たときだけ専用のエディタが立ち上がる**。Word や Excel に OLE オブジェクトが埋まっているのと同じ感覚で、文書の地の部分は最後までテキストのままである。

この区別は実装にも効く。地の文には構造を持ち込まず、**特殊要素だけを「オブジェクト」として扱えばよい**。

## 4. 特殊要素は外部ファイルに分ける

埋め込みオブジェクトの中身を Markdown に直書きせず、**別ファイルへの参照**として書く。

```markdown
## 認証フロー

ログイン時の画面遷移を以下に示す。

```dgm src="auth-design/login-flow.dgm"```

上図の ③ でセッションを発行する。
```

### なぜ外部ファイルなのか

1. **再利用できる。** システム構成図・用語集・項目定義表は複数の設計書に登場する。直書きだとコピーが増殖し、必ず食い違う。これは Excel 設計書で実際に起きている問題そのもの。
2. **専用エディタが素直に立つ。** `.dgm` を開けば作図エディタ、`.table` を開けばグリッド。VS Code のカスタムエディタは**拡張子で紐づく**ので、Markdown からフェンス領域を切り出して渡すより遥かに単純。
3. **差分が独立する。** 図の変更が 2000 行の Markdown に埋もれず、その図のファイルの変更として出る。`git log` も `git blame` もその要素単位で効く。
4. **R3（外部ファイル参照）と機構が一本化される。** 図・表を特別扱いせず、外部参照の一種として扱える。仕組みが二重化しない。
5. **並行編集で衝突しにくい。** 同じ文書の別々の図を二人が直しても、触るファイルが違う。
6. **フェンス入れ子問題が消える。** 図や表の中にコードブロックが入る場合のエスケープ規則を考えなくてよい。

### 地の文はむしろ読みやすくなる

40 行の作図ソースが本文に埋まっているより、参照 1 行のほうが**素の Markdown として読みやすい**。本文は目次のように見通せる状態を保てる。軸 A はこの選択で弱まるどころか強まる。

### インラインを許す境界

**専用エディタが要るもの・Markdown で表現できないものは、必ず外部ファイル。**
逆に**素の Markdown で書ける範囲（単純な表、箇条書き）は直書き**でよい。

| | 書き方 |
|---|---|
| 単純な表（結合なし） | Markdown テーブルを直書き |
| セル結合のある表・項目定義表 | `.table` ファイル |
| 図 | `.dgm` ファイル |
| 画像 | `assets/` の画像ファイル |

この規則は、前回未確定だった「素の Markdown テーブルと専用記法の境界をどこに引くか」への回答でもある。境界は**「専用エディタが要るか」**。

単純な表が育ってセル結合が要るようになったら、**「この表をファイルに切り出す」操作**で移行する。コードの「関数に抽出」と同じ発想。

## 5. ディレクトリ規約 — 共有かどうかをパスで表す

```
docs/
  auth-design.md
  auth-design/                  ← この文書専用の要素
    login-flow.dgm
    screen-items.table
  assets/
    login-screen.png
shared/                         ← 複数文書で再利用する要素
  system-architecture.dgm
  glossary.table
```

**パスが「共有物かどうか」を表す。** `shared/` にあるものを編集するときは他文書に影響するので、エディタは編集前に警告できる。

> この図は 3 つの文書から参照されています。

これを出すには**被参照の逆引き**が要る。共有要素を編集する際の影響範囲把握は実務上必須であり、未確定要求 **D12（横断一覧）と同じ仕組みに乗る**。

参照先が存在しない場合は**ビルドを失敗させる**。壊れた参照を黙って無視してはならない。

## 6. 埋め込みオブジェクトの種類と、当てるエディタ

| 要素 | ファイル | エディタ | 移植元（[参照実装](stack.md)） |
|---|---|---|---|
| 図 | `.dgm` | 作図キャンバス | `Canvas.Geometry` / `Pointer` / `Selection` / `Shapes` / `Rendering` |
| **表** | `.table` | **グリッドエディタ** | **`Canvas.Grid` / `Canvas.GridFields` / `ErColumnGrid`** |
| 画像 | `.png` 等 | ドロップ＋注釈オーバーレイ（§9） | 図キャンバスを流用 |
| 地の文 | `.md` | Markdown エディタ（プレビュー併走） | — |

### 表のグリッドは参照実装がある

`ErCreator.Canvas` のグリッドは既に次を備えている（[実装スタック](stack.md)のとおり、コードの再利用ではなく TypeScript への移植元として扱う）。

- **セル範囲のドラッグ選択**（Shift 不要）
- **TSV のコピー＆ペースト** — 「セルで Ctrl+V → タブ＝列・改行＝行 で複数セルに展開、不足行は自動追加」
- 列幅リサイズと保存

**Excel からコピーしてそのまま貼れる**という、「Excel の操作性を崩さない」の中核が、動く形で既に存在する。`.table` はこの操作モデルをセル結合に対応させて一般化したものになる。

なお `.dgm` の内部が「意味 / レイアウト / スタイル」のセクション分割である点は[作図モデル設計案](diagram-model.md)の決定のとおりで、本設計と矛盾しない。**ファイルを分けるのは Markdown との間**であって、`.dgm` 自体は 1 ファイルのままである。

## 7. VS Code Notebook API に乗る

VS Code は独自拡張子のノートブックを扱える（`NotebookSerializer` の実装で `.ipynb` 以外でもセル UI になる）。**Polyglot Notebooks がその実装例**である。

§4 で特殊要素を外部ファイルにしたことで、この実装はさらに素直になる。

- Markdown → セル配列のシリアライザは、**参照行を検出するだけ**でよい。中身のパースは不要
- 各セルの中身のエディタは、**拡張子に紐づくカスタムエディタ**としてそのまま再利用できる

セル UI を経由せず `.dgm` を直接開いても同じエディタが立つ。**編集器が文書の文脈に依存しない。**

## 8. 書き戻しの規律 — 触っていない部分は 1 バイトも変えない

Markdown への書き戻しが起きる以上、整形が揺れると差分が汚れ、軸 A が崩壊する。

> **編集した箇所のバイト範囲だけを置き換える。それ以外のバイトは一切触らない。**

ファイル全体を parse → 再 serialize する実装にしてはならない。引用符の種類、空行の数、表の桁揃えといった些細な差で全体が書き換わり、「1 箇所直したのに 400 行の差分」が生まれる。[作図モデル設計案](diagram-model.md)の決定論的整形の規律を、文書全体に適用するということである。

外部ファイル化により、この規律は守りやすくなる。**図を編集しても Markdown は 1 バイトも変わらない。**

副次的に[バイト範囲アンカー](review-model.md)の移送精度にも直結する。無関係な整形差分が入らなければ、既存のコメントはほぼ無傷で移送できる。

## 9. 画像と、画面設計書への応用

画像はバイナリなので Git 差分が読めない。これは避けられないため `assets/` に置き、ファイル名に意味を持たせる。

ただし一点、有効な応用がある。

> **画像の上に、注釈・番号・枠を図形レイヤとして重ねる。**

画像自体はバイナリのままだが、**重ねた注釈は `.dgm` のテキストなので差分が読める**。「どの項目に何番を振ったか」「説明をどう変えたか」が Git で追える。

これは未確定要求 **D3（画面設計書・帳票レイアウト）への回答になりうる**。画面キャプチャに番号を振り、項目説明を対応させるという画面設計書の典型的な作り方が、そのまま成立する。

## 10. 二つのビュー — 編集は要素単位、閲覧は連続

Excel の「一覧性」は、要素が縦に並ぶ UI では失われる。これに対する答えは分離である。

| | ビュー |
|---|---|
| **編集** | 要素単位。各表現に最適なエディタが立つ |
| **閲覧・レビュー** | 連続レンダリング（HTML）。俯瞰できる |

顧客が見るのは常に後者であり（[レビューモデル設計案](review-model.md)）、要素の境界は意識されない。ノートブック的な構造は**執筆者の道具**であって、読者に見せるものではない。
