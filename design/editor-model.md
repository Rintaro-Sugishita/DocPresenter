# 編集 UI 設計案 — ノートブック型のセル構成

作成: 2026-09-20 / 対象: 要件 R8（Web / VS Code 双方での編集）の操作モデル
関連: [要件定義](requirements.md) / [作図モデル設計案](diagram-model.md) / [レビューモデル設計案](review-model.md)

## 0. 決定事項（ロック済み）

- **編集 UI はノートブック型**とする。1 ページに、文章・図・表・画像という**異なる表現のセルを混在**させ、上から下に並べる（Polyglot Notebooks / Jupyter と同じ操作感）。
- **UI はセル、ファイルは Markdown。** `.ipynb` のような JSON は**採らない**（§3）。
- **セル境界は Markdown のブロック境界に一致させる**（§4）。独自のセル区切り記法は発明しない。
- **セルの種類ごとに最適なエディタを当てる。** 表セルは Excel と同じグリッド操作（§5）。

## 1. 「Excel の操作性」の正体

[Excel 脱却要求の整理 §1](../docs/research/excel-migration-japan.md) で、方眼紙の価値は「自由レイアウト」「一覧性」だと整理した。だが**操作**の観点で見ると、設計者が実際にやっていることはもっと単純である。

> **シートの上に、文章・表・図・画像を、好きな順に置いていく。**

セルという単位はレイアウトの手段であって目的ではない。「方眼紙にする」のは、異種の要素を好きな位置に混在させたいからであって、表計算がしたいからではない。

**ノートブックのセル ＝ 上から下に並ぶ、種類の違うブロック**は、この操作感の正統な継承である。自由配置という一点だけを捨て、それ以外はそのまま残る。

## 2. なぜノートブック型が適合するのか

| 要求 | ノートブック型での解決 |
|---|---|
| 異種要素の混在 | セルの種類を混ぜられる。これがそのもの |
| **表を Excel と同じ操作で書きたい** | 表セルに**グリッドエディタ**を当てる（§5）。R7 の実現手段そのもの |
| 図を描きたい | 図セルにキャンバスを当てる。[作図モデル設計案](diagram-model.md) がそのまま乗る |
| テキストは軽快に書きたい | 文章セルは素の Markdown エディタ |
| Web と VS Code の両方 | VS Code は Notebook API を持つ（§6） |

R7（複雑テーブル）については特に効く。**セル結合のある表をテキストで手書きするのは苦痛**だが、グリッド UI なら Excel と同じ操作で作れる。そして保存形式は人間可読なテキストのまま保てる。これは「表をモデルとして持ち、記法は入力手段の一つにする」という既定方針の、UI 側の答えである。

## 3. 決定的な分岐 — ファイル形式に JSON を採らない

ここを間違えると、これまでの設計が全部崩れる。

**Jupyter の `.ipynb` は JSON であり、人間が読めない。** セル配列・出力・メタデータが 1 つの JSON に詰まっているため、1 文字直しただけで巨大な差分が出る。`nbdime` や `jupytext` といった道具が存在すること自体が、この形式が Git と相性最悪であることの証明である。

これは[要件定義](requirements.md)の**軸 A（ソースファイルそのものが人間に読める）と真正面から衝突する**。

したがって、

> **ノートブック型 UI を採ることと、ノートブック型のファイル形式を採ることは、完全に切り離す。**

`jupytext` は `.ipynb` ⇔ `.md` の相互変換でこの問題に後から対処している。我々は**最初から Markdown を正本にする**ので、変換層すら要らない。

## 4. セル境界 ＝ Markdown のブロック境界

これは発明ではなく**発見**である。Markdown はもともとブロック構造を持っている。ノートブック UI は、その既存の構造を視覚化しているにすぎない。

| セルの種類 | Markdown 上の表現 |
|---|---|
| 文章 | 地の文（そのまま） |
| 図 | ` ```dgm ` フェンスドコードブロック |
| 表 | ` ```table ` フェンス、または素の Markdown テーブル |
| 画像 | `![...](assets/...)` |

フェンスドコードブロックは既存の Markdown 構文であり、**Mermaid が ` ```mermaid ` で既に同じ方式を普及させている**。独自記法を発明する必要がない。

この一致から、次がすべて自動的に手に入る。

- **ファイルは普通の Markdown。** 人間が読め、AI が読め、Git の差分が読める（軸 A・軸 B）
- **GitHub でもそのまま読める。** UI が無い環境でも劣化しない
- **エディタを選ばない。** ノートブック UI を使わず、素のテキストエディタで編集してもよい
- **[バイト範囲アンカー](review-model.md)と自然に噛み合う。** セルは Markdown 上の連続したバイト範囲なので、「このセルへのコメント」は特別扱い不要

## 5. セルの種類と、当てるエディタ

| セル | エディタ | ErCreator からの再利用 |
|---|---|---|
| 文章 | Markdown テキストエディタ（プレビュー併走） | — |
| **表** | **グリッドエディタ** | **`Canvas.Grid` / `Canvas.GridFields` / `ErColumnGrid`** |
| 図 | 作図キャンバス | `Canvas.Geometry` / `Pointer` / `Selection` / `Shapes` / `Rendering` |
| 画像 | ドロップ＋注釈オーバーレイ（§8） | 図キャンバスを流用 |

### 表セルは、ほぼそのまま既存資産が使える

`ErCreator.Canvas` のグリッドは既に次を備えている。

- **セル範囲のドラッグ選択**（Shift 不要）
- **TSV のコピー＆ペースト** — 「セルで Ctrl+V → タブ＝列・改行＝行 で複数セルに展開、不足行は自動追加」
- 列幅リサイズと保存

**Excel からコピーしてそのまま貼れる**という、「Excel の操作性を崩さない」の中核がすでに実装済みである。DocPresenter の表セルは、この操作モデルをセル結合に対応させて一般化したものになる。

## 6. VS Code Notebook API に乗る

VS Code は独自拡張子のノートブックを扱える（`NotebookSerializer` を実装すれば `.ipynb` 以外でもセル UI で開ける）。**Polyglot Notebooks がまさにその実装例**である。

したがって VS Code 拡張は、セル UI をゼロから作るのではなく **Markdown ⇔ セル配列のシリアライザを書けばよい**。§4 でセル境界を Markdown のブロック境界に一致させたので、この変換は素直に書ける。

セルの中身のエディタ（グリッド・キャンバス）は、[サーバの位置づけ §7](server-architecture.md) のとおり WebView 上の Blazor キャンバスを共有する。**Web・デスクトップ・VS Code の三面が単一実装**という構図は維持される。

## 7. 書き戻しの規律 — 触っていないセルは 1 バイトも変えない

セル UI で編集する以上、Markdown への書き戻しが常に起きる。ここで整形が揺れると差分が汚れ、軸 A が崩壊する。

> **編集したセルのバイト範囲だけを置き換える。それ以外のバイトは一切触らない。**

ファイル全体を parse → 再 serialize する実装にしてはならない。引用符の種類、空行の数、表の桁揃えといった些細な差で全体が書き換わり、「1 箇所直したのに 400 行の差分」が生まれる。これは[作図モデル設計案](diagram-model.md)の決定論的整形の規律と同じものを、文書全体に適用するということである。

副次的に、これは[バイト範囲アンカー](review-model.md)の移送精度にも直結する。無関係な整形差分が入らなければ、既存のコメントはほぼ無傷で移送できる。

## 8. 画像セルと、画面設計書への応用

画像はバイナリなので Git 差分が読めない。これは避けられないため、**画像は外部ファイル参照**（R3）として `assets/` に置き、ファイル名に意味を持たせる。

ただし一点、有効な応用がある。

> **画像の上に、注釈・番号・枠を図形レイヤとして重ねる。**

画像自体はバイナリのままだが、**重ねた注釈は `.dgm` のテキストなので差分が読める**。「どの項目に何番を振ったか」「説明をどう変えたか」が Git で追える。

これは未確定要求 **D3（画面設計書・帳票レイアウト）への回答になりうる**。画面キャプチャに番号を振り、項目説明を対応させるという画面設計書の典型的な作り方が、そのまま成立する。

## 9. 二つのビュー — 編集はセル、閲覧は連続

Excel の「一覧性」は、セルが縦に並ぶ UI では失われる。これに対する答えは分離である。

| | ビュー |
|---|---|
| **編集** | セル単位。各表現に最適なエディタが立つ |
| **閲覧・レビュー** | 連続レンダリング（HTML）。俯瞰できる |

顧客が見るのは常に後者であり（[レビューモデル設計案](review-model.md)）、セルの存在は意識されない。セルは**執筆者の道具**であって、読者に見せる構造ではない。

## 10. 未確定事項

- **文章セルの粒度** — フェンス以外の連続した地の文を 1 セルにまとめるか、見出しごとに分けるか。前者は素直だが長大なセルが生まれる。見出しで折り畳む UI で足りるか要検証
- **セル種別の拡張性** — ` ```dgm ` / ` ```table ` 以外（OpenAPI、SQL、状態遷移表など）を後から足せる仕組みにするか。Polyglot Notebooks の「言語ごとにカーネルを切り替える」構造が参考になる
- **表セルの記法** — 素の Markdown テーブルで済む範囲と、セル結合を伴う ` ```table ` の境界をどこに引くか。両方を許すと表現が二重化する
- **フェンス内のフェンス** — 図や表のセル内にコードブロックが入る場合のエスケープ規則
