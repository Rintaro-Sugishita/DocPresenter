# 横断一覧設計案 — インデックスと一覧生成

作成: 2026-09-21 / 対象: 要求 D12（横断一覧・トレーサビリティ）の要件化
関連: [参照記法](reference-syntax.md) / [編集 UI](editor-model.md) / [レビューモデル](review-model.md) / [表モデル](table-model.md)

## 0. 決定事項（ロック済み）

- **D12 を要件 R12「横断一覧とトレーサビリティの生成」として要件化する。**
- 実体は **「ビルド時に全文書・全要素を走査したインデックス」と「そこからの一覧生成」**（§2）。
- **トレーサビリティは [R11](reference-syntax.md) のラベルと参照グラフにそのまま乗る**（§4）。新しい関係記法は作らない。
- 一覧は **生成物であり、文書に書かない**（[P1](decisions.md)）。

## 1. なぜ要件化するのか

保留のまま進めてきたが、**すでに 5 つの機能が「D12 と同じ仕組みに乗る」として設計されている**。

| 依存している機能 | 出典 |
|---|---|
| 凡例の文書単位集計 | [表モデル §5.1](table-model.md) |
| 共有要素の被参照警告 | [編集 UI §5](editor-model.md) |
| 図表一覧の自動生成 | [参照記法 §7.2](reference-syntax.md) |
| 相互参照の逆引き | [参照記法 §7.8](reference-syntax.md) |
| 目次の生成 | [テーマ §6.3](theme.md) |

さらに重要なことに、**[P6「黙って捨てない」](decisions.md)で約束した診断の実装基盤でもある**。

- 壊れた参照でビルドを失敗させる
- フォントに無い字を検出する
- アンカーを失ったコメントを surface する

これらはすべて「全体を走査して集めた結果」がなければ実装できない。
**D12 は利用者向け機能である前に、既に約束した挙動を支える基盤である。**

## 2. インデックスが持つもの

ビルド時に文書群を走査し、次を集める。

| 種別 | 内容 |
|---|---|
| 要素 | ファイル・種別・ラベル・キャプション・採番結果・バイト範囲 |
| 見出し | 階層・ラベル・採番結果 |
| **参照関係** | どの文書がどの要素を `@import` したか／どの参照がどのラベルを指すか |
| 使用トークン | 塗りつぶしの意味トークン（凡例用） |
| レビューコメント | 状態・アンカー・指摘元文書 |
| 診断 | 未解決の参照・欠字・orphaned コメント |

**すべてビルドで再生成される。ファイルには保存しない**（[P1](decisions.md)）。

## 3. 生成できる一覧

| 一覧 | 範囲 | 用途 |
|---|---|---|
| 目次 | 文書内 | 前付け |
| 図表一覧 | 文書内 | 前付け。通し番号の弱点（所在が分からない）を補う |
| 凡例 | 文書内 | 文書末 |
| **被参照一覧** | 横断 | 共有要素を編集する前の影響範囲把握 |
| **トレーサビリティ表** | 横断 | 要件 ↔ 設計 ↔ テストの対応（§4） |
| **指摘一覧** | 横断 | レビューの未対応・対応済（指摘管理表に相当） |
| 診断一覧 | 横断 | 壊れた参照・欠字・orphaned コメント |

## 4. トレーサビリティは R11 のラベルに乗る

[R11](reference-syntax.md) で、要素にラベルを付け、ラベルで参照する仕組みを作った。

> **その時点で、参照グラフは既にできている。**

トレーサビリティは、**そのグラフを別の切り口で見せるだけ**である。新しい仕組みは要らない。

### ラベルの接頭辞で種別を表す

既に `fig-` / `tbl-` / `sec-` で種別を表している。これを拡張する。

| 接頭辞 | 種別 |
|---|---|
| `req-` | 要件 |
| `des-` | 設計 |
| `tst-` | テスト |

```markdown
### ログイン認証 {#req-auth-01}
利用者は ID とパスワードでログインできること。
```

```markdown
### 認証処理の設計 {#des-auth-01}
@req-auth-01 を実現する。処理フローを @fig-login-flow に示す。
```

`des-auth-01` から `req-auth-01` への参照があるため、**要件 → 設計の対応が参照グラフから導ける**。
テスト仕様書が `@req-auth-01` を参照していれば、そこも繋がる。

### 関係の種類は持たない（当面）

「実現する」「検証する」といった**関係の意味**は区別しない。参照があるかどうかだけを見る。

意味を持たせる記法（`@satisfies(...)` のような）は考えられるが、**まず接頭辞と参照だけで運用し、
不足が実際に出てから判断する**。[P4「記法を発明しない」](decisions.md)の適用である。

### 抜けを検出できる

参照グラフがあるため、**どこからも参照されていない要件**が分かる。

> `req-auth-03` はどの設計からも参照されていません。

これは RTM を手で作るときに最も見落とされるもので、**生成する価値の中心**でもある。

## 5. 一覧の置き場所

| 範囲 | 置き場所 |
|---|---|
| 文書内（目次・図表一覧・凡例） | テーマが前付け・後付けとして出す（[決定済み](theme.md)） |
| 横断（被参照・トレーサビリティ・指摘・診断） | **ビルドの成果物として独立に出力する** |

横断一覧は特定の文書に属さないため、**文書に埋め込むのではなく別の成果物にする**のが素直である。
トレーサビリティ表は実務でも独立した納品物になる。

ただし**文書に埋めたい場合もある**（設計書の付録として RTM を載せる等）。その場合は生成物を参照する。

```markdown
@import "generated:traceability" {#tbl-rtm caption="要件トレーサビリティ"}
```

`generated:` という擬似パスで分岐する。記法は `@import` のままで、**新しい記法を増やさない**。

## 6. 副次的に解決したこと

[レビューモデル](review-model.md)で未確定だった**「生成専用コンテンツへのコメント」**が解ける。

トレーサビリティ表や指摘一覧にコメントが付いた場合、**一覧の各行は元の要素を指している**ため、
その要素のバイト範囲にアンカーを解決できる。生成物だからといって行き止まりにはならない。
