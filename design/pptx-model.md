# PPTX 出力設計案 — スライド分割とレイアウト

作成: 2026-09-21 / 対象: [未決事項 A-3](open-issues.md)
関連: [出力モデル](output-model.md) / [テーマ設計案](theme.md) / [表モデル](table-model.md) / [レビューモデル](review-model.md)

## 0. 決定事項（ロック済み）

- **PPTX の期待される用途は「概要設計図の器」である**（§1）。1 スライドに 1 つの、**PowerPoint で自由に編集できる図**を置く。
- **長い設計書の全文変換は、機能としては備えるが、運用上は想定しない**（§1.2）。
- **分割は `---` が常に境界。既定は見出し単位**（`h2`。テーマで変更可）。
- **収まらない内容は継続スライドに送る。縮小も省略もしない**（§3）。ただし図は例外。
- **内容はスライドレイアウトのプレースホルダに流し込む**（§4）。図形を直接置かない。
- **スライドレイアウトは CSS からは導けない。** テーマは既定のレイアウトを生成し、`.potx` の持ち込みも許す（§5）。
- **既定のスライドサイズは 16:9**（§1.3）。

## 1. PPTX の位置づけ

### 1.1 主役は図である

[要件定義](requirements.md)で PPTX の読者は「報告・レビューを受ける人」とした。だが**実際に期待される使い方は
もっと具体的**である。

> **1 スライドに 1 つの概要設計図を置き、受け取った側が PowerPoint で自由に編集できる状態にする。**

システム構成図・業務フロー・画面遷移の俯瞰といった、**設計の全体像を 1 枚で見せる図**が主役であり、
スライドはその器である。

このことは R6 の意味を正確にする。

> **R6 の核心は「編集可能な PPTX」ではなく、「編集可能な図」である。**

[図形語彙を DrawingML のプリセットに限定した](diagram-model.md)のは、まさにこのためだった。
ラスタ画像を貼った pptx では、受け取った側は何も直せない。**ネイティブの図形として出て初めて意味がある。**

### 1.2 長い設計書の全文変換は、機能として持つが運用しない

本文・表・箇条書きを含む設計書全体を PPTX にすることは**機能としてはできる**（§2 以降）。
しかし**運用上はそうしない**。設計書の全文は PDF で読むものであり、PPTX にすれば 100 枚を超えて誰も読まない。

実務上は、**概要図を中心とした短い文書を別に書き、それを PPTX にする**のが自然な形になる。

```
docs/
  auth-design.md          詳細な設計書 → PDF / HTML
  auth-overview.md        概要設計図を並べた短い文書 → PPTX
  auth-design/
    system-architecture.dgm    ← 両方から @import される
```

共有要素の仕組み（[編集 UI](editor-model.md)）がそのまま効く。**同じ図が、詳細設計書にも概要資料にも載る。**
図を直せば両方に反映される。

この整理により、「設計書全文を載せるとスライドが大量になる」という懸念は**運用で解消される**。
機能側で抑制する仕組み（`slide=false` 等）は用意するが、それに依存しない。

### 1.3 図が主役なら 16:9

スライドサイズの既定は **16:9** とする。図を大きく置けるためである。

（本文や表を詰め込む用途なら 4:3 のほうが情報量が多いが、§1.1 のとおりそれは主用途ではない。）

### 1.4 自由配置型の図が直結する

概要設計図は、ポンチ絵・構成イメージの類であり、**グラフ構造を持たない**ことが多い。
[作図モデル](diagram-model.md)で**自由配置型を基盤と位置づけた**判断が、ここで直接効く。

| 図の種類 | PPTX 用途との関係 |
|---|---|
| **自由配置型** | **概要設計図そのもの。最も重要** |
| グラフ型 | フロー図・画面遷移図。載ることはある |
| 委譲（ER・シーケンス） | 別ツールの領分。PPTX では画像になる（実害なし。下記） |

最後の行について。Mermaid と `.ermlx` に委譲した図は DrawingML の図形にできず、PPTX では画像として貼られる。
だが**これは実害にならない**。

**ER 図を PPTX にして PowerPoint で編集する場面が無い**からである。ER 図はモデルから導かれるものであり、
図形を手で動かして意味が変わるものではない。シーケンス図も同様で、[レイアウトが順序から完全に導出される](diagram-model.md)以上、
PowerPoint で手直しする動機がそもそも無い。

#### 境界が一致している

このことは偶然ではない。

> **「自前で持つか委譲するか」の境界と、「PowerPoint で手編集する価値があるか」の境界が一致している。**

どちらも**「人が位置を決めることに意味があるか」**という同じ問いに帰着するためである。

| | 人が位置を決める | 自前で持つ | PPTX で編集する価値 |
|---|:--:|:--:|:--:|
| 自由配置型 | ◎ | ○ | ◎ |
| グラフ型 | △（ピン留めのみ） | ○ | ○ |
| ER 図 | ✗ | 委譲 | ✗ |
| シーケンス図 | ✗ | 委譲 | ✗ |

[委譲の判断](diagram-model.md)と、PPTX の価値提案が、**衝突せずに整合している**。

### 1.5 内容を再構成はしない

「1 スライド 1 メッセージ」のような資料設計の原則を自動適用しようとすると、**内容の取捨選択という
人間の判断が要る領域**に踏み込む。本製品はそれをしない。**文書の構造をそのままスライドに写す。**

除外したい要素は属性で指定する。

```markdown
@import "auth-design/detail.table" {#tbl-detail slide=false}
```

## 2. 分割規則

| 優先 | 規則 |
|:--:|---|
| 1 | **`---` は常に境界**（[出力モデル](output-model.md)。PDF の改ページと同じ記法） |
| 2 | **見出しでスライドを切る。** 既定は `h2`。テーマで `h1` / `h3` に変更可 |
| 3 | 見出しが無い長い本文は、収まらない分を継続スライドへ（§3） |

`h1` は**章扉スライド**とする（見出しだけの 1 枚）。PDF で「章は改ページから始める」のと同じ扱い。

### PDF と分割位置が一致する

`---` は PDF では改ページ、PPTX ではスライド分割として働く（[決定済み](output-model.md)）。
著者が区切りを 1 回決めれば、**両方の出力で同じ位置に反映される**。

## 3. 収まらない内容の扱い

スライドは固定サイズであり、PDF のように自動で流れない。**必ず溢れる**。

| 内容 | 扱い |
|---|---|
| 本文・箇条書き | **継続スライドへ送る**（タイトルに「（続き）」） |
| **表** | **分割して、各スライドにヘッダ行を繰り返す** |
| 図 | **縮小する**（例外。§3.2） |
| 画像 | 縮小する |

**縮小も省略もしない**のが原則である。文字を小さくして詰め込めば読めなくなり、省略すれば情報が消える。
どちらも設計書として成立しない。

### 3.1 表の分割は PDF の実装がそのまま使える

[検証済みの表分割アルゴリズム](../prototype/table-paging/FINDINGS.md)は、**「与えられた高さに行を詰め、
`rowspan` を境界で切り、次ページの先頭に継続セルを出す」**というものである。

**この「ページ」をスライドの本文領域に読み替えれば、そのまま動く。** 出力形式に依存しない。

PDF と PPTX でレンダラは別系統だが、**分割のロジックは共有できる**。表をモデルとして持つ設計の、二度目の見返りである。

### 3.2 図は縮小してよい。むしろスライドに合わせる

図を継続スライドに分割することはできない。そして**図形はベクタとして出力する**（[決定済み](diagram-model.md)）ため、
**縮小は劣化ではない**。ラスタ画像の縮小とは意味が違う。

そもそも §1.1 の主用途では、**1 スライドに図が 1 つ**である。この場合は「収まらないから縮める」のではなく、
**スライドの領域いっぱいに図を配置する**のが自然な扱いになる。

ただし文字が読めなくなる下限があるため、**縮小率が閾値を下回ったら警告する**。

## 4. プレースホルダに流し込む

**編集可能な PPTX を出す**（R6）とは、単に図形が配置された pptx を作ることではない。

> 受け取った側が PowerPoint で**レイアウトを変えられる**こと。

そのためには、**スライドレイアウトのプレースホルダに内容を流し込む**必要がある。図形を絶対座標で直接
置いた pptx は、見た目は同じでも、受け取った側がレイアウトを選び直した瞬間に崩れる。

### 必要なレイアウト

| レイアウト | 用途 |
|---|---|
| **図** | **タイトル ＋ 図（スライドのほぼ全面）。§1.1 の主用途** |
| 表紙 | 文書番号・題名・版数・日付 |
| 章扉 | `h1` |
| 本文 | タイトル ＋ 内容 |
| 表 | タイトル ＋ 表 |
| 継続 | タイトル（続き）＋ 内容 |

**図レイアウトが中心**である。他は全文変換（§1.2）のために備えるが、主役ではない。

## 5. スライドレイアウトは CSS からは導けない

ここが PDF と決定的に違う。

| | PDF | PPTX |
|---|---|---|
| 組版 | **CSS**（ブラウザが行う） | **OOXML**（自前で組む） |
| テーマから引けるもの | 全部 | **トークンだけ** |

CSS は「本文は 10.5pt、見出しは太字」といった**トークン**を与えられるが、
「タイトルはスライド上部 1.2cm から高さ 2cm」といった**スライド上の配置**は表現できない。

したがって分担はこうなる。

- **色・フォント・サイズ階層は CSS のトークンから引く** → PDF と見た目が揃う
- **配置はスライドレイアウトが持つ**

既定のスライドマスタは、CSS のトークンから**生成する**。これにより「テーマは CSS」という原則を保てる。

そのうえで、**`.potx` の持ち込みを許す。** 企業には標準のプレゼンテンプレートがあり、それに合わせたい需要は必ずある。
これは[フォントを「同梱すれば持ち込み可」とした](theme.md)のと同じ構造である。

```
theme/
  theme.css
  fonts/
  templates/
  master.potx      ← 任意。無ければ CSS のトークンから生成する
```

## 6. ヘッダ・フッタと番号

| 項目 | 扱い |
|---|---|
| 文書番号・版数 | フッタのプレースホルダに出す（PDF と同じ情報） |
| スライド番号 | 標準のスライド番号プレースホルダ |
| **図表番号** | **PDF と同じ番号**（[採番は文書単位](reference-syntax.md)のため） |
| 相互参照 | 「図 3」と表示。PPTX ではリンクを張らず、スライド番号を併記 |

**図表番号が PDF と一致する**のは重要である。同じ設計書の PDF と PPTX を並べてレビューする場面で、
「図 3」が両方で同じものを指す。

## 7. レビューコメントとの接続

顧客は **PowerPoint のコメント機能**で指摘を書く（[決定済み](review-model.md)）。
取り込むには、**図形 ID → ソースのバイト範囲**の対応表が要る。

PPTX の各図形は ID を持つため、生成時にこの対応を出力すれば、PDF のソースマップと同じ仕組みに乗る。
HTML は DOM 要素、PDF はページ座標、**PPTX は図形 ID** — 経路は違うが、**行き着く先はどれもバイト範囲**である。

## 8. 往復（PowerPoint で直された図を戻せるか）

§1.1 の用途では、**受け取った側が PowerPoint で図を直す**。その結果を `.dgm` に戻せれば価値は大きい。

### 8.1 自分が出した PPTX なら、かなり戻せる

一般の PPTX を読み解くのは難しいが、**自分が出力した PPTX を読み戻すのは別の問題である**。
出力時に**各図形へ `.dgm` 上のノード ID を埋め込んでおけば**、読み戻しで図形とモデル要素を突き合わせられる。

これにより、**実際に最も多い編集**が確実に戻せる。

| PowerPoint での編集 | 戻し先 | 可否 |
|---|---|:--:|
| **図形を動かした・大きさを変えた** | **L2 レイアウト層** | **○** |
| **ラベルの文字を直した** | **L1 意味層** | **○** |
| 線をつなぎ替えた | L1 | ○ |
| 語彙内の図形を追加した | L1 ＋ L2 | ○ |
| 色をテーマのトークンで変えた | L3 | ○ |
| 語彙外の図形・効果・任意の書式を使った | — | **✗** |

**位置の変更が L2 に、文字の変更が L1 に落ちる**のは、[3 層モデル](diagram-model.md)でエディタがやっていることと同じである。
PowerPoint を「もう一つの編集 UI」として扱える。

### 8.2 それでも完全にはできない

PowerPoint では語彙外の図形・効果・書式が自由に使えるため、**戻せない編集は必ず生まれる**。
また、我々が出力していない PPTX を読む場合は ID が無く、一般の取り込みになる。

方針は次のとおり。

- **一方向（`.dgm` → PPTX）を基本とする**
- **自分が出した PPTX の読み戻しは、ID による突き合わせで積極的に取りにいく**（§8.1）
- 一般の PPTX 取り込みは[段階 3](diagram-model.md) のベストエフォート
- 戻せなかった要素は**黙って捨てず、警告として一覧に出す**（[コメントの orphaned 扱い](review-model.md)と同じ原則）

### 8.3 要検証

**ID をどこに埋めるか**は実測が要る。候補は図形名、代替テキスト、拡張リストなど。

**PowerPoint で保存し直したときに保持されるか**が判断基準になる。代替テキストは UI から見えて
利用者が書き換えられてしまうため、見えない場所に置けるならそのほうがよい。**実際の PowerPoint で
往復させて確認する必要がある**（本環境には PowerPoint が無いため未検証）。
