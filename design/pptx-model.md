# PPTX 出力設計案 — スライド分割とレイアウト

作成: 2026-09-21 / 対象: [未決事項 A-3](open-issues.md)
関連: [出力モデル](output-model.md) / [テーマ設計案](theme.md) / [表モデル](table-model.md) / [レビューモデル](review-model.md)

## 0. 決定事項（ロック済み）

- **PPTX は「設計書の投影」であって、プレゼン資料ではない**（§1）。内容を再構成しない。
- **分割は `---` が常に境界。既定は見出し単位**（`h2`。テーマで変更可）。
- **収まらない内容は継続スライドに送る。縮小も省略もしない**（§3）。ただし図は例外。
- **内容はスライドレイアウトのプレースホルダに流し込む**（§4）。図形を直接置かない。
- **スライドレイアウトは CSS からは導けない。** テーマは既定のレイアウトを生成し、`.potx` の持ち込みも許す（§5）。

## 1. PPTX の位置づけ

[要件定義](requirements.md)で PPTX の読者は「報告・レビューを受ける人」とした。用途は三つある。

1. 設計レビュー会でスクリーンに映す
2. 報告資料として配る
3. **受け取った側が PowerPoint で編集する**（R6 の核心）

**これはプレゼン資料を作る仕事ではない。** 「1 スライド 1 メッセージ」のような資料設計の原則を自動適用しようとすると、
内容の取捨選択という**人間の判断が要る領域**に踏み込むことになる。本製品はそれをしない。

> **設計書の構造を、そのままスライドに写す。**

したがって**既定は全内容を載せる**。プレゼン用に要点だけ抜き出したいなら、属性で除外を指定する。

```markdown
@import "auth-design/detail.table" {#tbl-detail slide=false}
```

## 2. 分割規則

| 優先 | 規則 |
|:--:|---|
| 1 | **`---` は常に境界**（[出力モデル](output-model.md)。PDF の改ページと同じ記法） |
| 2 | **見出しでスライドを切る。** 既定は `h2`。テーマで `h1` / `h3` に変更可 |
| 3 | 見出しが無い長い本文は、収まらない分を継続スライドへ（§3） |

`h1` は**章扉スライド**とする（見出しだけの 1 枚）。PDF で「章は改ページから始める」のと同じ扱い。

### PDF と分割位置が一致する

`---` は PDF では改ページ、PPTX ではスライド分割として働く（[決定済み](output-model.md)）。
著者が区切りを 1 回決めれば、**両方の出力で同じ位置に反映される**。

## 3. 収まらない内容の扱い

スライドは固定サイズであり、PDF のように自動で流れない。**必ず溢れる**。

| 内容 | 扱い |
|---|---|
| 本文・箇条書き | **継続スライドへ送る**（タイトルに「（続き）」） |
| **表** | **分割して、各スライドにヘッダ行を繰り返す** |
| 図 | **縮小する**（例外。§3.2） |
| 画像 | 縮小する |

**縮小も省略もしない**のが原則である。文字を小さくして詰め込めば読めなくなり、省略すれば情報が消える。
どちらも設計書として成立しない。

### 3.1 表の分割は PDF の実装がそのまま使える

[検証済みの表分割アルゴリズム](../prototype/table-paging/FINDINGS.md)は、**「与えられた高さに行を詰め、
`rowspan` を境界で切り、次ページの先頭に継続セルを出す」**というものである。

**この「ページ」をスライドの本文領域に読み替えれば、そのまま動く。** 出力形式に依存しない。

PDF と PPTX でレンダラは別系統だが、**分割のロジックは共有できる**。表をモデルとして持つ設計の、二度目の見返りである。

### 3.2 図だけは縮小してよい

図を継続スライドに分割することはできない。そして**図形はベクタとして出力する**（[決定済み](diagram-model.md)）ため、
**縮小は劣化ではない**。ラスタ画像の縮小とは意味が違う。

ただし文字が読めなくなる下限があるため、**縮小率が閾値を下回ったら警告する**。

## 4. プレースホルダに流し込む

**編集可能な PPTX を出す**（R6）とは、単に図形が配置された pptx を作ることではない。

> 受け取った側が PowerPoint で**レイアウトを変えられる**こと。

そのためには、**スライドレイアウトのプレースホルダに内容を流し込む**必要がある。図形を絶対座標で直接
置いた pptx は、見た目は同じでも、受け取った側がレイアウトを選び直した瞬間に崩れる。

### 必要なレイアウト

| レイアウト | 用途 |
|---|---|
| 表紙 | 文書番号・題名・版数・日付 |
| 章扉 | `h1` |
| 本文 | タイトル ＋ 内容 |
| 図 | タイトル ＋ 図（大きめの領域） |
| 表 | タイトル ＋ 表 |
| 継続 | タイトル（続き）＋ 内容 |

## 5. スライドレイアウトは CSS からは導けない

ここが PDF と決定的に違う。

| | PDF | PPTX |
|---|---|---|
| 組版 | **CSS**（ブラウザが行う） | **OOXML**（自前で組む） |
| テーマから引けるもの | 全部 | **トークンだけ** |

CSS は「本文は 10.5pt、見出しは太字」といった**トークン**を与えられるが、
「タイトルはスライド上部 1.2cm から高さ 2cm」といった**スライド上の配置**は表現できない。

したがって分担はこうなる。

- **色・フォント・サイズ階層は CSS のトークンから引く** → PDF と見た目が揃う
- **配置はスライドレイアウトが持つ**

既定のスライドマスタは、CSS のトークンから**生成する**。これにより「テーマは CSS」という原則を保てる。

そのうえで、**`.potx` の持ち込みを許す。** 企業には標準のプレゼンテンプレートがあり、それに合わせたい需要は必ずある。
これは[フォントを「同梱すれば持ち込み可」とした](theme.md)のと同じ構造である。

```
theme/
  theme.css
  fonts/
  templates/
  master.potx      ← 任意。無ければ CSS のトークンから生成する
```

## 6. ヘッダ・フッタと番号

| 項目 | 扱い |
|---|---|
| 文書番号・版数 | フッタのプレースホルダに出す（PDF と同じ情報） |
| スライド番号 | 標準のスライド番号プレースホルダ |
| **図表番号** | **PDF と同じ番号**（[採番は文書単位](reference-syntax.md)のため） |
| 相互参照 | 「図 3」と表示。PPTX ではリンクを張らず、スライド番号を併記 |

**図表番号が PDF と一致する**のは重要である。同じ設計書の PDF と PPTX を並べてレビューする場面で、
「図 3」が両方で同じものを指す。

## 7. レビューコメントとの接続

顧客は **PowerPoint のコメント機能**で指摘を書く（[決定済み](review-model.md)）。
取り込むには、**図形 ID → ソースのバイト範囲**の対応表が要る。

PPTX の各図形は ID を持つため、生成時にこの対応を出力すれば、PDF のソースマップと同じ仕組みに乗る。
HTML は DOM 要素、PDF はページ座標、**PPTX は図形 ID** — 経路は違うが、**行き着く先はどれもバイト範囲**である。

## 8. 未確定事項

- **既定のスライドサイズ** — 16:9 か 4:3 か。設計書のレビュー用途では 4:3 のほうが情報が載る
- **本文の継続スライドの分割単位** — 段落単位か、行単位まで踏み込むか
- **図の縮小率の下限** — 何 % を下回ったら警告するか
- **`.potx` 持ち込み時のプレースホルダ対応付け** — 相手のレイアウト名が我々の想定と違う場合どう解決するか
- **ノート（発表者ノート）** — 使うか。本文の一部をノートに送る需要があるか
- **スライドが大量になる問題** — 設計書全文を載せると 100 枚を超えうる。`slide=false` の指定だけで実用に足るか
