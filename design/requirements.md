# 要件定義 — 二つの軸と R1〜R9

作成: 2026-09-20
関連: [既存サービス調査](../docs/research/existing-solutions.md) / [Excel 脱却要求の整理](../docs/research/excel-migration-japan.md) / [作図モデル設計案](diagram-model.md)

## 0. 基本原則 — 読者は二人いる

DocPresenter が生成・管理するファイルには、**人間と AI という二人の読者**がいる。どちらか一方ではなく、**両方が「ファイルそのもの」を読める**ことを土台に置く。

| 軸 | 定義 |
|---|---|
| **軸 A: 人間可読性** | 成果物（HTML / PDF / PPTX）ではなく、**ソースファイルそのもの**が人間に読める。Git の差分がレビュー単位として成立する |
| **軸 B: 機械可読性** | AI が内容を正確に理解できる。図・表・参照関係の意味が失われない |

### この二つは対立しない

両方を同時に殺しているのが、Excel 方眼紙であり draw.io の XML である。**機械が生成した不透明な構造**は、人間にも AI にも読めない。
逆に両方を同時に満たすのが、**構造を持った整形済みテキスト**。軸 A と軸 B は、同じ一つの要求を別の側から見たものに過ぎない。

### ただし緊張はある

- 構造化を突き詰めると JSON / XML に寄り、**人間が読みにくくなる**
- 可読性を突き詰めると散文に寄り、**機械が構造を取り出せなくなる**

本設計での解は次の三点。

1. **表層は Markdown**（軸 A を優先）
2. **構造は明示的なマークとして埋め込む**（軸 B のために、散文に構造を埋める）
3. **完全に構造化された形は「出力」として別に出す**（§5）。ソースを JSON 化するのではなく、同じモデルから投影する

R2 と R7 が両軸で ◎ なのは、**図と表こそが「人間にも AI にも読めなくなる」最大の破綻点**だから。ここが本製品の中心にある。

## 2. 軸 A から導かれる設計制約

1. **生成物が本文を侵食しない。**
   座標・レイアウト・内部 ID といった機械が書いた情報を、人間が読む本文に混ぜない。[作図モデル設計案](diagram-model.md) の 3 層分離は、この原則の作図版である。同じ規律を表・文書全体に広げる。
2. **安定した人間可読 ID。GUID は禁止。**
   `db-primary` のような命名。差分に GUID が並んだ時点でレビューは成立しない。
3. **決定論的な整形。**
   同じ内容からは常に同じバイト列が出る。順序が揺れると、意味を変えていないのに差分が出て、レビューが破壊される。
4. **機械が書き戻しても人間可読を保つ。**
   GUI 編集を持つ以上、テキストは「人間が書いたもの」と「ツールが書き戻したもの」が混在する。**後者が前者と同じ品質で読めること**が必須。これが最も難しく、かつ本製品の技術的な核心（§6）。

## 3. 軸 B から導かれる設計制約

1. **図は画像ではなくテキスト表現を持つ**（R2 で充足）。
   「仕様書の図は画像にすると AI が読めない」という指摘に直接対応する。
2. **表は結合の意味が保持される構造で持つ**（R7 で充足）。
   HTML table を直書きすると、人間の差分も AI の理解も同時に壊れる。
3. **文書構造が明示的である。**
   章立て・項目定義・参照関係が、推測ではなくマークとして取り出せる。
4. **外部参照を解決した形で出せる**（R3 の裏要件）。
   AI に渡すときに `include` が未解決のままだと、文脈が欠落した状態で読まれる。**参照を展開した投影を出せること**が要る。
5. **トークン効率。**
   冗長な XML ではなく簡潔なテキストで同じ構造を伝える。軸 A と利害が一致する。

## 4. R9 の位置づけ — AI は第四の読者

R4〜R6 が「人間の読者それぞれに向けた投影」であるのと同じ意味で、**AI 向けの投影**を出力先として対等に並べる。R9 は別systemではなく、既存の出力体系の自然な拡張である。

| 読者 | 出力 | 要件 | 指摘の経路（R10） |
|---|---|---|---|
| 画面で読む人 | HTML | R4 | Web ビューアのコメント |
| 印刷・納品する人 | PDF | R5 | PDF 注釈の取り込み |
| 報告・レビューを受ける人 | PPTX | R6 | PowerPoint コメントの取り込み |
| **AI** | **構造化コンテキスト** | **R9** | （将来） |
| エンジニア | リポジトリそのもの | — | Pull Request |

R10 により、この表は出力の一方通行ではなく**双方向**になる。詳細は [レビューモデル設計案](review-model.md)。

R9 の出力が満たすべき性質:

- 外部参照が**解決済み**である（§3-4）
- 図が**テキスト表現に展開**されている（画像ではない）
- 表が**構造**として出ている（結合の意味を保持）
- 冗長さが削られている（トークン効率）

この対称性が成立するのは、**中間モデルを持つ設計だから**である。

> **用語の整理**: 企画初期には中間モデルを `.docmlx` という独自ファイル形式として構想していたが、
> [編集 UI 設計案](editor-model.md)で「地は Markdown、特殊要素は外部ファイル」と決めたことにより、**中間モデルはファイル形式ではなくなった**。
> 保存されるのは `.md` / `.dgm` / `.table` であり、中間モデルはそれらを読み込んだ**実行時の内部表現**を指す。
> 研究ドキュメント（`docs/research/`）に残る `.docmlx` は企画初期の記録である。

Markdown を直接各形式に変換する先行事例には、この四番目の出力先を素直に足す場所が無い。2026 に入って「Markdown だけでは足りない」「構造化情報の表現が苦手」という反省が出ているのは、まさにこの構造を持たないことの帰結と見ている。

## 5. 最も難しい要求

> **GUI で編集した結果が、人間が読めるテキストとして書き戻されること。**

R8（Web / VS Code での編集）と軸 A を同時に満たすということは、これを意味する。draw.io が Git で使えないのも、Excel が AI に読めないのも、突き詰めればこの一点を解いていないからである。

[作図モデル設計案](diagram-model.md) の 3 層分離・グリッド量子化・id 順の安定出力・疎なピン留めは、**作図という一領域でこの問題を解いた事例**であり、同じ規律を表と文書全体に一般化することが次の設計課題になる。
