# 参照記法の比較 — 埋め込みオブジェクトをどう書くか

作成: 2026-09-20 / 対象: [編集 UI 設計案 §11](editor-model.md) の未確定事項「参照の記法」
関連: [要件定義](requirements.md)

## 1. 比較のための題材

同じ内容を各記法で書き、読みやすさと素の Markdown としての劣化具合を見る。

> 3.2 ログイン画面の節に、**画面遷移図**・**画面項目表**・**画面キャプチャ（幅指定あり）**・**共通用語集の一部（先頭 20 行のみ）**を置く。

## 2. 先行事例 — Markdown Preview Enhanced

MPE は**まさに同じことを既にやっている**。外部ファイルを種別ごとに適切な形でレンダリングして埋め込む。

| ファイル型 | MPE の扱い |
|---|---|
| `.csv` | **Markdown テーブルに変換** |
| `.mermaid` / `.dot` / `.plantuml` | **図として描画** |
| 画像各種 | 画像として埋め込み |
| `.pdf` | SVG に変換して埋め込み |
| Markdown | 解析して直接埋め込み |
| その他 | コードブロックとして表示 |

構文は 4 形式を受理する。

```
@import "your_file"
<!-- @import "your_file" -->
![](path/to/your_file)
![[ path/to/your_file ]]
```

属性も実績込みで設計されている。

```
@import "test.png"  {width="300px" height="200px" title="..." alt="..."}
@import "test.md"   {line_begin=2 line_end=10}
@import "test.json" {as="vega-lite"}
@import "test.puml" {code_block=true class="line-numbers"}
```

**`line_begin` / `line_end` は、[編集 UI 設計案](editor-model.md)で未確定にしていた「部分参照」への回答そのもの**である。共有の用語集から一部だけを引く、という需要に既に答えが出ている。

## 3. 候補と具体例

### 案 A — MPE 互換 `@import`

```markdown
## 3.2 ログイン画面

ログイン時の画面遷移を以下に示す。

@import "auth-design/login-flow.dgm"

画面項目は次のとおり。

@import "auth-design/login-items.table"

実際の画面イメージを示す。

@import "assets/login-screen.png" {width="600px"}

用語は全体で共通のものを用いる。

@import "shared/glossary.table" {line_begin=1 line_end=20}
```

### 案 B — フェンス ＋ `src` 属性

````markdown
## 3.2 ログイン画面

ログイン時の画面遷移を以下に示す。

```dgm src="auth-design/login-flow.dgm"
```

画面項目は次のとおり。

```table src="auth-design/login-items.table"
```

実際の画面イメージを示す。

```image src="assets/login-screen.png" width="600px"
```

用語は全体で共通のものを用いる。

```table src="shared/glossary.table" rows="1-20"
```
````

**中身が空のフェンスが並ぶ**のが致命的に不自然。2 行を消費し、視覚的にも重い。

### 案 C — 画像記法の拡張

```markdown
## 3.2 ログイン画面

ログイン時の画面遷移を以下に示す。

![ログイン画面遷移](auth-design/login-flow.dgm)

画面項目は次のとおり。

![画面項目](auth-design/login-items.table)

実際の画面イメージを示す。

![ログイン画面](assets/login-screen.png){width="600px"}

用語は全体で共通のものを用いる。

![用語集](shared/glossary.table){line_begin=1 line_end=20}
```

**完全に標準 Markdown**で、GitHub 上でも alt テキストが見える。ただし表を「画像」と書くのは意味的にねじれている。

### 案 D — ディレクティブ

```markdown
## 3.2 ログイン画面

ログイン時の画面遷移を以下に示す。

:::dgm src="auth-design/login-flow.dgm"
:::

画面項目は次のとおり。

:::table src="auth-design/login-items.table"
:::
```

案 B と同じく**閉じ記号が空で冗長**。MyST 等の先行はあるが、この用途では利点が出ない。

### 案 E — Quarto 風ショートコード

```markdown
## 3.2 ログイン画面

ログイン時の画面遷移を以下に示す。

{{< dgm auth-design/login-flow.dgm >}}

用語は全体で共通のものを用いる。

{{< table shared/glossary.table rows="1-20" >}}
```

1 行で済むが、`{{< >}}` は Hugo / Quarto の文脈が強く、標準 Markdown から見ると異物感が大きい。

## 5. 推奨 — A を正式記法とし、C も受理する

> **正式記法（ツールが書き戻す形）: `@import "path" {attr}`**
> **読み取り時は `![alt](path){attr}` も受理する**

MPE がこの 2 形式を両方受理しているので、**両対応は MPE 互換そのもの**であり追加コストがほとんど無い。

### `@import` を正式記法にする理由

1. **対象ユーザーが完全に重なる。** VS Code で Markdown を書き、図を描き、PDF に出す層は、まさに MPE の利用者層である。知っている記法をそのまま使える。
2. **属性設計が実績込みで手に入る。** 特に `line_begin` / `line_end` は部分参照の答えとして即使える。ゼロから設計して同じ結論に至る公算が高いものを、先に検証済みの形で借りられる。
3. **1 行で読みやすい。** 本文を目次のように見通せる状態（[編集 UI 設計案 §4](editor-model.md)）を最もよく保つ。
4. **既存 MPE 文書の受け入れ余地が生まれる。** 完全互換は狙わないが、記法が同じなら移行の敷居は明確に下がる。

### `![alt](path)` も受理する理由

GitHub 等、本製品のレンダラが無い環境で **alt テキストが表示される**のは実利がある。「ここに何の図があるか」が伝わる。

**ただし書き戻しは常に `@import` に統一する。** 人が `![]()` で書いた箇所は[書き戻しの規律](editor-model.md)によりそのまま保たれ、ツールが勝手に書き換えることはない。

### 採らない形式

- `<!-- @import "..." -->` — GitHub 上で**何も表示されず文書に穴が空く**。`@import` がそのまま文字列として見えるほうがまだよい
- `![[ ... ]]` — Wiki リンク風。Obsidian 系の文脈が混ざるため採らない

## 6. 種別の決定 — 拡張子で決める

`@import` は種別を書かないため、**拡張子がレンダラを決める**。これは MPE と同じ方式。

| 拡張子 | レンダラ |
|---|---|
| `.dgm` | 作図 |
| `.table` | 表 |
| `.png` / `.jpg` / `.svg` 等 | 画像 |
| `.md` | Markdown として展開 |
| `.mmd` / `.mermaid` | Mermaid の図。`{view="code"}` でコード、`{view="both"}` で図とコード |
| その他 | コードブロック |

本文のコードブロックも同じ考え方で、**言語名が扱いを決める**。` ```mermaid ` は図として描き
（開きの行に `{view="code"}` / `{view="both"}` を書ける）、それ以外の言語名は色付けに使う。
コードブロックの中の行は、`#` で始まっても見出しにならず、`---` もシートの区切りにならない。

拡張子と違う扱いをしたい場合は、MPE と同じく `{as="..."}` で上書きできる。

## 7. 番号と相互参照

### 7.1 決定事項

- **図表番号・章番号は自動採番する。ファイルには保存しない。**
- **採番は文書単位。** 共有要素が複数の文書から参照される場合、**文書ごとに別の番号**が振られる
- **図と表は文書ごとの通し番号**（図 1・図 2…／表 1・表 2…）とし、章番号は含めない（§7.2）。**設定にはしない**
- **見出しは階層番号**（1／1.1／1.1.1）。図表とは別の体系
- したがって **番号を本文や要素の中に直接書いてはならない。** 必ず参照として書く

最後の項が「相互参照の問題」である。番号を計算で決めると決めた時点で、自動的に要請される。

### 7.2 図表は通し番号にする

「図 3.1」形式（章番号込み）と「図 12」形式（通し番号）のうち、**通し番号を採る**。

#### 番号が再生成されるなら、ずれること自体は問題ではない

番号はファイルに保存せず毎回計算するため、番号が変わっても**文書の中では何も壊れない**。参照はラベルで書かれており、自動で追従する。

問題は**文書の外に出た番号**である。

- 顧客がメールで「図 3.1 について」と指摘した
- 議事録に「図 3.1 の構成を見直す」と書かれた
- 印刷して回覧した PDF に番号が刷られている

これらは再生成されない。**番号が変われば、文書の外にある参照はすべて壊れる。**

したがって判断基準は一つに絞られる。

> **どちらの方式が、番号の変動要因が少ないか。**

#### 通し番号のほうが変動要因が少ない

| 方式 | 番号が変わる条件 |
|---|---|
| 章番号込み（図 3.1） | 図を増減したとき **＋ 章を挿入・移動・削除したとき** |
| **通し番号（図 12）** | **図を増減したときのみ** |

章番号込みは、**図をまったく触っていないのに番号が変わる**。章を 1 つ挿入しただけで、以降の全図の番号がずれる。設計書の改訂では章構成の変更は普通に起きる。

通し番号なら、図の番号は**図の増減にのみ依存し、章構成から独立する**。関心が分離されている。

これは[レビューコメントを行番号ではなくバイト範囲に固定した判断](review-model.md)と同じ考え方である。**外部に露出する識別子は、変動要因を最小化する。**

#### 代償と、その手当て

通し番号の弱点は、**番号から所在が分からない**ことである。「図 27」が何章にあるか推測できない。

これは**図表一覧の自動生成**で補う。番号・キャプション・所在節を並べた一覧を文書冒頭に置く。採番が計算で決まる以上、一覧の生成は追加コストがほぼ無い。未確定要求 D12（横断一覧）と同じ仕組みに乗る。

#### 設定にしない

採番方式は frontmatter の設定にせず、**通し番号で固定する**。方式が文書ごとに違うと、設計書の束としての体裁が崩れ、文書をまたぐ参照（§7.6）の表記も揺れる。[意味トークンを 4 種で固定した](table-model.md)のと同じ規律である。

### 7.3 なぜ番号の直書きが成立しないか

[サンプル](../sample/README.md)の `screen-items.table` に、実際に次の行を書いてしまった。

```
| 操作 | 4 | ログイン | — | — | — | 押下で図 3.1 の遷移を開始 |
```

これは二重に壊れている。

1. **章を挿入すれば図 3.1 は図 4.1 になる**が、この文字列は変わらない
2. この表が共有要素なら、**参照先の番号は文書ごとに違う**。どの番号を書いても必ずどこかで間違う

番号が計算で決まる以上、番号を書いた瞬間にそれは古くなる。これは[レイアウト座標を保存しない](diagram-model.md)、[コメントの現在位置を保存しない](review-model.md)のと同じ原則である。

> **計算で出せるものはファイルに書かない。**

### 7.4 記法 — ラベルを付け、ラベルで参照する

対象にラベルを与える。キャプションも属性として持たせる（手書きの見出し行を廃止する）。

```markdown
@import "auth-design/login-flow.dgm" {#fig-login-flow caption="ログイン画面遷移"}
```

地の文からはラベルで参照する。

```markdown
ログイン時の画面遷移を @fig-login-flow に示す。
```

レンダリング結果:

> ログイン時の画面遷移を **図 2** に示す。
>
> （図の下に）**図 2 ログイン画面遷移**

ラベルの接頭辞が種別を決める（Quarto と同じ方式）。

| 接頭辞 | 種別 | 表示例 |
|---|---|---|
| `fig-` | 図 | 図 2（通し番号） |
| `tbl-` | 表 | 表 1（通し番号） |
| `sec-` | 章・節 | 3.2 節（階層番号） |

見出しにも同じ記法でラベルを付けられる。

```markdown
### 3.2 画面項目 {#sec-screen-items}
```

**見出し番号も自動採番する**ため、`### 画面項目 {#sec-screen-items}` と書けば `3.2` は生成される。

**文書の先頭にある `h1` は題名として扱い、採番しない。** その次の階層から 1 が始まる（実装時に確定）。

### 7.5 共有要素の中にも参照を書ける

番号ではなく参照として書けば、**文書ごとに正しく解決される**。§7.3 の例は次のように直る。

```
| 操作 | 4 | ログイン | — | — | — | 押下で @fig-login-flow の遷移を開始 |
```

この表が別の文書から参照されても、そこでの採番に従って解決される。**参照は文書文脈で評価される**ため、共有要素が番号を持たないことと矛盾しない。

これは[凡例を文書単位で集計する](table-model.md)判断とまったく同じ構造である。共有要素は「文書に置かれて初めて番号を得る」。

### 7.6 文書をまたぐ参照

```markdown
外部 IdP との連携は @SD-LINK-002:sec-idp に定める。
```

> 外部 IdP との連携は **外部連携設計書 4.2 節** に定める。

相手文書での採番を引くため、**ビルドはリポジトリ全体を見る必要がある**。単一文書だけでは解決できない。

### 7.7 解決できない参照はビルドを失敗させる

参照先のラベルが存在しない、文書が削除された、といった場合は**警告ではなくエラー**とする。壊れた相互参照を黙って出力してはならない。[参照先ファイルが無い場合](editor-model.md)と同じ扱いである。

### 7.8 逆引きを持つ

「この図はどこから参照されているか」を引けるようにする。[共有要素の被参照警告](editor-model.md)と同じ仕組みに乗り、未確定要求 D12（横断一覧）とも共有できる。

### 7.9 出力形式ごとの扱い

| 出力 | 参照の表現 |
|---|---|
| HTML | クリックで該当箇所へ移動するリンク |
| PDF | 内部リンク ＋ ページ番号の併記（「図 12（8 ページ）」） |
| PPTX | スライド番号を併記。リンクは張らない |

## 8. 未確定事項

- ~~`.table` の中身の形式~~ → **決定**: CSV は取り込み経路であって保存形式にしない（[表モデル設計案](table-model.md)）
- **`line_begin` / `line_end` の妥当性** — 行番号による部分参照は、参照先の編集で簡単にずれる。[レビューモデル](review-model.md)で行番号を避けた判断と整合しない。名前による範囲指定（`{rows="基本用語"}` など）を併用すべきか
- **MPE 互換をどこまで謳うか** — コードチャンク実行など MPE 固有機能は対象外。互換性の範囲を明示しないと誤解を招く
- **同一要素を 1 文書内で複数回参照した場合** — 別々の図として採番するか、同じ番号を再掲扱いにするか
- **文書をまたぐ参照の解決** — 単一文書内は実装済み。全ルートのインデックス（[R12](index-model.md)）が要る
- **文書をまたぐ参照の記法**（§7.6）— 文書番号で指すか、パスで指すか

## 8. 画像の属性（2026-10-01 実装）

MPE の `{width=…}` をそのまま借り、**`align` を 1 つだけ足した**。

```markdown
@import "auth-design/screen.png" {#fig-shot caption="ログイン画面" width="55%" align="center"}
@import "https://example.com/diagram.png" {caption="外部の図"}
```

| 属性 | 値 | 既定 |
|---|---|---|
| `width` | `55%`（版面に対する割合）または `120mm` などの長さ | 原寸（版面を超えない） |
| `align` | `left` / `center` / `right` | `left` |

**割合を既定の書き方にした。** エディタのつまみが書くのもこれである。px や mm は紙の
大きさと余白が変われば意味が変わるが、割合は変わらない。書けない値（`url(...)` など）は
**無視して何も出さない**——文書の指示としてスタイルが 1 つだけ出力に届く経路なので、
そこを素通しにはしない。

**`http(s)://` で始まるものは住所であって、パスではない。** 取り込み展開も参照閉包も
これを素通りさせる（`https://` を作業フォルダからの相対として畳むと `https:/` になる）。
取り込みは[ビルドが一度だけ行う](pdf-engine.md)。
