# 画面設計を作図で行う

作成: 2026-09-26 / 対象: R2（作図）の適用範囲
関連: [作図モデル](diagram-model.md) / [要件定義](requirements.md)

## 0. 決定事項（ロック済み）

- **画面設計は自由配置の作図（`free`）で行う。** 新しい種類のファイルは作らない（§1）。
- **枠線を持たない文字**（`"…"`）を図形の語彙に加える（§2）。
- **色は書いた人が選ぶ**（`fill` / `line` / `color` に直値）。表・本文と同じ（§2）。
- **文字の寄せ**（`align: left / center / right`）を加える（§2）。
- **部品テンプレートは未実装。** 設計は §3 に置く。

## 1. なぜ新しいファイル形式を作らないか

画面設計は**位置が意味を持つ図**である。それは[自由配置型](diagram-model.md)がすでに扱っているものと同じで、

- 差分が読める（`idBox @ (70, 116) 320x34` が 1 行変わる）
- 図形・座標・色が層に分かれている（意味 / レイアウト / スタイル）
- 印刷にも PPTX にも出せる

画面モックのための形式を別に作れば、この全部を二度実装することになる。

### 画像への注釈と使い分ける

| 手段 | いつ使うか |
|---|---|
| **`free` で描く** | **設計時点。実装前の画面を起こす** |
| [`overlay` で画像に注釈](diagram-model.md) | **実装後。動いている画面に番号を振る** |

前者は文言や項目の増減が差分に出る。後者は画像そのものは差分に出ないが、番号と文言は出る。
**どちらも要る。** サンプルでは両方を並べてある。

## 2. 足りなかった語彙

実際に[ログイン画面](../sample/docs/auth-design/login-screen.dgm)を描いて分かったこと。

| 足りなかったもの | 加えたもの |
|---|---|
| 枠線のない文字（ラベル・注記・リンク文言） | **`"…"` が `text` 図形**。何も描かず、ラベルだけを置く |
| 部品ごとの色（ボタンの青、入力欄の薄い灰） | **`fill` / `line` / `color` に直値**。テーマは既定値を与えるだけ |
| 文字の寄せ | **`align: left / center / right`**。画面のラベルは中央揃えではない |

三つ目は見落としやすい。**中央揃えの文字だけで組んだ画面は、誰も作らない画面に見える。**

```
free {
  idLabel  "ログイン ID"
  idBox    [yamada@example.co.jp]
  submit   (ログイン)
}
layout {
  idLabel @ ( 70,  96) 320x18
  idBox   @ ( 70, 116) 320x34
  submit  @ ( 70, 284) 320x38
}
style {
  idLabel { color: #3a4048, align: left }
  idBox   { fill: #fbfbfc, line: #aeb4bd, align: left }
  submit  { fill: #2f6fb5, line: #2f6fb5, color: #ffffff }
}
```

## 3. 部品テンプレート（設計のみ・未実装）

上の例には問題がある。**入力欄を 10 個置けば、同じ `fill` と `line` を 10 回書くことになる。**
システムごとに共通のスタイルがあるなら、それは一箇所に置きたい。

### 3.1 部品は「名前のついたスタイルと既定の大きさ」である

部品に要るのは、結局この二つだけである。

```
# shared/ui-parts.dgm — 部品テンプレート
parts {
  textbox  [ ] { fill: #fbfbfc, line: #aeb4bd, align: left }  320x34
  label    "…" { color: #3a4048, align: left }                320x18
  primary  ( ) { fill: #2f6fb5, line: #2f6fb5, color: #fff }  320x38
  checkbox [ ] { fill: #ffffff, line: #aeb4bd }                16x16
}
```

使う側は**部品名を図形の代わりに書く**。

```
use "../shared/ui-parts.dgm"

free {
  idLabel  label:"ログイン ID"
  idBox    textbox:"yamada@example.co.jp"
  submit   primary:"ログイン"
}
layout {
  idLabel @ ( 70,  96)      # 大きさは部品の既定を使う
  idBox   @ ( 70, 116)
  submit  @ ( 70, 284)
}
```

**スタイルの記述が消える。** 変わるのは座標だけになり、差分はさらに読みやすくなる。
部品の見た目を変えれば、その部品を使っている全画面が一度に変わる。

### 3.2 決めるべきこと

- **`use` の解決規則** — `@import` と同じ相対パスでよいか。[共有物は `shared/`](editor-model.md) の約束に乗る
- **部品の上書き** — 個別に `style` で上書きできるべきか。できるべきだが、**上書きが増えたら部品の設計が間違っている**
- **部品の一覧を出せるか** — [横断一覧](index-model.md)に「この部品を使っている画面」を出せると効く
- **PPTX への写り方** — 部品は DrawingML のグループにするのか、展開するのか

### 3.3 なぜ今作らないか

**部品の語彙は、画面を何枚か描いてからでないと決まらない。** 1 枚描いただけで
「入力欄・ラベル・ボタン・チェックボックス」と決めると、2 枚目で足りなくなる。
[サンプルを書いて穴を見つける](../sample/README.md)というこのプロジェクトのやり方をここでも取る。

## 4. GUI での操作

現状、画面も他の図と同じく**ソースを直接書く**。[ドラッグでの配置](diagram-model.md)は未実装である。
画面設計はとりわけ**マウスで置きたい**図なので、[自由配置型はマウスが主](diagram-model.md)という
既存の判断がそのまま当てはまる。

## 5. ループの表現（作図一般）

繰り返しは二つの書き方がある。どちらも既存の語彙で足りる。

| 書き方 | 使いどころ |
|---|---|
| **接続が戻る**（`save --> read`） | 制御の流れとしての繰り返し。自動レイアウトが脇の通路を通して戻す |
| **群れに名前を付ける**（`group loop "繰り返し: 全件" { … }`） | 「ここからここまでが繰り返し」という範囲の明示 |

両方を重ねるのが普通で、[戻る接続は図形を貫かずに迂回する](decisions.md)ので読める。
