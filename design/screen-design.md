# 画面設計を作図で行う

作成: 2026-09-26 / 対象: R2（作図）の適用範囲
関連: [作図モデル](diagram-model.md) / [要件定義](requirements.md)

## 0. 決定事項（ロック済み）

- **画面設計は自由配置の作図（`free`）で行う。** 新しい種類のファイルは作らない（§1）。
- **枠線を持たない文字**（`"…"`）を図形の語彙に加える（§2）。
- **色は書いた人が選ぶ**（`fill` / `line` / `color` に直値）。表・本文と同じ（§2）。
- **文字の寄せ**（`align: left / center / right`）を加える（§2）。
- **部品テンプレートは実装済み**（2026-10-01、§3.4）。語彙は画面を 3 枚描いてから決めた。

## 1. なぜ新しいファイル形式を作らないか

画面設計は**位置が意味を持つ図**である。それは[自由配置型](diagram-model.md)がすでに扱っているものと同じで、

- 差分が読める（`idBox @ (70, 116) 320x34` が 1 行変わる）
- 図形・座標・色が層に分かれている（意味 / レイアウト / スタイル）
- 印刷にも PPTX にも出せる

画面モックのための形式を別に作れば、この全部を二度実装することになる。

### 画像への注釈と使い分ける

| 手段 | いつ使うか |
|---|---|
| **`free` で描く** | **設計時点。実装前の画面を起こす** |
| [`overlay` で画像に注釈](diagram-model.md) | **実装後。動いている画面に番号を振る** |

前者は文言や項目の増減が差分に出る。後者は画像そのものは差分に出ないが、番号と文言は出る。
**どちらも要る。** サンプルでは両方を並べてある。

## 2. 足りなかった語彙

実際に[ログイン画面](../sample/docs/auth-design/login-screen.dgm)を描いて分かったこと。

| 足りなかったもの | 加えたもの |
|---|---|
| 枠線のない文字（ラベル・注記・リンク文言） | **`"…"` が `text` 図形**。何も描かず、ラベルだけを置く |
| 部品ごとの色（ボタンの青、入力欄の薄い灰） | **`fill` / `line` / `color` に直値**。テーマは既定値を与えるだけ |
| 文字の寄せ | **`align: left / center / right`**。画面のラベルは中央揃えではない |

三つ目は見落としやすい。**中央揃えの文字だけで組んだ画面は、誰も作らない画面に見える。**

```
free {
  idLabel  "ログイン ID"
  idBox    [yamada@example.co.jp]
  submit   (ログイン)
}
layout {
  idLabel @ ( 70,  96) 320x18
  idBox   @ ( 70, 116) 320x34
  submit  @ ( 70, 284) 320x38
}
style {
  idLabel { color: #3a4048, align: left }
  idBox   { fill: #fbfbfc, line: #aeb4bd, align: left }
  submit  { fill: #2f6fb5, line: #2f6fb5, color: #ffffff }
}
```

## 3. 部品テンプレート（設計のみ・未実装）

上の例には問題がある。**入力欄を 10 個置けば、同じ `fill` と `line` を 10 回書くことになる。**
システムごとに共通のスタイルがあるなら、それは一箇所に置きたい。

### 3.1 部品は「名前のついたスタイルと既定の大きさ」である

部品に要るのは、結局この二つだけである。

```
# shared/ui-parts.dgm — 部品テンプレート
parts {
  textbox  [ ] { fill: #fbfbfc, line: #aeb4bd, align: left }  320x34
  label    "…" { color: #3a4048, align: left }                320x18
  primary  ( ) { fill: #2f6fb5, line: #2f6fb5, color: #fff }  320x38
  checkbox [ ] { fill: #ffffff, line: #aeb4bd }                16x16
}
```

使う側は**部品名を図形の代わりに書く**。

```
use "../shared/ui-parts.dgm"

free {
  idLabel  label:"ログイン ID"
  idBox    textbox:"yamada@example.co.jp"
  submit   primary:"ログイン"
}
layout {
  idLabel @ ( 70,  96)      # 大きさは部品の既定を使う
  idBox   @ ( 70, 116)
  submit  @ ( 70, 284)
}
```

**スタイルの記述が消える。** 変わるのは座標だけになり、差分はさらに読みやすくなる。
部品の見た目を変えれば、その部品を使っている全画面が一度に変わる。

### 3.2 決めるべきこと

- **`use` の解決規則** — `@import` と同じ相対パスでよいか。[共有物は `shared/`](editor-model.md) の約束に乗る
- **部品の上書き** — 個別に `style` で上書きできるべきか。できるべきだが、**上書きが増えたら部品の設計が間違っている**
- **部品の一覧を出せるか** — [横断一覧](index-model.md)に「この部品を使っている画面」を出せると効く
- **PPTX への写り方** — 部品は DrawingML のグループにするのか、展開するのか

### 3.3 なぜ今作らないか

**部品の語彙は、画面を何枚か描いてからでないと決まらない。** 1 枚描いただけで
「入力欄・ラベル・ボタン・チェックボックス」と決めると、2 枚目で足りなくなる。
[サンプルを書いて穴を見つける](../sample/README.md)というこのプロジェクトのやり方をここでも取る。

### 3.4 実装（2026-10-01）— 3 枚描いてから決めた

**先に画面を 2 枚足した**（パスワード再設定・アカウントロック）。§3 の語彙のまま、
色を書き写して描いた。3 枚で **style の宣言は 29 行、うち違う見た目は 11 種類**だった。

| 推測（§3.1） | 実際に要ったもの |
|---|---|
| textbox / label / primary / checkbox | 左の 4 つ **＋ title・body・hint・link・secondary・frame・banner・alert・error** |

**§3.3 の予想は当たっていた。** 4 種で決め打っていれば、2 枚目で副ボタンが、
3 枚目で警告の面とエラー文が足りなくなっていた。

#### 決まったこと（§3.2 への回答）

| 問い | 答え |
|---|---|
| `use` の解決規則 | `@import` と同じ。**書いたファイルからの相対**。`shared/` の約束に乗る |
| 部品の上書き | **できる。** 画面側の `style` が部品に勝つ。上書きが増えたら部品の設計が間違っている、は変わらない |
| 部品の一覧 | **部品ファイルは自分の見本を描く**（下）。「どの画面が使っているか」は[横断一覧](index-model.md)の仕事として残す |
| PPTX への写り方 | **展開する。** 部品は見た目と大きさでしかないので、解決してから書き出せば PowerPoint は部品を知らなくてよい |

**解決は、誰かが図を見るより前に済ませる。** 描画器・キャンバス・PPTX・PDF のどれも
手を入れていない——受け取ったときには、部品はもう普通の図形と普通のスタイルである。

#### 部品ファイルは、自分の見本を描く

部品だけのファイルには置くものが無い。**では何を描くのか**——その答えは「自分自身」で、
部品を 1 つずつ、名前と実寸を添えて並べた見本になる。設計書の読み手が部品の一覧に
求めるものはそれであり、「部品はどう見えるか」を画面と同じ描画器が答えることになる。

### 3.5 部品の見た目は何で決まるのか（2026-10-02）

**「frame と textbox と checkbox の違いが分からない」という指摘への答え。**
答えは身も蓋もなくて、**3 つとも長方形**である。違うのは色と大きさだけだった。
部品が持てるものは、いまも昔もこの 3 つしかない。

| 持つもの | 書き方 | 決まり方 |
|---|---|---|
| **図形** | `[ ]` `( )` `" "` `{ }` `--` など | 作図の語彙 14 種から選ぶ。[Mermaid から借りた括弧](diagram-model.md)である |
| **見た目** | `{ fill: …, line: …, color: …, align: …, weight: …, arrow: … }` | 直値。テーマは既定値を与えるだけ |
| **既定の大きさ** | `320x34` | ピンが大きさを言わなければこれを使う |

**だから部品の見本には「どう書くか」を並べてある。** 長方形が 3 色あっても、何が
それを決めているかは絵からは読めない——`[ ]` と書いてあれば読める。

#### 自分で足すには

```
parts {
  # 1. 色と大きさで足りるなら、1 行
  myBox     [ ] { fill: #fff8e1, line: #d8b96b, align: left }  320x34

  # 2. 絵が要るなら、同梱のステンシルを指す
  myRadio   [ ] { icon: ui/radio-on }                           16x16

  # 3. 自分で描いた絵でもよい
  myLogo    [ ] { icon: ./icons/logo.svg }                     120x40
}
```

**丸と点でできたラジオボタンは、1 の書き方では作れない。** 図形は 14 種しか無く、
「丸の中に点」はその中に無いからである。[図形は語彙、部品は絵](diagram-model.md)という
分け方の通りで、**UI コントロールは絵の側**に置いた。

### 3.6 同梱の部品（2026-10-02）

**作業場に何も置かなくても `use "default"` で一式が使える。**
「最低限のものは用意しておくべき」という指摘への答えで、35 種を同梱している。

| 区分 | 部品 |
|---|---|
| 面 | `frame` `panel` `banner` `alert` |
| 文字 | `title` `label` `body` `hint` `error` `link` `required` |
| 入力 | `textbox` `textarea` `select` `spinner` `slider` `checkbox` `checked` `radio` `selected` |
| ボタン | `primary` `secondary` `danger` |
| 一覧 | `grid` |
| 線 | `divider` `dividerV` `pointer` `guide` |
| 行を持つもの | `tree` `list` `menu` |
| その他 | `scrollbar` `scrollbarH` `image` `icon` |

**ファイルではなく文字列として製品に入っている。** CLI でも、フォルダを開いていない
ブラウザでも、地図を 1 つ持っただけの試験でも、同じものが在る必要があるからである。

作業場の部品ファイルはこれを**下敷きにできる**。違うところだけ書けばよい。

```
use "default"

parts {
  primary ( ) { fill: #2f6fb5, line: #2f6fb5, color: #ffffff } 320x38
}
```

#### 文字の行き先は、絵が決める（2026-10-02）

同じ `icon:` でも、文字がどこへ行くべきかは絵によって違う。**絵が自分で宣言する**。

| | 文字 | 例 |
|---|---|---|
| `under` | 絵の**下に**置く。名前のある「もの」の既定 | ルータ、作者が指した `.svg` |
| `inside` | 絵の**中に**。値を持つコントロール | ドロップダウン、数値入力 |
| `none` | **持たない** | スクロールバー、スライダー、ラジオ、画像枠 |

指摘で見つかった。ドロップダウンと数値入力の文字が、絵の下に置かれて**沈んで**いた——
どの絵も「名前が下に付くもの」として扱っていたからである。

**`none` の部品に文字を書いたら、黙って消さずに言う**（P6）。スクロールバーに文字を
書くのは間違いだが、消えたことが分からないほうが悪い。

#### 長いものは、長いまま描く

スクロールバーは隣の一覧と同じ高さであり、正方形のスクロールバーは
スクロールバーではない。**伸びる絵は箱の形に合わせて伸ばす**（ステンシルが
「何×何の格子に描いたか」を宣言する）。ルータのように形が決まっているものは
従来どおり正方形のまま中央に置く。

#### 候補が増えたら、区分の小窓に分ける（2026-10-02）

絵を 10 枚足したら、キャンバスの「＋ 部品」が**画面に収まらなくなった**。
収まらない先は誰にも押せないので、これは機能が無いのと同じである。

最初は**見出しで区切って送れるようにした**が、それでは足りなかった——
見出しがあっても一覧は 1 本のままなので、**下の区分に行くには上の区分を全部
送って通り過ぎる**ことになる。送る量は見出しを付けても変わらない。

| 直したこと | |
|---|---|
| **区分は「開く行」** | 上の段には区分だけが並ぶ。いまは 2 行（ネットワーク／画面部品）で、送るところが無い |
| **開いた先は親の横** | その区分の絵だけが、親の一覧の右に出る。右に余地が無ければ左に出る（画面の端でも押せる） |
| **一度に一区分** | 別の区分へマウスを移すと、前の区分は閉じる。開いているのは常に 1 本の枝 |
| **ひと呼吸置いて入れ替わる** | 小窓へ向かう手は斜めに動き、途中で隣の行を通る。触れた瞬間に入れ替えると、開いた一覧が手の届く前に消える。何も開いていないときは失うものが無いので即座に開く |
| **キーボードでも** | ↓↑ で行、→ で開く、← と Esc で 1 つ戻る。Esc で全部閉じるのは上の段にいるときだけ——区分を間違えた人が欲しいのは区分の一覧で、空の画面ではない |
| **区分は絵が持つ** | 名前の接頭辞（`net/` `ui/`）はファイルのためのもので、見出しは人のためのもの。別々に持たせる |

**十数個までは読まれ、それを超えると探される。** 小窓は、探すのを読むのに戻す
——読む一覧の長さが「区分の数」と「一区分の中身」に分かれ、どちらも十数個で収まる。

区分が十数個に育ったら、同じ理由でもう一段深くする余地がある（枝は 1 本しか
開かないので、段が増えても画面に出るのは常に 2 枚）。

#### 仕切る線・指す線（2026-10-02）

**「複雑な画面を描くなら、繋ぐための線とは別に、単独の線分が要る」という指摘への
答え。** 画面を仕切る罫線も、何かを指す矢印も、2 つの図形を関係づけてはいない。

```
free {
  titleRule  divider:          # 同梱の部品。色も太さも部品が持っている
  noteArrow  pointer:          # 矢印つきの線も部品でよい
  bare       --                # 部品を使わずに 1 本引くこともできる
}

layout {
  titleRule  @ ( 50,  80) 480x0    # 高さ 0 なら水平線
  noteArrow  @ (330, 240)  60x24   # 幅も高さもあれば、箱の対角線
}

style {
  titleRule { line: #c8ccd2, weight: 2 }   # 太さは数で書く
  noteArrow { slope: up }                  # 対角線は 2 本ある
}
```

**部品にできることが要点である。** 「この製品で何かを指す矢印」を `pointer` という
名前で 1 回決めれば、使うたびに色と太さと矢じりを書き直さずに済む——部品の存在
理由がそのまま当てはまる。記法と層の決め方は[作図モデル §10.1](diagram-model.md)。

GUI では、**線を選ぶと操作列に矢印 4 つと太さ 3 つが出る**。押すと書かれるのは
スタイル層の 1 行で、[ドラッグと同じく 1 回の操作 ＝ 1 つのバイト範囲](diagram-model.md)である。
線は細くて掴みにくいので、エディタの中だけ**見えない太い線を重ねて**ある。

#### 表（一覧）の部品

**行数も列数も画面ごとに違うので、絵が言うのは「表がここに入る」ことだけ**にした。
見出し行と数行、列の区切りが引いてあり、中身は線で表す。中に入力欄やチェックを
置きたい場合、いまは座標で重ねれば描ける——[入れ物としての表](#45-まだやっていないこと2026-10-02-の指摘より)は別の話として残っている。

#### どんな絵があるか

**一覧も見本で答える。** `use "icons"` と 1 行だけ書いたファイルを文書に取り込むと、
**同梱の絵が全部、書くべき名前つきで**出る。一覧は手で書かずに絵の表から作るので、
絵を足せば一覧も増える。

```
# shared/icon-list.dgm
use "icons"
```

同梱は 21 枚——ネットワーク 10（`net/*`）と画面部品 11（`ui/*`）。
ベンダのアイコンセットは[同梱しない](diagram-model.md)ので、必要なら
`{ icon: ./icons/ec2.svg }` のように自分のファイルを指す。

#### 画面を 4 枚目まで描いて分かったこと

入力部品を一通り使う画面（利用者検索）を描いたら、**PDF では同梱の絵がすべて
歪んでいた**。`mapPathData` が SVG の**相対コマンドを絶対として読み**、`h` `v` `c` を
黙って捨てていた。ネットワーク図のアイコンも同じように壊れていたはずで、
4 枚目を描くまで誰も気づいていなかった。[描いてから決める](#33-なぜ今作らないか)は
語彙だけの話ではない。

#### 画面側に残るもの

```
use "../../shared/ui-parts.dgm"

free {
  idLabel  label:"ログイン ID"
  idBox    textbox:"yamada@example.co.jp"
  submit   primary:"ログイン"
}
layout {
  idLabel  @ ( 70,  96)      # 大きさは部品の既定
  idBox    @ ( 70, 116)
  submit   @ ( 70, 284)
}
```

**画面のファイルに色は 1 つも書かれていない**（`tools/check-parts.mjs` が 58 項目で確かめる）。
残るのは「何が、どこに」だけで、差分に出るのもそれだけになる。部品を 1 行変えれば、
それを使う画面がすべて変わる——検査はこれを、エディタで 1 回書き換えて 3 枚とも
変わることで確かめている。

### 3.7 並べ方は入れ物が決める（2026-10-03）

**「いまの形は WinForms。WPF のように積んで並べたいこともあるし、同じものを
ピクセル単位で揃えたいこともある」という指摘への答え。**

座標を 1 つずつ書く形式には、**同じ事実が座標の数だけ複製される**という弱点が
あった。項目を 1 つ挿入すると下の全部が書き換わり、1 行足しただけの変更が 6 行の
差分になる。[記法と層の決め方は作図モデル L2](diagram-model.md) にあり、ここでは
画面を描く側から書く。

```
free {
  frame   frame:
  title   title:"サービスにログイン"
  idField ""                       # 何も描かない入れ物（枠線の無い文字）
  idLabel label:"ログイン ID"
  idBox   textbox:
  submit  primary:"ログイン"
}

layout {
  frame @ ( 40,  20) 380x392       # 座標を持つのは枠だけ

  stack frame (down; gap: 22; pad: 30) { title ; idField ; submit }
  stack idField (down; gap: 2; pad: 0) { idLabel ; idBox }
}
```

**揃うのは計算の結果なので、ずれようがない。** 「ピクセル単位で全く同じものを
いくつも並べる」は、幅を書かないことで達成される——縦に積めば幅は枠いっぱいに
揃い、部品が同じなら高さも同じになる。

2 列の画面は `grid` で、**セルに名前を書く**。

```
  grid frame (cols: 1fr, 1fr; gap: 16 40; pad: 30) {
    title     ; title              # 同じ名前を並べると、そのセルをまたぐ
    titleRule ; titleRule
    filters   ; results
    search    ; clear              # . と書けば空のセル
  }
```

#### 入れ物と、行を持つ部品

| | 子は何か | 用 |
|---|---|---|
| `stack` | **id** | 縦か横に積む。交差軸は伸びる |
| `grid` | **id** | 行と列。列の幅は `cols:`、省けば均等割り |
| `tabs` | **id** | 見出しは全部・中身は 1 枚。`show:` でどの頁を描くか |
| `scroll`（設定） | — | `stack` にも `grid` にも付く。切れていて続きがあることを描く |
| `tree` / `list` / `menu` | **文字** | 入れ物ではなく**行を持つ部品**。中身は id ではなく階層や並び。下記 |

**`scroll` は入れ物の種類ではなく設定にした。** 「スクロールする領域」は、必ず
何らかの並べ方も持っている——`scroll` を種類にすると `stack` と同じ計算をもう 1 つ
書くことになり、しかも「表の領域がスクロールする」が書けなくなる。CSS で
`overflow` が箱の性質であって配置方法でないのと同じ理由である。

```
  tabs detail (show: perm) { basic ; addr ; perm }     # 見出しは頁の名前から
  stack permList (down; gap: 10; pad: 10; scroll) { row1 ; row2 ; row3 }
```

| 決めたこと | |
|---|---|
| **頁の名前が見出し** | `basic "基本情報"` の文字が見出しになる。頁の中には書かれない——同じ題を 2 か所に書かせない |
| **描かれない頁は、下に並べない** | 置き場所の無い図形は図の下に並べる規則があるが、タブの頁は**わざと描いていない**ので対象外 |
| **切れた行は描かない** | 入りきらない行は無い扱い。SVG の切り抜きは id を要り、PDF と PPTX に同じ結果を渡せないので、幾何で落とす |
| **切れているのは間違いではない** | だから `scroll` の付いた入れ物には「入りきらない」の注記を出さない |
| **大きさは中身ではなく自分で持つ** | スクロールする領域は「中身より短い」ことが仕様なので、高さは部品の既定かピンから取る |

**子が id なら入れ物、子が文字なら部品。** この線引きが要るのは、ツリーの項目 20 個に
id を 20 個与えると[項目一覧](#6-項目一覧との連動設計のみ未実装)が 20 行になるからで、
実際に項目定義が要るのは**ツリー 1 つ**である。中身を持つ部品は markdown の箇条書きで書く。

```
free {
  nav tree: {
    - 全社
      + 営業本部           # + ＝ 閉じている枝
      - 管理本部
        - 情報システム部 *  # * ＝ 選んでいる行
        - 総務部
  }
}
```

| 決めたこと | |
|---|---|
| **行は markdown の箇条書き** | `-` と `+`、末尾の `*`。**状態の印はこの 2 つだけ**に固定する——増やし始めると表記が壊れる |
| **深さは字下げの入れ子** | 「空白 2 つで 1 段」と決め打ちしない。自分の中で揃っているファイルはどちらでも読める |
| **図形の範囲は一覧ごと** | 消せば一覧ごと消える。1 つの図形が複数行を占める唯一の形 |
| **入りきらない行は描かない** | 描かれなかったぶんは縁のバーが言う。スクロールする入れ物と同じ答え |
| **絵は中身から描く** | 同梱の `ui/tree` などは「行が無いとき」の絵であり、行があればそこから描き直す。ここだけが**内容で変わる絵**である |
| **行を持たない部品に書いた行は、黙って消さない** | `textbox:` に行を書いたら注記が出る |

GUI では、行を持つ図形の**文字の編集と種類変更を出さない**。1 行の入力欄では
複数行の中身を編集できないためで、いまはソースで書く。

#### この形にした理由

| | |
|---|---|
| **実装と同じ語彙になる** | WPF の人は StackPanel、Web の人は flex として読める。座標だけの形式は「WinForms で作れ」と言っているのに近い |
| **差分が事実と一致する** | 項目を 1 つ足す ＝ 1 行。下の全部は動かない |
| **[項目一覧](#6-項目一覧との連動設計のみ未実装)の順番が決まる** | Y 座標でソートするという暗黙の規則が要らない。書いてある順がそのまま項目番号になる |
| **入れ子が深くならない** | 入れ物の中に入れ物を書かず、名前で繋ぐ。どんな画面でもブロックの深さは 1 |

**入りきらない中身は、描いたうえで注記する**（`入れ物に中身が入りきらない: frame`）。
隠せば間違いも隠れる。標本の 4 画面はこの形で書き直してあり、**子の座標は 1 つも無い**。
5 枚目（[利用者詳細](../sample/docs/auth-design/detail-screen.dgm)）はタブと
切れる一覧の標本である。

#### GUI では

| 操作 | 書かれる行 |
|---|---|
| 入れ物の中の図形をドラッグ | その図形に**ピンが付く**（入れ物から外れる）。既存の規則そのまま |
| 「入れ物に戻す」 | ピンの行が消え、また並びに乗る |
| 入れ物の中の図形を削除 | 図形の行・ピンの行に加えて、**入れ物からも名前が消える**（`grid` は空セル `.` になり形を保つ、`stack` は名前ごと抜ける） |

#### まだやっていないこと

| | |
|---|---|
| **ドラッグでの並べ替え** | いまドラッグは「外す」。セルからセルへ動かして入れ替えるのは、当たり判定をセルに対して持つ必要がある |
| **一覧の行を GUI で編集する** | いまはソース。複数行なので、1 行の入力欄では足りない |
| **セルの中での寄せ** | いまは幅いっぱい。右寄せの `1 行だけ` は、ピンで外すか列を分けることになる |
| **入れ物の既定の大きさ** | 入れ物はピンか親のセルから大きさをもらう。どちらも無ければ注記して、並べずに置く |

## 4. GUI での操作

部品ライブラリは**ソースで開く**。置かれたものが無いので動かすものも無く、見本は
ファイルそのものではなく**ファイルを描いた絵**だからである——それをキャンバスで
開けば、どこにも書き戻らない絵を動かせてしまう。

画面そのものは他の図と同じく**ソースを直接書く**。[ドラッグでの配置](diagram-model.md)は未実装である。
画面設計はとりわけ**マウスで置きたい**図なので、[自由配置型はマウスが主](diagram-model.md)という
既存の判断がそのまま当てはまる。

## 4.5 まだやっていないこと（2026-10-02 の指摘より）

|---|---|

| **項目一覧との連動** | 下の §6 |

## 6. 項目一覧との連動（設計のみ・未実装）

**画面を描いたら、項目一覧の表はほぼ必ず作る。** いまは画面と表が別々に書かれており、
同じ事実（この項目は必須か、右寄せか、何番か）が 2 か所にある。[計算で出せるものは
ファイルに書かない](decisions.md)という原則からすると、これは直すべき重複である。

| つなぐもの | いま | こうしたい |
|---|---|---|
| **番号** | 表の No 列は手書き。画面の丸番号も手書き | 画面の並び順から**生成**し、画面にも表にも同じ番号が出る |
| **寄せ** | 画面の `align` と表の「寄せ」列が別 | どちらかが正本で、他方は**生成** |
| **必須** | 表の「必須」列だけにある | 必須なら画面の見た目にも出る（印、枠の色） |

**鍵は、表の行と画面の図形を何で結ぶかである。** 画面の図形は既に `idBox` のような
id を持っているので、表に「項目 ID」の列を置けば結べる。番号は結んだ結果から計算できる。

決めるべきこと: どちらを正本にするか（表か画面か）、結びの列をどう書くか、
結べなかった行・結ばれなかった図形をどう報告するか（P6）。

## 5. ループの表現（作図一般）

繰り返しは二つの書き方がある。どちらも既存の語彙で足りる。

| 書き方 | 使いどころ |
|---|---|
| **接続が戻る**（`save --> read`） | 制御の流れとしての繰り返し。自動レイアウトが脇の通路を通して戻す |
| **群れに名前を付ける**（`group loop "繰り返し: 全件" { … }`） | 「ここからここまでが繰り返し」という範囲の明示 |

両方を重ねるのが普通で、[戻る接続は図形を貫かずに迂回する](decisions.md)ので読める。
