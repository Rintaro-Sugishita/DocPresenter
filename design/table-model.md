# 表モデル設計案 — `.table` の形式

作成: 2026-09-20 / 対象: 要件 R7（複雑なテーブル）
関連: [編集 UI 設計案](editor-model.md) / [作図モデル設計案](diagram-model.md) / [要件定義](requirements.md)

## 1. 必要なもの、と、やらないこと

設計書の表に実際に要るのは次である。

- **セル結合**（縦・横）
- **罫線の制御** — ヘッダ下を太く、区切りを二重に、外枠、といった実務上の要求
- **セル内の Markdown** — 強調・インラインコード・リンク・改行、そして**箇条書き**
- 列幅・寄せ・網掛け
- **Excel からの貼り付け**

一方、**やらないこと**を先に決めておかないと際限がない。

| やらない | 理由 |
|---|---|
| 数式・計算 | 設計書の表は計算表ではない |
| 条件付き書式 | 同上 |
| グラフ | 図（`.dgm`）の領分 |
| 任意のフォント・サイズ・色 | **テーマのトークンに限定する**（§5） |

線引きの基準は **「設計書の表として意味があるか」** であり、見た目の自由度はテーマで縛る。

そしてもう一つ、[作図モデル設計案 §5](diagram-model.md) と同じ制約が効く。

> **語彙を、出力先が表現できる範囲に制限する。**

PPTX（DrawingML の表）と PDF の双方でそのまま再現できないものは採らない。ここを緩めると R6（編集可能な PPTX）が崩れる。

## 2. CSV は保存形式にしない

前段で「単純な表は CSV 互換にすれば Excel から直接書き出せる」と述べたが、**撤回する**。

結合も罫線もセル内 Markdown も CSV には載らない。CSV を保存形式にすると、装飾を別ファイルに逃がすことになり、[作図モデル設計案](diagram-model.md)で 1 ファイル・セクション分割と決めた方針とも食い違う。

> **CSV / TSV は「取り込み経路」であって、保存形式ではない。**

Excel からの貼り付けは、§3 の内容層へ直接流し込む（`ErCreator.Canvas` のグリッドが既にやっていること）。

## 3. 二層構成 — 内容（結合込み）とスタイル

[作図モデル設計案](diagram-model.md)の 3 層分離と同じ原則を適用する。ただし表では**結合を内容層に置く**。結合はグリッドの形そのものであり、これを分離すると**L1 だけ読んでも表の形が分からなくなる**ためである。

### L1 内容層 — グリッドと結合

```
| 分類 | 項目       | 型              | 必須 | 説明                    |
|------|-----------|-----------------|------|------------------------|
| 認証 | 方式       | `varchar(32)`   | ○    | OAuth 2.0 / PKCE 必須   |
| ^    | 有効期限   | `int`           | ○    | 単位は**分**。既定 1440 |
| ^    | 再発行     | `bool`          | —    | @1                      |
| 権限 | ロール     | `varchar(16)`   | ○    | 下記のいずれか          |
| ^    | 継承       | `bool`          | —    | 継承は行わない          |

[@1]:
- 失効前 5 分以内のみ許可
- 連続再発行は 3 回まで
```

- `^` … **上のセルと結合**（縦結合）
- `<` … **左のセルと結合**（横結合）

結合マーカーを行内に置くことで、**素の Markdown として読んでも表の形が見える**。軸 A がそのまま保たれる。

### L2 スタイル層 — 罫線・寄せ・幅

```
style {
  theme: grid                      # 既定は全セル細罫線

  header      { bottom: thick }    # ヘッダ下を太罫線
  col:分類    { right: thick, align: center }
  col:必須    { align: center, width: 6em }
  col:説明    { width: 40% }
  row:odd     { fill: shade }
}
```

## 4. 罫線は「既定 ＋ 変えたところだけ」

ここが表形式で最も壊れやすい点である。全セル分の罫線を書くと、10 列 30 行の表で 300 行の装飾定義が生まれ、差分は読めなくなる。

[作図モデル設計案](diagram-model.md)の**疎なピン留め**と同じ規律を適用する。

> **既定はテーマが決める。人が変えたところだけを疎に記録する。**

セルを 1 つ増やしても装飾定義は 1 行も変わらない。これが成立して初めて、GUI で罫線をいじっても差分が汚れない。

### セレクタは意味で指す

```
header          ヘッダ行
col:分類        「分類」列（ヘッダ名で指す）
row:odd         奇数行
```

**A1 形式（`B3` 等）も逃げ道として認める**が、既定にはしない。行や列を挿入すると全ての参照がずれ、[レビューコメントで行番号を避けた判断](review-model.md)と同じ問題を招く。ヘッダ名で指せば、列の並べ替えにも耐える。

## 5. スタイルの値はテーマのトークンに限る

```
  border : none / thin / thick / double / dashed
  fill   : none / shade / accent / warn
  align  : left / center / right
```

`#3A7BD5` のような直値は書かせない。理由は三つ。

1. **出力先が保証できる。** PPTX・PDF・HTML で同じ見た目になる範囲に収まる
2. **文書間で見た目が揃う。** 設計書の束としての体裁が崩れない
3. **差分が読める。** `thick` は読めるが `1.5pt solid #333` は読めない

テーマ自体は差し替え可能にし、案件ごとの体裁はそこで吸収する。

## 6. セル内 Markdown の範囲

| 要素 | 扱い |
|---|---|
| 強調・インラインコード・リンク | **グリッド内に直接書ける** |
| 明示的な改行 | 書ける |
| 箇条書き・段落・コードブロック | **参照方式**（`@1` → グリッド下で定義） |
| 表の入れ子 | **やらない** |

ブロック要素をグリッド内に直接書くと、1 セル 1 行という前提が壊れて可読性が失われる。§3 の `[@1]:` 形式は **Markdown の参照リンク記法と同じ発想**であり、既存の書き手にとって異物ではない。

`|` はセル内でエスケープが必要になる。これは Markdown テーブルと同じ制約なので、そのまま踏襲する。

## 7. 段階的に作る

「やることが多い」のは事実なので、順序を決めておく。

| 段階 | 範囲 | 満たす要求 |
|---|---|---|
| **1** | 内容層 ＋ 結合 ＋ ヘッダ、罫線は既定テーマのみ、Excel 貼り付け | R7 の中核。**ここだけで既存 Markdown を明確に超える** |
| **2** | スタイル層（罫線・寄せ・幅・網掛け） | 日本の設計書の体裁要求 |
| **3** | セル内ブロック（参照方式） | 箇条書きを含むセル |

段階 1 の時点で「セル結合のある表を Excel から貼り付けて、HTML / PDF / PPTX に出せる」が成立する。先行事例がどれも満たしていない水準に、最初の段階で到達する。

## 8. 未確定事項

- **結合マーカーの記号** — `^` / `<` でよいか。既存の Markdown 表拡張（PHP Markdown Extra 系、DDmdTable 等）との衝突を確認する
- **列幅の単位** — `em` / `%` / `px` の混在を許すか。PPTX と PDF で解釈を揃えられるか
- **ヘッダ名が重複・空の場合のセレクタ** — `col:説明` が一意に定まらないとき、A1 形式へ落とすか
- **結合セルの罫線** — 結合されたセルの内部に罫線を引く指定をどう表すか（Excel では起きうる）
- **グリッドの桁揃え** — 書き戻し時に `|` の位置を揃えるか。揃えると 1 セルの編集で行全体のバイトが動き、[書き戻しの規律](editor-model.md)と衝突する。**揃えない**のが整合的だが、素の可読性は落ちる
