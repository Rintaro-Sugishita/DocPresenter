# 表モデル設計案 — `.table` の形式

作成: 2026-09-20 / 対象: 要件 R7（複雑なテーブル）
関連: [編集 UI 設計案](editor-model.md) / [作図モデル設計案](diagram-model.md) / [要件定義](requirements.md)

## 0. 編集はグリッドで行う（§7）

表のソースを直接書きたい場面は稀である。**表をクリックしたらグリッドが開く。**
ソースは逃げ道として 1 クリックで出せるが、既定ではない。

## 1. 必要なもの、と、やらないこと

設計書の表に実際に要るのは次である。

- **セル結合**（縦・横）
- **罫線の制御** — ヘッダ下を太く、区切りを二重に、外枠、といった実務上の要求
- **セル内の Markdown** — 強調・インラインコード・リンク・改行、そして**箇条書き**
- 列幅・寄せ・網掛け
- **Excel からの貼り付け**

一方、**やらないこと**を先に決めておかないと際限がない。

| やらない | 理由 |
|---|---|
| 数式・計算 | 設計書の表は計算表ではない |
| 条件付き書式 | 同上 |
| グラフ | 図（`.dgm`）の領分 |
| 任意のフォント・サイズ・色 | **テーマのトークンに限定する**（§5） |

線引きの基準は **「設計書の表として意味があるか」** であり、見た目の自由度はテーマで縛る。

そしてもう一つ、[作図モデル設計案 §5](diagram-model.md) と同じ制約が効く。

> **語彙を、出力先が表現できる範囲に制限する。**

PPTX（DrawingML の表）と PDF の双方でそのまま再現できないものは採らない。ここを緩めると R6（編集可能な PPTX）が崩れる。

## 2. CSV は保存形式にしない

前段で「単純な表は CSV 互換にすれば Excel から直接書き出せる」と述べたが、**撤回する**。

結合も罫線もセル内 Markdown も CSV には載らない。**寄せ（右寄せ・左寄せ・中央）すら表現できない。** CSV を保存形式にすると、装飾を別ファイルに逃がすことになり、[作図モデル設計案](diagram-model.md)で 1 ファイル・セクション分割と決めた方針とも食い違う。

対比すると、表現力の階層は次のようになっている。

| | 内容 | **寄せ** | 結合 | 罫線 | セル内 Markdown |
|---|:--:|:--:|:--:|:--:|:--:|
| CSV | ○ | **✗** | ✗ | ✗ | ✗ |
| Markdown テーブル | ○ | **○（列単位）** | ✗ | ✗ | インラインのみ |
| **`.table`** | ○ | **○（列＋セル単位）** | ○ | ○ | ○ |

**Markdown テーブルが区切り行で寄せを表現できている**点は重要で、§3 でこれをそのまま使う。

> **CSV / TSV は「取り込み経路」であって、保存形式ではない。**

Excel からの貼り付けは、§3 の内容層へ直接流し込む（`ErCreator.Canvas` のグリッドが既にやっていること）。

## 3. 二層構成 — 内容（結合込み）とスタイル

[作図モデル設計案](diagram-model.md)の 3 層分離と同じ原則を適用する。ただし表では**結合を内容層に置く**。結合はグリッドの形そのものであり、これを分離すると**L1 だけ読んでも表の形が分からなくなる**ためである。

### L1 内容層 — グリッドと結合

```
| 分類 | 項目       | 型              | 必須 | 説明                    |
|------|-----------|-----------------|:----:|------------------------|
| 認証 | 方式       | `varchar(32)`   | ○    | OAuth 2.0 / PKCE 必須   |
| ^    | 有効期限   | `int`           | ○    | 単位は**分**。既定 1440 |
| ^    | 再発行     | `bool`          | —    | @1                      |
| 権限 | ロール     | `varchar(16)`   | ○    | 下記のいずれか          |
| ^    | 継承       | `bool`          | —    | 継承は行わない          |

[@1]:
- 失効前 5 分以内のみ許可
- 連続再発行は 3 回まで
```

- `^` … **上のセルと結合**（縦結合）
- `<` … **左のセルと結合**（横結合）
- **区切り行の `:` で列の寄せを表す** — 標準 Markdown テーブルとまったく同じ記法（`|:---|` 左、`|:---:|` 中央、`|---:|` 右）

結合マーカーと寄せを行内に置くことで、**素の Markdown として読んでも表の形が見える**。軸 A がそのまま保たれる。

#### グリッド部は「ほぼ妥当な Markdown テーブル」になる

寄せを区切り行で表すことで、`.table` のグリッド部は **GFM のテーブルとして読める状態**に保たれる。独自なのは結合マーカー `^` / `<` とブロック参照 `@1` だけである。

これは軸 A・軸 B の両方に効く。本製品を知らない人間も、AI も、**表として読める**。寄せをスタイル層に追い出していたら、この性質は失われていた。

### L2 スタイル層 — 罫線・幅・網掛け、および寄せの例外

列単位の寄せは L1 の区切り行が持つので、**スタイル層に書くのは例外だけ**である。

```
style {
  theme: grid                      # 既定は全セル細罫線

  col:分類    { width: 18% }       # 列幅は表全体に対する割合
  cell:表示/説明 { fill: #fdf0d5 }  # 色は書いた人が選ぶ
  col:必須    { width: 6em }
  col:説明    { width: 40% }
  row:odd     { fill: tint-1 }     # 縞（手で書けば効く。GUI からは出さない）
  col:再発行  { fill: pending }    # 未確定であることを示す

  cell:認証/説明 { align: center } # 特定セルだけ寄せを変える（例外）
}
```

## 4. 罫線は「既定 ＋ 変えたところだけ」

ここが表形式で最も壊れやすい点である。全セル分の罫線を書くと、10 列 30 行の表で 300 行の装飾定義が生まれ、差分は読めなくなる。

[作図モデル設計案](diagram-model.md)の**疎なピン留め**と同じ規律を適用する。

> **既定はテーマが決める。人が変えたところだけを疎に記録する。**

セルを 1 つ増やしても装飾定義は 1 行も変わらない。これが成立して初めて、GUI で罫線をいじっても差分が汚れない。

### セレクタは意味で指す

```
header          ヘッダ行
col:分類        「分類」列（ヘッダ名で指す）
row:odd         奇数行
```

**A1 形式（`B3` 等）も逃げ道として認める**が、既定にはしない。行や列を挿入すると全ての参照がずれ、[レビューコメントで行番号を避けた判断](review-model.md)と同じ問題を招く。ヘッダ名で指せば、列の並べ替えにも耐える。

## 5. スタイルの値はテーマのトークンに限る

```
  border : none / thin / thick / double / dashed
  fill   : （§5.1）
  align  : left / center / right
  width  : （§8 未確定）
```

`#3A7BD5` のような直値は書かせない。理由は三つ。

1. **出力先が保証できる。** PPTX・PDF・HTML で同じ見た目になる範囲に収まる
2. **文書間で見た目が揃う。** 設計書の束としての体裁が崩れない
3. **差分が読める。** `thick` は読めるが `1.5pt solid #333` は読めない

テーマ自体は差し替え可能にし、案件ごとの体裁はそこで吸収する。

なお**塗りつぶしは L1 に置かない**。結合は表の形、寄せは標準 Markdown が持つ表現だったが、塗りつぶしは純粋に見た目であり、内容層に混ぜる理由が無い。

### 5.1 塗りつぶしは「意味」と「区分」を分ける

設計書で塗りつぶしが使われる場面を並べると、二種類に分かれる。

| 用途 | 例 |
|---|---|
| **意味を持つ** | 変更箇所・対象外・要確認・削除予定 |
| **区分を分けるだけ** | 機能グループごとの色分け |

そこでトークンも二系統に分ける。

```
# 意味トークン（何を表すか）
fill: changed     変更あり
      pending     未確定・要確認
      disabled    対象外・入力不可
      removed     削除予定

# 区分トークン（意味を持たない色分け）
fill: tint-1 / tint-2 / tint-3 / tint-4
```

> **2026-09-26 撤回。** 意味トークンの語彙は固定しない。**塗りつぶしも文字色も、書いた人が色を選ぶ**
> （`fill: #fdf0d5` / `color: #c62828`）。撤回の理由は[文字書式 §2.1](inline-format.md) に書いた。
> 要点は、語彙の中心にあった `changed` が**そもそも人の書くべき情報ではなかった**ことである。
> 変更箇所は[Git の差分から自動で付ける](diff-marking.md)（R13）。
> 以下は撤回された案の記録として残す。`{.changed}` などで書かれた既存ファイルは今も描画する。

意味トークンは**この 4 種で確定**とする。案件ごとの拡張は行わない。増やせるようにすると、文書ごとに語彙が食い違い、凡例も AI の解釈も一貫しなくなる。4 種で表せないものは、塗りつぶしではなく表の列（「状態」列など）で表すべきである。

**意味トークンを分けて持つ利点は、凡例を自動生成できること。**

> ▨ 変更あり ▨ 未確定 ▧ 対象外

塗りつぶしが `#FFF2CC` のような直値だと、何を意味するかはツールに分からず、凡例は人が手で書いて保守するしかない。`changed` と書いてあれば、**使われているトークンを集めて凡例を出力できる**。これは軸 B（AI が正確に読める）にも直結する。AI は黄色から意味を推し量れないが、`changed` は読める。

#### 凡例は文書末に出す

凡例の位置は**文書末**とする。出力形式ごとの扱いは次のとおり。

| 出力 | 位置 |
|---|---|
| HTML | 末尾 |
| PDF | 最終ページ |
| PPTX | 最終スライド |

規則は三つ。

1. **実際に使われた意味トークンだけを載せる。** 語彙の全 4 種を常に並べない
2. **区分トークン（`tint-*`）は載せない。** 意味を持たないため、凡例に出しても情報にならない
3. **文書単位で集計する。** 表は外部ファイルとして複数文書から参照されるため（[編集 UI 設計案](editor-model.md)）、凡例はその文書が**実際に参照している表**から集める。同じ表でも、置かれる文書によって凡例の内容は変わりうる

### 5.2 印刷と色覚への配慮はテーマが担う

- **白黒印刷で潰れない。** 設計書は印刷・納品される（R5）。テーマ側で濃度を印刷安全な範囲に収める
- **色だけに依存しない。** 意味トークンにはテーマが網掛けパターンを併用できる。直値を許さないからこそ、この配慮を一箇所で効かせられる

これは「値を直接書かせない」という制約が、単なる縛りではなく**利益を生んでいる**例である。

### 5.3 範囲セレクタ

区分の色分けでは、連続したセルの塊を指したい。

```
style {
  header               { fill: #eef0f3 }
  row:odd              { fill: tint-1 }
  col:必須             { width: 6em }
  cell:認証/説明       { align: center }
  range:認証..権限     { fill: tint-2 }   # 行の範囲
}
```

範囲も**位置ではなく意味（ヘッダ名・見出しセルの値）で指す**。行番号で指すと挿入のたびに全部ずれる。

## 6. セル内 Markdown の範囲

| 要素 | 扱い |
|---|---|
| 強調・インラインコード・リンク | **グリッド内に直接書ける** |
| 明示的な改行 | 書ける |
| 箇条書き・段落・コードブロック | **参照方式**（`@1` → グリッド下で定義） |
| 表の入れ子 | **やらない** |

ブロック要素をグリッド内に直接書くと、1 セル 1 行という前提が壊れて可読性が失われる。§3 の `[@1]:` 形式は **Markdown の参照リンク記法と同じ発想**であり、既存の書き手にとって異物ではない。

`|` はセル内でエスケープが必要になる。これは Markdown テーブルと同じ制約なので、そのまま踏襲する。

## 7. 段階的に作る

「やることが多い」のは事実なので、順序を決めておく。

| 段階 | 範囲 | 満たす要求 |
|---|---|---|
| **1** | 内容層（結合 ＋ ヘッダ ＋ **列の寄せ**）、罫線は既定テーマのみ、Excel 貼り付け | R7 の中核。**ここだけで既存 Markdown を明確に超える** |
| **2** | スタイル層（罫線・塗りつぶし・幅・セル単位の寄せ）＋ 凡例の自動生成 | 日本の設計書の体裁要求 |
| **3** | セル内ブロック（参照方式） | 箇条書きを含むセル |

段階 1 の時点で「セル結合のある表を Excel から貼り付けて、HTML / PDF / PPTX に出せる」が成立する。先行事例がどれも満たしていない水準に、最初の段階で到達する。

## 8. 未確定事項

- **結合マーカーの記号** — `^` / `<` で実装した（[`packages/core`](../packages/core)）。既存の Markdown 表拡張（PHP Markdown Extra 系、DDmdTable 等）との衝突確認は未了
- ~~ファイル内のコメント記法~~ → **決定**: `#` で始まる行。**グリッドの前にのみ置ける**（グリッド行は `|` で始まるため衝突しない）
- ~~セル内の `|`~~ → **決定**: `\|` でエスケープする（Markdown テーブルと同じ）
- **列幅の単位** — `em` / `%` / `px` の混在を許すか。PPTX と PDF で解釈を揃えられるか
- **ヘッダ名が重複・空の場合のセレクタ** — `col:説明` が一意に定まらないとき、A1 形式へ落とすか
- **結合セルの罫線** — 結合されたセルの内部に罫線を引く指定をどう表すか（Excel では起きうる）
- ~~意味トークンの語彙~~ → **決定**: `changed` / `pending` / `disabled` / `removed` の 4 種で確定。拡張しない（§5.1）
- ~~凡例の出し方~~ → **決定**: 文書末。使われたトークンのみ、文書単位で集計（§5.1）
- ~~グリッドの桁揃え~~ → **決定・実装済み**: 編集時の自動整形は**行わない**。1 セルの編集で表全体が再整形されると[書き戻しの規律](editor-model.md)が崩れるため。代わりに**明示的な「表を整形」コマンド**を用意し、整形は独立したコミットとして出す（コードフォーマッタと同じ扱い）。自動と手動を混ぜないことが要点。ただし**1 セルの編集では、そのセルの桁幅を保てる範囲で保つ**（短くなる・同じなら埋め戻す）ので、普段は崩れない（§7）

## 7. グリッド編集

### 7.1 書き戻しの粒度

| 操作 | 書き換える範囲 |
|---|---|
| セルの編集 | **そのセルの行 1 行だけ** |
| 行の追加・削除 | その 1 行の挿入・削除 |
| 寄せの変更 | **区切り行だけ** |
| 列の追加・削除 | グリッドの全行（列は全行にまたがるので、それが変更の実体） |
| 貼り付け | 貼った範囲を含むグリッド |
| 表を整形 | グリッド全体（**明示的に実行したときだけ**） |

セルはバイト範囲ではなく**行単位**で書き戻す。`\|` のエスケープと桁を合わせるための空白が入るため、
セルごとにバイト範囲を追うより**行の中のフィールドを差し替えるほうが正確**であり、1 行はすでに十分小さい。

`#` コメント・`@` ブロック・`style {}`・`range {}` の各節には、どの操作でも触れない。

### 7.2 1 セルの編集で桁を崩さない

自動整形はしないが、**フィールドの幅は保てる範囲で保つ**。値が短くなる・同じなら空白で埋め戻し、
長くなるときだけ押し広げる。日常の編集では源ファイルの桁が崩れず、崩れたときは「整形」で直す。

### 7.3 選択セルの上に常にテキストボックスを置く

これは**日本語入力のための構造**である。

セルを「フォーカスできるだけの要素」にすると、**IME の変換対象が存在しない**。
最初の 1 打が消える表は使い物にならない。したがって、

> **選択セルの上に、常に focus を持ったテキストボックスを重ねる。**

移動中は透明で、セル自身の文字が透けて見える。何か入力された時点（`compositionstart` または
`input`）で編集中に切り替わり、セルの文字を隠す。Excel 系のグリッドが同じ構造を採るのはこのためである。

### 7.4 スタイルの操作

塗りつぶし・文字色・列幅をグリッドから付ける。**UI の語彙は、ファイルが既に持っているセレクタそのもの**である。

| ボタンの「対象」 | 書かれるセレクタ |
|---|---|
| このセル | `cell:行の名前/列の名前` |
| この行 | `range:名前..名前`（自分自身への範囲） |
| この列 | `col:列の名前` |
| ヘッダ | `header` |

UI のために新しい概念を作っていないことが要点である。**行も列もセルも「名前」で指す**ので、
[行が動いても規則は同じものを指し続ける](#)。位置で指していたら、行を 1 つ挿れただけで全部ずれる。

**縞（奇数行 / 偶数行の塗り）は対象に入れない。** 縞は「この表について何かを言っている」わけではなく
見た目であり、[ヘッダ下の罫線と同じくテーマが引く](theme.md)。表ごとに設定させると、表を作るたびに
同じ指定を書くことになり、差分にも並ぶ。既定テーマは `--stripe` トークンを 1 つ持つだけで、縞を出す
テーマはそれを塗りに変える。**ファイルに既にある `row:odd` / `row:even` は読み続け、描画も続ける**
（[P6 黙って捨てない](decisions.md)）。手で書けば効く逃げ道は残る。

「この行」に `range:` を使うのは、`row:` セレクタが奇数 / 偶数 / 全部しか表せないためである。
範囲セレクタは先頭行と末尾行を**その行の先頭セルの文字**で指すので、1 行だけの範囲がそのまま
「この行」になる。語彙を増やさずに済んだ。

書き戻しは規則 1 行の追加・書き換え・削除である。

- 同じセレクタの規則が既にあれば、**行を足さずに書き換える**
- 宣言が空になった規則は、**空の `{ }` を残さず行ごと消す**
- `style { }` 節がまだ無ければ、ファイル末尾に作る
- 付いている色をもう一度押すと外れる

#### 罫線の太線・二重線はやめた

**設計書の表として過剰である。** ヘッダ下の罫線のような「常にそうしたい」ものは
**テーマが引く**べきもので、表ごとに書くものではない。表ごとに書けるようにすると、
文書によってヘッダの見え方が変わる。

#### 行と列は右クリックのメニューに置く

上下・左右の両方を出すと 6 個になり、**常に使う色や寄せを押しのける。**
行と列の増減は「ときどき使うもの」なので、右クリックに逃がす。

ツールバーに残すのは、**押す頻度が高いもの**（寄せ・色）と、**そこにしか無いもの**
（ソース整形・ソース表示）だけである。

**セルを編集中は自前のメニューを出さない。** そのときに要るのはコピー・貼り付けで、
ブラウザの持っているメニューのほうが優れている。

#### セルの中はテキストボックスとして振る舞う

選択セルに重ねたテキストボックスは、[IME のために常に focus を持っている](#73-選択セルの上に常にテキストボックスを置く)。
そのため**編集中のマウス操作はテキストボックスのものとして通す**必要がある。
ドラッグで文字を選べなければ、コピーも、一部だけに色を付けることもできない。

#### 「ソース整形」は何のためにあるか

出力される表は変わらない。変わるのは**ソースファイルの桁**である。

```
| 用語 | 説明 |              | 用語     | 説明           |
| --- | --- |          →    | -------- | -------------- |
| アクセストークン | 認可 |    | アクセストークン | 認可     |
```

本製品の売りは**差分が人に読めること**なので、`.table` の桁が揃っているかどうかは実利がある。
ただし[自動では整形しない](#)（1 セルの編集で表全体の差分が出るため）ので、**明示的に押す**。
コードフォーマッタと同じ扱いで、整形だけを独立したコミットにできる。

#### 見出しもセルである

**見出しの文字も inline markdown として描く。** 色も強調も単位の上付きも効く。
見出しだけ語彙を欠くと、書式バーで付けた記法がそのまま読者に見える（[P6](decisions.md)）。

#### グリッドは「見た目」を出す

グリッドのセルには**描画結果**を出す。記法が見えるのは**そのセルを開いたときだけ**である。

これを外していたために、見出しに色を付けても「変わっていない」ように見えた。
出力は正しかったのに、**作業している画面が結果を見せていなかった**。
グリッドは表を編集する場所であって、記法を眺める場所ではない。

同じ理由で、**寄せもグリッドに出す**。どの寄せが当たるかはレンダラが決める（区切り行と規則）ので、
グリッドは列の寄せだけを読むのではなく**同じ判定を使う**。

#### 寄せは「対象」に従う

Markdown の区切り行は**列に 1 つの寄せ**しか書けない。これは記法の制約として受け入れる。
ただし**見出しと本文で寄せを分けたい**ことはある。

> 数値は右寄せ、その見出しは中央。理科系の表でごく普通の組み合わせである。

これは語彙を増やさずに書ける。**寄せもスタイルの宣言として扱い、対象に書く。**

```
| 項目 | 濃度 |
| --- | ---: |          ← 列の寄せ（区切り行）。本文セルに効く
...
style {
  header { align: center }   ← 見出しだけ中央に
}
```

セルに当たる寄せは**一箇所で決める**。区切り行の寄せを既定とし、その位置に当たる規則が
`align` を持っていればそれが勝つ。class を 2 つ出して CSS の順序に勝敗を委ねると、
テーマを差し替えた瞬間に結果が変わる。

GUI の `左 / 中 / 右` も**色と同じ「対象」に従う**。対象が「この列」のときだけ区切り行を書き、
それ以外は規則として書く。**「対象」の選択は操作のたびに戻らない**（選び直させない）。

#### 列幅はドラッグで決める

ヘッダの右端をドラッグする。書かれるのは**表全体に対する割合**（`width: 30%`）である。
同じ文書が HTML にも PDF にも PPTX にもなるので、px は出力ごとに違う意味になってしまう。
割合なら、どの出力でも同じ見た目になる。1 回のドラッグが 1 回の変更として記録される。

**グリッドの上でも、印刷される表と同じ class を当てる。** 付けた瞬間に見えなければ、
どれが付いたのか分からない。表示の実装は[レンダラと同じもの](../packages/render/src/html/table.ts)を使う。

#### 図表は好きな場所に差し込める

シートの末尾だけでなく、**ブロックとブロックの間すべて**に差し込み口がある。
図はそれを導入する文の隣にあるべきで、末尾に作って動かすのは「そこに足す」ことではない。

差し込み口は 3 つを出す。

| | 何をするか |
|---|---|
| **＋ 表 / ＋ 図** | 新しいファイルを作って `@import` する |
| **＋ 参照** | **すでにある図表**を選んで `@import` する |

3 つ目が要る。実務の図表は大半が既にどこかにあり、とくに `shared/` の図を
**もう 1 部作ってしまう**のが避けたい失敗である。どのファイルが在るかは器が知っているので、
一覧は器から受け取る。

#### セル結合

**範囲を選んでから結合する。** 選択は `Shift+矢印`、`Shift+クリック`、ドラッグ。
1 セルずつ広げる操作も残してあるが（「下のセルと結合」「右のセルと結合」）、
3x3 を作るのに 8 回押すのは操作ではない。

ファイルが結合を**「明け渡した側の印」**（`^` と `<`）で表しているので、範囲の結合は
**左上のセルを残し、他の位置に印を書く**ことに落ちる。範囲が既存の結合をまたぐときは、
**その結合を丸ごと含むまで矩形を広げる**（半分だけ巻き込むと読めない形になる）。

#### 消える文字は先に知らせる

結合すると左上以外の文字は失われる。**黙って捨てない**（[P6](decisions.md)）。
消えるセルがあるときは、押した場所にそのまま確認を出す。

```
3 個のセルの文字が消えます
────────────────────────
左上の「アクセストークン」だけを残して結合
やめる
```

表計算ソフトが同じことを聞くのは、**取り返しがつかないから**である。

ここで記法の穴が 1 つ見つかった。**下へ伸ばしてから右へ広げた 2x2 が読めなかった。**

```
| 1 | < | 3 |        | 1 | < | 3 |
| ^ | ^ | 6 |        | ^ | < | 6 |
  ↑ 読めた             ↑ 読めなかった
```

同じ形に印の置き方が 2 通りあり、片方しか解釈していなかった。`<` の左は
**その行で始まったセルとは限らず、上から伸びてきたセルでもありうる**。
併せて、**幅を決めるのは本体が始まる行だけ**（下の行の `<` は「覆われている」ことを示すだけ）とした。

### 7.5 クリップボードは両方向に通す

表は Excel やスプレッドシートで生まれることが多く、ときどきそこへ戻る。**片道しか通らないグリッドは使われない。**

| 操作 | 形 |
|---|---|
| コピー / 切り取り | 選んだ矩形を**タブ区切り**で出す。表計算がそのまま貼れる形 |
| 貼り付け | タブ区切りを読み、はみ出す分だけ表を広げる（[§2 の「取り込み経路」](#2-csv-互換という前提を撤回する)） |

三点だけ決めておく。

1. **結合で覆われた位置は空にする。** 覆っているセルの文字を繰り返すと、貼り付けた先で本物の重複データになる。
2. **切り取りは結合の印（`^` / `<`）を消さない。** 印は「何が書いてあるか」ではなく「表がどんな形か」を言っているので、
   中身を消す操作が形まで壊してはいけない。
3. **セルを開いている間、クリップボードはその文字のもの。** セルの一部をコピーする手段を潰さない。

貼り付けと切り取りはそれぞれ 1 回のバイト範囲の書き換えである（貼り付けは表の形が変わりうるのでグリッド全体、
切り取りは触れた行だけ）。

### 7.6 まだ無いもの

- **区分トークン `tint-3` / `tint-4`** — ボタンには 2 つだけ出している
- **セル内の改行** — セルは 1 行に収める。`@` ブロック参照で複数行を入れる道はある
