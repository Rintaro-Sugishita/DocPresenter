# ライセンス方針

作成: 2026-09-22 / 関連: [提供形態](platforms.md) / [作図モデル](diagram-model.md) / [テーマ](theme.md)

## 0. 決定事項（ロック済み）

- **DocPresenter 本体は ErCreator と同じ方針とする。無償（商用利用を含む）・非オープンソース・全権利留保。**
- **[中継サーバのみオープンソース](platforms.md)**（MIT / Apache-2.0 を推奨）。
- 依存ライブラリは**すべて非オープンソース製品に組み込める**ことを確認済み（§2）。
- **初公開と同時にリポジトリを public にする**（§6）。ソースは読めるが、オープンソースにはしない。**設計書（`design/`）も含めて公開する**。
- **パーサとレンダラはライブラリとして配る**（[パッケージ分割](packaging.md)）。**再配布は許し、改変は許さない**（§6）。
- **ビルド・バンドル・最小化・トランスパイルは改変に当たらない**と条文に書く（§6.3）。
- **保守が止まったときの自衛の修正を認める**条項を置く（§6.3）。
- **ファイル形式そのものは誰が実装してもよい。** ライセンスはコードにかかるのであって、記法にはかからない（§6.4）。
- **PR は受け付ける。ただし取り込みには許諾（CLA）を要する**（§6.7）。譲渡ではなく**広い利用許諾 ＋ 人格権不行使**の形にする。
- **fork の実装をそのまま取り込まない**（§6.6）。取り込むなら作者から許諾を取る。

## 1. 本体を非オープンソースにすることの技術的な但し書き

**Web 版は TypeScript をブラウザに配信する。** バンドルと minify は行うが、
**リバースエンジニアリングは容易**である。

> **「非オープンソース」は法的な制限であって、技術的な秘匿ではない。**

ErCreator の Blazor WebAssembly も同じ立場にあるが、**TypeScript はさらに読みやすい**。
[実装スタックを TypeScript 単一言語に決めた](stack.md)判断は、この点を不利にしている。

ただし決定を覆す理由にはならない。

- 言語境界を無くす利益（[実装スタック §4](stack.md)）のほうが大きい
- ErCreator が既に同じ条件で成立している
- 保護は**ライセンス条文**（改変・再配布・逆コンパイルの禁止）で行う

**実効性に限界があることは承知のうえで採る。**

## 2. 依存ライブラリのライセンス（実測）

本設計で採用を決めたものを確認した。**すべて非オープンソース製品に組み込める。**

| 依存 | ライセンス | 組み込み | 注意 |
|---|---|:--:|---|
| **pdf-lib** | MIT | ○ | — |
| **@pdf-lib/fontkit** | MIT | ○ | — |
| **Paged.js** | MIT | ○ | — |
| **Playwright**（CLI で headless Chrome を駆動） | Apache-2.0 | ○ | — |
| 推移的依存 | MIT / 0BSD / MIT AND Zlib | ○ | — |
| **TALA / D2**（[自動レイアウト](diagram-model.md)） | **MPL-2.0** | ○ | **ファイル単位のコピーレフト。§3** |
| **Noto Sans / Serif CJK JP**（[同梱フォント](theme.md)） | SIL OFL 1.1 | ○ | 著作権表示の保持。フォント単体の販売は不可 |
| **harfbuzzjs / HarfBuzz**（[サブセット化](../prototype/pdf-text/FINDINGS.md)） | **要確認** | — | 採用前に確認する |

## 3. MPL-2.0 の扱い — 改変しない運用を前提にする

TALA と D2 は **MPL-2.0** である。これは**ファイル単位のコピーレフト**であり、

- **MPL のファイルをそのまま使う限り**、自社コードの非公開は維持できる
- **MPL のファイルを改変した場合、その改変したファイルのみ**公開義務が生じる（自社コード全体ではない）

したがって方針は明確である。

> **MPL のファイルは改変しない。プロセス分離またはそのままの利用に留める。**

改変が避けられなくなった場合は、**そのファイルだけを公開する**。製品全体には波及しない。

## 4. 運用上やること

- **ライセンス条文を用意する**（§6。PolyForm Strict を下敷きに、ビルド例外と保守停止時の例外を追補）
- **CLA を用意するか、PR を受け付けないと明記するか**を決める（§6.5）
- **ファイル形式の仕様を別文書として公開する**（§6.4）
- **THIRD-PARTY-NOTICES を持つ**（ErCreator が既に採っている形）
- **Noto フォントの著作権表示**を成果物または配布物に含める
- **MPL ファイルの改変有無を CI で監視する**（意図しない改変で義務が発生するのを防ぐ）
- **harfbuzzjs のライセンスを採用前に確認する**（§2）

## 5. ErCreator と揃うことの意味

2 製品で方針が一致することで、利用者から見た位置づけが揃う。

> **無償・商用可・アカウント不要・データが外に出ない。ただしオープンソースではない。**

[ErCreator の訴求](../docs/research/existing-solutions.md)をそのまま引き継げる。
新規に説明すべきことが減り、2 製品を併用する利用者にとっても分かりやすい。

**中継サーバだけがオープンソース**である点は、[その必要性](platforms.md)とともに明示する。

## 6. ソースを見せる。ただしオープンソースにはしない

### 6.1 決めたこと

| | |
|---|---|
| **リポジトリ** | 初公開と同時に public。設計書（`design/`）も含めて見せる |
| **配り方** | パーサとレンダラを npm のライブラリとして配る。GUI は製品として配る |
| **再配布** | **許す。** 組み込んだ製品と一緒に配ってよい |
| **改変** | **許さない。** 派生物を作って配ることを認めない |
| **ビルド** | **改変ではない**（§6.3）。バンドルも最小化もトランスパイルも自由 |
| **保守停止時** | **自衛の修正を認める**（§6.3） |
| **ファイル形式** | **誰が実装してもよい**（§6.4）。仕様として公開する |
| **貢献** | **PR は受け付ける。** 取り込みには許諾（CLA）が要る（§6.7） |

「ソースが読めないと不安で採用できない」という声に応えるためであって、**自由を与えるためではない**。
[§1 のとおり](#1-本体を非オープンソースにすることの技術的な但し書き)、
どのみち JavaScript は読める。だったら**隠して不安を買うより、見せて信用を買う**ほうがよい。

### 6.2 「再配布可・改変不可」は既存の OSS ライセンスには無い

[OSI の定義](https://opensource.org/osd)は**改変の自由を要求する**ので、この形は定義上オープンソースではない。
呼び方は **source-available** が正しい。近い既成ライセンスは次の 3 つで、**PolyForm Strict が最も近い**。

| ライセンス | 改変 | 備考 |
|---|:--:|---|
| **PolyForm Strict 1.0.0** | **不可** | 「使ってよい・配ってよい・変えてはいけない」を目的に書かれている。求めている形そのもの |
| Elastic License 2.0 | 可 | 改変は許し、マネージドサービス提供を禁じる。目的が違う |
| BUSL 1.1 | 可 | 期限後に Apache へ転換。改変は許す |
| CC BY-ND | 不可 | **ソフトウェアには使わない**（CC 自身が非推奨。リンクや実行の扱いが未定義） |

**PolyForm Strict を下敷きに、次の 2 点を追補した独自ライセンスを用意する**（条文の最終確認は法務に回す）。

### 6.3 追補する 2 つ（決定）— ビルドは改変ではない / 保守が止まったら直してよい

**これを書き落とすと、ライブラリとして成立しない。**
バンドラは取り込んだコードを minify し、tree-shake し、トランスパイルする。
条文をそのまま読めば、それは全部「改変」である。

> **ビルド・バンドル・最小化・トランスパイル・ソースマップ生成は、改変に当たらない。**

もう 1 つ。**当社が保守を止めた場合の逃げ道**を書いておく。
改変不可のライブラリを組み込む側が最も恐れるのは、脆弱性が直らないまま放置されることである。

> **一定期間（例: 12 か月）更新が無い場合、自衛のための修正を認める。**

この 1 文があるかないかで、採用の判断が変わる。

### 6.4 記法は誰が実装してもよい（決定）

ライセンスは**コードにかかる**。`.dgm` / `.table` という**ファイル形式そのものには何もかからない**。

> **形式は仕様として公開し、誰が実装してもよいと明記する。**

[記法を借りて作った](diagram-model.md)以上、こちらだけ囲うのは筋が通らない。
そして普及の観点でも、**形式が広まることと、道具が売れることは矛盾しない**（Markdown と各エディタの関係と同じ）。

### 6.5 public にすると起きること

- **fork ボタンは押せる。** GitHub の public リポジトリは fork できる。
  ライセンスで改変を禁じても、fork して直した版を公開する人を技術的には止められない。
  [§1 と同じ](#1-本体を非オープンソースにすることの技術的な但し書き)——条文は抑止であって防壁ではない。
- **PR が届く**（§6.7）。
- **設計書が読まれる。** `design/` を含めて公開する。思想がそのまま出るが、それは**強み**として出す。
  「日本語だから読まれない」には期待しない——翻訳は誰でもできる。読まれる前提で書く。

### 6.6 fork にいい実装があったとき、書き戻してよいか

**そのまま取り込むのは避ける。** 二つの理由がある。

1. **相手にも著作権がある。** その fork が改変禁止に反していても、**その人が書いた部分の創作性は、その人のもの**である。
   こちらのライセンス違反は、こちらが相手の著作物を自由に使える理由にはならない
   （日本法では二次的著作物の利用に原著作者の権利も及ぶが、二次的著作物の著作者の権利が消えるわけではない。
   **両者の許諾が要るというのが安全側の理解**である。最終判断は法務に回す）。
2. **筋が通らない。** 「改変は許さない」と言いながら、改変されたものを黙って取り込むのは、
   自分で決めた条件を自分で破ることになる。**製品の信用の問題**であって、法律以前の話である。

やることは 3 つ。

| やり方 | 中身 |
|---|---|
| **許諾を取る** | その人に声をかけ、§6.7 の CLA に同意してもらって取り込む。**これが第一手** |
| **考えだけ借りる** | **アイデアに著作権は無い。** 「こう直すと速い」を理解して、**自分のコードとして書き直す**のは問題ない |
| **見ないで直す** | 込み入った場面では、報告だけ受けてコードは見ずに実装する（clean-room）。争いになったときに説明できる |

**ソースを見せると決めた以上、fork は起きる。** 起きたときに慌てないよう、先に決めておく。

### 6.7 PR は受け付ける。著作権は「譲渡」ではなく「許諾」で取る

**改変不可のライセンスのままでは、外からの修正を受け取れない。** 貢献者は「改変」してから送ってくるからである。
だから**貢献の経路だけ別に開ける**。

**DCO では足りない。** DCO は「このコードを、このプロジェクトのライセンスの下で出せる」と署名する仕組みだが、
そのライセンスが改変を禁じているので、署名のしようがない。**CLA が要る。**

CLA には 2 つの形があり、**譲渡ではなく許諾を採る**。

| | 譲渡（assignment） | **許諾（licence grant）** |
|---|---|---|
| 著作権 | 当社へ移る | **貢献者が持ったまま** |
| 当社ができること | 何でも | **再ライセンスを含む広い利用**（永続・全世界・取消不能・サブライセンス可） |
| 貢献者の心理的な壁 | 高い | **低い** |
| 日本法の面倒 | 著作者人格権は譲渡できない | 同じ問題はあるので**不行使特約**を置く |

> **Apache ICLA 型の許諾 ＋ 著作者人格権の不行使。これで proprietary のまま出し続けられる。**

譲渡まで求めると、普及を優先する今回の方針と噛み合わない。**許諾で必要十分**である。

運用は次のようにする。

- **小さな報告は Issue で受ける。** 直すのはこちら。CLA の手間を貢献者にかけない。
- **コードが来る PR は CLA 同意を条件にマージする**（GitHub の CLA bot で自動化できる）。
- **CONTRIBUTING.md にこの 2 段構えを書く。** 「PR は歓迎、ただし取り込みには同意が要る」と最初に言う。
