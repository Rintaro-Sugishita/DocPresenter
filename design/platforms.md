# 提供形態 — デスクトップ・Web・CLI

作成: 2026-09-21 / 対象: [未決事項](open-issues.md)「デスクトップ配布形態」
関連: [実装スタック](stack.md) / [サーバの位置づけ](server-architecture.md) / [ビルド単位](build-model.md)

## 0. 決定事項（ロック済み）

- **デスクトップ専用アプリは作らない。VS Code 拡張がデスクトップ体験を担う**（§1）。Tauri / Electron は採らない。
- **次の投資先は AI 連携**（§2）。
- **Web 版は「お試しと閲覧」を既定とする**（§3）。ローカルフォルダを開けるのは Chromium 系デスクトップのみ。
- **リモート Git 連携は Web 版の必須機能とする**（§3.2）。これにより**認証中継サーバが必須**になるが、**設計書の中身はサーバを通らない**。
- **Chromium 系では、ローカルフォルダを開いてそこで執筆できる**（§3.3）。ただし**レビュー機能は成立しない**。
- **ZIP での書き出しは全環境で提供する**（§3.4）。OPFS しか使えない環境の**唯一の持ち出し口**であり、ZIP は**無圧縮で自前生成する**。
- **デスクトップ（VS Code 拡張）と CLI は、引き続きサーバ無しで完全に動く。**

## 1. デスクトップは VS Code 拡張が担う

[実装スタックを TypeScript 単一言語に決めた](stack.md)時点で、デスクトップ配布形態が未決だった。
Tauri / Electron で包む案もあったが、**作らない**。

VS Code 拡張が、必要なものを最初から全部持っているためである。

| デスクトップ版に要るもの | VS Code 拡張なら |
|---|---|
| ブラウザエンジン（[PDF パイプライン](pdf-engine.md)が要求） | **WebView が Chromium** |
| ファイルシステムへのアクセス | **標準で持つ** |
| Git 統合 | **標準で持つ** |
| 配布とアップデート | **Marketplace** |
| セル UI・カスタムエディタ | **Notebook API / カスタムエディタ API** |

Tauri / Electron で作ると、**同じものを二度作ることになる**。

### 割り切り

ErCreator の「自己完結の単一ファイルを配って終わり」に相当する体験は**提供しない**。
VS Code を使わない利用者は、**Web 版か CLI** を使うことになる。

対象が[新規に Markdown で書き始めるチーム](../docs/research/excel-migration-japan.md)である以上、
VS Code の利用率は高いと見て、この割り切りを取る。

## 2. 次の投資先は AI 連携

デスクトップアプリを作る労力は、**AI 連携に回す**。R9（機械可読出力）を要件として持っている以上、
そこを厚くするほうが価値が出る。

想定する方向（要件化はしていない。優先度の記録）:

- **構造化コンテキスト出力の充実** — 参照を解決し、図をテキスト表現に展開し、表を構造として出す
- **MCP サーバとして設計書を提供する** — AI エージェントが設計書を読み、書けるようにする
- **[インデックス](index-model.md)を AI に渡す** — トレーサビリティ・未参照要件・指摘一覧は、そのまま AI の入力になる

三つ目が効く。**R12 で作るインデックスは、人間向けの一覧であると同時に、AI にとって最良の入力である。**

## 3. Web 版のファイルアクセス

### 3.1 ローカルフォルダは Chromium 系でしか開けない

実測に基づく現状。

| 環境 | ローカルフォルダを開く（`showDirectoryPicker`） |
|---|:--:|
| Chrome / Edge / Opera（デスクトップ） | **○** |
| Firefox | **✗**（OPFS のみ） |
| Safari | **✗**（OPFS のみ） |
| モバイル全般 | **✗** |

つまり **Web 版だけで本格的な執筆を成立させることはできない**。

### この制約は、Web 版の位置づけと衝突しない

[サーバの位置づけ](server-architecture.md)で、**Web 版は「まず触ってみる」導線**と定めた。
本格運用はデスクトップ（＝VS Code 拡張）と CLI である。

| Web 版の用途 | 必要なファイルアクセス |
|---|---|
| **お試し**（サンプルを開いて編集してみる） | OPFS で足りる。全環境で可 |
| **閲覧・レビュー**（[顧客が HTML を見てコメント](review-model.md)） | **不要** |
| 手元のフォルダを開いて編集 | Chromium 系のみ（できる環境では提供する） |
| 本格的な執筆 | **VS Code 拡張に任せる** |

**Chromium 系で開けることは「無料でついてくる」ので提供する**が、それに依存した設計にはしない。

### 3.2 リモート Git 連携を必須にする — 何を受け入れることになるか

Web 版でローカルフォルダが使えない環境が多い以上（§3.1）、**GitHub / Azure DevOps への直結を
オプションではなく必須機能**とする。以下はその判断で受け入れる制約である。

#### 制約 1 — 認証中継サーバが必須になる（回避できない）

| | 状況 |
|---|---|
| GitHub の PKCE 対応 | 2025-07 に**対応した** |
| しかし | **クライアントシークレットは依然として必須。** GitHub は公開クライアントと機密クライアントを区別しない |
| さらに | **トークンエンドポイントに CORS が無い。** ブラウザから `POST /login/oauth/access_token` を呼べない |

**したがってブラウザ単体では OAuth を完了できない。** 薄いバックエンド（BFF）が要る。

代替として**個人アクセストークンの手入力**ならサーバ不要だが、実運用の導線としては弱い。
**既定は OAuth、PAT は逃げ道**とする。

#### 制約 2 — ただし「設計書の中身」はサーバを通らない

ここが判断の分かれ目である。**GitHub の REST API は CORS に対応している**
（`Access-Control-Allow-Origin: *` を返す）。したがって、

> **トークンさえ手に入れば、以降はブラウザから GitHub API を直接叩ける。**

```
ブラウザ ──(OAuth の code だけ)──▶ 認証中継サーバ ──▶ GitHub
   │                                  （中身は通らない）
   └────(設計書の読み書き)────────────────────────▶ GitHub REST API
```

サーバが見るのは **OAuth の認可コードとトークンだけ**で、設計書の内容は一切通らない。
[「データが開発元に渡らない」という訴求](server-architecture.md)は維持できる。

**この形を守るために、`git clone` 方式は採らない。** GitHub の git smart HTTP には CORS が無く、
isomorphic-git でブラウザから clone するには **CORS プロキシが要る。プロキシには中身が全部通る。**
これは避ける。

#### 制約 3 — Git 操作が REST API 経由になる

clone しない以上、Git の操作は API で行う。本設計が Git に依存している箇所は次のとおり。

| 依存 | REST API での実現 |
|---|---|
| [コミットハッシュ ＋ バイト範囲のアンカー](review-model.md) | ref 指定でファイル内容を取得 ○ |
| コメントの移送（差分を辿る） | Compare API で差分取得 ○（バイト範囲の追跡は自前） |
| [改訂履歴](platforms.md) | Commits API ○ |
| **[R12 の全ルート走査](index-model.md)** | **Git Trees API ＋ 各ファイルの取得。ここがコスト** |

**レート制限は認証済みで 5,000 req/時。** 対策は二つ。

- **blob の SHA でキャッシュする。** 内容が変わらなければ SHA が同じなので、OPFS に置けば再訪が安い
- **アーカイブ一括取得**（`/repos/{owner}/{repo}/tarball/{ref}`）で 1 リクエストにできないか。**CORS の可否は要検証**

#### 制約 4 — 顧客のセキュリティ審査が戻ってくる

[サーバを持たないことの利点](server-architecture.md)として「顧客のセキュリティ審査を回避できる」を挙げていた。
認証中継サーバを持つ以上、**これは部分的に失われる**。

緩和策は二つ。

- **サーバが何を見るかを明示する**（制約 2 のとおり、設計書の中身は通らない）
- **self-host を可能にする。** 認証中継は数十行の薄いもので、自社で立てられる

#### 制約 5 — Azure DevOps は GitHub より難しい

| | 状況 |
|---|---|
| Azure DevOps 独自の OAuth 2.0 | **非推奨。新規登録を受け付けていない** |
| 推奨経路 | **Microsoft Entra ID** 経由 |
| Entra ID の SPA ＋ PKCE | 公開クライアントとして対応している |
| **Azure DevOps REST API の CORS** | **不透明。要検証** |

最後の行が通らなければ、Azure DevOps では制約 2 の形（中身がサーバを通らない）を作れず、
プロキシが要ることになる。**GitHub を先行させ、Azure DevOps は CORS の実測後に判断する。**

#### 誰が認証中継を運用するのか

**両方提供する。** 開発元がホスト版を運用し、self-host の手順も出す。

| | 開発元ホスト | 利用者が self-host |
|---|---|---|
| 導入の手間 | **無し** | OAuth App の登録 ＋ 中継の配置 |
| トークンが通る先 | **開発元のサーバを一瞬通る**（保持しない） | **自社のみ** |
| 顧客のセキュリティ審査 | 引っかかりうる | **通しやすい** |
| 向く相手 | お試し・個人・小規模 | 企業 |

**片方だけでは成立しない。**

- **開発元ホストが無いと、最初の 1 人も使えない。** 「まず触ってみる」は Web 版の存在意義そのものであり、
  OAuth App の登録から始めさせたら導線が死ぬ
- **self-host が無いと、企業に入れない。** 業務システムの設計書を扱う以上、
  「なぜトークンが第三者を通るのか」は必ず聞かれる

#### 運用コストは小さい

認証中継は**認可コードをトークンに交換するだけ**の数十行であり、Cloudflare Workers や
Vercel Functions の無料枠で動く。状態を持たないためスケールもしない。

ただし**ErCreator には無かった「運用責任」が発生する**ことは事実である。可用性・鍵の管理・
インシデント対応が事業側の負担として新たに乗る。

#### コメント収集サーバと統合する

[コメント収集サーバ](server-architecture.md)も「self-host 可能な薄い層」と決めてある。
**認証中継と性質がまったく同じ**である。

| | 認証中継 | コメント収集 |
|---|:--:|:--:|
| 薄い | ○ | ○ |
| ドキュメントの状態を持たない | ○ | ○ |
| self-host 可能 | ○ | ○ |

**1 つのバイナリにまとめる。** 利用者から見て「立てるサーバは 1 つ」にする。

#### サーバは公開する（オープンソースにする）

self-host を提供する以上、**配布は必須**である。そのうえで**ソースを公開するか**は、
法的には別の問題だが、**目的から見れば実質的に必須**になる。

##### 閉じたバイナリでは目的を果たせない

self-host を用意する理由は、[顧客のセキュリティ審査を通すこと](platforms.md)だった。
だが中身の見えないバイナリを渡すと、審査の問いが移動するだけである。

> 「なぜトークンが第三者を通るのか」
> → 「**このバイナリは何をしているのか。トークンをどこかへ送っていないか**」

**OAuth トークンを扱う不透明なバイナリ**は、審査がまさに警戒する対象である。
self-host にした意味が失われる。

##### 実装形態からしても、素直にやればソースが出る

[実装は TypeScript 単一言語](stack.md)と決めてある。中継の配置先として想定する
Cloudflare Workers / Vercel Functions は**スクリプトをデプロイする形**であり、
配布物は事実上ソースになる。難読化は可能だが、§前段のとおり逆効果である。

##### 公開しても失うものが無い

重要なのは、**公開する範囲に製品の価値が含まれない**ことである。

| | 中身 | 公開 |
|---|---|:--:|
| **中継サーバ** | 認可コードのトークン交換 ＋ コメントの Git 書き戻し | **する** |
| DocPresenter 本体 | 作図・表・組版・出力・エディタ | **本体の方針に従う**（別途判断） |

中継は数十行で、[差別化要因](../docs/research/existing-solutions.md)（編集可能な PPTX・複雑テーブル・作図）を
一切含まない。**公開による競争上の損失がほぼ無く、信頼の獲得だけが残る。**

##### コメント収集を統合する以上、なおさら公開が要る

[コメント収集サーバと統合する](server-architecture.md)と決めた。認証中継がトークンを**通過させるだけ**なのに対し、
**コメント収集は指摘の本文を扱う**。機微度はこちらのほうが高い。

統合したバイナリは両方を含むため、**透明性の要求は上がる**。公開する判断と整合している。

##### ライセンス

**寛容なオープンソースライセンス（MIT / Apache-2.0）を推奨する。**

目的が「検証できること」である以上、改変や再配布を制限しても得るものが無い。
むしろ自由に検証・改変できるほうが信頼される。

**DocPresenter 本体のライセンス方針とは切り離す。** ErCreator が採る「無償・商用可だが非オープンソース」を
本体で踏襲するとしても、**中継サーバだけをオープンソースにすることに矛盾は無い**。
README とライセンス表記で、どこまでが公開範囲かを明示する。

#### 設計上の要請

self-host を成立させるには、**Web 版が接続先を差し替えられる必要がある**。

- **`client_id`**（利用者が登録した OAuth App のもの）
- **認証中継の URL**

この 2 つを設定できれば、**Web アプリ本体は開発元ホストのままでも、自社の OAuth App と
自社の中継を使える**（コールバック URL に開発元のドメインを登録すればよい）。
Web アプリ自体も静的ファイルなので、まるごと self-host することもできる。

#### まとめ

| | サーバ無しで動くか |
|---|:--:|
| **VS Code 拡張** | **○ 完全に** |
| **CLI** | **○ 完全に** |
| Web 版・お試し（OPFS） | ○ |
| Web 版・ローカルフォルダ（Chromium 系） | ○ |
| Web 版・ZIP 書き出し | ○ |
| **Web 版・リモート Git 連携** | **✗ 認証中継が要る** |

**「コアはサーバ無しで全機能が動く」という原則は、Web 版のリモート連携に限って例外を持つ**ことになる。
[サーバの位置づけ](server-architecture.md)の原則そのもの（正本は常に Git、サーバは状態を持たない）は維持される。
認証中継サーバは**トークンを中継するだけで、ドキュメントの状態を一切持たない**。

### 3.3 フォルダを開いての執筆（Chromium 系のみ）

Git 操作はブラウザからできない（§3.2 制約 3）が、**ファイルを読み書きするだけなら別である**。
File System Access API でディレクトリのハンドルを取れば、そこに実ファイルとして書ける。

```js
const dir = await showDirectoryPicker({ mode: 'readwrite' });
const file = await dir.getFileHandle('auth-design.md', { create: true });
const writable = await file.createWritable();
await writable.write(source);
await writable.close();
```

- ハンドルは **IndexedDB に保存できる**ので、再訪時に同じフォルダを開き直せる（再許可のためのユーザー操作が 1 回要る）
- `.dgm` / `.table` が別ファイルに分かれた構成も、ディレクトリハンドルから普通にたどれる
- **書いたものは本物のローカルファイル**なので、利用者は手元の git / VS Code でそのままコミットできる

つまり **Web 版が git を持たなくても、利用者の git と共存できる。**

#### ただしレビュー機能は成立しない

[コメントはコミットハッシュ ＋ バイト範囲にアンカーする](review-model.md)。
Git を介さずフォルダを直接編集している間は、**アンカーが指すコミットが存在しない**。

| モード | 執筆 | レビュー |
|---|:--:|:--:|
| リモート Git 直結 | ○ | ○ |
| **ローカルフォルダ直編集** | **○** | **✗** |
| OPFS（お試し） | ○ | ✗ |

したがってこれは**「Chromium で無料でついてくる執筆モード」**であって、Web 版の主線（リモート Git 直結）を
置き換えるものではない。§3.1 の判断（依存した設計にはしない）は変えない。

### 3.4 ZIP での書き出し — 全環境の持ち出し口

フォルダを開けない環境（Firefox / Safari / モバイル）にとって、**ZIP ダウンロードが唯一の持ち出し口**である。
これはサーバ無しで、全環境で成立する。

```js
const blob = new Blob([zip], { type: 'application/zip' });
const a = document.createElement('a');
a.href = URL.createObjectURL(blob);
a.download = 'auth-design.zip';
a.click();
```

#### 何を固めるか — 2 通りある

| 書き出す対象 | 何のため |
|---|---|
| **素材一式**（`.md` / `.dgm` / `.table` / 画像） | 持ち帰って VS Code や git で続きをやる |
| **成果物**（HTML / PDF / PPTX） | レビュー相手・顧客に渡す |

前者が、**「Web でお試し → 本格運用はデスクトップへ」という導線そのもの**になる。
範囲は[ビルド単位](build-model.md)と同じ、`output:` を持つ文書からの**参照閉包**とする。

#### ZIP は無圧縮で自前生成する

| 方式 | 判断 |
|---|---|
| fflate（MIT、約 8KB）で deflate | **採らない** |
| **store 形式（無圧縮）を自前で書く** | **採る** |

設計書の実体は markdown と `.dgm` / `.table`、つまり**テキストで合計数百 KB**であり、同梱する画像は
**すでに圧縮済み**である。**圧縮率がほとんど効かない**ため、依存を 1 つ増やす理由が弱い。
ZIP の store 形式は local file header と central directory を並べるだけで、100 行に満たない。

これは[依存の監査](licensing.md)の方針とも整合する。**入れないで済む依存は入れない。**

## 4. 改訂履歴は Git から生成する

### 4.1 ファイルに書くことは必須ではない

改訂履歴は **Git が既に持っている情報**である。ファイルに書けば二重管理になり、
[P1「計算で出せるものはファイルに書かない」](decisions.md)に反する。

> **既定は、Git のコミット履歴から生成する。**

### 4.2 範囲は「その文書の参照閉包」

[ビルド単位](build-model.md)で参照閉包が分かっているため、**その文書に実際に影響したコミットだけ**を拾える。

- 本文を直したコミット
- **その文書が参照している図や表を直したコミット**
- 共有要素であっても、その文書が参照していれば含まれる

リポジトリ全体の履歴を垂れ流すのではない。**ビルド単位を決めた副産物である。**

### 4.3 改訂として出すコミットを選別する

素の履歴には `fix typo` や `wip` が並び、改訂履歴として使えない。
**改訂として出したいコミットに印を付ける。**

```
表 3 の桁数を修正

Doc-Revision: 初版レビュー指摘を反映
```

**トレーラを持つコミットだけを改訂履歴に出す。** 情報は Git に置いたまま、意味のあるものだけを選別できる。

版の区切りは frontmatter の `version:` の変化、または Git タグで判定する。

### 4.4 手書きも許す

手で書いた改訂履歴がある場合は、**それを優先する**。移行期や、Git 履歴が使えない場面のための逃げ道。
