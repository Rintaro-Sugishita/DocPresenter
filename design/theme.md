# テーマ設計案 — フォントとスタイルの指定

作成: 2026-09-21 / 対象: [未決事項 A-4](open-issues.md)（テーマの定義形式）のうち、フォントに関する部分
関連: [PDF 生成エンジン](pdf-engine.md) / [表モデル](table-model.md) / [出力モデル](output-model.md)

## 0. 決定事項（ロック済み）

- **テーマは CSS で書く。** [PDF をブラウザで組版する](pdf-engine.md)決定の帰結として、テーマ言語は自動的に CSS になる。
- **フォントのサイズ・ウェイト・行送り・字送りは自由に指定できる。**
- **フォントファミリは「埋め込み可能で、テーマが同梱しているもの」に限る**（§2）。OS のシステムフォントは指定できない。
- 既定で **Noto Sans CJK JP（ゴシック）/ Noto Serif CJK JP（明朝）/ 等幅**を同梱する。
- **テーマは CSS だけではなく、前付けの HTML テンプレートも持つ**（§6.1）。
- **既定は A4 縦。** 要素単位で横向きページに送れる（§6.2）。
- **前付け（表紙・改訂履歴・目次・図表一覧）は本文に書かない。** frontmatter と生成物から組み立てる（§6.3）。

## 1. テーマが CSS であること

PDF は HTML を組版して作る（[決定済み](pdf-engine.md)）。したがって

> **画面の HTML も、PDF も、まったく同じ CSS で組まれる。**

テーマは独自形式を発明せず、CSS そのものとする。フォントに関しては次がそのまま使える。

```css
:root {
  --font-heading: "Noto Sans CJK JP";
  --font-body:    "Noto Serif CJK JP";
  --font-mono:    "Noto Sans Mono CJK JP";
}

body   { font-family: var(--font-body); font-size: 10.5pt; line-height: 1.8; }
h1, h2 { font-family: var(--font-heading); font-weight: 700; }
code   { font-family: var(--font-mono); font-size: 0.9em; }
```

**サイズ・ウェイト・行送り・字送りは自由。** ここに制限を設ける理由が無い。

## 2. フォントファミリだけは自由にできない

### 理由 — PDF に埋め込むにはバイト列が要る

[検証](../prototype/pdf-text/FINDINGS.md)のとおり、PDF はフォントを**埋め込んで**作る。ここから二つの制約が出る。

1. **ブラウザからローカルのシステムフォントのバイト列は取得できない。** 画面には出せても PDF には入れられない
2. **OS 同梱フォント（游ゴシック・メイリオ・ヒラギノ等）は再配布・埋め込みが制限される**

`font-family: "游ゴシック"` と書けた場合に何が起きるかを考えると分かりやすい。

| | 画面（HTML） | PDF |
|---|---|---|
| 游ゴシックがある環境 | 游ゴシックで表示 | **埋め込めないので代替フォント** |
| 無い環境 | 代替フォント | 代替フォント |

**画面と PDF が一致しない。** これは[直値を禁止してトークンに限定した](table-model.md)のとまったく同じ問題であり、同じ理由で禁じる。

> **テーマで使えるのは、そのテーマが同梱しているフォントだけ。**

### フォントの持ち込みはできる

同梱していれば良いので、利用者が自分のフォントをテーマに入れることは妨げない。

```
theme/
  theme.css
  fonts/
    CorporateGothic.otf
```

```css
@font-face { font-family: "Corporate Gothic"; src: url("fonts/CorporateGothic.otf"); }
```

**そのフォントを埋め込んで良いかというライセンス上の責任は、持ち込んだ利用者が負う。** ビルド時に
フォントの埋め込み許可ビット（`fsType`）を確認し、禁止されていれば警告する。

### 既定で同梱するもの

| 用途 | フォント | 備考 |
|---|---|---|
| ゴシック | Noto Sans CJK JP | 44,810 字。SIL OFL 1.1 |
| 明朝 | Noto Serif CJK JP | 同上 |
| 等幅 | Noto Sans Mono CJK JP | 同上 |

設計書に必要な書体は、実務上ほぼこの 3 種で足りる。

## 3. 和欧文混植はブラウザが解決する

```css
body { font-family: "Inter", "Noto Serif CJK JP"; }
```

このように書けば、ブラウザが**文字ごとに**フォントを解決する。欧文は Inter、和文は Noto Serif になる。

**我々はレイアウト済みの DOM を読む**ため（[PDF パイプライン](pdf-engine.md)）、**どのテキスト実行体がどのフォントで
組まれたかは、読む時点で既に決まっている**。あとはそれぞれを埋め込むだけでよい。

混植のためのフォールバック規則を自前で実装する必要が無い。ブラウザを組版に使うことの副次的な利点である。

### 複数書体の埋め込みは検証済み

ゴシックと明朝を 1 つの PDF に埋め込んで、描画・抽出とも正常であることを確認した。
事前サブセットのため **2 書体で 35.5 KB** に収まる（[検証結果](../prototype/pdf-text/FINDINGS.md)）。

## 4. ウェイトは別フォントとして埋め込む

太字は合成（fake bold）ではなく、**そのウェイトのフォントファイルを埋め込む**。合成太字は日本語で
品質が落ちるうえ、PDF のテキストとしても扱いが悪い。

サブセット化するため、ウェイトを増やしても増加分は小さい。ただし**テーマが使うウェイトの数だけ
フォントファイルが要る**ため、同梱セットのサイズには影響する。

## 5. 欠字検出はテーマ依存になる

[検証](../prototype/pdf-text/FINDINGS.md)で、**フォントが持たない字は「描画は豆腐、抽出は消滅」**という
壊れ方をすることが分かっており、書き出し前の検出を必須としている。

この検出は**テーマが選んだフォントに対して**行う。したがって

- テーマを差し替えると、欠字の有無が変わる
- 字種カバーの狭いフォントを持ち込むと、欠字が増える

ビルド時に「このテーマのフォントでは次の文字が出せない」と具体的に示す必要がある。

## 6. ページ設計

### 6.1 テーマは CSS だけでは足りない

表紙には題名・文書番号・版数・承認欄・罫線といった**構造**がある。CSS は見た目を決められるが、**構造そのものは作れない**。

したがってテーマは次の三つで構成する。

```
theme/
  theme.css          体裁（§1）
  fonts/             埋め込むフォント（§2）
  templates/
    cover.html       表紙
    revision.html    改訂履歴
```

テンプレートは HTML で書き、frontmatter の値と生成物を差し込む。**最終的に HTML ＋ CSS になる**ため、
[レンダリング経路](pdf-engine.md)は変わらない。

### 6.2 用紙・余白・向き

```css
@page {
  size: A4 portrait;
  margin: 25mm 20mm 20mm 20mm;
}
```

**横長の表や図のために、ページ単位で向きを変えられる。** 項目定義表は横長になりがちで、実務上これが無いと困る。

```css
@page landscape { size: A4 landscape; }
.landscape { page: landscape; }
```

```markdown
@import "auth-design/screen-items.table" {#tbl-items page="landscape"}
```

### 6.3 前付け — 本文には書かない

表紙・改訂履歴・目次・図表一覧は、**本文に書かず、テーマが出す**。

| 前付け | 中身の出どころ |
|---|---|
| 表紙 | frontmatter（文書番号・題名・版数・日付・作成者） |
| 改訂履歴 | **未確定**（§7）。Git から生成するか、frontmatter に持つか |
| 目次 | 見出しから**生成** |
| 図表一覧 | [採番](reference-syntax.md)から**生成** |

テーマは、どれをどの順で出すかを宣言する。

```css
:root { --front-matter: cover, revision, toc, figures; }
```

これは[「計算で出せるものはファイルに書かない」](diagram-model.md)原則の適用である。目次も図表番号も
計算で決まるため、本文に書けば必ず古くなる。

### 6.4 ヘッダ・フッタ

CSS のマージンボックスと名前付き文字列を使う。

```css
h1 { string-set: chapter content(text); }          /* 現在の章名を拾う */

@page {
  @top-left     { content: string(doc-id) "  " string(doc-title); }
  @top-right    { content: string(confidentiality); }   /* 社外秘 など */
  @bottom-left  { content: string(chapter); }
  @bottom-right { content: counter(page) " / " counter(pages); }
}
```

frontmatter の値は、生成する HTML に隠し要素として埋めて `string-set` で拾う。

**制約**: 名前付き文字列は**テキストしか運べない**。ロゴ画像を入れたヘッダなどは、この方法では組めず
テンプレート側で対処する必要がある。

### 6.5 ページ番号の体系

日本の設計書の慣行に合わせる。

| 区間 | ページ番号 |
|---|---|
| 表紙 | **なし** |
| 改訂履歴・目次・図表一覧 | 別体系（`i, ii, iii` 等）または無し |
| 本文 | **1 から** |

```css
@page cover { @bottom-right { content: none; } }
@page front { @bottom-right { content: counter(page, lower-roman); } }
```

**「1 / 24」形式の総数は、前付けを除いた本文の総ページ数とする。** `counter(pages)` は文書全体を数えるため、
本文だけを数える仕組みが別途要る（§7）。

### 6.6 改ページ制御

| 規則 | 指定 |
|---|---|
| 章は改ページから始める | `h1 { break-before: page; }`（テーマ既定） |
| 見出し直後で切らない | `h2, h3 { break-after: avoid; }` |
| 図表とキャプションを離さない | `figure { break-inside: avoid; }` |
| 孤立行・寡婦行 | `p { orphans: 2; widows: 2; }` |
| 個別の強制改ページ | **`---`**（[出力モデル](output-model.md)） |
| 個別に「またがせない」 | `{keep-together}` 属性 → `break-inside: avoid` |

**規則はテーマ、例外は `---` と属性。** [罫線](table-model.md)や[ピン留め](diagram-model.md)と同じ分担である。

### 6.7 表がページをまたぐとき — Paged.js の弱点

`break-inside: avoid` は、**そもそも 1 ページに収まらない表には効かない**。項目定義表は数ページに渡るのが
普通なので、**分割して、続きのページにヘッダ行を繰り返す**必要がある。これは設計書で必須の体裁である。

ここに既知の問題がある。

> **Paged.js は単純な表しか扱えず、複雑な表には独自の CSS / ハンドラが必要。**
> ヘッダ行の繰り返しは長く未解決の課題（issue #84）で、対応ハンドラが版の更新で動かなくなった報告もある。
> 表が次ページに送られた際にヘッダが二重に出る事例も報告されている。

**我々の表はまさに「複雑な表」である**（セル結合を持つ）。素の Paged.js では期待どおりにならない公算が高い。

対処の方向は二つある。

| 案 | 内容 |
|---|---|
| A | Paged.js のハンドラ機構を使い、**表の分割とヘッダ繰り返しを自前で実装する** |
| B | **表の分割を我々が先に行う。** 行構造と結合を把握しているのは我々なので、Paged.js の断片化に任せず、あらかじめページ境界で分割した表を渡す |

**案 B のほうが筋が良い可能性がある。** 断片化器と戦うより、モデルを持っている側が制御するほうが確実で、
結合セルがページ境界にかかる場合の扱いも自分で決められる。ただし「どこで切れるか」を知るには
一度レイアウトさせる必要があり、二段階の処理になる。

**これは実装時に最初に潰すべき課題**として[未決事項](open-issues.md)に挙げる。

### 6.8 画面（HTML）ではどうなるか

HTML は連続表示でページが無い。同じ CSS の中で、紙と画面の規則を分ける。

| 要素 | 画面 |
|---|---|
| 表紙 | 題名・版数のみ簡潔に |
| 目次 | **出す**（навигация として有用） |
| 図表一覧 | 出す |
| ヘッダ・フッタ | **出さない** |
| 改ページ | **区切りのガイド表示のみ**（[出力モデル](output-model.md)） |

**テーマは 1 つ。** 画面用と紙用で別のテーマを作るのではなく、1 つの CSS が両方の規則を持つ。
これは[テーマ二重化を認めない](pdf-engine.md)という決定の、ページ設計における現れである。

## 7. まだ決まっていないこと（A-4 の残り）

- **表のページ分割とヘッダ行の繰り返し**（§6.7）— 案 A / 案 B の判断。**実装時の最優先課題**
- **改訂履歴の出どころ** — Git の履歴から生成するか、frontmatter に持つか。Git と二重管理になる問題
- **本文だけの総ページ数**（§6.5）— `counter(pages)` は文書全体を数えるため、別の仕組みが要る
- PPTX のスライドマスタとの対応
- [表の罫線・塗りつぶしトークン](table-model.md)と[作図のスタイルトークン](diagram-model.md)を CSS でどう表現するか
- テーマの配布単位と、文書がテーマを指定する方法
- 既定テーマをいくつ用意するか
