# 出力モデル設計案 — ページとスライドの区切り

作成: 2026-09-21 / 対象: [未決事項 A-2 / A-3](open-issues.md)（PDF のページ設計、PPTX のスライド分割）
関連: [参照記法の比較](reference-syntax.md) / [編集 UI 設計案](editor-model.md)

## 0. 決定事項（ロック済み）

- **強制的な区切りは `---`**（Markdown の水平線記法）とする。Marp と同じ。
- **`---` は PDF では改ページ、PPTX ではスライド分割**として働く。**一つの記法が両方を担う**（§2）。
- **`---` は水平線ではない。** 区切りとして解釈し、HTML でも罫線を描画しない（§4）。
- **`---` は編集 UI ではシートの区切りでもある**（[シートモデル](sheet-model.md)）。HTML での扱いは同ドキュメント §4 で**強制改ページに改めた**。
- 体系的なページ制御（章の頭で改ページ、表をまたがせない等）は `---` ではなく**テーマと属性が持つ**（§5）。

## 1. なぜ `---` か

1. **Marp の先行がある。** VS Code で Markdown を書き、PDF やスライドに出す層は Marp の利用者層と重なる。知っている記法をそのまま使える
2. **標準 Markdown の構文である。** 新しい記号を発明していない。本製品を知らない環境でも壊れない
3. **見た目が意味と一致する。** ソースを読んだときに、そこで切れることが視覚的に分かる

### 記法を発明しない、という方針

これで既存記法の借用は三度目になる。

| 借用元 | 記法 | 用途 |
|---|---|---|
| Markdown Preview Enhanced | `@import "path" {attr}` | 外部要素の参照 |
| Mermaid | `A[ラベル] --> B{判定}` | グラフ型の作図 |
| **Marp** | **`---`** | **ページ・スライドの区切り** |

意図して一貫させている。**定着した記法があるなら、それを借りる。** 学習コストを増やさず、既存の資産と道具が通用する範囲を広げられる。独自記法は、借りられるものが無いところ（セル結合の `^`、自由配置の座標）だけに限る。

## 2. 一つの記法が PDF と PPTX の両方を担う

これが最大の利点である。当初 [未決事項](open-issues.md) では A-2（PDF のページ設計）と A-3（PPTX のスライド分割）を別々の課題として挙げていたが、**区切りという一つの概念で両方に効く**。

> **`---` ＝ 出力単位の境界。**

| 出力 | `---` の意味 |
|---|---|
| PDF | 改ページ |
| PPTX | スライド分割 |
| HTML | 強制改ページ（罫線は描かない。§4 / [シートモデル §4](sheet-model.md)） |

同じ文書から PDF と PPTX を出したとき、**区切り位置が一致する**。著者は一度決めれば済み、出力形式ごとに指定を書き分ける必要がない。

### ただし既定の分割規則は形式ごとに違う

`---` は**明示的な境界**であって、分割の全部ではない。

| 出力 | 既定の分割 | `---` の役割 |
|---|---|---|
| PDF | **内容量に応じて自動で流れる** | 流れに逆らって**強制的に切る** |
| PPTX | **見出し単位で切る**（自動で流れる概念が無い） | 見出しの途中でも**追加で切る** |

PDF は自動改ページが基本で `---` は例外指定。PPTX は自動で流れる概念が無いため、見出しによる既定分割が要る。**`---` はどちらでも常に境界として尊重される**点が共通である。

見出しの何段目でスライドを切るかはテーマが決める（§5）。

## 3. 注意すべき曖昧性 — setext 見出し

CommonMark では、次は水平線ではなく **H2 見出し**である。

```markdown
概要
---
```

`---` の直前に文字列があると setext 形式の見出しとして解釈される。Marp も同じ問題を抱えている。

対策:

- **`---` の前後には空行を必須とする**
- **setext 形式の見出しを lint で禁止する**（`#` 形式に統一）

設計書で setext 見出しを使う理由は無いため、禁止して実害は無い。

## 4. `---` は水平線ではない

Markdown の `---` は本来 `<hr>` を生む。しかし本製品では**区切りとして解釈し、HTML では罫線を描画しない**。

理由は、著者が `---` を書いたのは「ここでページを切りたい」からであって、「ここに線を引きたい」からではないため。HTML は連続表示なのでページという概念が無く、**意図していない線が本文に現れるほうが誤り**である。

代わりに、**編集画面のプレビューでは区切り位置をガイドとして表示する**。印刷したときにどこで切れるかが、書きながら分かる。

なお、HTML 出力そのものでの扱いは[シートモデル §4](sheet-model.md) で改めた。区切りごとに `<section>` に分け、印刷時には実際に改ページする。罫線を描かないという判断は変わらない。

これは水平線という表現を失うことを意味するが、設計書で `<hr>` を必要とする場面は無い。Marp も同じ割り切りをしている。

## 5. 体系的なページ制御はテーマと属性が持つ

`---` は著者が個別に打つ**手動の指定**である。実務で必要なページ制御はそれだけではない。

| 要求 | 担い手 |
|---|---|
| 章は改ページから始める | **テーマ**（`break-before: h1` 等） |
| この表はページをまたがせない | **要素の属性**（`@import "..." {keep-together}`） |
| PPTX はどの見出し段でスライドを切るか | **テーマ** |
| 表紙・目次・図表一覧の有無と順序 | **テーマ** |

**規則として全文書に効かせたいものはテーマに、個別の例外は `---` と属性に。** この分担は、[罫線を「既定はテーマ、変えたところだけ疎に指定」とした表モデル](table-model.md)や、[作図の疎なピン留め](diagram-model.md)とまったく同じ構造である。

**著者が意図した版面の単位は `---` で表し**（＝シート）、**全文書に一律で効かせたい体裁の規則はテーマが持つ**。`---` をテーマの代わりに使っているなら、それはテーマの設計が間違っている兆候である。判断は打つ数の多寡ではなく、何のために打っているかによる（[シートモデル §7](sheet-model.md)）。
