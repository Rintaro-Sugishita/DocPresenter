# 検証結果 — 表のページ分割とヘッダ行の繰り返しを自前で実装できるか

実施: 2026-09-21 / 対象: [テーマ設計案 §6.7](../../design/theme.md) の案 B
環境: Chromium（Playwright 同梱）/ Paged.js

## 結論

**できる。案 B（自前で分割する）が正しい選択だった。**

63 行・12 列・`rowspan` によるセル結合を持つ表を A4 横に組んだ結果:

| ページ | ヘッダ行 | 行数 | 先頭セル | はみ出し |
|---|:--:|---:|---|---:|
| 1 | **あり** | 27 | 入力 | なし |
| 2 | **あり** | 26 | **検証（続き）** | なし |
| 3 | **あり** | 10 | **通知（続き）** | なし |

**行数は 63 で保存**され、**結合セルはページ境界で切られて次ページに継続**した（`split.png`）。
Excel や Word と同じ体裁になる。

素の Paged.js に任せた場合は[ヘッダ行が繰り返されなかった](../paged-landscape/FINDINGS.md)。

## アルゴリズムの核心 — 結合セルをページ境界で切る

行を高さで詰めていくだけでは足りない。**`rowspan` がページ境界をまたぐ場合**の処理が要る。

1. 行をページに詰める（高さで貪欲に）
2. グリッドを走査し、**現在有効な span** を列ごとに保持する
3. ページの末尾で、そこに跨っているセルの `rowspan` を**そのページに収まる行数まで切り詰める**
4. 次ページの先頭に、**残りの行数を持つ継続セル**を出す

```
ページ 1 末尾    検証 ← rowspan を 6 に切り詰め（本来 7）
ページ 2 先頭    検証（続き） ← rowspan 1 の継続セル
```

**これができるのは、[表をモデルとして持っている](../../design/table-model.md)からである。**
行構造と結合を把握していない断片化器には、原理的にこの処理はできない。

## 一発では決まらない — 収束ループが要る

最初の実装では**1 チャンクが溢れた**。原因は、継続セルに付けた「（続き）」の分だけ**行が高くなり**、
分割前の計測値とずれたためである。

対処は、予測せずに**実測して収束させる**こと。

```
計測 → 分割 → 生成した結果を実測 → 溢れたチャンクの見積もりを補正 → 再分割
```

今回は **1 回で収束**した（各チャンクの実高 673 / 666 / 265 px、上限 680 px）。

これは組版が二段階になることを意味するが、[向きごとの別パス](../paged-landscape/FINDINGS.md)と
[ページ番号の確定](../../design/reference-syntax.md)で**既に二段階が確定している**ため、追加の構造的コストは無い。

## 残る課題

1. **1 行がページ高を超える場合** — セル内に長い箇条書きが入ると起こりうる。**行そのものの分割**が要るが、今回は未対応
2. **ヘッダが複数行・結合を含む場合** — 繰り返すヘッダ自体が結合セルを持つケース
3. **収束しない場合の打ち切り** — 現在は 8 回で打ち切り。打ち切り時の扱いを決める必要がある
4. **「（続き）」の表記** — 体裁なので[テーマ](../../design/theme.md)が決めるべき。付けない選択肢も要る

## 再現手順

```bash
npm install
node run.mjs      # 計測 → 分割 → 収束 → Paged.js で組版 → 検証
```

`split.mjs` が分割アルゴリズム、`run.mjs` が計測と検証。
