## PPTX の読み戻しを試す（`order-slides.md`）

`auth-design.md` は 1 枚に載る量が多く、PowerPoint で直すには窮屈なので、読み戻しを試すための
短い資料を別に置いた。1 枚に見出し・1 文・図か表 1 つだけで、図は読み戻しで扱いの違う 3 種類にしてある。

| スライド | 図 | 試せること |
|---|---|---|
| 1 注文の流れ | `order-flow.dgm`（ピン留めなし） | 図形を動かすと、**動かした図形だけ**が `layout {}` にピンとして足される |
| 2 システム構成 | `order-system.dgm`（全要素に位置あり） | 図形を動かすと、その図形の位置の行だけが書き換わる。文字を直すと、その図形の行だけが書き換わる |
| 3 注文の状態 | `order-states.dgm`（1 つだけピン留め） | 大きさを変えると、位置と大きさがピンに書かれる |
| 4 状態の一覧 | `order-states.table`（結合表） | 結合セル（`^`）が PowerPoint の結合された表になる。列の幅は `.table` の `width` どおり。表は読み戻さない——PowerPoint で直すと、どの表が変わったかを警告に出す |
| 5 改訂履歴 | `revision.md` の Markdown の表 | 本文の中の Markdown の表も、PowerPoint の表になる |

1. 書き出す: `node tools/build.mjs --in sample`（VS Code なら文書を開いて「書き出し: PPTX」）
2. `out/build/order-slides.pptx` を PowerPoint で開き、図形を動かす・文字を直す・大きさを変える。保存する
3. 読み戻す: `node tools/pptx-back.mjs out/build/order-slides.pptx --in sample`
   （VS Code なら `.pptx` を右クリック →「PPTX の修正を図に読み戻す…」）。何が変わるかが出るので、
   よければ `--write` を付けて書き込む

何も触らずに読み戻すと「変更なし」になる。図形を足す・線をつなぎ替える・線のラベルを直すのは読み戻せず、警告に出る。

## 意図どおりに機能した点

- **本文が目次のように読める。** 40 行の作図ソースが埋まっていないため、`auth-design.md` は素の Markdown として最後まで見通せる
- **疎なピン留めが自然に書けた。** `login-flow.dgm` は 8 要素中 2 つだけを固定し、残りは自動レイアウトに任せている。`token-lifecycle.dgm` は `layout {}` が空
- **結合マーカー `^` で表の形が読める。** `screen-items.table` は素のテキストのまま、どこが結合されているか分かる
- **委譲が自然に混ざる。** `.mmd` と `.ermlx` が `@import` 一行で本文に並ぶ。他の要素と書き味が変わらない
- **レビューファイルが指摘管理表として読める。** 指摘・対象箇所・回答・状態が 1 つの YAML に収まった

## 見つかった穴

### 1. 図表番号と相互参照が無い ← 最大の問題 → **解決済み（R11）**

初版では `*図 3.1 ログイン画面遷移*` と**手で採番**し、地の文でも「図 3.1 に示す」と**手で参照**していた。設計書では図を 1 つ挿入した瞬間に以降の番号が全部ずれ、参照も全部壊れる。

さらに悪いことに、`screen-items.table` の中にも番号を直書きしていた。

```
| 操作 | 4 | ログイン | — | — | — | 押下で図 3.1 の遷移を開始 |
```

**表が共有要素なら、参照先の番号は文書ごとに違う**ため、どの番号を書いても必ずどこかで間違う。

これは要件 R1〜R10 のどこにも入っていない**要件レベルの漏れ**であり、**R11** として追加した。本サンプルは現在この記法で書き直してある。

```markdown
ログイン時の画面遷移を @fig-login-flow に示す。

@import "auth-design/login-flow.dgm" {#fig-login-flow caption="ログイン画面遷移"}
```

詳細は[参照記法の比較 §7](../design/reference-syntax.md)。

### 2. `line_begin` / `line_end` が実際には曖昧

`@import "../shared/glossary.table" {line_begin=1 line_end=8}` と書いたが、**この 1〜8 行が何を指すのか決まっていない**。

`glossary.table` にはコメント行・ヘッダ行・区切り行・`style {}` セクションがあるため、

- ファイルの物理行なのか
- 表のデータ行なのか

で結果がまったく変わる。MPE から借りた記法をそのまま持ち込んだが、**対象が「ファイル」ではなく「表」である本形式では意味が定まらない**。

行番号は参照先の編集でずれる問題も元からある。**名前による範囲指定**へ寄せるべき。

→ 本サンプルは `glossary.table` に `range {}` セクションを置き、`{rows="認証関連"}` で引く形に修正した。行番号を一切使わない。記法としては未確定のままだが、方向は確定した。

### 3. 相対パスの基準が要素ごとに違う

- `auth-design.md` → `@import "../shared/system-architecture.dgm"`（md からの相対）
- `login-screen-overlay.dgm` → `overlay "../assets/login-screen.png"`（dgm からの相対）

**書いている最中に基準を取り違えた。** 各ファイルからの相対で統一されてはいるが、`docs/` と `docs/auth-design/` を行き来するため、`../` の数が要素ごとに変わり間違えやすい。リポジトリルートからの絶対指定を併用できるほうがよい。

### 4. `.table` のスタイルセレクタが結合セルで曖昧

`cell:表示/説明 { fill: changed }` と書いた。「分類＝表示 の行の 説明列」の意図だが、

- 「表示」分類の行が複数ある場合、どの行か決まらない
- 今回はたまたま 1 行だったので通った

結合セルを持つ表でセルを一意に指す規則が決まっていない。

### 5. オーバーレイの記法が未定義だった

```
① @ (168, 126) -> (188, 132)  "ログイン ID"
```

引き出し線の始点と終点のつもりで書いたが、**そんな記法は設計されていない**。丸番号を文字として直書きするのか自動採番するのか、引き出し線を持つのかも未決。

加えて既知の問題として、**座標が画像のピクセルに依存する**ため、キャプチャを撮り直すと全部ずれる。

### 6. 図形と括弧の対応が未確定

Mermaid から `[]` `([])` `[()]` `{}` を借りたが、注釈に使った `>社内 NW からのみ接続可]` は非対称で読みにくい。`group` だけ別構文になっているのも一貫していない。

また `note1 -- api`（矢印なしの接続線）を使ったが、線種の記法を決めていなかった。

### 7. ファイル内コメントが未定義

`.dgm` と `.table` の先頭に `#` でコメントを書いたが、**形式としてコメントを許すか決めていない**。表ファイルでは `#` 始まりの行が表の一部と紛らわしい。

### 8. 文書メタデータと改訂履歴

frontmatter（`document` / `version` / `status` など）を**その場で作った**。設計書には文書番号・版数・承認者・改訂履歴が要る。

改訂履歴は Git が持つ情報と二重管理になるため、**Git から生成するのか、手書きするのか**の方針が要る。

**2026-10-01 追記 — 改訂履歴は共有できない。** 初版では `shared/revision.md` に置き、設計書と概要の
両方から取り込んでいた。**1 つのフォルダに文書が 1 本とは限らない**以上、これは成り立たない——
現に概要（SD-AUTH-000）に「1.1 ロック回数を 5 回に変更」という、**設計書の改訂**が出ていた。

`docs/<文書名>/` はその文書専用、`shared/` は共有、という[決定](../design/decisions.md)に照らせば、
改訂履歴は共有物ではない。各文書のフォルダに移した。共有できるのは、**どの文書から見ても同じもの**
——用語集や全体構成図——だけである。同じ用語集を引いても、**表の番号は文書ごとに違う**
（設計書では表 2、概要では表 1）。これが穴 1 の出発点でもある。

### 9. セル内改行

今回は `@1` のブロック参照で回避できたが、実務では 1 セル内での改行は頻出する。記法が未決。

### 12. 一覧の絵と、行を持つ一覧の見分けが画面上で付かなかった → **解決済み**

検索画面の「検索結果」は `list grid:` と書いてあった。`grid` は**中身を持たない絵**
（表がここに入る、とだけ言う絵）なので、行を押しても何も起きない。見た目はほとんど
同じなのに、`list:` は行を持てて `grid:` は持てない——**どちらなのかが画面から読めない**。

検索結果を `list:` に書き換え、8 件の行をそのまま書いた。入りきらない 2 件は描かれず、
縁にバーが出る（50 件の注記と同じことを絵が言う）。選べる部品の一覧は
**ライブラリの見出しごと**に出るようになったので、「中身を行で持つもの」という区分が
そのまま答えになっている。

### 11. 画面の並びを座標で書くと、1 行足しただけで差分が 6 行になった → **解決済み**

4 枚を部品テンプレートで書き直したあとも、**座標だけは 1 要素につき 1 行**残っていた。
`pwLabel @ (70, 162)` の 162 は「116 ＋ 34 ＋ 12」の答えであって、事実は「縦に積む・
間隔 12・幅は枠いっぱい」の 3 つしかない。項目を 1 つ挿入すると下の全部が書き換わる。

**レイアウト層に入れ物（`stack` / `grid`）を入れて、4 枚とも書き直した**——
いまこの 4 枚に**子の座標は 1 つも無い**。詳細は[画面設計 §3.7](../design/screen-design.md)。

### 10. 画面部品は 1 枚では決まらなかった → **解決済み**

画面を 1 枚だけ描いた時点では「入力欄・ラベル・ボタン・チェックボックス」の 4 種で足りると
思っていた。**2 枚目で副ボタンが、3 枚目で警告の面とエラー文が足りなくなった。**

3 枚描いたところで style の宣言は 29 行、違う見た目は 11 種類。そこで語彙を決めて
`shared/ui-parts.dgm` に置き、3 枚とも書き直した——**画面のファイルから色が消えた**。
詳細は[画面設計 §3.4](../design/screen-design.md)。
