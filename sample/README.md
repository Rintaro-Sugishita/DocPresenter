# サンプル — 認証機能 設計書

作成: 2026-09-21 / 目的: 設計した形式で**実際に設計書を 1 本書き、記法の過不足を洗い出す**

## 構成

```
sample/
  docs/
    auth-design.md                    本文
    auth-design/                      この文書専用の要素
      login-flow.dgm                  グラフ型（画面遷移）— 疎なピン留めあり
      token-lifecycle.dgm             グラフ型（状態遷移）— ピン留めなし
      screen-items.table              結合表（意味トークン使用）
      login-screen-overlay.dgm        画像への注釈オーバーレイ
      login-sequence.mmd              Mermaid へ委譲（シーケンス図）
    assets/
      login-screen.png                画面キャプチャ（プレースホルダ）
  shared/                             複数文書で再利用する要素
    system-architecture.dgm           自由配置型
    glossary.table                    共有表
    customer-domain.ermlx             ErCreator へ委譲（ER 図）
  reviews/
    2026-10-01-customer.review.yml    顧客レビュー（指摘管理表に相当）
```

要件 R1〜R10 と、設計上の主要な判断をひととおり通している。

## 意図どおりに機能した点

- **本文が目次のように読める。** 40 行の作図ソースが埋まっていないため、`auth-design.md` は素の Markdown として最後まで見通せる
- **疎なピン留めが自然に書けた。** `login-flow.dgm` は 8 要素中 2 つだけを固定し、残りは自動レイアウトに任せている。`token-lifecycle.dgm` は `layout {}` が空
- **結合マーカー `^` で表の形が読める。** `screen-items.table` は素のテキストのまま、どこが結合されているか分かる
- **委譲が自然に混ざる。** `.mmd` と `.ermlx` が `@import` 一行で本文に並ぶ。他の要素と書き味が変わらない
- **レビューファイルが指摘管理表として読める。** 指摘・対象箇所・回答・状態が 1 つの YAML に収まった

## 見つかった穴

### 1. 図表番号と相互参照が無い ← 最大の問題 → **解決済み（R11）**

初版では `*図 3.1 ログイン画面遷移*` と**手で採番**し、地の文でも「図 3.1 に示す」と**手で参照**していた。設計書では図を 1 つ挿入した瞬間に以降の番号が全部ずれ、参照も全部壊れる。

さらに悪いことに、`screen-items.table` の中にも番号を直書きしていた。

```
| 操作 | 4 | ログイン | — | — | — | 押下で図 3.1 の遷移を開始 |
```

**表が共有要素なら、参照先の番号は文書ごとに違う**ため、どの番号を書いても必ずどこかで間違う。

これは要件 R1〜R10 のどこにも入っていない**要件レベルの漏れ**であり、**R11** として追加した。本サンプルは現在この記法で書き直してある。

```markdown
ログイン時の画面遷移を @fig-login-flow に示す。

@import "auth-design/login-flow.dgm" {#fig-login-flow caption="ログイン画面遷移"}
```

詳細は[参照記法の比較 §7](../design/reference-syntax.md)。

### 2. `line_begin` / `line_end` が実際には曖昧

`@import "../shared/glossary.table" {line_begin=1 line_end=8}` と書いたが、**この 1〜8 行が何を指すのか決まっていない**。

`glossary.table` にはコメント行・ヘッダ行・区切り行・`style {}` セクションがあるため、

- ファイルの物理行なのか
- 表のデータ行なのか

で結果がまったく変わる。MPE から借りた記法をそのまま持ち込んだが、**対象が「ファイル」ではなく「表」である本形式では意味が定まらない**。

行番号は参照先の編集でずれる問題も元からある。**名前による範囲指定**へ寄せるべき。

→ 本サンプルは `glossary.table` に `range {}` セクションを置き、`{rows="認証関連"}` で引く形に修正した。行番号を一切使わない。記法としては未確定のままだが、方向は確定した。

### 3. 相対パスの基準が要素ごとに違う

- `auth-design.md` → `@import "../shared/system-architecture.dgm"`（md からの相対）
- `login-screen-overlay.dgm` → `overlay "../assets/login-screen.png"`（dgm からの相対）

**書いている最中に基準を取り違えた。** 各ファイルからの相対で統一されてはいるが、`docs/` と `docs/auth-design/` を行き来するため、`../` の数が要素ごとに変わり間違えやすい。リポジトリルートからの絶対指定を併用できるほうがよい。

### 4. `.table` のスタイルセレクタが結合セルで曖昧

`cell:表示/説明 { fill: changed }` と書いた。「分類＝表示 の行の 説明列」の意図だが、

- 「表示」分類の行が複数ある場合、どの行か決まらない
- 今回はたまたま 1 行だったので通った

結合セルを持つ表でセルを一意に指す規則が決まっていない。

### 5. オーバーレイの記法が未定義だった

```
① @ (168, 126) -> (188, 132)  "ログイン ID"
```

引き出し線の始点と終点のつもりで書いたが、**そんな記法は設計されていない**。丸番号を文字として直書きするのか自動採番するのか、引き出し線を持つのかも未決。

加えて既知の問題として、**座標が画像のピクセルに依存する**ため、キャプチャを撮り直すと全部ずれる。

### 6. 図形と括弧の対応が未確定

Mermaid から `[]` `([])` `[()]` `{}` を借りたが、注釈に使った `>社内 NW からのみ接続可]` は非対称で読みにくい。`group` だけ別構文になっているのも一貫していない。

また `note1 -- api`（矢印なしの接続線）を使ったが、線種の記法を決めていなかった。

### 7. ファイル内コメントが未定義

`.dgm` と `.table` の先頭に `#` でコメントを書いたが、**形式としてコメントを許すか決めていない**。表ファイルでは `#` 始まりの行が表の一部と紛らわしい。

### 8. 文書メタデータと改訂履歴

frontmatter（`document` / `version` / `status` など）を**その場で作った**。設計書には文書番号・版数・承認者・改訂履歴が要る。

改訂履歴は Git が持つ情報と二重管理になるため、**Git から生成するのか、手書きするのか**の方針が要る。

### 9. セル内改行

今回は `@1` のブロック参照で回避できたが、実務では 1 セル内での改行は頻出する。記法が未決。
