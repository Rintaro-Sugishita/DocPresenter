# 日本の「Excel 設計書脱却」要求の整理と、DocPresenter 要件の充足性検証

作成: 2026-09-20 / 対象: 世間の要求を棚卸しし、現行要件 R1〜R8 で足りるかを検証する
関連: [既存サービス調査](existing-solutions.md) / [作図モデル設計案](../../design/diagram-model.md)

## 1. なぜ Excel 方眼紙は生き残ってきたのか

脱却を設計するなら、まず**方眼紙が実際に提供している価値**を認めるところから始める必要がある。「悪習だから捨てる」で入ると移行は失敗する。

| 方眼紙が提供している価値 | 中身 |
|---|---|
| **自由レイアウト** | 列幅を固定できる。画像を思った位置に揃えて置ける。規則性のない罫線の表もボタン 1 発で引ける |
| **一覧性** | 大きな表を 1 枚で俯瞰できる。項目定義表・画面項目一覧・トレーサビリティマトリクスが自然に書ける |
| **印刷と承認** | ページ体裁があり、印刷して回覧・押印する文化に乗る |
| **到達性** | 非エンジニア（業務部門・顧客）がツール導入ゼロで開ける。追加コストが一切要らない |
| **商習慣** | 顧客のオーダーも既存プロジェクト文書も Excel。受託開発では従わざるを得ない |

一方、批判されている点は以下に集約される。

- 印刷環境の差による改ページ・印刷出力の乱れ
- 不完全な WYSIWYG
- 目次機能が無い
- 修正・変更の手間が大きい

**重要な観察**: 挙がっている弱点は**「編集」と「再利用」**に集中しており、**「表現力」と「到達性」ではない**。つまり Excel の代替物は、表現力と到達性で少なくとも同等でないと採用されない。ここを軽く見た移行が失敗している。

## 2. 2025〜2026 に脱却が加速した真の理由は「生成 AI」

動機が時期によってはっきり変わっている。ここを取り違えると要件を外す。

| 時期 | 主な動機 |
|---|---|
| 〜2023 | バージョン管理・差分レビュー・「設計ドキュメントが腐る問題」 |
| **2025〜2026** | **生成 AI に読ませること** |

AI は結合セルや複雑なシート構成を持つ Excel を正確に理解できず、方眼紙は非構造データとして扱われてしまう。設計書を AI に渡して実装コードを生成させたい、という動機が業界全体の移行を押している。その結果、Excel→Markdown 変換の OSS やプロンプト術（markitdown、excel2md、LLM による変換）が 2025〜2026 に集中して現れた。

**この変化が要件に与える含意**: 脱却の目的が「人間のレビュー」から**「機械可読性」へ移った**。DocPresenter の現行要件は「人間がみてレビュー可能なファイル」という軸だけで書かれており、**AI 可読性という第二の軸が明示されていない**。

さらに 2026 に入り、Markdown 一本槍への反省も出始めている。

- 「Markdown は構造化情報の表現が苦手。XML や JSON 形式も検討に値する」
- 「AI 駆動開発時代の設計書は Markdown だけではない」（アイオス, 2026-08）
- 「仕様書の図は AI に読ませるな — 軽量コードを添える設計パターン」（SIOS）：**図を画像で貼ると AI が読めない**ので、図のテキスト表現を併記せよという指摘

この 3 つはいずれも、DocPresenter が構想している**中間モデル（`.docmlx`）と、テキストを 1 次ソースとする作図**の方向を裏付けている。

## 3. 移行が難航する具体的ポイント（実例からの抽出）

| # | 障壁 | 出所・内容 |
|---|---|---|
| B1 | **画面設計書・帳票のレイアウト** | 画面イメージや帳票の物理レイアウトは Markdown で表現できない |
| B2 | **複雑テーブル（結合セル）** | 標準 Markdown にセル結合が無い。方眼紙の表がそのまま移せない |
| B3 | **非エンジニアが読めない** | 素の `.md` は装飾が無く読みづらい。プレビュー環境を毎回整えるのが負担 |
| B4 | **レビューの会話ができない** | Wiki と違い「第三者が内容にコメントを残す」「複数人が会話しながら同時編集する」ができない。Markdown 開発の限界として明確に指摘されている |
| B5 | **表記ゆれ** | 設計書間・メンバー間の揺れで本質的なレビューがしにくくなる。markdownlint 導入で対処する事例がある |
| B6 | **顧客納品** | 納品先が Excel / Word を要求する |
| B7 | **既存資産の移行コスト** | 今ある方眼紙をどうするか。変換ツールが多数生まれているのは裏返しで、**これが最大の実務課題** |
| B8 | **図が画像になると AI が読めない** | §2 参照 |

B4 については、Wiki 設計書を導入して 4 年運用できたという事例もあり、「Markdown + Git」以外の解に流れる圧力が実際に存在する。

現行要件（R1 Markdown / R2 作図 / R3 外部参照 / R4 HTML / R5 PDF / R6 PPTX / R7 複雑テーブル / R8 Web・VSCode 編集）に、§1〜§3 で抽出した要求を当てる。

| # | 世間の要求 | 対応する現行要件 | 充足 |

| D1 | **既存 Excel 資産の移行（インポート）** | — | **✗** |

| D3 | 画面設計書・帳票レイアウト | （R2 で吸収可能か要検討） | **△** |

## 5. 検証結果

### 5.1 現行要件で足りているもの

D2 / D4 / D5 / D6 / D13 / D14。
すなわち **「これから Markdown で新規に書き始めるチーム」の要求はほぼ満たしている**。

### 5.2 欠けている要求

現行 R1〜R8 では以下が落ちる。重要度順に整理する。

1. **D1 既存 Excel 資産の移行** — 最大の実務課題。これが無いと「新規案件でしか使えないツール」になり、日本市場の主戦場である受託開発に入れない。ErCreator が Excel / a5er / live DB インポートを備えているのとまったく同じ構えが要る。
2. **D10 Word / Excel 出力** — 納品先が Office を要求する商習慣がある以上、PDF/PPTX だけでは商流に乗り切らない場面が残る。
3. **D11 機械可読出力** — §2 のとおり、これが現在の脱却動機そのもの。中間モデルを持つ設計なら JSON/YAML として出すのは自然。
4. **D12 横断一覧・トレーサビリティ** — 個票から項目定義表や RTM を**生成**する。Excel の「一覧性」に対する直接の回答であり、手で二重管理している現状への強い訴求になる。
5. **D7 非エンジニアが書ける導線** — フォーム／チェックリスト入力など、Markdown を書かせずに更新させる道。B3 の裏返し。
6. **D8 レビューの会話** — Git の PR に寄せる判断で良いかを決める必要がある。Wiki 比較で明確な弱点として挙がっている。
7. **D9 lint・表記ゆれ** — 規約をツール側に内蔵できる。先行事例が実際に markdownlint で解いている領域。
8. **D3 画面設計書・帳票レイアウト** — 作図サブシステムで吸収できるか要検討。

### 5.3 要件の軸そのものへの指摘

当初の目標は**「人間がみてレビュー可能なファイルを構築する」**だった。§2 の調査結果を踏まえると、ここに

> **「AI が正確に読めるファイルであること」**

を第二の軸として明示的に加えるべき。2025〜2026 の脱却需要はこちらが主動機であり、かつ「人間可読」と「機械可読」は**中間モデルを持てば同時に満たせる**（Markdown で人に見せ、構造化データで AI に渡す）。これは Markdown 一本槍の先行事例が 2026 に突き当たっている壁を、設計段階で回避できることを意味する。

### 5.4 優先度の見直し提案

R6（PPTX）は競合調査で見つけた**差別化要因**として価値が高い。一方、日本市場の**切実さ**という観点では D1（Excel 移行）と D12（横断一覧）のほうが上にくる可能性がある。両者は目的が違う。

- R6 = 「他に無いから選ばれる」理由
- D1 / D12 = 「無いと検討の土俵に乗らない」条件

順序としては D1 を土俵に乗るための前提として先に置き、R6 を差別化として後から効かせる形が自然。

## 6. 次に決めるべきこと

1. **主戦場をどちらに置くか** — 「既存 Excel 資産を抱えた受託開発」か「新規に Markdown で始めるチーム」か。要件の優先順位が大きく変わる。
2. **Office（Word / Excel）出力を要件に入れるか** — 商習慣に乗るか、PDF/PPTX で押し切るか。
3. **「AI が読める」を明示要件に昇格させるか** — §5.3。
4. **レビューの会話を Git の PR に委ねるか、製品として持つか** — B4 への回答。
